Why paged prefill touches fabric

Fabric is the communication system connecting Tenstorrent devices. Paged KV cache uses it to fetch only the required cache rows from whichever device owns them.

Production: Galaxy SP=8 / TP=4 Proxy: QB SP=4 / TP=1 Model-side only
Start here

What is fabric?

Think of each accelerator as a building with its own memory. Fabric is the road network that lets one building send data to, or read data from, another.

Device Arequester

Runs attention and needs a KV row.

FABRIC
routes traffic between devices
Device Bowner

Owns the requested physical KV page.

Fabric is not the KV cache and it does not decide ownership. It is only the transport used after the model determines where the required data lives.

Important production detail

Galaxy uses UDM and normal collectives together

Production is SP=8, TP=4. UDM handles remote paged-cache reads across SP, while existing all-gather/reduce-scatter operations still exchange model data across TP.

UDM traffic

Fine-grained request/response reads: “fetch this exact KV row from SP owner 5.”

Collective traffic

Coordinated TP communication: all-gather and reduce-scatter across four tensor-parallel ranks.

QB SP=4, TP=1 verifies remote paging but does not fully exercise this coexistence. Galaxy testing is still required to validate UDM plus TP=4 traffic under production load.

Job 1 · Startup

Make UDM explicit and fail early

Python enum

Expose FabricTensixConfig.UDM so the prefill runner can open the correct fabric mode.

Mode getter

Expose the active UDM state to C++ operations for validation.

Operation checks

Paged indexer and sparse SDPA reject distributed paging if UDM is not active.

Why: a missing UDM setup should produce a clear host error, not compile a device kernel that later hangs while waiting for a response that can never arrive.
Job 2 · Correct data movement

Align the relay’s temporary read buffers

A remote read is relayed through a small fabric memory pool before returning to the requesting kernel. Tenstorrent NoC reads require compatible DRAM-alignment offsets.

Before

The pool base could begin at an unaligned address even when the source tensor was aligned.

unsafe offset

Now

The builder aligns the pool base and the device code statically verifies the invariant.

aligned poolcompile-time guard
Files: fabric_tensix_builder_impl.cpp aligns the allocation; udm_memory_pool.hpp prevents an invalid configuration from compiling.
Job 3 · Concurrency

Do not accept more responses than the relay can track

Each remote read reserves a response record. Under many concurrent requests, that finite response FIFO can become full.

1

2

3

4

Resume after drain

The relay now consumes an inbound packet only when response_pool.has_space(). Existing fabric flow control then naturally pushes back on the sender instead of overflowing or asserting.
Job 4 · UDM + TP collectives

Initialize ordinary collective packets as “posted”

In UDM mode, packet headers contain extra request/response metadata. Existing TP collectives populate their normal routing fields, but they do not know about those new UDM fields.

Uninitialized metadata

An ordinary collective write might be misread as “send me an acknowledgment,” consuming a response slot incorrectly.

Safe default

New packet headers default writes to posted = 1: send the write, expect no UDM response.

Actual UDM reads explicitly overwrite their control metadata. The default only protects ordinary CCL traffic, which matters specifically for the production TP=4 configuration.
Audit result

What should stay, and what can be trimmed?

Keep as prerequisites

  • Expose UDM startup mode
  • Validate UDM for distributed paged operations
  • Align the UDM response memory pool
  • Backpressure when the response FIFO is full
  • Initialize collective packet headers safely
  • Retain the alignment static assertion

Candidates to remove

  • Unused Python get_fabric_udm_mode() binding
  • UDM sparse-multicast compatibility with no GLM call site
  • UDM worker-routing extension with no GLM call site
“Candidate” means code inspection found no paged-prefill call site. It should still be removed and rebuilt in a controlled cleanup change before claiming it is unnecessary for every UDM user.
