# TT-RDMA — Inbound (RX) Line-Rate Research: is 200 Gbps/rail reachable?

**Status:** research findings (2026-07-26). Deep-dive into the Blackhole ETH RX hardware to answer
"when/whether we can get 200 Gbps inbound RX." Sources: the dead classifier driver
(`bh-erisc-fpga/src/common/api/eth_rx_flow.{cpp,h}`), the RX register map
(`bh-erisc-fpga/src/common/registers/eth_core_a_reg.h`, 7071 lines), and the current RX path
(`eth_init.cpp`, `bh_rdma_rx_dispatch.cpp`, `tt_rdma_eth_rx.h`). No local IP datasheet — register
semantics are inferred from the autogenerated header and the (prototype) driver, and must be
validated against the golden `../docs/` spec before silicon bring-up.

## TL;DR verdict

**"200 G RX is a HW-classifier problem" is half right.** The Blackhole RX datapath is far richer than the
3-queue ring we use today — there's a real **64-row TCAM classifier + inline ICRC + header-split +
per-flow metering**. Those offloads take *classification, CRC validation, and header parsing* off the
RISC. **But the classifier's terminal action is a 2-bit queue index into a *fixed L1 ring* — there is
no RX register anywhere that names a per-rule destination address, and no RX DMA/scatter engine.** So
the *last hop* (ring → final MR address) has **zero hardware support**. Something must move each frame
from the ring to its destination, per frame.

Therefore the real gate on 200 G RX is **not the classifier — it's the landing model:**

- **Per-flow-fixed landing** (a QP/connection lands in a fixed region, RNIC-style): reachable. Classifier
  steers by flow → ICRC validates → header-split → land in a per-flow ring, and a **TX-style pre-armed
  HW/overlay drainer** does the fixed ring→region hop. RISC only sets up flows. This is the path to line rate.
- **Per-frame-variable landing** (today's design: each WRITE carries an arbitrary `rkey`+`offset`):
  **not** reachable at line rate — per-frame address resolution (`rkey`→MR→addr) has no HW block on BH,
  so the RISC stays in the per-frame loop. This is exactly today's ~13–18 Gbps/rail ceiling.

**Outbound (TX) is already 200 G** (HW-driven, measured 199.8 Gbps). Every inbound gap is the RX
control-plane, and closing it to line rate is an **architecture change (adopt per-flow-fixed landing +
build a RX ring drainer)**, not a tuning exercise.

## 1. What the Blackhole RX hardware actually offers

Register map `ETH_RXCLASS_A` @ `0xFFB9C000` + the RXQ blocks + `ETH_CTRL_A`. Much more than the raw ring we use:

| Capability | Register block | RISC-off? | Notes |
|---|---|---|---|
| **64-row TCAM classifier** | `fl` @ `0xFFB9CC00` | ✅ | Match ethertype / MAC SA·DA / IPv4·IPv6 5-tuple / L4 ports, ternary masks. `TCAM_ETHERTYPE_WRITE` @ `0xFFB9CDC0` → **can match 0x1AF6**. |
| Steer to a queue | `FL_FTABLE_ACTIONS.queue:2` @ `0xFFB9CE84` | ✅ | The *only* spatial routing action — 2-bit queue index (3 queues instantiated). |
| Drop / header-strip / prepend flow-info / timestamp | `FTABLE_ACTIONS.{drop,rmhdr,prependflowinfo,keeptimestamp}` | ✅ | `rmhdr` + `pe` block captures the removed header (`REMOVED_HEADER_0..13`). |
| **Inline CRC-32 (ICRC) check** | `ROCE_ICRC` @ `0xFFB98100` | ✅ | `rx_check_en` bit8; `RX_CALCULATED` vs `RX_RECEIVED`; 21 header-mask words. Already probed by `bh1_icrc_probe`. |
| Per-flow policing + statistics | `fs` @ `0xFFB9E000` | ✅ | Leaky-bucket (`GAUGE`/`LEAK_INTERVAL`) + per-flow-label counters. |
| HW header-error checks | `FD_HEADER_ERROR_CONTROL` | ✅ | Bad IPv4 IHL / IPv6 next-hdr / TCP data-offset. |
| Frame preemption (802.3br) | `RXPKT_BUF_E/P_STAT` | ✅ | Express vs Preemptible FIFOs. |
| **Land payload at an arbitrary address** | — | ❌ | **No such register.** RXQ has only `BUF_START_WORD_ADDR` (15-bit **word**, L1-local) + `BUF_SIZE_WORDS` + `buf_wrap`. No `DEST_ADDR`, no descriptor ring, no scatter. |
| RSS / hash spread | — | ❌ | grep empty. Spreading is deterministic TCAM→queue only. |

**The decisive asymmetry:** the **TXQ** block *has* `TRANSFER_START_ADDR` / `TRANSFER_SIZE_BYTES` / `DEST_ADDR`
(arbitrary NoC write — this is why TX is line-rate HW-driven). The **RXQ** block has **no analog**. RX is
"receive into a fixed local ring"; there is no "receive and DMA to a caller-chosen address."

## 2. What the RISC does per inbound frame today (the bottleneck)

Measured anchors: **408k fps / ~13 Gbps CRC-on**, **≥560k fps / ≥18 Gbps CRC-off** (sender-limited).
Line rate = **6M fps / 166 ns per frame** (jumbo). Per-frame work in `bh_rdma_rx_dispatch.cpp`:

| Step | Offloadable? | By what |
|---|---|---|
| Read 32B header (8 wrap-aware loads), parse op/len/rkey/off | Partly | classifier + `prependflowinfo` gives pre-parsed metadata |
| CRC-32 over 28 bytes (bit-serial, ≥0.5 µs, ≥25% of throughput) | ✅ | `ROCE_ICRC` inline (or slice-by-4 table) |
| MR-table lookup by `rkey>>24`, access/bounds check | ✅ *iff* per-flow-fixed landing | no HW `rkey`→addr block exists for per-frame-variable |
| Issue `noc_async_write` descriptor (ring → MR addr) | ✅ *iff* fixed dest + a drainer | **the irreducible per-frame hop with no RX HW support** |
| Advance ring ptr, stats, pace, barrier | ✅ | hoist out of hot loop |

**Confirmed: the payload byte-copy is already HW/NoC, not the RISC** — proven by the old RISC-copy path
(~2k fps / 0.02 Gbps) vs `noc_async_write` (~256k fps / 8.5 Gbps), **128×**. So the ceiling is per-frame
*control* work (parse + CRC + lookup + descriptor issue), and even a bare "read header + issue one
descriptor" loop is estimated ~300–500 ns/frame → **~65–100 Gbps/rail** — still short of the 166 ns
budget. **A single ~1 GHz RISC cannot hit line rate in the per-frame path, full stop.**

## 3. The two architectures, and which one reaches 200 G

**(A) Per-frame-variable landing (today).** Each WRITE carries `rkey`+`offset`; the RISC resolves
`rkey`→MR→address per frame. No BH HW does this resolution. Ceiling ≈ RISC control rate.
Fully optimized (ICRC offload + hoisted stats/pace + coalesced descriptors): **~20–30 Gbps/rail**
(unmeasured above 18 — a straightforward experiment with the 143 G DOCA sender). Multi-rail (2 external
rails, each its own eth core/RISC1): **~40–60 Gbps aggregate**, scales ~linearly with rails.

**(B) Per-flow-fixed landing (the line-rate path).** Restructure so a *flow* (QP/connection) maps to a
classifier rule and a **fixed landing region** — the RNIC model. Then:
1. Classifier matches the flow (ethertype/5-tuple/QP-id) → dedicated queue, RISC-free.
2. `ROCE_ICRC` validates inline, `rmhdr` strips L2/header, `prependflowinfo` tags it.
3. A **pre-armed HW/overlay descriptor drainer** moves the fixed-stride payloads from the queue's L1 ring
   to the flow's region — the RX mirror of TX's proven "RISC arms, HW drives" (which gives TX its 200 G).
4. The RISC only sets up flows + services exceptions (new MR, CRC fail, unknown op, resync).

(B) is where per-rail 200 G lives. It needs (b1) the classifier revived + validated, and (b2) a RX ring
drainer — which BH has **no dedicated register block for**, so it would be an **overlay/data-mover
program on another RISC/Tensix**, or a clean-sheet HW engine. (b2) is the real open risk.

## 4. Honest ceilings

| Config | BW/rail | Status |
|---|---|---|
| Today (CRC-on, per-frame-variable) | ~13 Gbps | **measured** |
| CRC-off / ICRC-offloaded | ≥18 Gbps | measured lower bound (sender-limited) |
| Fully optimized per-frame-variable (A) | ~20–30 Gbps | **estimate**, unmeasured |
| 2-rail aggregate (A) | ~40–60 Gbps | estimate |
| Per-flow-fixed + HW/overlay drainer (B) | up to ~line rate | **architecture change**, unproven |
| **TX (for contrast)** | **~200 Gbps** | **measured, HW-driven** |

## 5. De-risking experiment ladder (cheapest first)

1. **Ingress-ceiling test (one-line kernel change, decides the whole question). ✅ DONE 2026-07-26 —
   GREEN.** Tool: `bh1_ingest_probe` (`kernels/bh_rdma_ingest_probe.cpp`) — RISC does zero per-frame work,
   only snapshots the raw MAC RX counters. Driven by the DOCA HW-TX sender (~198 Gbps jumbo). **Result:
   peak MAC→L1 ingress 198.3 Gbps (99% of 200 G line rate), `PACKET_DROP_CNT` = 0, ingress AFIFO
   fullness = 0** — 19.2 M jumbo frames landed drop-free (`PKT_END_CNT` Δ ≈ 19.2 M). **The MAC→L1 write
   side is NOT the ceiling** — it absorbs line rate with the RISC idle. Therefore the entire ~16→200 G RX
   gap is downstream (RISC control-plane + the L1→MR drain), and architecture (B) — classifier + Tensix
   drainer pool — is viable on the ingress side. (Bandwidth derived from `PKT_END_CNT`×landed-bytes;
   `WORD_CNT`/`BYTE_CNT` under-count in raw-wrap mode on this HW.)
2. **ROCE_ICRC engagement (already tooled: `bh1_icrc_probe`).** Does the engine engage on raw 0x1AF6
   framing? Yes → flip `RX_CHECK_EN`, CRC leaves the hot path (~25%+ headroom immediately). No → slice-by-4
   SW table (~7 ops/byte vs ~32 bit-serial). Either result is decision-grade.
3. **Optimized per-frame-variable ceiling.** Point the 143 G DOCA sender at a kernel with CRC off,
   stats/pace hoisted, descriptors coalesced for contiguous same-MR frames. Pins the real (A) ceiling.
4. **Classifier revival spike.** Repair `eth_rx_flow.cpp` (it's non-compiling prototype WIP — enum
   comma errors, duplicate/inverted register writes, `#if 0` blocks, out of sync with its header, never
   in a makefile), install one rule: ethertype 0x1AF6 → dedicated queue, and **verify on silicon that
   `ETH_RXCLASS` is actually inserted into the live RX datapath** (its self-test *zeroes* `MAC_RX_ROUTING`,
   so even that is unproven). De-risks the steering front-half of (B).
5. **RX drainer prototype.** If 1+4 are green, prototype the per-flow-fixed overlay drainer (Tensix/RISC
   walking a fixed-stride flow ring → fixed region) and measure against the 143 G sender.

## 6. Recommendation / scheduling

- **Now (cheap, high-value):** run experiment **1** (ingress ceiling) and **2** (ICRC) — a few hours,
  no new HW, both already tooled. They tell us whether line-rate RX is even reachable and hand us a free
  ~25% via the CRC offload.
- **Phase 3 (perf):** experiment **3** to pin the real per-frame-variable ceiling; ship (A) optimized +
  multi-rail as the **near-term RX story (~40–60 Gbps aggregate)** — real, correct, no architecture risk.
- **Phase 3+/4 (line-rate):** the 200 G RX goal is architecture (B) — **adopt per-flow-fixed landing
  (QP model)** + build the RX drainer. This is the largest single design decision in the project and
  should be taken deliberately: it changes the wire model from per-frame `rkey` to per-flow QP context.

**Bottom line for the original question:** outbound 200 G is done; inbound 200 G is reachable *only* by
moving from per-frame-variable to per-flow-fixed landing and building a RX drainer — the classifier is
the necessary front-half, not the whole answer. Experiment 1 is the go/no-go, and it's one line of code.
