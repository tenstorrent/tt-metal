# TT-RDMA Phase 2.1 — PFC / MAC pause bring-up (lossless RX)

**Status: code written + compile-clean + gated OFF by default. NOT YET HW-VALIDATED — needs a reflash
+ bench session.** This is the base-FW half of Phase 2 reliability (the software-ARQ half, 2.2, is done
and silicon-validated — see `tt-rdma-production-plan.md`).

## Why PFC
The TT↔TT HW retransmit (`eth_enable_packet_mode`) makes the *TT-internal* links lossless, but it does
not apply to a TT↔BlueField-3 external link (the far end is not a TT ETH_TXQ). Without link-level flow
control the BH RX ring is lossy above its drain ceiling. PFC (or 802.3x link pause) makes the BH→BF3
direction lossless by having the BH MAC emit pause frames when its RX buffer fills, so the DPU sender
backs off instead of overrunning. This pairs with the software ARQ (2.2): PFC removes *congestion* loss;
ARQ still covers *residual* loss (bit errors, transient drops, reorder).

## Two register blocks (do not conflate)
- **RSM410 MAC** (`0xFFBA2xxx`, `rsm410_a_reg.h`) — the actual 802.3x + 802.1Qbb pause engine.
- **ETH-CTRL glue** (`0xFFB98xxx`, `eth_core_a_reg.h`) — the firmware-writable XOFF *request*
  (`TX_FLOW_CONTROL` @ `0xFFB981C0`) and the RX buffer fullness gauges.

There is **no auto-HW watermark** register: nothing compares RX-buffer fullness to a threshold and emits
a pause frame by itself. Lossless RX is **firmware-driven** in two parts.

## Part A — static MAC enable (DONE, gated)
Implemented at `bh-erisc-fpga/src/common/api/eth_init.cpp` (the former PFC TODO), gated on the new
`pfc_enable` boot param (`eth_params.yaml` #59, default 0 → dead-code-eliminated). It programs:

| Register | Addr | What |
|---|---|---|
| `STN_ADD_47_32/31_0` (TX+RX) | `0xFFBA2210/2214`, `2418/241C` | station MAC (pause-frame SA + honor DA-match) |
| `MAC_PAUSE_TIME` | `0xFFBA2230` | `tx_pause_xoff=0xFFFF`, `tx_pause_xon=0` (802.3x quanta) |
| `MAC_PFC_TIME` | `0xFFBA2234` | `tx_pfc_xoff=0xFFFF`, `tx_pfc_xon=0` (PFC quanta) |
| `TX_MAC_FC_CONFIG0` | `0xFFBA2224` | `tx_fc_enb`, `tx_rx_fc_enb`, `tx_per_fc_xoff/xon_enb`, `tx_per_pfc_xoff/xon_enb`, `tx_pfc_enb=0xFF` |
| `RX_MAC_FC_CONFIG` | `0xFFBA240C` | `rx_fc_enb=1` (honor 802.3x), `rx_pfc_enb=0xFF` (honor PFC classes) |

To enable: set `pfc_enable: value: 1` in `eth_params.yaml`, `make` in `autogenerated_files/`, then build
the bundle + `tt-flash` + `sudo reboot` (the standard flash path in `CLAUDE.md`).

## Part B — runtime XOFF driver (DONE, watermarks bench-tune)
Implemented as `eth_service_pfc_pause()` in `eth_runtime.cpp`, called **every iteration** of the main
service loop (`main.cpp` while(true)) for a tight pause reaction time. Gated on the same `pfc_enable`.

1. Reads `RXPKT_BUF_P_STAT.rx_afifo_fullness` (`0xFFB980F4`, 0..127 gauge).
2. Hysteresis: `full >= HI` → set `ETH_CTRL TX_FLOW_CONTROL.tx_fc_pause` (`0xFFB981C0`); `full <= LO` →
   clear it. The MAC auto-regenerates refresh pause frames while the bit is held. **First-cut HI=48/LO=16
   — bench-tune.** XOFF-assert count is logged to `macpcs_results.spare[9]` for observability.
3. For a RoCE BF3 peer, switch `tx_fc_pause` → `tx_pfc_pause[prio]` (mlx5 honors PFC-on-priority).

**Open items for the bench (cannot be resolved from the register header alone):**
- **Watermark units + values.** `rx_afifo_fullness` is a 7-bit gauge with no documented unit; the
  high/low-water thresholds must be tuned empirically against the RXQ2 depth and the pause round-trip
  reaction time (set high-water low enough that in-flight frames after XOFF still fit).
- **Auto-HW vs firmware path.** `TX_MAC_FC_CONFIG0` resets to `0x16` (per-request XOFF pre-enabled),
  which hints there may be a hardware request line from `RXPKT_BUF` fullness to the MAC. Confirm on the
  bench whether firmware must drive `TX_FLOW_CONTROL` or the hardware asserts it automatically.
- **Control-frame filtering.** Verify inbound pause DAs (`01-80-C2-00-00-01`) are terminated by the MAC
  and do **not** leak into RXQ1/RXQ2 (the RDMA ring). Check `MAC_RX_ROUTING` behavior.

## BlueField-3 interop (critical)
A RoCE-tuned ConnectX-7/BF3 honors **PFC on the negotiated priority (commonly 3)**, *not* 802.3x link
pause — mlx5 makes global pause and PFC mutually exclusive, and PFC is the RoCE default. So:
- Drive **PFC on the RoCE priority**, and make sure BH-generated pause carries the matching VLAN PCP.
- Confirm the BF3 side: `mlnx_qos -i <dev>` shows PFC enabled on that priority; the DOCA/RoCE sender
  marks the same PCP. Mismatched class = no backpressure.
- If the deployment uses global pause instead, enable it explicitly on the NIC (`ethtool -A`).

**Architectural caveat:** the current RDMA RX uses a single shared `RXPKT_BUF` with no visible
PFC-class→queue mapping, so per-priority losslessness may not be independently achievable — only global
(all-class) pause is meaningful until the RX buffer is partitioned per class.

## HW eval result (2026-07-27) — flashed + activated, but the AFIFO signal is WRONG for this loss
Flashed the `pfc_enable=1` bundle (blob-swap), activated with `tt-smi -r`. Findings:
- **FW is stable:** regression **17/17** on the PFC FW; link trains at 200G on both rails; survives a
  200G DPU overload without wedging (clean-shutdown via resync-on-bad). The gated static config + runtime
  driver do **no harm**.
- **But PFC never engaged under real overload.** DPU-side blast (bypasses the eSwitch cap that limits the
  host sender to ~2.3G) drove the BH RX past its drain ceiling: **`bad=169862`** frames dropped,
  `crc_err=4845` — yet **`spare[9]=0`** (XOFF never asserted).
- **Root cause:** the loss is **L1-ring lapping** (the single RISC1 dispatch drains at ~13–18G vs ~200G
  ingress; the consumer falls behind and the HW overwrites unread ring data). The MAC ingest AFIFO
  (`rx_afifo_fullness`, the driver's signal) **stays below the watermark** because the HW keeps writing to
  L1 regardless of the consumer — the AFIFO never backs up on a ring-lap. So the driver's signal cannot
  see the bottleneck, and pause is never triggered.

**Consequence — PFC-on-AFIFO is not the lossless-RX fix here.** The RX overload loss is a *consumer-drain*
problem, not a *MAC-ingest* problem. Two real fixes:
1. **RISC1-driven PFC on L1-ring occupancy** — have the RX dispatch kernel (which knows `wp - read_pos`)
   assert `TX_FLOW_CONTROL.tx_fc_pause` when its ring passes a high-water. This makes RX **lossless but
   throttled to ~the drain rate (13–18G)** — a valid interim for correctness, not for line rate. (The
   static MAC config already built is exactly what this needs; only the *trigger* moves from the base-FW
   AFIFO poll to the RISC1 ring-occupancy check.)
2. **Tensix drainer pool (Phase 3.1)** — fan the per-frame work out so the consumer keeps up at line rate;
   this is the real 200G-lossless answer. PFC then only backstops residual/burst pressure.

The `rx_afifo_fullness` driver stays (gated, harmless) as the MAC-ingest backstop, but it is **not** the
line-rate-RX solution. Next step for Phase 2.1: move the pause trigger into the RISC1 kernel (ring
occupancy) for the lossless-but-throttled interim, and/or proceed to Phase 3.1.

## Acceptance gate (Phase 2.1)
With `pfc_enable=1` flashed and the runtime driver in place, driving the 143G+ DPU sender:
- MAC pause TX counters (`TX_PAUSE_XOFF_DUR_SHDW_CNT`, `PFCPAUSE*FRAMESTXD` MIB) non-zero under overload.
- `ETH_RXQ_PACKET_DROP_CNT` / buffer-discard = **0** (was non-zero without pause).
- RX lossless (`bad=0` in the dispatch stats) at ≤ the ceiling — the streaming test that previously
  needed rate-matching now survives an unpaced blast.
