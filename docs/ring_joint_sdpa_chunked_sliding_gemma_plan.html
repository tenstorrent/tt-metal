RingJointSDPA chunked sliding: Gemma integration plan

Scope: make the bounded, causal RingJointSDPA sliding path usable by Gemma and GPT-OSS through one cache-backed sequence-parallel path, without treating a valid first Q group as an error or silently reading an incorrect halo.

Outcome. The feature branch implements the operator geometry fix, Gemma structural shape support, and a unified cache-backed GPT-OSS path. The complete-group alignment assertion remains intentionally in place; partial-group support is a separate feature.

Problem statement

Commit 4b673f79015 introduced a compact, one-hop predecessor halo for chunked causal sliding attention. For a ring of R devices and a per-device Q slab of Qlocal, one logical Q group is G = R × Qlocal.

The original runtime validation rejects an invocation unless logical_n ≥ 2G and logical_n % G == 0:

T_FATAL(args.logical_n >= 2 * q_group_size,
        "Chunked sliding attention requires a complete predecessor and current Q group");

This incorrectly classifies the first complete chunk (logical_n == G) as invalid. The first group does not have a prior group, but it is still a valid causal sliding problem: device 0 clips its left window at token 0 and devices 1…R−1 obtain their predecessor from earlier devices in the same group.

Root cause

LayerAssumption in the original specializationWhy it fails for the first group
Host validationTwo full groups are required.Rejects the valid first-group dispatch before program creation.
Q/K work-plan geometryThe current group is selected as logical_n / G - 1.This is safe at one group, provided the wrap from device R−1 to device 0 is clipped rather than underflowed.
Halo source/layoutHalo setup is disabled below two groups.The factory sees no neighbor halo even though devices 1…R−1 need one within the first group. A short-window geometry can also compute a wrong compact-buffer index if this is changed inconsistently.

The constraint is therefore not a model semantic requirement and not a Gemma head-dimension/GQA limitation. It is an incomplete implementation of the compact-halo geometry.

Implementation status

Implemented on this feature branch The three geometry consumers now use the one-group threshold and the fixed-payload first-group wrap rule. Validation now accepts Gemma’s structural GQA/tile geometry rather than GPT-OSS-only values.

The first-group change was made in:

  • ttnn/.../ring_joint_sdpa_device_operation.cpp — validation;
  • ttnn/.../kernels/sliding_window_work_plan.hpp — source-tail calculation and first-group wrap guard;
  • ttnn/.../sliding_halo_layout.cpp — enable the neighbor halo for one complete group.

The shape generalization replaces GPT-OSS-only value gates with structural GQA, tile, and one-hop-halo constraints for Gemma’s 4Q:2K:2V, D256, W1024 geometry.

Chosen solution: complete first group

Make the supported contract explicit:

G = ring_size * input_q.logical_shape()[2]
require logical_n >= G
require logical_n % G == 0
require ceil((window - 1) / k_chunk_size) * k_chunk_size <= Qlocal

For logical_n == G, retain a fixed-size halo exchange. For the device R−1 → device 0 wrap in group 0, clamp the source group to zero, keeping the fixed payload length; device 0’s clipped work plan never consumes this payload. The source-tail helper must return zero only for that wrap case, not for every source in the first group. This preserves the compact buffer layout, device kernels, and program-cache behavior; trace replay across changing chunks needs the operator's metadata-tensor path.

Implementation record

  1. Verified the complete-group contract. The operator requires logical_n ≥ G and logical_n % G == 0; its chunked preflight still distinguishes cache-backed K/V from equal-length local K/V.
  2. Patched all first-group geometry consumers. Host validation, Q/K work planning, source-tail selection, and halo layout agree on the one-group threshold. The R−1 → 0 group-0 wrap clamps its source to zero and retains the fixed transfer payload.
  3. Generalized shape validation. Fixed GPT-OSS W=128, 8Q:1K:1V, D64 gates were replaced by structural GQA, tile, K/V, chunk, and one-hop-halo checks that admit Gemma’s 4Q:2K:2V, D256, W1024 geometry.
  4. Added focused regressions. The existing cache-replay/PCC test now covers logical_n == G and the W=128 short-halo case; a Gemma-geometry smoke case covers first and later groups with W=1024 and 4Q:2K:2V D256 dispatch.
  5. Unified GPT-OSS. Chunk 0 now writes K/V to cache and uses the same RingJointSDPA path as later chunks; the Q/K/V all-gather/normal-SDPA/reduce-scatter bootstrap was removed.
  6. Remaining performance follow-up. Measure unified chunk-0 latency, CCL bytes, peak DRAM/L1, and trace capture cost against the historical bootstrap path. Correctness no longer depends on retaining that fallback.

Why GPT-OSS now uses the same path

GPT-OSS formerly avoided the logical_n ≥ 2G constraint by routing chunk 0 through an explicit all-gather Q/K/V path, and only started RingJointSDPA at chunk 1 where logical_n == 2G. That staging path duplicated the execution graph and prevented a single program from serving full prefill.

GPT-OSS now writes chunk-0 K/V into cache and calls RingJointSDPA at logical_n == G, like every later chunk. This avoids the replicated full-Q/K/V bootstrap. It should lower communication and memory for GPT-OSS W=128, whose K/V halo is small. For Gemma W=1024 the halo is a full predecessor slab, so the benefit is smaller; the remaining A/B measurement will quantify the trade-off.

Do not conflate this with partial-group support

Do not remove logical_n % G == 0 as part of the first-group fix. The compact plan currently positions Q as the final full group (logical_n - G) and emits a fixed halo. A partial current group needs different Q ownership, valid-row masks, and a halo with an explicit valid range; merely dropping the assertion risks wrong reads or a reader/compute hang.

If Gemma’s real schedule supplies a partial group, make that a phase-2 operator feature:

  1. derive each device’s valid Q interval from kv_actual_isl and logical_n, rather than from a completed group;
  2. teach the sliding work plan to use those absolute Q intervals and clip K/V by the logical end;
  3. carry halo source base and valid-row count to the exchange/reader, masking unused rows so an incompletely populated predecessor is never read;
  4. patch all values on cache hits and the trace-safe metadata path; and
  5. add partial-first, partial-middle, wrap-to-device-0, and cache-replay oracle tests.

If partial groups are rare prompt tails, an interim caller fallback to normal SDPA for that final dispatch is safer than weakening the RingJointSDPA contract. It is not the preferred steady-state solution because it creates divergent tracing/caching behavior.

Acceptance criteria

  • A Gemma first chunk with logical_n == G runs RingJointSDPA and no longer hits the fatal assertion.
  • A GPT-OSS first chunk with logical_n == G runs the same cache-backed RingJointSDPA path as chunk 1+, with no Q/K/V bootstrap gather.
  • First- and later-group results agree with a causal sliding reference; no drift appears across cache/program-cache replay.
  • W=128 and W=1024 regression cases both pass, proving the halo source is correct beyond the full-slab coincidence.
  • On the host-scalar kv_actual_isl path, trace capture at chunk 0 replays for later complete groups. The metadata path must be tested according to its distinct program-cache keying.
  • Non-aligned logical_n remains explicitly rejected until phase 2 is implemented.

Risk and rollout

The patch is low-risk because it only extends an existing one-hop layout to the first valid group; it does not change math, allocate a larger halo, or relax the one-hop bound. The important review risk was changing only the fatal, so all geometry consumers were updated together and focused hardware tests were run before enabling Gemma and GPT-OSS chunk 0. A performance comparison against the historical bootstrap is the remaining rollout follow-up.
