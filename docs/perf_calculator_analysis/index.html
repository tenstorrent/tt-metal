How the data movement calculator predicts time

It replays requests through directed NoC routes and shared resources, then takes the last completion time. Its useful foundation is a transport simulator; complete algorithm timing still needs a dependency and compute layer.

The captured configuration contains a 17 × 12 physical torus, 110 usable workers arranged as an 11 × 10 logical grid, eight allocator banks, and a 1350 MHz clock. Physical routing dimensions and usable worker dimensions serve different purposes.

Workbook Sheet1 also retains a “120 Tensix cores” header. The current model uses the explicit 110-worker topology. Older workbook examples refer to source directories that are absent from this checkout; their embedded measurements remain inspectable but those harnesses are not reproducible from the referenced paths here.

Workbook serialized estimate (µs): bytes / (effective_GBps × 1000) + (9 × round_trip_links + 4 × 5) / clock_MHz + residual_ns / 1000 Workbook batched L1-copy estimate (µs): total_bytes / (effective_GBps × 1000) + ceil(pages / batch) × fixed_completion_latency_us

The workbook uses a measured 64 KiB effective transfer rate and a residual calibrated from a local 64-byte read. The Python model instead reserves individual packet resources. Those rates and residuals should not be stacked on top of its bank and link queues: that can count the same transport cost twice.

Events live in a time-ordered heap. For each resource, the simulator remembers when it is next free. A packet waits only when that resource is occupied. Different resources and independent cores can progress at the same time.

start = max(arrival, resource_free) resource_free = start + occupancy next_hop_arrival = start + propagation_delay payload_packet_flits = 1 + ceil(payload_bytes / 64) request_without_data_or_ACK_flits = 1 bank_occupancy = ceil(payload_bytes / 47.0805) cycles duration_us = max(core_and_NoC_completion_cycles) / iterations / clock_MHz

Each NoC injection, directed link, and ejection resource is reserved for the packet's flit count, at one flit per cycle. Propagation adds 5 cycles at injection, 9 per link, and 5 at ejection. The packet tail adds flits − 1 cycles once at the destination. Consecutive links overlap: multiplying the full packet serialization cost by the number of hops would be wrong.

A batch advances only after all its requests complete. In split mode each NoC owns half the batch and advances independently; there is no join between the two halves after each batch. All simulated cores start at time zero. Read request j starts at j × issue_interval; write request j starts at (j + 1) × issue_interval. That deliberate timing-origin asymmetry is part of the current implementation.

Mixed does not mean copy. Mixed mode runs independent reads on NoC0 and writes on NoC1. It does not require a write to wait for its source read, share a produced buffer, or wait for compute.

3. Placement changes the route and the shared links

NoC0 routes in increasing X, then increasing Y. NoC1 routes in decreasing Y, then decreasing X. Both wrap around the physical torus. The return packet uses the same NoC's routing rules, so it generally does not retrace the request path.

RequestResponse / ACK● Worker · ■ selected bank endpoint · dotted edges are torus wraps

Routes come directly from routing.links() and topology_bh.json. Worker indexing is row-major. The bank endpoint can differ between NoCs; both still reserve the same logical bank resource. Arrow offsets separate request and return paths visually. Hover a link for its physical endpoints.

Balanced mapping uses page % 8; hotspot mapping targets bank 0. With the default 64 pages/core, every core begins at the same bank phase. Therefore balanced total bytes can still create bursts toward the same bank or link. Splitting traffic can reduce link pressure, but it does not double a bank's capacity.

4. Batching hides repeated completion latency

For the historical 64 KiB far-source L1 copy, changing from one page per barrier to eight reduces the saved measured duration from 8.589 µs to 1.802 µs, approximately 4.77× faster. The bytes are unchanged; fewer serial completion waits make the difference.

The slider recomputes the workbook formula for the far-source 32-page copy. Only batch 1 and 8 have measurements in this view. Other settings are illustrative extrapolations. The formula omits issue limits and contention; the current Python simulator also rejects partial batches.

Timing and validation boundaries

The generic probe measures each core/RISC locally, divides its four-iteration TRANSPORT span by four, and takes the maximum local duration; trials are then summarized by the median. There is no synchronized cross-core start. The simulator instead starts all cores at time zero. These are related metrics, but they are not an independently established global operation makespan.

The generic harness checks the entire output exactly, including untouched hotspot pages. Pure-write source data is initialized in L1 outside timing. For read/mixed probes, post-scope verification writes can overlap slower workers and disturb their measured traffic. The older read-probe source harness is not retained alongside its 24 saved measurements.

The single-core write set informed the first-command issue-time correction, so its excellent agreement is development evidence. The saved multicore predictions were frozen before measurement. Their source hashes still match this checkout and the available raw holdout file, and replay reproduced all 36 saved predictions and measured values.

shortlist.py correctly deduplicates full configuration identities, keeps distinct schedules with equal estimates, and preserves supplied provenance. It does not generate workloads, implement kernels, validate correctness, or establish that the predicted ranking is correct. The caller must include all executable placement and scheduling choices.

The 18 existing CPU tests passed. They check useful invariants: bytes, routing concentration, shared bank capacity, read-profile reproducibility, write completion semantics, and shortlist behavior. Passing these tests does not establish hardware prediction accuracy or cover the missing scheduling mechanisms above.

7. Extending transport into an algorithm duration

Represent the operation as events with explicit dependencies and finite resources. Each read, compute step, and write becomes ready only when its prerequisites are met. The scheduler then naturally models overlap, fill, drain, and backpressure.

Illustrative independent three-stage pipeline, n tiles: serial time = n × (T_read + T_compute + T_write) ideal overlapped time = T_read + T_compute + T_write + (n − 1) × max(T_read, T_compute, T_write)

The ideal formula is a teaching bound under independent stage resources and sufficient buffering. Reads and writes here share banks and may share links, so their per-tile service times change when overlapped. For a real kernel, those activities must run in the same event simulation, with circular-buffer limits and dependencies.

  1. Make results reproducible: unify runtime parameters, validate inputs, preserve raw measurements and hashes, and document exactly which completion is estimated.
  2. Explain the balanced-write gap: freeze predictions, sweep route overlap and outstanding depth, separate issue/flush/ACK phases, and test credit or VC hypotheses without fitting a universal slowdown multiplier.
  3. Implement a minimal dependent copy: read-complete → buffer-ready → write → ACK, with finite buffers. Validate serial and double-buffered variants.
  4. Add measured compute stages: then examine reader/compute/writer overlap and multiple core placements.
  5. Validate ranking as well as duration: compare the predicted shortlist with correct on-device implementations and measure the cost of selecting the wrong configuration.
Practical use today: explain transport bottlenecks and prioritize experiments within measured regimes. General multicore algorithm duration still requires the missing scheduling layer and stronger validation of balanced write transport.
