Prefill → KV Migration: Current Contract

What prefill provides, how migration resolves KV bytes, and which format assumptions are load-bearing
Scope. This describes the code as it exists in tt-llm-engine and tt-metal. It focuses on the current cache/address format and the information boundary between prefill and migration. It intentionally does not propose a paging design.

1. Executive summary

Prefill currently gives migration a startup-time, exhaustive logical-to-physical snapshot. For each cache config, slot, layer, and 32-token natural-position chunk, the table identifies an absolute DRAM NoC address, byte count, and replica device group. Prefill separately supplies a FabricNodeId → 64-bit ASIC unique-ID map so the worker can open the correct UMD device.

After setup, each migration request carries only a UUID, source/destination endpoint and slot, layer range, and token-position ranges. It carries no addresses, allocation identity, table generation, or per-request page list. The worker resolves source and destination locations from the two endpoints' previously exchanged tables.

Most important dependency. The installed table must remain valid from publication through every read and completion that uses it. The worker rejects a second SET_TABLE, precomputes sender queues from the first table, and the multi-rank splitter requires a nonzero entry for every configured slot × layer × max-sequence chunk.
Current multi-cache gap. TT-Metal's table/protobuf supports multiple configs, and DeepSeek may publish config 0 = KVPE plus config 1 = index cache. The active DCN splitter, sender, and migration command use the default config only; there is no config ID in MigratePayload. Therefore config 1 is serialized but is not migrated by this path.

2. End-to-end data and control flow

1. Prefill allocates One max-sequence cache tensor with folded user/layer dimension and 32-token DRAM shards.
2. Prefill describes Enumerates every logical chunk into a KV address-table protobuf and builds the device map.
3. Worker freezes setup Imports SET_TABLE, applies the device map, splits by host/rank, exchanges endpoint tables, then reports ready.
4. Scheduler requests Sends logical source/destination slots plus layer and token rectangles. Layer acknowledgements carry only a counter increment.
5. Worker moves bytes Looks up source and destination chunks, reads one source replica, and writes to every destination replica using a self-addressed wire header.

Startup handoff from prefill

  1. The model runtime builds and serializes the model-specific KvChunkAddressTable.
  2. The client places only the protobuf file path in the shared-memory table queue.
  3. Prefill sends AssignDevMap(count), followed by one device-map entry per chip.
  4. The worker imports and distributes the table. A second SET_TABLE terminates the worker.
  5. On connection, both endpoints exchange their full tables and rank/device ownership. Sender queues are then built.
  6. WORKER_READY gates request processing on table and device-map readiness.

Per-chunk readiness and migration

Prefill sends the runner only three 32-bit values: {slot_id, actual_start, actual_end}. After each layer finishes writing KV, the runner synchronizes device work and increments a shared counter. The acknowledgement has no payload. The scheduler uses FIFO order to interpret acknowledgement number n as layer n of the current chunk, then submits:

source slot + destination slot + [layer, layer+1) + [migration_start, actual_end)

A burst UUID groups all layer/chunk members of one request. The source slot remains owned until the destination drains device writes, sends completion acknowledgements, and the scheduler receives MIGRATION_COMPLETE.

4. Current prefill storage geometry

The primary MLA cache is allocated as [num_users × num_layers, 1, max_seq_len / SP, head_dim]. The folded outer index is user-major: slot × num_layers + layer. It is stored in DRAM with 32-token ND shards distributed round-robin over the device's actual DRAM bank count and replicated across the relevant mesh columns.

The address-table builder replays that exact physical walk. For each SP row, slot, layer, prefill block, and natural 32-token position it records:

noc_addr = (bank_id << 32) | (tensor.buffer_address() + bank_offset)

bank_id advances round-robin; bank_offset increases by the physical chunk size after a complete bank sweep. Natural token positions are mapped block-cyclically across SP rows, so migration needs the full map, not merely a tensor base and a linear per-token stride.

  • Logical/physical atomicity is 32 tokens.
  • Dense BF8 MLA with head dimension 576 uses 18 BF8 tiles: 18 × 1088 = 19,584 bytes per chunk.
  • BF16 row-major cache chunks use 32 × head_dim × 2 bytes.
  • A final non-aligned logical end is rounded up and causes the enclosing full physical chunk to be copied.
  • Sparse models may have a second cache with a different byte geometry and a compact layer namespace.

5. Critical contract for any changed physical allocation

The following information is what migration actually requires from prefill. This is a contract inventory, not a proposed representation.

Required informationWhy migration needs itWhere it exists today
Cache config identity Distinguishes KVPE, index, K/V head caches, their layer namespaces, and byte geometry. In protobuf entries/configs, but absent from migration commands; only config 0 is consumed.
Logical owner identity Correlates a request/slot with the physical mapping that was written and acknowledged. Only slot and UUID are carried; no allocation epoch/generation exists.
Valid logical extent Defines which natural 32-token chunks are populated and safe to read. Scheduler supplies migrated token ranges; the installed table nevertheless describes maximum capacity.
Per-chunk physical location Identifies FabricNode replica group, DRAM bank/channel, absolute byte address, and byte count. Static KvCacheLocation entries published once before requests.
Mapping lifetime/version Prevents an acknowledgement or migration from resolving through stale/reused addresses. Implicitly guaranteed by immutable maximum-size storage; no explicit field exists.
Device and host ownership Resolves FabricNodeId to local ASIC/UMD access and remote MPI rank. Table host map plus separate FabricNodeId → ASIC unique-ID map.
Read-after-write readiness The migration worker reads out of band from the model's TTNN command queue. Device synchronization followed by anonymous per-layer counter acknowledgements.

Observed breakpoints in the current implementation

  • Dense completeness: the multi-rank splitter loops through all configured slots, layers, and maximum-sequence chunks and fatals when size_bytes == 0.
  • Immutable setup: a second SET_TABLE is fatal; remote tables and per-device sender queues are constructed once.
  • No mapping identity: neither prefill metadata, layer acknowledgement, nor MigratePayload identifies an allocation or table generation.
  • Uniform geometry: sender buffer sizing and destination indexing assume compatible source/destination chunk_n_tokens and chunk bytes. Compatibility is not explicitly validated.
  • Per-entry size: parts of the sender use config-level chunk_size_bytes, while reads and wire headers use entry-level size_bytes; variable per-entry sizes are unsafe.
  • Config 0 only: multi-config protobuf support is ahead of the active migration command/splitter/sender path.
  • Alignment: range starts must be 32-token aligned; the final end may be partial but copies the enclosing full chunk.
  • Failure behavior: missing, stale, or invalid mappings generally trigger TT_FATAL, termination, or scheduler abort rather than a recoverable per-request error.
Present integration status. The current prefill runner explicitly rejects simultaneous non-rectangular cache mode and migration, suppresses the KV table and LayerAck setup in that mode, and the runtime refuses table publication. This matches the contract gap above; it is not merely a missing command-line combination.
