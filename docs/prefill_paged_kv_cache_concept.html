Paged KV Cache for Prefill

Feasibility, recommended architecture, and impact on GLM-5.2 storage, kernels, models, scheduling, and migration
Scope. This is a high-level design investigation for the prefill side on current main. It does not specify a final API or implementation. Decode may remain dense in the first version.

1. Verdict

Feasible. Allocate one fixed-capacity shared DRAM pool, then map each request's logical token blocks to physical blocks at runtime. TTNN already has working paged cache writers and paged SDPA readers that prove this indirection model. GLM-5.2 needs new integration because its custom MLA, sparse attention, indexer, and migration paths currently assume one dense, maximum-sized slot.

The safest useful first milestone is paged prefill storage + page-aware writes + gather of the active request into the existing batch-1 attention scratch. This gains multi-user capacity without immediately rewriting the fused ring or sparse attention computation. Page lookup can later be fused into those readers for performance.

2. Why the current allocation does not scale

Today, the engine allocates the complete cache once at startup. The primary cache has the physical shape [users × layers, 1, max_seq_len / SP, width]. Slot recycling overwrites a fixed region; it does not allocate or free memory.

GLM-5.2 makes this especially costly: it has 78 layers and a 1,048,576-token maximum context. It allocates a BF16 row-major 576-wide primary KVPE cache for every layer and a separate BFP8 128-wide index-key cache for its 21 full indexer layers.

Scale illustration. At the full 1M-token limit, one user's logical cache is approximately 87.75 GiB primary + 2.79 GiB index = 90.54 GiB across one SP group, before unrelated model memory. SP divides that footprint across its chips, while TP replicas multiply the fleet allocation. The exact physical total depends on topology, padding, and cache format.

The root problem is therefore not merely unused bytes inside a request. It is that number_of_users × maximum_context is committed before the actual prompt lengths are known.

3. Recommended architecture

Logical identity

slot + token position remains stable and is what the scheduler and model use.

Runtime translation

(allocation epoch, cache kind, logical block) → physical block ID

A small device-resident INT32 table supplies the translation to data-movement kernels.

Physical storage

Fixed shared pools sized for the service's desired concurrent token capacity, not for every slot's maximum context.

Pool organization

  • Use separate physical pools where format or layer ownership differs: at minimum, a primary KVPE pool and an index-key pool.
  • Preserve the current SP block-cyclic placement and 32-token DRAM-bank unit inside each allocation.
  • Keep pool geometry fixed after startup. Only page-table contents and free-list ownership change, so kernel programs can remain cached.
  • Use fixed-size blocks to avoid external fragmentation. Only the final block of a request wastes capacity.

Recommended first allocation granularity

Distinguish the physical storage/transfer page from the allocator block. The existing physical and migration unit is 32 tokens. Allocating individual 32-token pages for a 1M context would require 32,768 entries per row (128 KiB of INT32 metadata), which is awkward to stage in L1 and creates excessive host bookkeeping.

A practical first version can allocate one logical prefill chunk at a time: 5,120 global tokens, containing the existing 32-token physical subpages. Every layer advances through the same token interval, so one request-level allocation can reserve a coordinated layer bundle for the primary and applicable index layers. At 1M context this is about 205 logical entries per request, while migration can still address the contained 32-token chunks. The final block size should remain configurable and be selected from memory-waste, table-size, and kernel-bandwidth measurements.

Do not encode raw NoC addresses in the attention page table. Prefer stable physical block IDs and let the existing TensorAccessor map pool page IDs to DRAM banks. Raw address descriptors are appropriate only at the migration boundary, where the current wire protocol already transfers physical source/destination chunks.

4. Request lifecycle

1. AdmitCompute missing logical blocks for the complete turn.
2. ReserveAtomically reserve primary and index blocks before any kernel runs.
3. PublishWrite the mapping and its generation to the device page table.
4. ExecuteWriters and readers resolve logical positions through that mapping.
5. PinAttention and migration hold immutable mapping snapshots while in flight.
6. ReleaseReturn pages only after eviction and all device/migration completions.

Reserving the whole submitted turn before execution is recommended initially. An out-of-memory result is then a retryable admission failure; it cannot occur halfway through the model after some layers have already modified the cache.

Slot ID alone is no longer sufficient because a physical block can be reused. Each allocation needs {slot_id, slot_epoch}, plus a mapping_generation. In-flight chunks and migration completions retain these values, preventing a late completion from touching a newly reused slot.

EventKV behavior
SUBMITReserve missing blocks, publish a new immutable generation, then enqueue prefill.
Turn completesCommit the new logical end; keep pages resident for continuation.
STOPStop work but preserve the resident KV mapping, matching current semantics.
EVICTDrain writes and migrations, unpublish the mapping, release all pages, and advance the slot epoch.
Failure before executionRoll back the reservation and leave the previously committed mapping unchanged.

Utilities / tests Zeroing, PCC, readback, and address-table generation expect a dense tensor. Operate only on allocated logical blocks and validate unallocated entries explicitly.

Why program caching remains possible

Existing TTNN paged cache operations bind the pool and page-table buffers through runtime arguments. Table values may change without recompilation; stable pool shape, format, block size, and table geometry remain structural program inputs. DeepSeek's existing writer already patches slot and logical position as runtime arguments. A paged writer can follow the same pattern.

6. Migration impact

The current migration table is a startup-time dense grid over every slot × layer × max-sequence chunk. Migration commands contain logical slot, layer, and token ranges but no cache config, allocation epoch, mapping generation, or page list. The worker installs the table once and derives permanent queues from it. That contract cannot safely describe recycled physical pages.

Migration should consume an immutable mapping snapshot captured for the exact logical range. The snapshot identifies:

  • allocation ID (slot + epoch), mapping generation, and cache config_id;
  • logical layer/block range;
  • resolved source device, NoC address, and byte count for each allocated physical chunk;
  • compatible resolved destination chunks.

Pages in the snapshot remain pinned until MIGRATION_COMPLETE. The scheduler's current in_flight_count, writer-pending count, and migration-completion gates are good lifecycle foundations; the pin must apply to the exact captured pages, not merely to a logical slot.

Useful compatibility path. Prefill can become paged first while decode remains dense. Migration resolves the paged source snapshot and the existing dense destination addresses, validates format and chunk compatibility, and uses the current physical destination-address wire format.

7. Suggested implementation sequence

  1. Lifecycle foundation: introduce a KvPageManager abstraction with allocation IDs, generations, snapshots, and pin counts, initially backed by the existing dense cache.
  2. Paged storage and write: allocate fixed primary/index pools, publish device tables, and add a page-aware DeepSeek writer.
  3. Functional attention path: gather only the active slot's allocated prefix into the current batch-1 scratch; retain existing dense/sparse attention kernels.
  4. Paged-source migration: replace the startup dense source table with immutable resolved snapshots; keep dense decode destinations.
  5. Performance: fuse page lookup into ring gather and optimize sparse/index gathering after profiling.
  6. Later robustness: dynamic paged destinations, prefix-copy allocation, recoverable migration failure, cancellation, and crash reconstruction.

8. Main risks and decisions to validate

Block sizeBalance tail waste and admission flexibility against page-table size, L1 staging, and address-lookup overhead.
Layer bundle vs per-layer allocationBundles simplify atomic admission and compact tables; independent blocks improve flexibility but enlarge metadata and rollback state.
Gather MVP costMeasure the extra DRAM pass versus the capacity gain; use the already shared batch-1 scratch rather than per-user scratch.
SP/TP/PP identityMake local/global layer identity and per-SP mappings explicit; verify TP replicas receive consistent ownership updates.
Atomic two-cache reservationGLM requires primary blocks for all owned layers and index blocks only for full-indexer layers; partial reservation must roll back.

Conclusion: paging is technically compatible with the TT-Metal memory model. The critical engineering boundary is consistent logical-to-physical translation across every producer, consumer, and migration lifetime—not the DRAM allocation itself.
