1. Check that the model implementation the tool writes actually works
    - When a model is not in HF format the tool writes its own PyTorch version of it, and every later
      test is scored against that version. What it checks only confirms the weights fit, not that the
      maths is right, and a wrong RoPE or a wrong epsilon leaves every shape identical. Ours was
      correct, but we only know that because we compared it against our own reference by hand.
    - Fix: have it write a real check that the model works, and prove the check can fail by breaking
      the model on purpose. Otherwise you get a test that passes whatever happens. It already did
      exactly this for our model, in a comment: it drove the speech path and found that a wrong RoPE
      gives a buzz that never stops. Make that run.

2. Fix bring-up from a local folder
    - A folder on disk is not treated the same as a model name downloaded from HuggingFace. It gets
      a shallower check and the run dies three stages later pointing at the wrong thing. Optimizer
      stage then confuses the folder holding the weights with the folder holding the generated code,
      and loses track of which model it came from, so it cannot build its own correctness check. We
      named it by hand.
    - Fix: accept a folder everywhere a name from HuggingFace works, and keep track of both.
    - Also, running a model's own code is only allowed for one hardcoded model name. Ours passed the
      early checks and then failed when it ran, blaming the model rather than the setting. A model's
      config already declares that it ships its own code, so decide from that. We did, and it worked.

3. Use the saved inputs in the tests, and allow more than one prompt
    - Real inputs and outputs are saved for every component, and the log says the tests use them, but
      they do not. The main input is random noise and the others are guessed from argument names. For
      our model that meant a 3-D activation where a complex RoPE table was expected, the additive
      causal mask dropped so the reference itself became non-causal, and floats where integer codebook
      indices were needed. We wrote them by hand before the tests meant anything.
    - The end to end test also decides pass or fail for the whole model from a single prompt.
    - Fix: use the saved inputs, compare against the saved output, accept more than one prompt, and
      make the log say what the test actually used.

4. The decode step exists twice, and speed and correctness were measured on different ones
    - The version that ships has no KV cache, the traced one does. Speed was measured on the traced
      one, correctness on the other. It reported 17.2% faster; what ships got 13.2%, 297.69 to 258.26
      ms per audio frame. Our hand written port of the same model on the same board runs at 26.9 ms.
    - The cache never reaches the component during bring-up. The saved example holds a real cache, but
      the same object goes to the reference and then to the port, so the port sees one entry too many
      and the cache is dropped; and the argument name is not on the recognised list, so it arrives
      empty anyway. With no cache the test compares a single value and returns 1.0 whatever the inputs
      are, so using the cache and ignoring it score the same. The simpler one was accepted, and the
      shipped path then recomputes the whole prompt on every frame.
    - Fix, in order: copy the saved inputs before passing them to each side, add the cache to the
      recognised list, let the component use it since its signature already has the argument, and
      update the expected call counts and the component check in the same change, or a correct fix
      will look like a regression. For the traced version the position is baked into the recording, so
      it has to become a tensor on the device.
    - And check that the code measured for speed is the code that generates speech.
