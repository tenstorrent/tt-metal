1. Enable bring-up of models which are not natively in HF format, because there is a lot of models
   not in this format
    - In TTS these are the majority. Natively-transformers TTS is a short list (SpeechT5, VITS/MMS,
      Bark, Parler-TTS, Moshi, CSM, Dia). Most of what people use ships its own inference code:
      XTTS-v2, StyleTTS2, F5-TTS, CosyVoice, Fish Speech, GPT-SoVITS, ChatTTS, MeloTTS, Kokoro,
      Tortoise, and Voxtral-TTS. Being hosted on the HF Hub is not the same as being loadable by
      AutoModel.from_pretrained, which is what the loader requires.
    - You already have a resolver for exactly this, and it is off:
      scripts/tt_hw_planner/reference_loader_resolver.py targets "non-transformers checkpoints --
      e.g. Mistral/vLLM-native consolidated.safetensors + params.json, GGUF, or trust_remote_code
      variants" and is OFF BY DEFAULT unless TT_HW_PLANNER_LOADER_RESOLVER=1. It writes one
      model-local tests/pcc/_reference_loader.py that the generated PCC tests pick up as a fallback,
      and correctness stays gated by PCC.
    - Fix: enable it by default, or at least name it in the failure message when from_pretrained
      fails. Today a non-transformers model looks unsupported.
    - We did not test the resolver -- we converted the model to HF format ourselves before starting,
      so we cannot say how well it works. If converting is the intended path, document what the
      wrapper must provide: config.json with auto_map, a configuration_*.py + modeling_*.py pair, and
      a transformers-format tokenizer converted from the native one. It took us several days.

2. Fix the model bring up from local path
    - Local path bring-up uses different logic from a Hub model id, and the difference surfaces late
      with a misleading diagnosis. Three instances:
        - F1: a local model dir gets a degraded probe; the run dies three stages later and the
          diagnosis points somewhere else.
        - F9: optimize <local dir> is mistaken for a demo dir, which makes optimize unusable by
          model id.
        - F10: the workaround for F9 (pass the demo dir) loses the model id, so optimize cannot build
          its own correctness gate even though it had already written one. We had to pass --pcc-test.
    - Fix: treat a local directory as a first-class model id throughout, and carry it alongside the
      demo dir rather than instead of it.
    - Related, F21: trust_remote_code is an allowlist of exactly one model
      (base_model_name in ["Phi-3-mini-128k-instruct"]). A custom-architecture checkpoint clears
      preflight and static analysis, then fails at execution with a message blaming the repository
      rather than the loader. Fix: decide from the checkpoint -- auto_map in config.json is itself
      the declaration that a model ships custom code. We patched this and it worked.

3. Support multiple input prompts for the tests
    - Two layers here, and the component tests are worse than "one prompt":
        - e2e gate (F28): one prompt decides PASS/FAIL for the whole port (E2E_ALL_TASKS=0), and no
          flag widens it. One sample cannot separate a systematic error from a lucky prompt.
        - per-component gates (F36): no prompt at all -- they use torch.randn. Preflight captures
          real IO for every component (43 MB each for attention and decoder_layer, including the
          reference output.pt) and prints "per-component PCC tests will use real inputs". The
          generated tests contain no torch.load at all: 0 hits across all 7 files. Inputs are
          synthesised from the forward signature by argument name. The captures are opened only to
          decide which submodule to test.
    - Fix (components): load args.pt/kwargs.pt when a capture exists, and compare against the
      captured output.pt so the gate becomes a golden test. Everything needed is already on disk.
    - Fix (e2e): take the sample count from the batch dimension the test already has, or expose a
      flag.
    - Fix (both): make the log line state what the gate actually ran on.

4. Model has two implementations of decode step, eager one without KV cache and traced one with KV
   cache:
    - Correction to sequencing: both live in tt/pipeline.py and are written by emit-e2e, not
      bring-up. Bring-up produces the _stubs/.
    - A cache never reaches the component, by two independent routes:
        - The capture holds a real 208-deep KV cache, but the harness hands the same object (no copy)
          to the reference and then to the stub. VoxtralAttention.forward mutates it
          (cache[cache_key] = (k, v)), so the stub would attend over a cache one position longer than
          the golden did. So the cache is dropped, and the harness records the consequence itself:
          "Dropping the cache instead makes the test vacuous: at S=1 with no cache the softmax is
          over a single key, so it returns 1.0 whatever q and k are." (F27)
        - The generated test builds arguments by name and skips unrecognised optional ones
          (tests/pcc/test_attention.py:461). cache is not in _WELL_KNOWN_INPUTS, and
          past_key_values / cache_position / use_cache are explicitly nulled.
      So a cache-using and a cache-ignoring implementation score identically (0.9999). The simpler
      one was written and graduated.
    - Why the shipped path then recomputes: Gate 1 requires the demo to route through the graduated
      stubs, and a cacheless stub leaves only one correct option -- hand it the whole prefix again
      every frame.
    - Watch out when fixing: e2e_plan.json gate_2_invoked requires tts_backbone == 1 + n_frames, so a
      correct fix fails Gate 2 (and Gate 1) as written. Update the expected counts in the same commit
      or a good change will look like a regression.
    - On the traced one: decode_step is correct at any position as ordinary Python (pos is a
      parameter). It is position-locked only when captured, because the Python int is frozen into the
      recording -- a trace taken at position 200 always writes cache slot 200. To replay it in a loop
      the position has to be an on-device index tensor.
    - Impact: the optimizer ranked all 26 attempts and 11 commits against decode_step while the e2e
      PCC gate ran run_tts. It reported -17.2%; the shipped path improved -13.2% (297.69 -> 258.26 ms
      per audio frame), because most edits landed in shared helpers that both paths use. So the work
      is not lost, but nothing measured what ships. For scale, our hand-written port of the same
      model on the same board is 26.9 ms/frame.
    - Fix, in order:
        1. deepcopy the captured args before handing them to each side.
        2. add cache to the test's recognised inputs, so the component is specified against it.
        3. let the stub carry the cache -- its signature already declares the parameter and the
           reference already defines the contract (layer(x, cis, bias, cache)).
        4. re-derive the plan's invocation counts (tts_backbone == 1), updating Gates 1 and 2 in the
           same change.
        5. for the traced path, move the position on-device as an index tensor.
    - Also cheap and independent: assert that the perf test's hot function is reachable from the
      demo's entry point before the first measurement. That check alone would have caught this.
