1. Enable bring-up of models which are not natively in HF format, because there is a lot of models
   not in this format
    - In TTS these are the majority. Natively-transformers TTS is a short list (SpeechT5, VITS/MMS,
      Bark, Parler-TTS, Moshi, CSM, Dia). Most of what people use ships its own inference code:
      XTTS-v2, StyleTTS2, F5-TTS, CosyVoice, Fish Speech, GPT-SoVITS, ChatTTS, MeloTTS, Kokoro,
      Tortoise, and Voxtral-TTS. Being hosted on the HF Hub is not the same as being loadable by
      transformers, which is what the loader requires.
    - You already have a resolver for exactly this case. It writes a model-local loader that the
      generated tests pick up as a fallback, and correctness stays gated by PCC, so it cannot weaken
      a test. But it is disabled by default and only reachable after a component has already failed
      to build its reference, so in practice a non-transformers model simply looks unsupported.
    - Fix: enable it by default, or at least point at it in the error message when loading fails.
    - We did not exercise it -- we converted the model to HF format ourselves before starting, so we
      cannot say how well it works. If converting is the intended path, document what the wrapper
      has to provide. It took us several days.

2. Fix the model bring up from local path
    - A local path takes different code paths from a Hub model id, and the difference surfaces late
      with a misleading diagnosis:
        - a local model directory gets a reduced probe, and the run dies three stages later with a
          diagnosis pointing somewhere else
        - the optimize stage mistakes a local model directory for a demo directory, which makes it
          unusable by model id
        - the workaround for that, passing the demo directory instead, loses the model id, so
          optimize cannot build its own correctness gate even though it had already written one. We
          had to name the gate test explicitly on the command line to get one at all.
    - Fix: treat a local directory as a first-class model id everywhere, and carry it alongside the
      demo directory rather than instead of it.
    - Related: support for custom-architecture checkpoints is an allowlist containing exactly one
      model name. Such a model clears preflight and static analysis, then fails at execution with a
      message blaming the model repository rather than the loader. Fix: decide from the checkpoint
      instead -- its config already declares that it ships custom code, and HF refuses to load it
      without permission, so that declaration is decisive and no allowlist is needed. We patched
      this and it worked.

3. Support multiple input prompts for the tests
    - Two layers, and the per-component tests are in worse shape than "one prompt":
        - end-to-end gate: a single prompt decides pass/fail for the whole port, and no option
          widens it. One sample cannot separate a systematic error from a lucky prompt.
        - per-component gates: the real captured inputs are never used. The pipeline captures real
          inputs and outputs for every component, and reports that the component tests will use
          them, but none of them do. The main input is random noise.
        - and out of the box it is worse than noise: inputs are guessed from the argument names on
          the component's signature, which for this model produced a wrongly shaped activation where
          a rotary table was required, silently dropped the causal mask so the reference itself
          became non-causal, and passed floats where integer codebook ids were needed. Those inputs
          had to be written by hand during bring-up before the tests meant anything.
    - Fix (components): use the captured inputs when they exist, and compare against the captured
      output, so the gate becomes a real golden test. Everything needed is already on disk.
    - Fix (end-to-end): take the sample count from the batch dimension the test already has, or
      expose an option.
    - Fix (both): make the log line say what the gate actually ran on.

4. Model has two implementations of decode step, eager one without KV cache and traced one with KV
   cache:
    - Both are created in the wiring stage, not during bring-up. Bring-up produces the components.
    - The cache never reaches the component, for two independent reasons:
        - the captured example does contain a real cache, but the same object is handed to the
          reference and then to the port. The reference writes into it as it runs, so the port would
          attend over one position more than the reference did. So the cache is dropped -- and the
          harness records the consequence itself: with no cache the attention is over a single key
          and returns 1.0 whatever the inputs are, which makes the test meaningless.
        - separately, the test builds its inputs from a list of recognised argument names, and the
          cache is not on that list, so it is always passed as null.
      A cache-using and a cache-ignoring port therefore score identically, so the simpler one was
      written and accepted.
    - Why the shipped path then recomputes: the rules require the demo to run through the accepted
      components, and a component that ignores the cache leaves only one correct option -- hand it
      the whole prompt plus everything generated so far, on every frame.
    - Watch out when fixing: the plan requires the backbone to run once per frame plus once for the
      prompt, so a correct fix will fail that check, and the component-identity check as well.
      Update the expected counts in the same change, or a good fix will look like a regression.
    - On the traced one: it is correct at any position when called normally, because the position is
      an argument. It is locked to a single position only once recorded, because the position is
      baked into the recording -- a recording made at position 200 always writes slot 200. To replay
      it in a loop the position has to live on the device as a tensor.
    - Impact: every optimizer attempt was measured against the traced path, while the end-to-end
      correctness gate ran the eager one. It reported a 17.2% gain; the shipped path improved 13.2%
      (297.69 -> 258.26 ms per audio frame), because most edits landed in code both paths share. So
      the work is not lost, but nothing measured what actually ships. For scale, our hand-written
      port of the same model on the same board runs at 26.9 ms per frame.
    - Fix, in order:
        1. copy the captured inputs before handing them to each side
        2. add the cache to the list of recognised inputs, so the component is specified against it
        3. let the component use the cache -- its signature already has the parameter, and the
           reference already defines the contract
        4. re-derive the plan's expected call counts, updating both checks in the same change
        5. for the traced path, move the position onto the device as a tensor
    - Also cheap and independent: check that the function the perf test measures is actually
      reachable from the demo's entry point, before measuring. That alone would have caught this.
