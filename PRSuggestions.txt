PR #46283 — suggested fixes
===========================

Context: we drove this PR's pipeline (bring-up -> emit-e2e -> optimize) end to end on a Blackhole
p150b against Voxtral-TTS — 4.0 B params, three stacks (autoregressive backbone + flow matching +
audio codec) — a model the tool had never seen. Bring-up did well: 7/7 components rewritten, 114/114
operations on device, no CPU fallback, one round, 42 minutes, and the resulting pipeline is correct
(e2e PCC 0.9999834, emitted audio codes exactly equal to the reference, zero code flips). The four
items below are what we'd ask you to fix.

Full evidence, log excerpts and reproduction commands: TOOL_FINDINGS.md (entry IDs referenced below).


1. Enable bring-up of models that are not natively in HF `transformers` format
------------------------------------------------------------------------------
There are a lot of these, and in TTS specifically they are the majority. Natively-`transformers` TTS
is a short list (SpeechT5, VITS/MMS-TTS, Bark, Parler-TTS, Moshi, CSM, Dia). Most of what people
actually reach for ships its own inference code: XTTS-v2, StyleTTS2, F5-TTS, CosyVoice, Fish Speech,
GPT-SoVITS, ChatTTS, MeloTTS, Spark-TTS, Kokoro, Tortoise — and Voxtral-TTS.

Worth separating two things that get conflated: being **on the HF Hub** and being in
**`transformers` format**. Nearly all of the above are hosted on the Hub (Voxtral under
`library=vllm`, XTTS under `library=coqui`) — but hosting is not the same as being loadable by
`AutoModel.from_pretrained`, which is what the loader requires.

The reason TTS skews this way is structural. `transformers` fits a decoder-only LM well: one model
class, one config, one forward. A modern TTS system is a *pipeline* — a backbone emitting semantic
tokens, then flow matching or diffusion, then a codec or GAN vocoder, plus a speaker encoder. There
is no natural single `PreTrainedModel` to be, so authors ship their own runner. Expect this to keep
being true rather than to converge.

**You already have the mechanism, and it is off.** `scripts/tt_hw_planner/reference_loader_resolver.py`
opens with:

    "LLM resolver for models whose weights won't load via transformers.AutoModel*.from_pretrained
     (non-transformers checkpoints — e.g. Mistral/vLLM-native consolidated.safetensors + params.json,
     GGUF, or trust_remote_code variants). ... OFF BY DEFAULT: resolve is a no-op unless
     TT_HW_PLANNER_LOADER_RESOLVER=1"

It names Voxtral's exact native format. It writes one model-local
`tests/pcc/_reference_loader.py` exposing `load_reference_model(model_id)`, which the generated PCC
tests pick up as a fallback, and correctness stays gated by PCC — so it cannot weaken a test. The
bring-up MCP tool that reaches it (`resolve_reference_loader`) is additionally described as
reachable only via the gate's `resolve_loader` rung, after a component has already failed to build
its torch reference.

- Fix: turn the resolver on by default, or at minimum surface it — mention it in the failure message
  when `from_pretrained` fails, and in the docs, so a user hits it before concluding the model is
  unsupported. Right now a non-`transformers` model looks like a hard "no".
- Caveat, stated plainly: **we never exercised the resolver.** We converted the model to
  `transformers` format ourselves before starting, so we cannot vouch for how well it works — only
  that it exists, is off, and targets exactly this case. Worth your own test before relying on it.
- If the intended path really is "convert first", say so in the docs and state what the wrapper must
  provide. Ours needed: `config.json` with `auto_map`, a `configuration_*.py` and `modeling_*.py`
  pair, a `transformers`-format tokenizer converted from the native one, and per-parameter shape
  metadata. That was several days of work and is a precondition, not a nice-to-have.


2. Fix bring-up from a local path
----------------------------------
A local directory takes different code paths from a Hub model id, and the difference surfaces late
and wearing the wrong diagnosis. Three distinct instances:

- **[F1] A local model directory gets a degraded probe**, and the run dies three stages later. The
  diagnosis printed at the point of failure points somewhere else entirely, so the time is spent in
  the wrong place.
- **[F9] `optimize <local dir>` is mistaken for a demo directory**, which makes `optimize`
  unusable by model id.
- **[F10] The workaround for F9 — passing the demo directory instead — loses the model id**, so
  `optimize` cannot build its own correctness gate, even though it had already written one. We had
  to pass `--pcc-test` explicitly to get a gate at all.

- Fix: treat a local directory as a first-class model id throughout, and carry it *alongside* the
  demo directory rather than substituting one for the other. The probe a local path gets should be
  the same probe a Hub id gets.

Adjacent, same family: **[F21] `trust_remote_code` is an allowlist containing exactly one model** —
`if self.base_model_name in ["Phi-3-mini-128k-instruct"]`. So a custom-architecture checkpoint clears
preflight ("transformers can load ... [ok]"), clears static analysis, and then fails at execution
with a message blaming the repository rather than the loader. Fix: decide from the checkpoint —
`auto_map` in `config.json` *is* the declaration that a model ships custom code, and HF refuses to
load such a model without `trust_remote_code`, so its presence is decisive and needs no allowlist.
We ran with this patched and it worked.


3. Support multiple input prompts for the tests
-----------------------------------------------
Correct, and there are actually two layers to it — the per-component tests are in worse shape than
"one prompt" suggests.

- **The e2e gate runs on one prompt.** `E2E_ALL_TASKS=0` and a single default prompt decide PASS/FAIL
  for the whole port, and no flag widens it. For a generative audio model, one sample cannot
  distinguish a systematic error from a lucky prompt. **[F28]**
- **The per-component gates run on no prompt at all — they use `torch.randn`.** **[F36]** Preflight
  captures real IO for every component (43 MB each for `attention` and `decoder_layer`, including the
  reference `output.pt`) and prints *"per-component PCC tests will use real inputs"*. The generated
  tests contain **no `torch.load` whatsoever** — 0 hits across all 7 files. Every input is synthesised
  from the forward signature by argument name, with a `torch.randn(1, 64, 64)` fallback. The captures
  are opened only to decide which submodule to test.

- Fix (components): load `args.pt`/`kwargs.pt` when a capture exists, falling back to synthesis only
  when it does not, and compare against the captured `output.pt` so the gate becomes a golden test.
  Everything needed is already on disk.
- Fix (e2e): take the sample count from the batch dimension the test already has, or expose a flag.
  Even n=4 separates systematic from lucky.
- Fix (both): make the log line state what the gate actually ran on. Announcing real inputs while
  using synthetic ones is the part that cost us most — we believed the gate for a day.


4. The model has two implementations of the decode step — eager without KV cache, traced with it
-------------------------------------------------------------------------------------------------
This is the most consequential finding and it is the root of the performance problem. One correction
to sequencing first: **both implementations are written by `emit-e2e`, not bring-up** — bring-up
produces the `_stubs/`, and `tt/pipeline.py` (containing both decode paths) is created by the
emit-e2e builder.

**Why the cache-less one exists.** Two things independently prevent a cache reaching the component:

- The capture holds a **real 208-deep KV cache**, but the harness hands the **same object** (no copy
  at all) to the reference and then to the stub. Because `VoxtralAttention.forward` mutates it
  (`cache[cache_key] = (k, v)`), the stub would attend over a cache one position longer than the
  golden did. So the cache is dropped — and the harness records the consequence itself: *"Dropping
  the cache instead makes the test vacuous: at S=1 with no cache the softmax is over a single key, so
  it returns 1.0 whatever q and k are."* **[F27]**
- Independently, the generated test builds arguments **by name** and skips anything optional it does
  not recognise (`tests/pcc/test_attention.py:461`):

        is_well_known = name in _WELL_KNOWN_INPUTS
        if not is_required and not is_well_known:
            continue

  `cache` is not in `_WELL_KNOWN_INPUTS` and has a default, so it is skipped; the same file also
  explicitly nulls `past_key_values`, `cache_position` and `use_cache`.

So a cache reaches the component under test by **no route at all**. A cache-using rewrite and a
cache-ignoring rewrite therefore score **identically (0.9999)**, and the simpler one was written,
passed, and graduated. Nothing here is forbidden — nothing was asked.

**Why that forces recomputation in the shipped path.** Gate 1 obliges the demo to route through the
graduated stubs (*"assert each routed object is an instance of the class defined in
`_stubs/<name>.py` ... the pipeline imports the stubs as-is"*). A stub that ignores caches leaves
exactly one correct option: hand it the whole prefix again, every frame. Which `run_tts` does —
re-running all 26 layers over the padded 224-token sequence per frame and keeping one row.

**And the plan then froze that as the specification.** `e2e_plan.json`'s `gate_2_invoked` requires
`tts_backbone == 1 + n_frames` — a count only achievable by recomputing. Note the consequence for
whoever fixes this: **a correct fix will fail Gate 2 as written**, and Gate 1 too, so the expected
counts must change in the same commit or a good change will look like a regression.

**Why the second implementation exists.** The trace gate needs fixed shapes, which needs a cache —
so `decode_step` was written, bypassing the stubs, with a resident cache and static shapes. On the
position: as ordinary Python it is **correct at any position** (`pos` is a parameter, and a caller
advancing it 200, 201, 202 gets the right answer). The limitation bites only at **trace-capture
time**, when the Python integer is frozen into the recording — so a trace captured at position 200
would, on every replay, write cache slot 200 and apply position 200's mask. Making one recording
valid at every step needs the position on-device as an index tensor. **[F46]**

**Measured consequence.** The optimizer ranked all 26 attempts and 11 commits against `decode_step`,
which the demo never calls, while the e2e PCC gate ran on `run_tts`. It reported **−17.2%**; the
shipped path actually improved **−13.2%** (297.69 -> 258.26 ms per audio frame), because most edits
landed in shared helpers (`tt_common.py`, `tt_backbone.py`) that both paths execute. So the work is
not stranded — but it arrives by side effect, not because anything measured what ships. A change that
helped `decode_step` and hurt `run_tts` would have been banked, and nothing would have noticed.

For scale: our hand-written TTNN port of the same model on the same board runs **26.9 ms/frame**
(RTF 0.357, i.e. 2.8× faster than real time) against the generated port's **258.26 ms/frame**
(RTF 3.319, 3.2× slower than real time). Most of that 9.6× is these two structural issues — no cache
and no trace replay — not tuning.

- Fix, cheapest first:
  1. `deepcopy` the captured args before handing them to each side.
  2. Add `cache` to the test's recognised inputs, so the component is actually specified against it —
     a cache-less rewrite then stops scoring 0.9999 on a vacuous comparison.
  3. Let the stub carry the cache. Its signature already declares the parameter
     (`def __call__(self, h, cis=None, bias=None, cache=None, cache_key=None)`) and the reference
     already defines the contract (`layer(x, cis, bias, cache)`) — the body simply ignores it.
  4. Re-derive the plan's invocation counts from the cached structure (`tts_backbone == 1`, not
     `1 + n_frames`), and update Gates 1 and 2 together with the change.
  5. Separately, for the trace path to be usable in a loop: move the position on-device as an index
     tensor so one recording is valid at every step.
- Also worth adding, cheap and independent: **assert that the perf test's hot function is reachable
  from the demo's entry point** before the first measurement. A static reachability check would have
  caught this whole class of problem on day one.
