1. Enable bring-up of models which are not natively in HF format, because there is a lot of models
   not in this format
    - In TTS most models are like this: XTTS-v2, StyleTTS2, F5-TTS, CosyVoice, GPT-SoVITS, Kokoro,
      Voxtral-TTS and others all ship their own code. Being on the HF Hub does not mean transformers
      can load it.
    - You already have this and it works. We hid every PyTorch version of the model on the machine and
      ran it anyway: it wrote the architecture itself, about a thousand lines covering all three
      stacks, and every stage matches our reference to rounding with the audio codes identical. It is
      a published architecture though, so this does not show it could do the same for a new one.
    - First problem, when it runs is inconsistent. Pointed at a checkpoint that is not in HF format
      the default path writes the loader on its own, but two other places that use it need an
      environment variable that is off by default, and one of those says the feature is off unless you
      set it, which is not true. We missed the feature completely because we had already converted the
      model to HF format by hand, which is the one thing that stops it running.
    - Second problem, its own check is a comment rather than code. The reasoning is good: it worked
      out that this model cannot be checked on text, because the text head is unused and every RoPE
      convention scores the same on it, so it drove the speech path instead and confirmed the model
      stops on its own at a length that tracks the text, then tried a wrong RoPE on purpose and got a
      buzz that never stops. Nothing can re-run any of that, and this file is what every later test is
      scored against, so a slightly wrong one would set every target wrong unnoticed.
    - Fix: one rule for when it runs, described correctly. Have it write that check as code and run
      it, keeping the deliberate wrong version, since a check never seen to fail proves little. And
      say in the log whether it adapted an existing implementation or wrote one itself.

2. Fix the model bring up from local path
    - A folder on disk behaves differently from a Hub name, and fails later with a confusing error:
        - a local folder gets a shallower check, and the run dies three stages later pointing at the
          wrong thing
        - optimize confuses the folder holding the weights with the folder holding the generated
          code, so you cannot point it at the model
        - pointing it at the generated code loses track of which model it came from, so optimize
          cannot build its own correctness check even though it wrote one. We named it by hand.
    - Fix: accept a folder anywhere a Hub name works, and keep track of both.
    - Related: models that ship their own code only work if their name is in a hardcoded list, and
      that list has one entry. Ours passed the early checks, then failed when it ran, blaming the
      model rather than the loader. Fix: look at the model. Its config already says it ships its own
      code. We changed this and it worked.

3. Support multiple input prompts for the tests
    - The end to end test uses one prompt to decide pass or fail for the whole model, and there is no
      way to add more. One prompt cannot tell a real bug from a lucky guess.
    - The per component tests never use real inputs. Real inputs and outputs are saved for every
      component, and the log says the tests use them, but they do not. The main input is random noise.
    - Worse, inputs are guessed from the argument names. For our model that passed a 3-D activation
      where a complex RoPE table was expected, dropped the additive causal mask entirely (so the
      reference itself became non-causal), and passed floats where integer codebook indices were
      needed. These had to be written by hand before the tests meant anything.
    - Fix: use the saved inputs and compare against the saved output. Let the end to end test take
      more than one prompt. Make the log say what the test actually used.

4. Model has two implementations of decode step, eager one without KV cache and traced one with KV
   cache:
    - Both are written when the pipeline is wired together, not during bring-up.
    - The cache never reaches the component, for two reasons:
        - the saved example contains a real cache, but the same object is passed to the reference and
          then to the port. The reference writes into it as it runs, so the port sees one entry too
          many. The cache is dropped to avoid that, and the tool notes what it costs: with no cache
          the test compares a single value and returns 1.0 whatever the inputs are.
        - the test only passes arguments whose names are on a recognised list, and the cache is not on
          it, so it always arrives empty.
      A version that uses the cache and one that ignores it therefore score the same, so the simpler
      one was accepted.
    - The version that generates speech then has to recompute. It must use the accepted components,
      and one that ignores the cache can only be given the whole prompt plus everything generated so
      far, on every frame.
    - A correct fix will fail two existing checks: the plan expects the model to run once per frame
      plus once for the prompt, and a second check verifies which components are used. Update both in
      the same change, or a good fix will look like a regression.
    - The traced version works at any position when called directly. The problem appears once it is
      recorded, because the position is baked into the recording, so a recording made at position 200
      always writes to slot 200. To replay it in a loop the position has to be a tensor on the device.
    - Speed was measured on the traced version and correctness on the eager one. It reported 17.2%
      faster; what ships got 13.2% (297.69 to 258.26 ms per audio frame), because most edits touched
      shared code. The work is not lost, but nothing measured what ships. Our hand written port of
      the same model on the same board runs at 26.9 ms.
    - Fix, in order:
        1. copy the saved inputs before passing them to each side
        2. add the cache to the recognised list
        3. let the component use the cache, its signature already has the argument
        4. update the expected call counts and both checks in the same change
        5. for the traced version, make the position a tensor on the device
    - Before measuring speed, check that the code measured is the code that generates speech.
