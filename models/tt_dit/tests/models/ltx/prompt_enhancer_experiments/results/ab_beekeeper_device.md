## Coexistence observations (4x8, resident E2B next to encoder + DiT + VAE)
- Load order that works: VAE decoder, upsampler, audio decoder+vocoder, DiT (48 s) in __init__; Gemma4 CCLManager (devices=32 num_links=2 topology=Ring async=0 persistent_buf=1, matches the LTX ring fabric, no topology warning), E2B weights from the warm cache, on-device sampler (force_argmax=1, unused under host sampling); then VAE encoder, Gemma-3 encoder (21 s), connectors, encoder trace capture at 19:02:47.
- After the capture one more "potentially unsafe" warning fires (19:02:48.9, first E2B op allocating transient activations under the live encoder trace); harmless because those buffers are consumed before the next replay, but it means any persistent E2B allocation after capture is a hazard. Traced decode for E2B would have to be captured before the encoder's trace.
- No DRAM/OOM, CCL, semaphore, eth or fabric errors in either log; both runs close with "Closing devices in cluster completed"; device released. E2B rewrite -> Gemma-3 encode (0.17 s trace replay) -> DiT -> VAE -> audio interleave cleanly across arms and probes. Host E2B (parity reference) coexists on host without issue.
- Cache: tensor_cache_bf16_mesh4x8 (11 GB, 38 entries) moved to /mnt/models/huggingface/tt_cache/gemma-4-E2B-it (group tt-cache, g+rwX); the enhancer's resolver picks it on its own, so TT_CACHE_PATH is redundant there. Warm load 50.3 s vs 16.8 s from the same dir: NFS page cache.
- Pipeline change owed (not patched, driver-only workaround): warm the enhancer before the encoder's first encode in both distilled warmup branches (pipeline_ltx_distilled.py:149-151, :224-226).

## Bottom line
The device E2B rewriter runs correctly beside LTX on one 4x8 handle when it is loaded before any trace capture; the enhanced prompt costs 53 s on top of a 24-30 s generate at today's 3.6-3.75 tok/s eager decode, which is the item to attack next (traced decode / on-device sampling / token cap), followed by the warmup-order fix.
