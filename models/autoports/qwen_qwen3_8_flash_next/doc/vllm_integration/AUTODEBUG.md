**Minimum correction for this pinned path:** canonicalize the decoder's stored `self.kind` from `full_attention` to `indexed_attention` at `TT/multichip_decoder.py:975`, before construction dispatch and state allocation. Keep the supplied config unchanged: the current adapter and vLLM both expect its raw labels. All other consumed values already match standalone. Changing only the decoder's `elif` leaves state allocation inconsistent; globally rewriting vLLM's config breaks its attention classification and the adapter predicates. No dependency upgrade or plugin change is indicated by this failure. A private normalized model config is a coherent broader alternative, but requires coupled adapter changes and is not the strict minimum.

## Complete causal chain

1. **Standalone normalization owns the alias conversion.** `HF/models/qwen4_exp/configuration_qwen4_exp.py:173-183` either constructs a linear/indexed pattern when labels are absent, or replaces each explicit `full_attention` with `indexed_attention`. Its architecture validation only accepts linear/indexed (`:187-191`). Thus the actual checkpoint has always required QSA semantics at layer 3; it is not a request to add dense full attention to TT.
2. **The bundled config intentionally retains another vocabulary.** `V/models/qwen4_exp/config.py:34,73` subclasses/calls `Qwen3NextConfig`. That parent stores explicit labels unchanged (`V/transformers_utils/configs/qwen3_next.py:249-255`). Qwen4-Exp's bundled config defines its attention aliases as `full_attention` and `qwen_sparse_attention` (`config.py:22-26`) and maps those to `attention` in `layers_block_type` (`:175-180`). Its comment about Transformers naming is not the installed standalone implementation: installed 5.22.2 uses `indexed_attention`.
3. **The new handoff removes normalization without replacing it.** `P/loader.py:38-44` passes `model_config.hf_config`; `TT/generator_vllm.py:44-52` passes the same object to `build_generator`; `TT/generator.py:1214-1220` passes it to `QwenModel`. `TT/model.py:105-107` now skips standalone AutoConfig whenever an injected object exists, then stores its text config directly. No alias translation intervenes.
4. **The consumer's first contradictory branch is deterministic.** `TT/multichip_decoder.py:975` reads `cfg.layer_types[layer_idx]`. At index 3 this is `full_attention`. Its only attention branches are linear (`:998`) and indexed (`:1001`); the else raises (`:1005`). Layer 0 and layer 1 are linear in both config variants, matching their recorded successful loading. Reduced selection skips layer 2. The decoder evaluates PLE selection and constructs both residual mixers before the rejecting branch (`:995-997`); actual MeshPLE construction occurs on layer 1, not layer 3. This explains why the error happens during construction rather than immediately on adapter entry.
5. **No asynchronous inference attribution is warranted.** Device setup/weight uploads precede this Python exception, but the failing branch never constructs `MeshQSA` for layer 3 and no request forward is shown. Earlier host progress is not proof all queued work completed; neither that uncertainty nor any kernel hypothesis is needed to explain this explicit exception.

## Smallest correction preserving the standalone model contract

This is an implementation recommendation, not a patch performed here.

1. **Canonicalize the stored decoder kind, without mutating config.** At `MultichipDecoder.from_state_dict`, replace the direct assignment at line975 with the equivalent of `raw_kind = cfg.layer_types[layer_idx]` followed by `self.kind = "indexed_attention" if raw_kind == "full_attention" else raw_kind`. Existing standalone indexed/linear labels remain unchanged. Construction (`:998-1005`) and `_create_base_state` (`:1012`) then agree. `QSA` validates the actual target dimensions, indexer fields and RoPE (`qsa.py:55-88`); it does not read `layer_types`. Preserve these validations: this is the known QSA checkpoint alias, not general dense-full-attention support. No newer Transformers import is needed.
2. **For this minimum repair, keep current adapter config predicates coherent.** Leave `QwenModel.config.layer_types` and the original vLLM config raw. Both `get_kv_cache_spec` and `allocate_kv_cache_per_layer` then still see the twelve `full_attention` labels (`generator_vllm.py:85,90`), while decoder instances use canonical `self.kind`. The audit found no other serving-path read of the raw layer label that requires conversion. This is sufficient at the source-contract level for the demonstrated label defect; it is not proof of successful hardware construction or serving.
3. **If choosing a canonical model-config interface instead, couple the adapter change.** An alternative is to normalize a private text-config copy in `QwenModel` before setup, preserving every other value and inherited field. Then the allocator's predicate must recognize canonical indexed labels; the spec hook still sees the raw original. A shared classifier accepting both forms in both hooks adds local adapter robustness, but does not establish end-to-end support for a canonicalized vLLM-owned config: pinned vLLM's scheduler attention count still expects its own full/sparse vocabulary (`V/config/model.py:1698-1725`). Bundled `qwen_sparse_attention` is another possible alias, not necessary for this recorded checkpoint. Keep vLLM's original config raw. This alternative has more change surface than normalizing `self.kind` alone.
4. **Preserve index/order ownership.** Scheduler attention ordinal `j` corresponds to real decoder index `4*j+3`. Reduced ascending selection `(0,1,3)` should accept twelve incoming logical specs and forward only ordinal0 for real layer3; full48 should forward all twelve in order. The generator requires indexed-attention-only specs in decoder order (`generator.py:213-218`). Do not reduce scheduler layer count for the reduced debug build. Arbitrary unsorted selections require mapping by actual model order, as noted below.

Why the narrow alternatives are incomplete:

- Merely admitting `full_attention` at `multichip_decoder.py:1001` leaves `self.kind="full_attention"`. `_create_base_state` checks for `indexed_attention` (`:1012`) and otherwise allocates GDN state (`:1049-1052`). Runtime chooses the constructed QSA object through `self.chunked_attn is not None` (`:1096-1100`), but receives that incompatible state. Canonicalize the stored kind, not just the first branch.
- Rewriting `hf_config.text_config.layer_types` in place leaves zero matches in current adapter spec/allocation predicates (`generator_vllm.py:85,90`). Bundled `layers_block_type` also recognizes only full/sparse aliases, so vLLM's attention count can become zero (`V/config/model.py:1698-1709`). A private TT copy keeps scheduler ownership coherent.
- Silently reconstructing a default config or reloading unrelated defaults risks changing explicit values. All needed current numeric fields already exist; label normalization is the only demonstrated model-consumed mismatch.

## Other potential issues / unresolved checks

- **Bare text-config input:** adapter and decoder unwrapping accept a text config, but `QwenModel` currently unconditionally accesses `.text_config` (`model.py:107`). A bare text config would raise an AttributeError. The logged wrapper has `.text_config`, so this does not cause this failure. Align unwrapping if that input form is intended to be supported.
- **Attention ordinal versus decoder-index names:** current spec keys embed real indices (`model.layers.3.self_attn`, etc.). The pinned plugin's uniform single-group `AttentionSpec` path allocates by twelve ordinals without parsing these names (`P/model_runner.py:878-882`). Multi-group mapping and heterogeneous-spec paths parse indices into arrays of length12 (`:728-744,883-958`), so indices such as15 would be invalid there. The current hook emits twelve identical specs; no evidence shows those other paths are reached in the failing run. This remains conditional, not a second explanation for the observed exception.
- **Unsorted reduced selections:** `_layer_indices` accepts arbitrary tuple order (`generator_vllm.py:19-21`) and model construction preserves it (`model.py:108,123-138`), whereas adapter spec filtering iterates ascending real-layer indices (`generator_vllm.py:89-98`). A selection such as `(7,3)` would order model states differently from pools. Require ascending unique selections or project specs in actual model order if generalizing this debug interface. The logged `(0,1,3)` and default full48 are unaffected.
- **Broader config portability:** default gate differences, custom intervals, alternate QSA aliases, and altered PLE/hash settings need explicit validation or implementation before claiming support. Their necessary preconditions are absent in this checkpoint. Do not turn them into precision/performance changes.
