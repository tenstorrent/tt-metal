# Independent source audit: MeshMoe and MeshGDN

CPU-only inspection of the live `tt/multichip_decoder.py`, its inherited Qwen fused/optimized components, native DeepSeek prefill dispatch/fused-SwiGLU/combine/reduce implementations, and the local Kolibri EP reference. No device operations or implementation edits were performed. Line numbers describe the source inspected on2026-11-13.

## P1: Every decode and non-32-token tail reaches an explicit native validation failure

Evidence: `MeshMoe.__call__` uses logical `n=x.shape[-2]` in `combine(seq_len_per_chip=n)` (line641), reshapes weights to `[1,1,n,10,1]` (line644), then calls `post_combine_reduce` (lines645–647). Native `ttnn/cpp/ttnn/operations/experimental/deepseek_prefill/post_combine_reduce/device/post_combine_reduce_program_factory.cpp:76–82` computes the token count from the **logical combine shape** and requires `num_tokens % 32 == 0`. Consequently logical decode1 and tails1..31 throw `Number of tokens ... must be divisible by32 for hardware tilization`. Physical TILE padding elsewhere does not satisfy this because combine output is ROW_MAJOR with logical shape `[1,1,n,10,2560]`. `decode_forward` passes its ordinary one-token input directly into this path.

Exact repair: preserve logical dispatch/counts and active experts, but pad the **post-combine reduction inputs** to32 tokens internally, run the native reduction on32, then slice the routed result back to `n` before adding shared-expert output. Pad the contribution rows with zeros, score rows with zeros, and IDs with a valid global expert ID. To avoid requiring a rank5 pad implementation, flatten ROW_MAJOR combined contributions to `[n*10,2560]`, zero-pad to `[32*10,2560]`, then reshape to `[1,1,32,10,2560]`. Pad scores and UINT16 IDs in rank2/4 before reshaping; their padded rows must actually own storage because the native reader accesses all32. Do not merely change `seq_len_per_chip` to32 without ensuring initialized/padded contribution and score buffers. A separately measured indexed batch1 implementation may replace this reduction path later. Required focused validation: logical1,2,31,32 and a33-token public prefill (32+1), with repeated replay and watcher enabled separately from profiling.

## P2: Tuple batch decode serializes the complete MoE, so the planned grouped batch path is absent

Evidence: `MultichipDecoder.decode_forward` (lines782–783) aliases `prefill_forward`. Its tuple branch (lines764–768) recursively executes an entire request, including `_chunk`'s `self.mlp(mixed)` (line761), before moving to the next request. Thus a tuple of32 one-token requests invokes32 independent one-token router/dispatch/fused-SwiGLU/combine calls. It never invokes the batched grouped expert path with32 diverse rows. The model's required maximum-batch execution and MoE decision rule therefore cannot be validated by simply calling the current tuple API.

Exact repair: add a decode-specific tuple path. First advance each request's attention/PLE state and obtain its post-attention residual plus MLP mixed input/injection. Concatenate the32 mixed rows along the token axis and invoke `MeshMoe` once; then slice each routed result row and apply the corresponding request's MLP residual write. Attention, position, recurrent, hash and page-table states must remain per-request, and request order must be preserved. Reuse the same physical grouped-MoE path for diverse batches2..32, using the internal padding repair above for incomplete reduction tiles. The numerical requirement is per-request batched-equals-solo within the specified PCC contract; benchmark a genuinely grouped batch32 against the serialized reference. This change does not require adding a full-model or serving implementation.
