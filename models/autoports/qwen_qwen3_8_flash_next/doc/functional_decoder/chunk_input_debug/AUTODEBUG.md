**Leading finding: long-prefill chunk preparation creates request-specific native slice workloads whose kernel binaries remain in DRAM. Preparing all 32 small decoder counts does not prepare those workloads.** The capacity proxy understates this cost by repeating offset 0. A model-local, descriptor-only BF16/UINT32 copy path with runtime offsets/counts, plus a runtime-count output writer, is a well-supported intervention. Its correctness, trace behavior, and resulting public capacity still require validation. The competing claim that `ttnn.full` causes the per-length slope is not supported by this revision's lowering or the saved allocation ledger.

**The native slice resource chain is directly supported by source.** `FunctionalDecoder.prefill_forward` sends lengths 1–32 directly to `_chunk` (`tt/functional_decoder.py:155–157`). For longer inputs it allocates the full output and executes every `start = 0,32,...`, slicing hidden states and token words before calling `_chunk` and `write_token_chunk` (`:158–171`). This keeps the following contracts through lowering:

| Operand | Public representation | Actual native slice path |
|---|---|---|
| Hidden states | BF16 TILE `[1,1,N,10240]`, padded height `ceil(N/32)*32` | Unit steps, tile-aligned start; `SliceTileProgramFactory` |
| PLE token words | UINT32 ROW_MAJOR `[1,N,16]` | Unit steps, full 64-byte row; `SliceRmProgramFactory` |

Device `__getitem__` calls `ttnn.slice` (`ttnn/ttnn/operations/core.py:136–149`). For these interleaved inputs there is no sharded composite hop or tensor-argument slice: the wrapper calls `prim::slice(...use_tensor_args=false...)` (`ttnn/cpp/ttnn/operations/data_movement/slice/slice.cpp:349–388,433–446`), and factory selection is explicit (`.../slice/device/slice_device_operation.cpp:425–456`). Tiled ends are rounded up to a tile boundary, then the result is viewed back to the logical count. The native copy is not inherently a view of the original data buffer: output allocation is at `slice_device_operation.cpp:410–422`.

`SliceDeviceOperation::compute_program_hash` includes starts, ends, steps, factory/configuration, **input logical and padded shapes**, and output specification (`slice_device_operation.cpp:459–525`). Thus equal output sizes are insufficient for reuse. New input N creates new entries even throughout 3649–3680, where all BF16 source tensors have the same padded height 3680. New starts at fixed N also create new entries. Repeating the same offset/count/N uses an existing entry. At a fixed aligned start, BF16 counts 1–32 can share the rounded physical slice, while RM counts remain distinct.

Cache entries own their mesh workloads (`tt_metal/api/tt-metalium/program_cache.hpp:67–85,145–169`). On a cache miss TTNN creates, uses, then stores the workload (`ttnn/api/ttnn/device_operation.hpp:334–368`). `MeshWorkloadImpl::load_binaries` allocates a distinct DRAM `kernel_bin_buf_` on first enqueue and stores it in that workload (`tt_metal/distributed/mesh_workload.cpp:170–219`; ownership at `mesh_workload_impl.hpp:77`). Releasing input/output tensors does not erase the program cache or its binary buffer. Host JIT reuse of identical kernel code does not deduplicate these per-workload device buffers.

Binary-buffer pages are 2048 B (`tt_metal/impl/dispatch/device_command.hpp:39`). Bank spreading rounds to at least one page per bank for a nonempty allocation (`tt_metal/impl/allocator/allocator.cpp:784–793`). With eight banks this gives a **minimum 16,384 B allocator footprint per new nonempty workload**. The native-only control matches both the cache-key prediction and that minimum exactly:

The zero warm baseline is expected: reading all of a 32-row tensor takes the identity/full-slice shortcut, so it does not prewarm the later native sub-slices. **The earliest relevant mismatch is the model's preparation boundary.** Public preparation calls prefill on standalone inputs of counts 32 and 1–31, then decode1, restoring all four states (`tests/probe_ple_decoder.py:291–333`). Every such prefill takes the direct `_chunk` branch. It warms bounded decoder math/hash signatures, but never executes long-source extraction or the long-output writer. The actual request then introduces new extraction programs while the large inputs/output and packed embedding are already resident. This is a caller/preparation mismatch with native slice's actual specialization contract; it is not evidence that native slice's shape/bounds key can simply be removed globally.

For N=3649, the real loop visits 115 chunks: 114 full chunks and tail `(3648,1)`. For N=3680 it visits 115 full chunks. Each previously unseen N therefore introduces **230 native slice signatures** for a complete PLE public prefill, provided execution reaches all offsets and cache is enabled, with a binary-buffer lower bound of 3,768,320 B. The aligned historical proxy visits only the two offset-0 slices, and the nonaligned proxy adds just two tail slices. It omits offset 32 and all intermediate offsets. All 32 new terminal lengths would potentially require 7,360 native slice entries, at least 115 MiB, if fully executed without cache collisions or earlier failure. These are source-derived resource bounds, not measured full-prefill allocations or a prediction of the exact failing offset.

The writer adds another preparation dependency. `tt/chunk_output.py:15,28,88` compiles logical source rows into the descriptor (`compile_args=[rows, tiles]`). Destination length and offset are already independent of the descriptor key for the supported interleaved layout. Thus each previously unseen tail count adds a writer workload even after standalone small decoder preparation. This is bounded by 32 row counts per width/grid, unlike the per-N/per-start native extraction growth, but it contributes to the terminal sequence and can prevent first writer use during capture.

**The `ttnn.full` alternative was challenged and demoted for this revision.** Public `ttnn.full` goes through `ttnn/cpp/ttnn/operations/creation/creation.cpp:347–362,181–248`. For BF16 TILE interleaved DRAM and size at least 128 KiB, it creates the tensor then invokes in-place unary `fill` (`:26,218–232`). UINT32 RM fails that eligibility check and uses a host vector plus device upload (`:68–89,215–218,236–244`). The similarly named `operations/full/FullDeviceOperation` is not this call's lowering.

The tiled unary hash excludes the ordinary logical shape/volume and includes tensor layouts, operation attributes, worker grid, and read-flow selection (`ttnn/cpp/ttnn/operations/eltwise/unary/device/unary_device_operation.cpp:346–415`). All terminal hidden inputs have the same tile/page geometry and 36,800 pages. The grid is the full worker grid for this size (`.../unary/common/unary_utils.cpp:610–633`); FILL has unmeasured cost and selects the default read flow (`:94–141,457–460`). Thus those new N values do not imply a new fill program per N. Full setup can require a first-use program or another configuration elsewhere, but no such per-N change was identified here.

An independent numerical check makes this distinction concrete. For each terminal N, the saved prepared/before-to-`resident_io` drop equals **only** the live I/O tensors:

```text
2 * ceil(N/32) * 32 * 10240 * 2  # hidden input plus output, BF16
+ 8 * ceil(N/8) * 64             # UINT32 token rows, bank-spread allocation
+ 655360 + 512                   # reserved decode hidden and token input
```

For N=3649 this is 151,622,656 B, exactly `340,782,592 - 189,159,936`. For N=3664 it is 151,623,168 B, exactly `339,537,408 - 187,914,240`. The same equality holds for every terminal candidate and both fresh boundary artifacts. There is zero unexplained net allocation at this snapshot to assign to new full-input factory programs. This also explains the small token-allocation steps within a BF16 padded-height bucket. Future footprint controls should still use setup-time host upload, matching `probe_ple_decoder.py:245–249,338–344`, to isolate copy programs without depending on factory behavior.

**A minimal model-local descriptor-only replacement is technically appropriate, subject to the following exact contracts.** Keep model math, existing decoder `_chunk`, state updates, chunk size, dtypes, output shape, and operation ordering. Replace only the two long-input slicing sites and move the writer's row count into a runtime argument. Do not patch native slice hashing, globally disable/clear the cache, or recategorize output allocations to conceal growth.

Generic op already hashes its descriptor rather than tensor arguments (`ttnn/cpp/ttnn/operations/generic/device/generic_op_device_operation.cpp:52–130`). It hashes kernel source, compile args, fixed core ranges/configuration, runtime core-list size, CB sizes/formats, and semaphores; runtime values are excluded. Interleaved `TensorAccessorArgs` compiles only accessor flags and aligned page size, not source N (`tt_metal/impl/buffers/tensor_accessor_args.cpp:207–220`). On cache hit the current descriptor's runtime arguments are reapplied (`ttnn/api/ttnn/mesh_device_operation_adapter.hpp:820–824`; `tt_metal/impl/program/program_descriptors.cpp:188–200`). Therefore source N, buffer addresses, start, and count can vary without changing a descriptor when physical page geometry remains fixed.

Use fixed core ranges, CB geometry, and the same positional runtime-argument schema on every call, including inactive work. Changing active core sets with count would recreate specialization. Use the ordinary descriptor hash, not `custom_program_hash`. Generic op's low-level validation does not establish the model-specific shape/layout contract: the Python helper must validate it on every call, including cache hits.

| Copy | Host-validated representation | Runtime addressing and work |
|---|---|---|
| Hidden reader | BF16 standard untransposed 32x32 TILE, source `[1,1,N,10240]`, padded `[1,1,ceil(N/32)*32,10240]`; output logical `[1,1,count,10240]`, padded `[1,1,32,10240]` | `WT=320`; for each tile column c, read page `(start/32)*320+c`, clear invalid rows `count..31`, write destination page c; 2048 B per tile |
| Token reader | UINT32 ROW_MAJOR, source logical/padded `[1,N,16]`; output `[1,count,16]` | For r in `[0,count)`, read accessor page `start+r`, write page r, exactly 64 B; one fixed core is sufficient |
| Output writer | Preserve existing BF16 tiled interleaved source/destination contracts and canary behavior | Pass source row count at a fixed runtime slot; retain existing destination tile/face mapping and write only those rows |

For readers require integer `start` and `count` before allocation/runtime-argument construction, `start >= 0`, `start % 32 == 0`, `1 <= count <= 32`, and `start+count <= N`. Restrict to allocated interleaved DRAM on the same supported device/mesh, reject source/output aliasing, and reject nonstandard tiles, extra padding, wrong rank/width, and unsupported storage views. Initially proving the existing single-device functional path is sufficient; do not claim arbitrary sharded or multichip support from this addressing argument. Reader alignment need not narrow the existing writer, which already supports unaligned output offsets.

The BF16 reader always writes `320*2048 = 655,360` physical bytes, even for count1. A full source-tile read at the final partial tile is in bounds because physical source height is padded. Explicitly zero the invalid output rows: valid source rows beyond a short requested count may exist, so copying a tile and relying on source padding is insufficient. Tile rows are not contiguous row-major rows. Their two 32-byte halves begin at `((r>>4)*512 + (r&15)*16)*2` and that offset plus 512, agreeing with `tt/chunk_output.py:28–35`. Clearing a contiguous suffix would corrupt or fail to clear face data.

The UINT32 path must copy all 16 words bit-for-bit, including high-bit values and validity words. Resolve each row through its tensor accessor; raw `base + start*64` arithmetic would ignore interleaved bank mapping. Output allocation can vary within its <=2048 B payload bound without changing compiled page geometry. Use `ttnn.empty` for these outputs; allocating or filling them through another shape-specialized device op would undermine the footprint goal.

A single data-movement kernel per reader is the smallest synchronization surface. Reserve one private scratch page, obtain its pointer, then for each assigned page: read, read barrier, optional BF16 tail clearing, write, write barrier before scratch reuse. BF16 loop bounds depend on fixed assigned tile columns; count controls row masking. UINT32 loop bounds depend on runtime count. If separate producer/consumer kernels are chosen, both must agree exactly on page count and partition: reserve/read/barrier/push(1) pairs with wait/write/barrier/pop(1). No consumer may wait for a padded nominal count when the producer sends only the logical count. No arithmetic compute kernel or conversion is required.

**Preparation must execute, not merely compile.** `prepare_generic_op` calls `device_operation::prepare` (`generic_op_device_operation.cpp:156–160`), whose preparation callback calls `experimental::program_preparation::prepare` (`ttnn/api/ttnn/device_operation.hpp:513–533`). That helper calls only `workload.impl().compile` (`tt_metal/distributed/mesh_workload.cpp:555–561`). It can populate a compiled cache entry without loading its binaries. First enqueue still reaches the lazy DRAM allocation at `mesh_workload.cpp:170–219`, which explicitly rejects loading new binaries during capture (`:193–199`).

Consequently, setup must actually execute and synchronize **all three descriptors**—BF16 reader, UINT32 reader, and runtime-count writer—before large resident I/O, the persistent-memory baseline, or trace capture. A count32 call on small scratch tensors is enough only if source N, start, count, and destination N are genuinely absent from the descriptors. Execute the helpers themselves; passing a 32-row input through the decoder's direct `_chunk` path does not exercise them. Release setup tensors after synchronization. Keep the existing separate all-count decoder/hash warmup and restore all recurrent/PLE/hash states afterward.

Runtime offsets/counts permit different eager calls and captures. They do **not** make a captured trace's plan dynamic. A captured trace retains the captured addresses/start/count; changing source contents in place is valid with proper queue ordering, while changing those plan values requires a different capture or an explicitly designed device-control contract.

**Other potential issues and limits, excluded from the headline diagnosis.** The existing writer obtains `get_write_ptr` without a prior `cb_reserve_back` (`tt/chunk_output.py:24`), whereas the API documents a reserved-region precondition (`tt_metal/hw/inc/api/dataflow/dataflow_api.h:310–313`). Its scratch is private, and no source/evidence chain ties this omission to per-N persistent DRAM growth or the reported OOM. Keep it as a local kernel-contract concern when revising the writer, not as the cause of this incident. Generic descriptor hashing also requires a stable runtime schema and ordinary hash discipline; no collision or stale-runtime-argument failure was observed here. Numerical/MoE/QSA changes and general allocator rewrites are outside this chunk-input investigation.

The final claim audit retained the preparation/cache ownership mismatch, the writer's count specialization, and the proxy coverage defect because each follows a concrete source path and predicts the saved sequence. It demoted factory-per-length growth, a tail16 numerical bug, and intrinsic context limits because lowering, phase evidence, or the fresh-process contrast contradict those stories. Cheap local checks independently recomputed every terminal I/O ledger, all candidate pass/failure phases, the native control's 324 exact checks/338 entries, runtime source hashes, and terminal/native log hashes. Hardware validation remains necessary to prove the proposed kernels, exact per-workload terminal allocation ownership, live-trace isolation, and the capacity gained by the minimal intervention.
