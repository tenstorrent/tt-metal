  4. New `swebench/watchdog.sh`: if the server stops answering, it kills the agent and logs to STATUS.md, so a crash cannot burn instances again.
  5. pkill note: `pkill -f "mini-extra swebench"` also matched (and killed) my own shell. I now match on `[v]envs/swe/bin/mini-extra`.

### 2026-11-19T09:39:19Z - SWE: sandbox containers expired after 2 h (harness bug; corrects the "KV stall" note above)
- **Symptom:** almost no progress 04:00-09:36Z (1 instance in ~5.5 h). All 7 step-limit (LimitsExceeded, empty-patch) results so far ended with every command returning `Error response from daemon: No such container`.
- **Cause:** mini-swe-agent's DockerEnvironment starts each sandbox as `docker run --rm ... sleep 2h` (`container_timeout` default "2h"). On this server, long trajectories run longer than 2 h, so the sandbox exits and is removed mid-run. The agent then burns its remaining steps on failing commands while its context keeps growing, which also caused the long-context KV pressure I misread earlier as the root cause.
- **Fix:** `environment.container_timeout: "48h"` in swebench/ornith_local.yaml. Verified that new sandboxes run `sleep 48h`.
- **Redo:** the 7 affected instances (astropy-14096, astropy-14369, django-10097, django-10554, django-11087, django-11138, django-11433) moved to swebench/full_out_container_expired_discarded/ and are being re-run. They never had a working sandbox for the whole run, so this is a harness failure, not a model outcome. This reverses the earlier "first attempt counts" restore of 6 of them.
- **Also stopped:** the 3 in-flight instances (sandboxes already dead), which are re-run from scratch. Supervisor restarted.
