# Host phase accounting

The opt-in observer records server host `perf_counter()` timestamps at the autoport boundary. It adds no device event, device synchronization, TTNN profiling, tensor transfer, or changed serving configuration. A Python list buffers completed events; an explicit local Unix-socket request copies that list and writes the snapshot after measured HTTP traffic. The socket uses an abstract address derived from the persistent snapshot path.

Enable each server with `ORNITH_BENCHMARK_TIMING=<absolute persistent per-profile JSON path>`. Add that path as `timing_snapshot` in `perf-bN-server.json`. Configure `roofline_command` as the evaluation Python plus the absolute `tools/collect_benchmark_roofline.py` path. The startup snapshot records the actual imported autoport path/hash, all32 layer indices, loaded precision summary, checkpoint revision, actual participating devices/grid, tensor shapes, and per-device allocated tensor bytes.

Prefill timing starts before adapter checks and input handling. A terminal prefill returns a host tensor after its existing readback. Discarded intermediate chunks do not imply completion and are held until a terminal read. Decode timing starts before adapter checks and ends after the existing `process_decode_output_host` materialization and sample bounds check. In the plugin, `async_decode.finalize_decode` has already waited on the existing read events before calling this boundary. The canonical generator also synchronizes that already-existing event when materializing; the observer adds no synchronization.

The canonical generator refuses prefill while any decode handle lacks completion (`generator.py`, `prefill_forward`). Thus the responsive 1:2 scheduler can overlap decode submissions with one another, but cannot execute a prefill through this adapter while one remains incomplete. The collector partitions one timeline: completed prefill intervals and the decode complement, including scheduler gaps. A gap between consecutive prefill calls with no decode belongs to prefill. Other gaps around decode belong to decode. It rejects genuinely ambiguous cross-phase overlap rather than attributing device enqueue duration as completion time.

The client detailed `start_times` share the same host monotonic clock. The collector excludes warmup and the initial probe before the earliest measured start, captures actual scheduler request IDs and prompt lengths, and checks that unique admissions and prompt totals match the performance JSON. Every measured request must have at least its delivered output count minus the first prefill token in completed decode steps. Executed asynchronous pipeline tail steps remain in work accounting; their counts are reported separately from delivered tokens. Any unfinished measured submission prevents collection. Both selected events and the complete raw event buffer are retained.

Decode DRAM traffic is estimated from actual stored projection/head/norm weight bytes, shared once per fixed-capacity trace step; page-rounded BFP8 KV reads and tile writes; complete FP32 recurrent and BF16 convolution state traffic; inactive-slot snapshot/restore; embedding reads; BF16 logit write/sample read; and sampled-token readback. All four TP ranks are counted. There is no MoE or DP replication. This is logical traffic accounting, not a physical bus-transaction measurement: repeated cache-tile fetches and small scalar/dispatch traffic are excluded. Fixed-capacity recurrent processing and inactive preservation remain counted even when fewer requests are active.

Prefill counts useful projection/head, causal attention, and recurrent contraction FLOPs for observed chunk lengths and positions. Tile padding, discarded/rebuilt work and scalar/SFPU work are excluded. The peak is the work-weighted harmonic LoFi/HiFi2/HiFi4 matrix peak, using the observed available compute grid, four chips, 4096 FLOP/core/cycle, and the published 1.35 GHz clock. These are explicitly modeled utilization estimates, with no acceptance threshold.

Peak sources: [p300c specifications](https://docs.tenstorrent.com/aibs/blackhole/p300.html) establish 1.35 GHz and 1024 GB/s per two-chip card (512 GB/s per chip); the checkout's [matrix-engine report](https://github.com/tenstorrent/tt-metal/blob/main/tech_reports/matrix_engine/matrix_engine.md) supplies 4096 FLOP/core/cycle and fidelity divisors for Blackhole. The actual available grid, rather than the larger marketed core count, is recorded by the server.

CPU validation: `python models/autoports/ornith_ai_ornith_1_5_9b/tests/benchmark_timing_test.py` passes seven tests covering async decode overlap, scheduler gaps, ambiguous overlap rejection, probe exclusion, missing completions, shared batch weight accounting, and the snapshot endpoint. See `setup/phase_host_tests.log`. Compilation checks passed for the recorder, adapter, and collector. No hardware command was executed by the phase-audit agent. Live startup storage API compatibility and actual event/request mapping must be demonstrated by the enclosing agent's setup performance probe before accuracy.
