# Serving hot-path source audit

CPU/source-only audit, 2026-11-13. Plugin HEAD: `2a1504554aa7babb1d426dfbca8c7db8c0a795ef`. No inference, hardware access, profiling, or runtime edits were performed. This audit concerns the primary greedy/device-sampled async path; stochastic top-k40 compatibility is a separate host path.

The serving adapter delegates to the canonical generator with the existing explicit reload commands. Steady device decode does **not** refresh device tokens, positions, or page tables, reconstruct a model per row, read full logits, or execute blocking traces. It does perform host metadata work beyond the canonical high-level token-output loop. Its cost has not been measured, so this is not evidence of serving/canonical latency equivalence.

Evidence: [`mixed_runtime_audit.json`](../../readiness_vllm/mixed_runtime_audit.json) and its [`mixed_trace.json`](../../readiness_vllm/mixed_trace.json) raw events cover the full 32-layer model, B32 capacity, context 262144, and a mixed correctness workload with three concurrent requests. Recounting the raw events gives:

| Decode mode / command | Steps |
|---|---:|
| Device, no input or page reload | 248 |
| Device, input reload | 8 |
| Device, page-only reload | 22 |
| Host, input reload | 69 |

There were 347 decode steps, 13 prefill calls, six initial trace captures, no new captures/retirement, and zero OOV tokens. The 69 host steps requested logprobs explicitly. The eight device input reloads are consistent with admission/layout/prefill/mode transitions under the planner; the compact events do not independently attribute every individual transition. Page-only commands preserve token and position residency. These are command counts, not transfer counts: `reload_inputs` also refreshes page tables, and one refresh copies each fixed row. The workload includes tracking/JSON logging and is explicitly not a performance run.

Source findings (plugin paths below are relative to `/home/ttuser/ornith-9b/dependencies/vllm-tt-plugin/src/vllm_tt_plugin/`):

* `tt/generator_vllm.py:230–258` checks cache identity, converts sampling parameters, and delegates. Its output assertion reads only returned token IDs. Decode event JSON/flush is disabled unless `TT_METAL_TRACE_ALLOC_TRACKING=1` (`:85`); performance runs should keep tracking disabled.
* `tt/generator.py:655–688,1033–1077,1079–1094` runs the same captured model/sampler as canonical generation. Captured `plus_one` advances positions and seed; sampling writes next-input tokens into resident storage. Both trace executions specify `blocking=False`. Input/position copies are conditional on `reload_inputs`; table copies are conditional on input/page reload. `capture(:773)` returns immediately when already captured.
* `tt/generator.py:1140–1198` queues one shard's token buffer to CPU asynchronously and records an event. Full vocabulary shards are transferred and concatenated only in host-sampling mode. Async completion ultimately waits for the read event; this is output readiness, not a blocking trace submission. Plugin `async_decode.py:1631` waits the event, then generator host processing waits that same already-completed event again. The second event API call is redundant in this composition, but its cost is unknown and the generator's standalone safety contract must remain intact.
* `model_runner.py:2318–2630` still builds CPU tokens/positions, sampling tensors, and full-width page tables on every submission, including steady async decode. `input_batch.py:778` gathers/clones each group's rows, masks its unused suffix, and pads width; the runner pads batch rows. At B32 and width 8192, one int32 group table is 1 MiB before additional copies/masks. This host reconstruction is distinct from an H2D refresh. `async_decode.py:416–488` compares tables with `torch.equal`; the steady eligibility check (`:669`) and actual submission (`:1401`) each call the planner, so an eligible steady step can repeat the comparison. Submitted table snapshots are cloned only on reload, not every step.
* The runner slices/pads sampling tensors each step (`model_runner.py:1238,2599`); `async_decode.py:1377` converts every sampling field to Python lists and constructs another parameter object even when `reload_sampling_params=False`. The adapter then constructs its canonical parameter type. This is avoidable host allocation/conversion in principle, not device sampler reconfiguration. CPU token/position construction is likewise unused by canonical steady preflight, but lifecycle transitions must retain authoritative values.
* Canonical `decode_forward` itself adds per-submission validation, handles/events, inactive-output masking and `_validate_resident_window(:1101)`, which scans every active row's causal host-table prefix. `_execute` updates per-slot sampling-progress tuples each step. The prefix scan and streaming submission machinery are absent from the tighter high-level `generate→replay` loop (`:1200,1320`), although `_execute` bookkeeping is shared. These differences must be included in a fair token-output baseline comparison. `decode_resident` intentionally omits intermediate host outputs and is not an equivalent streaming baseline.

The largest source-visible serving-specific opportunity is avoiding repeated full-width host page-table reconstruction/comparison on unchanged scheduler state, followed by unchanged sampling-parameter conversion and redundant planner evaluation. Any future change must preserve page growth, immediate resume/replacement, row movement, host/device transitions, and immutable pending-output ownership. Caching internal state does not inherently require a new model interface, but no such change is proposed for implementation here. Measure CPU preparation and an untracked, matched-capacity token-output comparison before assigning priority or predicting speedup. The current evidence supports resident device execution, not a quantified absence of host overhead.

Top-k40 remains outside the advertised device maximum32. Its full-logit host read and CPU sampling are expected compatibility costs and must not be attributed to the primary greedy path or hidden by changing sampling semantics.

Follow-up bounded CPU microbenchmark: [results and source snippets](hot_path_cpu_cost.json), [raw log](hot_path_cpu_cost.log), [reproducer](hot_path_cpu_cost_probe.py). Actual pinned methods/statements were extracted with AST and executed with CPU Torch and fake storage holders; no TT/plugin module import or device access. The successful serial run used 3.06 process CPU seconds, Torch 2.11.0+cpu, one intra-op and inter-op thread, Ryzen 7 9700X, 50 warmups and 1000 individual measurements per case. One int32 table group had width 8192 and 129 live blocks per active row; unused suffixes were cleared by the real method. Separate untimed dispatch instrumentation counted exact ATen calls.

| Active rows / wire capacity | Table build + padding + two equality checks, median / P99 µs | Sampling slice + optional padding + list conversion, median / P99 µs |
|---|---:|---:|
| 1 / 1 (shape control) | 28.27 / 30.06 | 20.45 / 23.13 |
| 1 / 32 (one request on B32 serving) | 513.04 / 632.63 | 71.74 / 78.24 |
| 32 / 32 | 535.12 / 599.32 | 37.93 / 40.09 |

At B32, one equality check alone measured 101.28 µs median; tensor-to-list conversion alone 4.85 µs. The table pipeline dispatched 16 ATen operations at 32/32 and 18 at 1/32, including exactly two equality checks. Sampling preparation dispatched 17 at 32/32 and 58 at 1/32, plus nine `tolist()` calls not represented in ATen dispatch. The padded sampling path first constructs the slice and then replaces it with padded parameters, matching the runner. The table work is therefore a larger measured candidate than list conversion in this controlled setup. P99 includes OS noise; these warm CPU component measurements omit scheduler work, model execution, transfers, async overlap, adapter conversion, and HTTP. Their sum is not measured serving latency or an established removable critical-path cost. The log retains two discarded setup attempts; the JSON contains only the successful run.
