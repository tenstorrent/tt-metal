# CPU implementation audit: sampling capacity64

No new correctness blocker was found in the integrated native/common/model64 diff for the validated Ornith path. Two-tile addressing, buffer capacity, masks, parameter propagation and seed advancement are consistent. All 13 native source hashes matched the successful [main rebuild manifest](ornith_integration/main_rebuild_20261113T212253Z/provenance.json). This was source/evidence inspection only: no devices, builds or algorithm changes, and no final stage-review verdict.

Two **pre-existing** limits remain:

- **Tied greedy maxima beyond candidate capacity.** The [common sampler](../../../../../common/sampling/tt_sampling.py) uses unstable local top-k and then selects the lowest global token ID among retained candidates. If one shard has more than 64 equal maxima, its true lowest-ID token can be discarded before correction. This is the documented former 32-candidate limitation, now at 64. The [Ornith generator](../../../tt/generator.py) does not enable the separate force-argmax configuration, so it also applies to its greedy requests. It concerns lowest-ID tie semantics, not selecting a nonmaximum logit. Sources: `TTSampling._adjust_values_for_tiebreak`, local `ttnn.topk(..., stable=False)`, force-argmax configuration and `OrnithGenerator.__init__`.
- **Direct invalid device-k values.** The [native validation](../../../../../../ttnn/cpp/ttnn/operations/reduction/sampling/device/sampling_device_operation.cpp) validates capacity, shape and dtype, but device-resident k values remain a documented caller precondition. The [native writer](../../../../../../ttnn/cpp/ttnn/operations/reduction/sampling/device/kernels/dataflow/writer_interleaved.cpp) and [64-candidate helper](../../../../../../ttnn/cpp/ttnn/operations/reduction/sampling/device/kernels/dataflow/sampling_64_utils.hpp) scan k entries; k above capacity can read beyond retained candidate storage. This existed for 32 and remains for 64. The common uploader clamps values, and Ornith admission rejects unsupported stochastic k before device mutation, so this audit found no exposed Ornith path to that invalid input.

Candidate-based greedy is the retained measured canonical strategy, not a new fallback introduced by this repair. The [full-model report](../../full_model/README.md) measured **0.482 ms versus 2.537 ms** for forced argmax, selecting the same host-greedy token. The [optimized full-model report](../../optimized_full_model/README.md) measured **0.571 ms versus 2.609 ms**. These are historical strategy measurements, not new capacity64 performance results or proofs for every tied input.

Tie evidence has a narrower scope: [primitive test](../../../../../../tests/ttnn/unit_tests/operations/reduce/test_sampling_64.py) exercises direct primitive input with 32 users, width 256, k40/p1 and equal or signed-zero logits; it checks membership in the first 40 input positions and observes ranks 32+. It bypasses the common sampler's upstream per-shard extraction. The unchanged-default32 comparison separately covers ordered/equal/signed-zero inputs for users 1/17/32 and widths 64/128/256. Neither establishes lowest-global-ID correctness for all upstream tie configurations.

The [acceptance note](ACCEPTANCE.md) links the 22-pass isolated suite, separate default32 parity and integrated TP4 synthetic k40/64 seed/history/trace checks. This audit does not extend those results to untested architectures, every input width, all ties, full-model serving correctness or P2/performance acceptance.
