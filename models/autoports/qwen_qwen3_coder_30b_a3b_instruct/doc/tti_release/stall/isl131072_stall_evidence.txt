--------------------------------------------------------------------------------
WHAT THE FINDING ACTUALLY IS: severe superlinear long-context prefill cost
--------------------------------------------------------------------------------

Compared with the next point down, at half the input length:

    isl=65536    TTFT   926.8 s     14.14 ms per input token
    isl=131072   TTFT  5662.5 s     43.20 ms per input token

    2x the input costs 6.11x the wall clock -> 3.05x worse PER TOKEN

Compared with this port's own context contract. The contract's
`prefill_sweep_seconds` are SINGLE-LAYER probe numbers; the only 48-layer
prefill ever verified end-to-end was a 128-token prompt (context_contract.json,
"stage 05 shipped with prefill unprofiled and disclosed it as a gap; stage 06
closes it. One verified 48-layer prefill of a 128-token prompt..."). Scaling the
single-layer sweep by the 48 layers gives a naive expectation:

    isl      1-layer probe   x48 layers    measured      measured / (48 x probe)
    65536         42.05 s      2018.4 s      926.8 s          0.46
    131072        85.85 s      4120.8 s     5662.5 s          1.37

    -> a 2.99x degradation relative to naive layer scaling between 65536 and
       131072. 65536 beats the naive estimate; 131072 badly misses it.

Extrapolating to the advertised maximum: 48 x the contract's 262144 single-layer
probe (192.23 s) is 2.56 hours as a LOWER bound, and that bound ignores the
superlinearity above, so a full 262144 prefill would plausibly take several
hours. This has never been measured end-to-end and should not be quoted as if it
had been.

MECHANISM — HYPOTHESIS, NOT PROVEN. `moe_prefill_optimized`
(tt/optimized_decoder.py) loops over the sequence in EXPERT_CHUNK_SIZE=32 chunks
and appends one device tensor per chunk to `outputs` before a single
ttnn.concat: 4096 live tensors at 131072 versus 2048 at 65536, on top of a KV
cache already allocated for 263168 tokens (8224 blocks x 32). That is consistent
with allocator pressure, but what exists is py-spy stacks showing the loop —
there is NO measurement isolating the allocator. Treat the mechanism as an
untested hypothesis.

steady-state cost at that length was never measured.

--------------------------------------------------------------------------------
THREE SUPERSEDED CONCLUSIONS, AND WHY EACH WAS WRONG
--------------------------------------------------------------------------------

This investigation reached three wrong conclusions before the point simply
finished. They are kept because the failure mode they share is the useful part:
EACH EXTRAPOLATED FROM A PARTIAL OBSERVATION WITHOUT A CONTROL.

(1) "The benchmark client is hung; the server answered and it never noticed."
    Rested on: a uvicorn access-log line "POST /v1/chat/completions 200 OK".
    Why wrong: uvicorn logs that line at http.response.start — when the response
    HEADERS are sent — not when a streaming body completes. For an SSE response
    it says nothing about completion. Refuted by reproducing the identical
    behaviour with a plain `requests` client, which ruled the harness out.

(2) "It is on trend and minutes from completing."
    Rested on: extrapolating the end-to-end TTFT curve up to 65536.
    Why wrong: it never checked how far through the request the engine actually
    was. The curve was fitted to completed points and applied to an in-flight
    one.

(3) "It is ~40 hours away."
    Rested on: sampling the chunk loop at 43.0 tok/s and multiplying one layer's
    rate by 48 layers.
    Why wrong: it assumed uniform per-layer cost. Every py-spy --locals sample
    taken during the prefill showed layer_idx=0, the last of them 73 minutes
    after the request was issued -- a LOWER BOUND of >=73 of the 94.4 minutes
    (>=77%) inside layer 0, not a measured split. The residual ~21.4 minutes is
    unattributed: it holds the rest of layer 0, the other 47 layers, the final
    concat and the first decode step, and sampling had stopped by then. The raw
    sampling timeline was not retained. Layer 0 carries one-off costs --
    first-touch allocation, kernel compilation for these shapes, cache warm-up
    -- that the other 47 layers do not. Multiplying the WORST layer by 48
    overstated the total by roughly 25x. The true answer was 94.4 minutes.

No 40-hour, 25-hour or "hang" figure in this file is a result. The only
measured number is 94.4 minutes.
