## Decode reuse hypothesis and sensitivity

The model charges each selected expert once per active batch/layer. For B useful active requests, the possible unique-expert count is8 through min(8B,256). Its central estimate is `256*(1-(31/32)^B)`, requiring hypothetical independent uniform selection of8 distinct experts per row. Real routing is neither measured nor assumed proven. One whole expert per layer costs `3*2048*512*17/16 = 3,342,336` bytes. The module returns lower/expected/upper total bytes using those counts; they coincide at B1.

Native full/shared/router/head weights are charged once per call under ideal across-row reuse. The useful-active scenario charges ordered linear input and output weights once per useful active row. The primary executed-row scenario charges them once per physical attention row and includes192 packed zero columns. Incorrectly charging linear weights only once per batch would omit material work. State bytes are4,194,304 FP32 recurrent read/write bytes plus98,304 BF16 convolution history read/write bytes per linear layer and active row. Per full layer, KV reads are4096×(position+1) aggregate bytes (including the just-written token) plus4096 write bytes per active row. Norms, convolution taps, selected decay values, embeddings, residual boundaries and terminal logits are included.

Primary executed-row scenario: `decode_batch` loops all physical attention rows unless `model_solo0` explicitly skips the second. `mesh_state_slab_recurrence.py:1-8` and `slot_state.py:257-277` show activity suppresses only persistent state writes; reads and compute still run. Consequently state read bytes scale with physical attention rows, writes with active rows. Embedding/residual/terminal boundaries scale with physical MoE rows. Terminal logits and sampler staging include32-row carriers (one terminal write/read and sampler-buffer write/read), as shown in `generator.py:103-105,492-501`. This scenario does not infer sorting or extra concat traffic. It is intentionally labeled executed-row logical streaming, including this known padding; the separate useful-active figure avoids presenting padded work as useful model work.

These are streaming hypotheses. Actual L1 retention can reduce DRAM reads; additional tiled/padded carriers, per-core rereads, replicated activation copies, page reads, route dispatch, collective scratch and sampler internals can increase traffic. Excluded padding/rereads are not free: their elapsed time remains in the denominator. No total traffic upper bound is claimed. No NoC/CCL byte count is relabeled DRAM.

## Hardware ceilings and mixed-fidelity treatment

The parent reports prior all40 initialization evidence with an11×10 worker grid per chip. The function defaults to110 workers and accepts `worker_cores` from the actual new initialization record. Four chips are used. Clock is the **nominal**, not sampled,1.35GHz. DRAM capability is4×512GB/s =2.048TB/s decimal. Source: [Tenstorrent card comparison](https://tenstorrent.com/hardware/cards), accessed2026-11-18, lists1.35GHz,512GB/s,120 cores and664 BLOCKFP8 TFLOPS for the eight-bank card. We scale compute to observed110 workers, rather than silently claiming all120 advertised workers or counting two cards as two chips.

The [Blackhole MVMUL documentation](https://github.com/tenstorrent/tt-isa-documentation/blob/main/BlackholeA0/TensixTile/TensixCoprocessor/MVMUL.md) delegates to the [matrix instruction definition](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/TensixTile/TensixCoprocessor/MVMUL.md):8×16×16 MACs give4096 FLOPs per issued instruction. The [matrix unit throughput](https://github.com/tenstorrent/tt-isa-documentation/blob/main/WormholeB0/TensixTile/TensixCoprocessor/MatrixUnit.md) is one instruction/cycle, with one issue per fidelity phase. Thus four110-core chips give2433.024TFLOP/s LoFi,1216.512 HiFi2 and608.256 HiFi4. BF16 activation/BFP8 weight storage does not make all operations LoFi.

The [Blackhole SFPU specification](https://github.com/tenstorrent/tt-isa-documentation/blob/main/BlackholeA0/TensixTile/TensixCoprocessor/VectorUnit.md) gives32 lanes and1 MAD/cycle. Its optimistic arithmetic peak is64FLOP/cycle/core, or38.016TFLOP/s aggregate. Ordered coefficient scans and corrected FP32 recurrent matrices must not be assigned the vastly larger tensor-unit peak. The64FLOP ceiling is optimistic for separate multiply/add, reductions and rounding correction; these overheads are not silently given free FLOPs.

`peak_rates(prefill, worker_cores)` computes ideal sequential service `sum(F_fidelity/P_fidelity)` and uses `total_FLOPs/ideal_seconds` as its workload-specific harmonic ceiling. Divide ideal seconds by full prefill wall seconds for the modeled percentage. This is an optimistic sequential resource-service model for the ordered graph, with perfect utilization and no communication; not a measured sustainable rate or universal hardware peak. Preserve the per-fidelity breakdown and separate raw TFLOP/s. A no-argument call is useful only for readiness metadata and returns unweighted LoFi capability; it must not be used for the final mixed-work percentage.
