## Slot, position and chunk ledger

`start_pos` is authoritative **only** when `reload_inputs=True`. The resident branch explicitly refuses even to inspect it, because under asynchronous scheduling it may belong to an earlier submission (`M/tt/serving.py:230-257`). On reload, snapshot slot-to-position from the accepted `rows`, ignore negative inactive positions, and reset the shadow to those values (`:233-250,364-370`). Otherwise derive the active set using the complete destination-to-source `slot_remap`, remap the CPU shadow by the same permutation, and use the remembered row layout; increment each active slot exactly once at each accepted model replay in queue order. The device does this after the decoder (`M/tt/model.py:450-489`; `M/tt/slot_state.py:59-70`). Seed a new prefill slot's shadow from its *end*, because `_prefill_forward` writes that end to its position (`M/tt/generator.py:416-427,452-461`); on release invalidate the slot and advance a slot-generation number. Preserve positions **at submission**, not completion, because multiple outputs can be outstanding. Handle `reload_inputs`, remap, inactive holes, prefill overwrite, release, errors and poison/rollback explicitly; if any state transition is unprovable, reject the sample rather than read device positions or use advisory host positions. The existing audit explicitly calls its async host positions advisory (`M/tt/generator_vllm.py:211-217`). Validate the shadow against authoritative reload points without altering model inputs.

For each prefill row retain `[start,end)` and charge `end-start` useful tokens. Scheduler-level chunks may interleave with decode and must be joined by slot generation and absolute ranges, without resetting a continued request. Count unique prompt coverage once for reconciliation, but count any genuinely re-executed prefix again as work; detect preemption and noncontiguous or repeated ranges explicitly. Within one adapter call, `BoundedPrefill` also breaks attention into linear chunks of at most 64 and full-attention chunks up to 256 with singleton alignment fallback; MoE uses its own chunk size and physical round-up (`M/tt/prefill.py:26-39,199-223`). The outer call already covers all internal chunks; do not multiply its wall duration by the number of internal chunks. Use logical lengths for useful FLOPs and record physical padded work separately. Prefill logits/head are produced once per serving call/chunk, including intermediate chunks (`M/tt/prefill.py:225-237`; `M/tt/serving.py:533-579`), not once per prompt token.

## Full-phase timeline and measured-cohort selection

The benchmark contract requires warmed, same-work, all-chip phase time, including communications, sampling/readback and intervening host gaps, with nonoverlapping accounting and no profiler or extra device synchronization (`/home/ttuser/qwen36-35b-a3b/codex_home/plugins/cache/tenstorrent-skills/tt-model-bringup/0.1.24/skills/benchmark-model/references/run-contract.md:307-353`). Buffer cheap timestamp/metadata events during serving and flush on `collect`, outside the measured path. Existing `_event` prints and flushes per decode (`M/tt/generator_vllm.py:93-120`); that is neither a low-overhead buffered collector nor evidence of timing neutrality. Measure instrumentation overhead in a follow-up, and never enable the verbose token/digest audit to manufacture timing.

A defensible offline reconstruction on the single server monotonic timeline is:

1. Mark the accepted measured cohort and retain every prefill and decode submission/completion event. Sort by `(monotonic_ns, sequence_number)`, maintain the set of in-flight IDs, and calculate the union of all accepted work intervals; never sum overlapping submissions, request latencies, or four device durations. Preserve the raw stream so this can be audited.
2. Sweep half-open intervals to classify prefill-only, decode-only, overlap and neither. Attribute each busy overlap **once**, by a documented rule justified by actual queue ordering and available completion events; record the amount and rule. The Qwen pool requires draining before prefill and on ownership-changing decode (`M/tt/generator.py:420`; `M/tt/serving.py:349-356,529`), but host processing and event logging can still overlap across threads. A pool drain is not proof that all phase intervals are disjoint; prove the actual ordering in each capture. If cross-phase ordering cannot be justified from the event stream, fail collection rather than independently summing unions.
3. Include host gaps between the first measured model-phase start and the final proven phase completion. A gap during in-flight async work belongs in that work's union. For a gap between model hooks, retain explicit preceding and following phase identities and use scheduler/output evidence to determine its owner; assign it once, with a documented convention only where the owner is actually supported. A fixed “next phase” rule can wrongly assign host sampling from the prior phase, and cannot by itself establish the contract. Unresolved gaps or phase overlap must remain unallocated and make collection fail. Keep separately identified client/network lead-in and tail outside the model-phase envelope; a final phase's sampling or token handling cannot be dismissed as network tail without evidence. Check `prefill_seconds + decode_seconds` equals the explicitly retained nonoverlapping phase envelope and each is within benchmark duration. If gaps include unrelated work, mixed measured/unmeasured phases, lost completion, or a clock/domain mismatch, reject the profile.
4. Work belongs to the same accepted steps represented by these intervals. For batched steps shared by measured and other requests, there is no exact per-cohort wall decomposition from model hooks alone: reject or provide a separately evidenced attribution rule, never silently count all work with only measured token totals. Similarly mark cancelled or discarded output and avoid assuming submitted equals delivered.

`vllm bench serve` has an initial readiness request and may do warmups before its main benchmark (`B/serve.py:850-916`); the Stage 11 runner also performs separate warmup/accuracy and collects before lone-user rows (`R/run.py:219-227,259-276`). The benchmark's main requests are gathered in request-list order, and `start_times`, `input_lens`, `output_lens`, `latencies`, and `errors` have the same output ordering (`B/serve.py:1052-1092,1291-1309`). For successful records, an approximate client observation range uses `start_times[i]` and `start_times[i]+latencies[i]`; latency ends at the last relevant streamed choices chunk, which need not be the HTTP teardown (`B/lib/endpoint_request_func.py:202-206,236-261`). Neither value is a server execution/phase boundary. Compare to server monotonic only after verifying the processes share clock domain/host, including container time namespace. Those bounds can exclude earlier probes and prove a closed cohort only if isolation, no unexpected traffic, successful completions, and the model-side lifetime/range/step counts all reconcile. Since request IDs are not in the result and the model hook sees no request ID, simultaneous candidates cannot in general be uniquely paired. An existing external server/client request-ID log or an authorized client-side wrapper that records IDs and timestamps can bridge the gap without editing plugin/vLLM; if it cannot be tied to slot generations through an observed server-side mapping, it is still insufficient. Do not assume FIFO pairing. If no valid mapping or isolated-cohort proof exists, `collect` must fail with a precise error; this limitation cannot be repaired solely by naming a timestamp.

## Model-specific FLOP and DRAM accounting

The checked-in text config gives hidden width `H=2048`, 40 layers (30 linear attention, 10 full attention), 256 experts, top-8 routes, expert and shared width `I=512`, 16 query heads, 2 KV heads, head width 256, linear-attention 32 value heads of width 128, and vocabulary `V=248320` (`M/doc/functional_decoder/hf/config.json:14-19,61-76,92-96`). The adapter requires one 1x4 mesh, not four data-parallel requests (`M/tt/generator_vllm.py:24-33`). Resolve the actual server's loaded policy and layer list; the selected artifact at inspection is `baseline_bfp8`: BFP8_B expert/full-attention/shared/head weights with LoFi expert and HiFi2 ordinary GEMMs, BF16 activations and KV, BF16 linear weights, FP32 recurrent state, mixed router/norm precision (`M/doc/datatype_sweep/selected_precision_config.json`; `M/tt/precision.py:20-56,83-103`). Do not assume an artifact equals the live server's identity.

A transparent **useful-work** prefill model with 2 FLOPs/MAC is, per logical token per layer:

| Term | Formula | FLOPs |
|---|---:|---:|
| Linear-attention input and output projections | `2 H (12352 + 4096)` | 67,371,008 |
| Full-attention input including gate, and output projections | `2 H (9216 + 4096)` | 54,525,952 |
| Top-8 routed gated experts | `6 × 8 × H × I` | 50,331,648 |
| One shared gated expert plus scalar gate | `2 × (3 H I + H)` | 6,295,552 |
| Expert router | `2 H × 256` | 1,048,576 |
| LM head, per produced logits row | `2 H V` | 1,017,118,720 |

Thus the projection/router/MoE baseline per token is `30×67,371,008 + 10×54,525,952 + 40×(50,331,648+6,295,552+1,048,576)`, plus `1,017,118,720` **per serving prefill row/chunk**, not per prompt token. For a full-attention prefill chunk of `n` tokens starting at absolute `s`, useful causal QK and PV work is `4×16×256×(n*s+n*(n+1)/2)` per full-attention layer. Sum actual chunks, rows and the 10 full layers. This assumes each query sees its complete causal prefix and is a logical count; account for replayed work and any applicable prefix caching separately. Linear recurrent/conv/gating, norms, routing selection, activations, softmax, communication, embedding and sampling are not in this compact dominant-matmul table: derive and itemize material work from the selected actual graph, including resumed-prefix and chunk geometry, or label an explicitly incomplete lower estimate. In particular the linear prefill graph uses chunk-64 machinery; a recurrent per-token equivalence is not automatically its executed FLOP count (`M/tt/prefill.py:26-39,199-223`; `M/tt/multichip_decoder.py:392-447,553-567`). Physical tile padding and grouped expert GEMM padding may make executed FLOPs much larger; useful FLOPs divided by peak is model-FLOP utilization, not a measured tensor-core occupancy.

For decode, estimate **aggregate four-chip streamed bytes per completed step**, then sum steps, using actual positions and active routes. Do not charge four copies of globally sharded weights as though they were replicated. Conversely account for intentional replication and rereads:

* BFP8_B stores 1,088 bytes per 1,024-element tile, or `17/16` byte/element (`tt_metal/api/tt-metalium/tt_backend_api_types.hpp:122-129`); BF16 is 2 bytes/element, FP32 4. Dense, sharded global useful values include 540,344,320 bytes for one full BFP8 LM head (`2048×248320×17/16`) and 3,342,336 bytes per routed expert per layer (`3×2048×512×17/16`). An actual tile/layout may need additional padding.
* For each layer and decode batch, let `U_l` be the number of **distinct** experts selected by at least one active row. A useful expert-stream lower estimate is `sum_l U_l×3,342,336` bytes per step if one load of each selected expert can serve all its rows. For `B` active rows, `8 ≤ U_l ≤ min(8B,256)`; empty/inactive rows must not add routes. Exact `U_l` is device-data dependent, and this adapter does not expose expert IDs without a new observation. Report bounds, or an explicitly modeled distribution, not fabricated observed routes. Under an explicitly hypothetical independent uniform selection of eight *distinct* experts per row, `E[U_l]=256×(1-(31/32)^B)`; actual routing may be skewed and correlated. Expert weights are held in both indexed TP4 and grouped EP4 layouts (`M/tt/multichip_decoder.py:1043-1056`); charge the path actually used, not both resident banks. A singleton uses indexed sparse TP4; multiple physical rows use grouped EP4 (`:1595-1661`). Output-slot capacity and actual selected physical trace can make a one-active-request server use a grouped path; use the trace key/geometry, not active count alone. Lower-bound unique streams are not measured bytes; selected expert weight reuse, padding and rereads depend on the selected kernel geometry.
* The linear attention TP4 path packs input to 12,544 columns and recursively streams individual rows (`M/tt/multichip_decoder.py:684-735,749-789`). Decode additionally uses an ordered 4096×2048 BF16 output projection per row. Its source-level packed input plus output weight footprint is `2048×12544×2 + 4096×2048×2 = 68,157,440` aggregate bytes per executed row/layer, before caching/reread qualifications. The 30 layers cannot simply be charged once per whole batch. Distinguish physical trace rows from useful active rows and avoid treating this footprint as a measured DRAM transaction count. In prefill, the output projection takes the native batched path (`:697-702`), so its batch reuse must be assessed separately.
* Full-attention K/V heads are deliberately duplicated across rank pairs (`M/tt/multichip_decoder.py:1104-1125`). A BF16 full-attention logical KV prefix of length `L` has `2×2×256×2×L = 2048L` read bytes/layer/request; the paired-rank representation is `4096L` aggregate bytes, plus an aggregate 4096-byte current K/V write under the historical logical convention (`M/tests/multichip_functional.py:3-8,37-49`). Decide whether `L` includes the just-written token consistently with actual call order, and avoid counting it twice. Include 30 layers' recurrent FP32 state read/write and BF16 convolution state, using actual active rows and tensor shapes: the historical per-layer logical values aggregated over ranks are `2×32×128×128×4 = 4,194,304` and `2×3×8192×2 = 98,304` bytes per active row, respectively (`M/tests/multichip_functional.py:32-36`). Page rounding, padding and cache reuse can change physical traffic.
* Account for shared weights, router, norms, embedding, activations and other material DRAM reads/writes and sampler staging under a stated reuse model; do not mix a measured-traffic claim with an optimistic logical minimum. Singleton ordered linear routing can use a BF16 router, while grouped/native routing can use FP32, so derive it from the actual path and policy (`M/tt/multichip_decoder.py:1595-1604,1844-1846,2002-2010`; `M/tt/fused_decoder.py:564,688-709`). Tensor collectives are not automatically DRAM bytes; count only evidenced DRAM traffic. State what is bounded or omitted and retain formulas and per-step ranges with the artifact.

The existing single-row model assumes 512 GB/s **per rank**, and consistently computes rank bytes divided by that rate (`M/tests/multichip_functional.py:3-8,40-49`). Four-rank aggregate accounting with that convention uses `4×512e9 = 2.048e12` bytes/s, but the code is an inherited assumption, not independent proof of the active board's hardware specification or sustainable rate. Verify the actual architecture and cite an authoritative applicable peak source in the future collector. Likewise provide a sourced four-chip FLOP/s peak appropriate to the actual dtype/fidelity mix. Since expert GEMMs are LoFi, ordinary GEMMs HiFi2, and other kernels differ, explicitly define how a single required peak summarizes that mixture (and supply per-fidelity breakdown/sensitivity); do not silently borrow a BF16 or LoFi peak as if it applied uniformly. No fully validated numeric peak or resulting percentage can be inferred from this inspection.

## Other potential issues and limits

* The plugin retains per-step request context and its own submit/completion timestamps (`P/src/vllm_tt_plugin/async_decode.py:549-570,1030-1069`). They corroborate the correct boundary, but are not passed into the autoport hooks or emitted in the benchmark results. Their existence does not solve the identity join without an independently authorized observation at that boundary.
* The adapter's `readbacks` counter counts internal synchronous processing but its async wrappers delegate without incrementing it (`M/tt/serving.py:413-418,574-579`; `M/tt/generator.py:832-838`). It is not an async completion counter. This is an accounting trap, not evidence of a device or correctness bug.
* Plugin prefill includes resumed/preempted history and one-token final chunks (`P/src/vllm_tt_plugin/model_runner.py:2397-2434,2443-2459`): executed prefill work can exceed unique benchmark prompt tokens. Keep executed tokens and unique measured input tokens distinct; reject cases whose attribution is unknown. Prefix-cache policy and request cancellations require explicit reconciliation.
* The adapter hook is before plugin host-side sampling and final output formatting (`P/src/vllm_tt_plugin/model_runner.py:4220-4249`; `P/src/vllm_tt_plugin/async_decode.py:1038-1069`). An intervening gap can include this work only if its phase ownership is established; the very last host-sampled output has no next model hook. If its natural final output boundary cannot be captured from an existing externally observable event, the model-only instrumentation is insufficient for complete end-of-phase timing; fail closed rather than substitute the earlier hook. This also applies to any material final token handling outside the hook. Device-sampled runs still need evidence that their chosen last boundary covers the contract's token-handling scope.
* A same-host start/end window, matching totals, and SHA-256 hashes are necessary cross-checks, not a proof that each server slot belonged to the measured requests. Likewise a roofline estimate is not a direct profiler measurement. The no-hardware restriction prevents verifying actual routing, precision identity, scheduling overlap, IPC flush overhead, or board peak here.
