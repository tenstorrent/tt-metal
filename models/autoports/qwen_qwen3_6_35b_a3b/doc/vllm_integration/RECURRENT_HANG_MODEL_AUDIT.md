# Recurrent combine hang: model lifetime and geometry audit

Independent source-only AutoFix hypothesis audit, 2026-11-16. No device access, target execution, reset, process termination, or production source change was performed. The only file written by this investigation is this report. Paths abbreviated `tt/` and `tests/` are relative to `models/autoports/qwen_qwen3_6_35b_a3b`; native paths are repository-relative.

## Finding

No concrete model-owned scratch lifetime, retained-trace ownership, or data-dependent zeroing-geometry inconsistency was found. The post-reboot failure repeats the same earliest visible producer as the pre-reboot failure: device 1, physical worker (1,2), NCRISC, in the combine sender's local DRAM-zero-write completion barrier. The other devices' reduction waits are downstream. This does **not** establish that the native primitive, hardware, or complete model is correct, and it does not close the stage's reliability failure.

The current standalone run uses slot 0 for every request. Consequently it replays `model_2` throughout ordinary generation; `model_fixed` is retained but not selected. Alternating B2/B32 execution, async serving overlap, vLLM page-table handling, and trace retirement are therefore not necessary conditions for this recurrence. They should not be blamed on the evidence available.

The two model traces may legitimately reuse temporary addresses because execution is serial. The meaningful failure condition would be a persistent post-capture allocation overlapping one of those temporary ranges, a stale captured address, or native DMA surviving its producer's completion. None has been demonstrated. Disabling tracking or simply keeping Python temporaries alive is not a justified repair.

## NoC command-state hypothesis

The fixed zero helper uses ordinary per-command DRAM writes after a completed local zero read. Its `Noc` object consistently uses `noc_index` for bank resolution, issue and barrier (`tt_metal/hw/inc/internal/noc_zero_dram.inl:15–51`). NCRISC dedicated-mode software counters are initialized from hardware at each kernel entry (`tt_metal/hw/firmware/src/tt-1xx/ncrisck.cc:58–62`), so a token-count wrap at 114 or 159 is not established by those token numbers.

Native writes and command-state inheritance remain plausible classes, not proven defects. An earlier kernel returning before all acknowledgements arrive could invalidate a later equality-based barrier baseline; an invalid routing/address command could leave an acknowledgement missing. The inspected fused expert writer already drains deferred writes with `noc.async_write_barrier()` near its exit, and combine writers also have terminal barriers. A generic extra model synchronization cannot repair a genuinely stuck in-kernel barrier, and a speculative global semaphore reset targets downstream state. The required discriminant is whether hardware acknowledgements are below or above the software expectation, with the actual destination and runtime interval, rather than another aggregate all-reduce counter read. Direct hardware status reads are not recommended here given the prior MMIO failure.

## Minimal useful next experiment

After the owning agent safely finishes failure preservation and recovery, keep the model, capacity 32, context 1024, precision, sampler, request fixtures, seed, trace region, tracking setting, and native sources identical. Run the **exact current three-request prefix** (q01 greedy256, q01 sampled256, q02 greedy256) with both traces retained but force `model_fixed` selection, using a bounded run and progress artifacts. The existing forced-bucket helper currently truncates to only q01 greedy and therefore needs a diagnostic-only fixture-selection extension to exercise this prefix. Do not silently equate its existing single-request pass with this experiment.

- A repeat on forced B32 at the same producer refutes an exclusively B2 execution defect and favors native/model-common history or hardware/address sensitivity.
- A B32 pass is evidence for a shape, timing, or address discriminator; one pass is not proof that B2 is the root cause. If this is the outcome, the next bounded comparison is the same prefix with only B2 captured (capacity and sampler still 32), versus retained B2/B32. This is a diagnostic harness configuration, not a proposed serving fallback, and should not weaken production bucket-contract validation.
- Keep all partial tokens and request identifiers. If failure recurs, record whether it is the same physical device/core and same native initialization frontier. Do not increase a watchdog simply because no token completes.

A native full dispatch→fused-expert→combine repeated-trace reproducer would be more informative than extending the already-passing zero-helper-only loop: the latter deliberately omits inherited command state, native combine's other workers, routing traffic, and full-model allocation pressure. It is a follow-up if the exact-prefix comparison leaves the hypothesis unresolved, not a claimed repair.

No production change is justified by this audit alone. The recurring failure remains work for AutoFix and the remaining serving gates.
