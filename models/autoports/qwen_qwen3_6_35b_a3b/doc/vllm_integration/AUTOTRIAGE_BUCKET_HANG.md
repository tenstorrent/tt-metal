# AutoTriage: full-40 prepared B2/B32 quality-control hang

## Diagnosis

The earliest captured producer stall is **device 1, physical worker (1,2), logical (0,0), NCRISC, deepseek combine output zeroing**, waiting for local NoC nonposted-write acknowledgements. It has not published the output-initialization completion semaphore. The other devices' later all-reduce waits and the host token read are downstream consequences.

This localizes the failed completion contract, but does **not** establish the source defect that broke it. In particular, the capture does not prove a fabric ring/counter wrap, a B2 attention error, a stale token, or a missing zeroing barrier. The sender's expected and hardware acknowledgement counters, output runtime address, page interval and bank mapping are absent from the capture. A source repair claiming an exact root cause would currently exceed the evidence.

Scope: CPU-only review of existing evidence and current source; no target execution, device access, reset, process termination, or implementation changes. Live owner reported by the caller: PID 3482959. This report follows the installed `tt-autodebug:autotriage` skill and its `references/AUTOTRIAGE_PROMPT.md`.

## Downstream effects

The causal chain supported by the capture is:

`device-1 sender DRAM zero-write completion` → `combine initialization publication` → `untilizer/route work and combine output` → `device-1 later reduction contribution` → `other-rank reduction CB availability` → `model/sampling completion` → `host token read`.

This explains the broad wait fanout without changing sampling, token feedback, adapter ownership, or all-reduce semaphore thresholds. Reducing an expected semaphore count from four to three would hide the absent contribution and produce incorrect output.

## Proposed fix / discriminating next work

No source patch is proven by this capture. Keep B2 unaccepted until a same-workload, full-40 long-run contrast resolves the failure; the existing short reduced probes do not establish this gate.

The smallest useful diagnostic follow-up, performed by the owning workflow after preserving the live evidence, is to obtain the **blocked sender's** runtime output pointer/page bounds, active NoC ID, hardware write-ack count, software expected write-ack count, and bank/address mapping. Validate those against the ledger above and retained-trace buffer ownership. If counters disagree, distinguish actual outstanding writes from incorrect software accounting before changing barriers or NoC selection. If the destination belongs to a retired/reused allocation, fix that lifetime at its owner rather than weakening the primitive's completion contract.

There is a concrete collection gap: `tools/triage/check_noc_status.py:139` selects `brisc`, `erisc`, `erisc0`, and `erisc1`, **not NCRISC**. Repeating the stock check will not obtain this producer's counters. A focused owner-run callstack command is `python tools/triage/dump_callstacks.py --dev=1 --loc=0,0 --full-callstack -vv --llm-output`; locals can be optimized out. A scoped diagnostic using the existing `dispatcher_data`, `elfs_cache`, and `create_memory_access` APIs should read only this NCRISC's `noc_index`, `noc_mode`, `noc_nonposted_writes_num_issued[0:2]`, `noc_nonposted_writes_acked[0:2]`, and the matching `NIU_MST_NONPOSTED_WR_REQ_SENT` / `NIU_MST_WR_ACK_RECEIVED` registers for both NoCs. The kernel's `rta_l1_base` (`api/dataflow/dataflow_api.h:108`–`:151`) provides the runtime-argument words: output address 4, init semaphore 5, barrier 6, sender count 7, expert bounds 8/9, page bounds 10/11, and done semaphore 12. These are exact diagnostic targets, not hardware actions performed by this review.

A controlled full-40 replay should hold prepared graphs, cache capacity, precision, prompt and output limit constant, first selecting retained B32 and then B2 in separate clean lifecycle runs. Use the same 18-token fixture and at least the full 256-output limit, not the existing 96-output server workload. ## Uncertainty and acceptance limits

- The first **observed** failed completion is clear; the first source-side programming error is not proven. Actual NoC counters/addresses at that site are the critical missing evidence.
- Parent-reported fixed32 full-server nine-request/96-output success and prior fixed32 context success are useful controls, but differ in duration, prompt, preparation/allocation history and timing. Eight reduced exact B2/B32 cases also differ in layer count and duration. These contrasts do not prove either a generic fabric wrap or B2 correctness at full depth.
- B2 changes attention work, scheduling pressure and retained-trace allocation even though MoE rows remain 32. A timing or address-lifetime trigger remains plausible; this is a hypothesis, not a finding.
- Device-side assertions and watcher were disabled in the captured configuration. Later triage warnings and unrelated invalid NoC indices prevent a blanket hardware-health claim.
- The report made no hardware experiment and did not modify any implementation or the live process. Root-cause repair and full-40 acceptance remain open work.

## AutoFix source-only follow-up: zero-write accounting

This follow-up tested the proposed native-zeroing/accounting explanation against current source. **No concrete missing increment, duplicate increment, wrong-NoC selection, or read/write command-buffer collision was found.** The conclusions below remain conditional on the focused live counters; they are not a declaration that the primitive is hardware-correct.

1. **Stateful zero reads do not alias the subsequent write command.** `internal/tt-1xx/noc_zero_l1.inl:28`–`:40` configures stateful reads of `MEM_ZEROS_BASE`; it completes them through `noc_async_read_barrier`. Dedicated NCRISC uses read command buffer 1 and write buffer 0 (`internal/dataflow/dataflow_cmd_bufs.h:27`–`:28`, Blackhole `noc_nonblocking_api.h:64`–`:67`). The DRAM helper then uses ordinary, non-stateful `noc_async_write_impl`, which programs write control, source, destination low address, destination coordinates and length on each command. A stale read-state configuration cannot directly overwrite these different write registers.
2. **The per-page write accounting matches the expected command count.** `internal/noc_zero_dram.inl:40`–`:46` passes 4096-byte chunks to `noc_async_write_impl`. Its default max-page template selects `ncrisc_noc_fast_write_any_len` (`internal/dataflow/dataflow_api_raw.h:148`–`:175`). At 4096 bytes, the `len_bytes > NOC_MAX_BURST_SIZE` loop is skipped; exactly one `ncrisc_noc_fast_write` executes (`blackhole/noc_nonblocking_api.h:986`–`:1033`). The call is nonposted, unicast, `num_dests=1`; its dedicated-mode path increments issued count by 1 and expected acknowledgements by 1 (`:654`–`:659`). Thus the source-derived sender's 52 pages produce 52 issued writes and 52 expected acknowledgements, not 104 or a byte count. Neither the helper nor the caller adds a second count.
3. **The selected NoC is coherent in this path.** `Noc()` stores `noc_index` (`api/dataflow/noc.h:214`), and the helper uses that same value for destination mapping, command issue and barrier. `preferred_noc_for_dram_read` returns NOC0 and the writer preference returns NOC1 (`tt_metal/api/tt-metalium/kernel_types.hpp:141`–`:153`). The combine factory gives the reader RISCV_1/read preference and writer RISCV_0/write preference (`combine_program_factory.cpp:1053`–`:1071`). These choices assign the simultaneous RISCs different NoCs; a new `Noc()` in `zero_pages` does not silently force an incompatible NoC.
4. **A plain 114-replay software-counter accumulation bug is unsupported.** `tt_metal/hw/firmware/src/tt-1xx/ncrisck.cc:58`–`:62` initializes dedicated-mode counters at each kernel entry from hardware status via `noc_local_state_init`. The latter copies all current hardware counters into software (`blackhole/noc_nonblocking_api.h:872`–`:886`); it does not assume zero. The helper therefore has no private counter advancing once per model replay. A wrap claim still needs actual before/after values and hardware width evidence; token step 114 supplies neither.
5. **Inherited write-command state is a specific but unproved alternative.** Ordinary Blackhole writes intentionally leave `NOC_RET_ADDR_MID` untouched and rely on the on-chip MID=0 contract (`blackhole/noc_nonblocking_api.h:641`–`:646`). `noc_init_one` clears MID at initialization (`:781`–`:782`), but firmware only reruns this initialization on NoC-mode changes (`tt_metal/hw/firmware/src/tt-1xx/brisc.cc:606`–`:609`). An earlier kernel that left PCIe routing or another invalid command state could misroute later zero writes. The end-of-kernel checks cover MID/tag state (`ncrisck.cc:89`–`:93`), but assertions were disabled. There is **no captured nonzero MID, earlier unclosed PCIe operation, or corrupt write command** establishing this hypothesis. The direct MoE path performs on-chip DRAM work, so it is not an identified PCIe culprit. Capture NoC0 command buffer 0's `NOC_RET_ADDR_MID`, `NOC_TARG_ADDR_MID`, `NOC_PACKET_TAG`, `NOC_CTRL`, destination coordinates/address and length if focused counters indicate issued-but-unacknowledged writes.
6. **A late acknowledgement from an earlier kernel could make equality permanently overshoot, but is not established.** Dedicated kernel entry seeds its expected ack count from the hardware count. If a prior kernel returned with outstanding acknowledgements, their later arrival could exceed the new kernel's expectation. The NCRISC epilogue asserts writes-sent but does not assert writes-acked (`ncrisck.cc:84`–`:90`); correct kernels must honor their own completion contract. This is a mechanism to test only if hardware acknowledgements exceed software expected acknowledgements, not a diagnosed firmware bug. The immediate model-level producer `moe_fused_swiglu_writer.cpp:642`–`:646` already drains its deferred output writes with `noc.async_write_barrier()`, so inserting another barrier there without contrary runtime evidence is not justified. The actual preceding on-core kernel must be identified before attributing a missing drain.

Counter discrimination: hardware sent equal to software issued with hardware ack **below** expected favors an outstanding/misrouted write or an overcount; hardware ack **above** expected favors stale baseline, another issuer or corruption; both equal would require checking whether the captured program/NoC changed or whether the observed stack was transient. Compare modulo the documented counter width, retaining the raw values. None of these directions can be inferred from the original full triage because it omitted NCRISC counters.
