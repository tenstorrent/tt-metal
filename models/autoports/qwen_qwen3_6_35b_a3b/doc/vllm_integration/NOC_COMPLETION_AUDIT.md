# Independent NoC completion audit

2026-11-16. Source-only adversarial review of the recurrent `reader_combine` zeroing stall. No device access, process changes, or native source edits. The existing AutoTriage report was treated as a hypothesis, and the relevant firmware and kernel implementations were read directly.

## Verdict

The fused SwiGLU reader has a real completion-contract gap: nonposted NoC0 multicast writes can remain unacknowledged when it returns. I found no implicit dedicated-NoC acknowledgement drain at the subsequent program boundary. An unconditional reader epilogue `noc.async_write_barrier()` is the smallest justified repair to that gap. **The gap is not yet established as the cause of the captured hang.** Hardware acknowledgement evidence or a controlled failing/passing transition remains necessary for attribution.

## Attempts to refute the boundary mechanism

1. **Does NCRISC firmware drain before completing? No.** `tt_metal/hw/firmware/src/tt-1xx/ncrisck.cc:58–62` initializes software counters from hardware at each dedicated-mode kernel entry, before `wait_for_go_message`. Lines 84–93 check reads complete, writes sent, atomics complete and posted writes sent, but omit nonposted write acknowledgement completion. `tt_metal/hw/firmware/src/tt-1xx/ncrisc.cc:191–199` returns from the kernel and immediately signals completion; `signal_ncrisc_completion` at line 97 only stores a local synchronization word.
2. **Does BRISC program completion drain the reader's NoC? No.** `tt_metal/hw/firmware/src/tt-1xx/brisc.cc:452–464` waits on local RISC completion flags, without checking NoC ACKs. Lines 688–718 contain a stronger all-NoC acknowledgement assertion only for `DM_DYNAMIC_NOC` and only when assertions are enabled. The fused reader/writer use dedicated defaults (`moe_fused_swiglu_program_factory.cpp:574–590`). The normal path then marks the launch done and notifies dispatch (`brisc.cc:731–751`). `tt_metal/hw/inc/internal/firmware_common.h:282–307` implements the Blackhole notification as a **posted** inline write on BRISC's selected NoC. It neither reads nor drains the NCRISC NoC0 ACK count. The remote-CB setup barrier (`brisc.cc:468–483`) drains atomics only, on its selected NoC.
3. **Does dispatch ordering indirectly prove ACK return? No source contract found.** Waiting for every worker to finish proves that receivers passed their semaphore waits; it does not prove that every return ACK reached the multicast sender. The dispatch notification travels through the writer's NoC1, whereas the suspect writes and acknowledgements belong to reader NoC0. Completion and next-program launch introduce substantial time, so late ACKs may normally disappear before initialization. That timing weakens an inference from the missing barrier alone, but is not a completion guarantee. The report must not claim every sent-only return produces a stall.
4. **Does a linked VALID flag imply sender completion? No.** `moe_fused_swiglu_reader.cpp:450–486` multicasts the metadata, then a terminating validity semaphore. Both flushes are `async_writes_flushed`, whose explicit contract is departure without completion (`tt_metal/hw/inc/api/dataflow/dataflow_api.h:1970–1993`). Linked ordering makes the receiver's validity observation useful as a payload-arrival proof; it does not wait for ACK return to the sender.
5. **Is a multicast destination-count error evident? No.** Metadata uses `HGROUPS * KGROUPS - 1` and H multicast uses rectangle area minus one (`reader.cpp:226–228,460`). These non-loopback APIs exclude self, exactly as specified at `dataflow_api.h:918–929`. `Noc::async_write_multicast` selects the non-loopback implementation unless `MCAST_INCL_SRC` is specified (`api/dataflow/noc.h:528–533`); the metadata path uses the default. Blackhole's write primitive marks nonposted requests for response and increments the software expected ACK count by `num_dests` for each command (`internal/tt-1xx/blackhole/noc_nonblocking_api.h:633–659`). Fragmentation invokes that primitive once per chunk (`:986–1033`). I found no local off-by-one count or missing per-fragment accounting. This does not independently validate the captured physical rectangle or runtime arguments.

## Empty and nonempty expert paths

The reader broadcasts metadata even when all local counts are zero. Such counts make `m_blocks == 0`, skipping the whole block loop (`moe_fused_swiglu_reader.cpp:611,671–673`). The final function brace at line 1365 has no write barrier. Consequently a legal all-zero fixture is the clearest way to isolate metadata completion, and the source root `(0,0)` is also the observed stalled combine sender. The captured workload's counts are unavailable; do not claim that this particular rank was empty.

For nonempty experts, `scatter_payload_to` does drain NoC0 writes (`moe_fused_swiglu_dataflow.hpp:157–181`), but phase-2 H multicasts happen later (`reader.cpp:1161,1275`). `h_slot_send_posted` is misleadingly named for the current configuration: `moe_fused_swiglu_geometry.hpp:42` sets `H_MCAST_POSTED=false`; its normal payload and terminating flag are both nonposted, and it ends with a sent-only flush (`reader.cpp:232–265`). `H_ROUND_NOC1_MASK=0` at geometry line 34 leaves these sends on the reader. The later read-prefetch drain (`reader.cpp:1346–1348`) is a read barrier and cannot discharge writes. The writer's own output barrier is on NoC1. Therefore an all-zero-only conditional repair would leave another legal path uncovered.

## Why the following zero barrier can stick

Blackhole `noc_local_state_init` samples the current ACK count H and overwrites the kernel's software baseline (`noc_nonblocking_api.h:873–886`). If P old ACKs are outstanding, the following combine reader adds 52 expected unicast ACKs to H. The hardware can ultimately reach H + P + 52, while `ncrisc_noc_nonposted_writes_flushed` requires exact equality to H + 52 (`:750–752`). If the polling loop misses the transient equality, it can wait indefinitely after overshoot. It is also possible to observe equality too early; the hypothesis predicts an accounting violation, not a deterministic hang on every transition. Existing triage does not expose H, P or the software expectation, so an undershoot/address/transport problem has not been excluded.

The recurrent captured op 320374 identifies the same retained launch metadata occurrence; it does not identify a fresh replay count, a particular layer, or prove that fused SwiGLU was the immediately preceding on-core operation. The Python sequence is fused SwiGLU then combine (`tt/multichip_decoder.py:1659–1696`), but the experiment should record the actual mixed-program transition. The 5,000-replay isolated zero-helper pass does not exercise old multicast ACKs across a different kernel's initialization.

## Minimal repair and decisive validation

Add only `noc.async_write_barrier();` after the reader's outer expert loop and before the final function return. Keep existing per-transfer sent-only flushes: they protect source reuse while allowing overlap. This single unconditional epilogue discharges metadata and final H multicasts on the owning NoC, including empty expert paths. Do not add a combine delay, alter ACK equality, reset counters, weaken zeroing, or put the barrier on the writer.

First compare the same retained multicast-program → native-zero-program fixture with and without the epilogue barrier, using ordinary diagnostic L1 output for the already-read software/hardware counters. Strong evidence is an undrained predecessor plus next-program ACK overshoot in the baseline, eliminated by the barrier. If the baseline cannot reproduce, label the repair a source-contract fix and avoid claiming that it explains the original recurrence. Then the original full-model qualitative workload and serving lifecycle must pass; a synthetic pass alone cannot establish stage acceptance. If the new epilogue itself stalls, preserve its counts and consider multicast accounting/transport instead of bypassing the wait.

## Follow-up: implemented epilogue and bounded experiments

Source-only follow-up, same date. The native reader diff contains exactly two comment lines and one executable addition, `noc.async_write_barrier();`, at line 1367 after the complete outer expert loop. The audited source SHA-256 is `24123b33d520b495a43a4f8b23286387e00bfaecb1bf8fac6b6adb11ed7359fb`, matching `readiness_vllm/noc_boundary_probe/native_drained.json`; baseline source SHA-256 in `native_baseline.json` is `5502f0c2236eefd638b1d58dbcd5a27c3b1c7a03de19170204438c39b82213fd`.

Every normal exit from this `kernel_main` reaches the barrier: the function starts at line 315 and has no explicit `return`, `goto`, or alternate exit. Its `Noc noc` is created at line 318 and remains in scope through the epilogue. Thus empty counts, rejected/zeroed expert regions, nonempty blocks, grouped and ordinary H rounds, and compile-time bias/weight-layout/prefetch variants all converge on the same completion check. A hardware assertion, an earlier infinite wait, or firmware debug bypass is not a successful kernel exit and is not repaired by this epilogue.

The barrier drains the reader's selected NoC and does not change which RISC owns any transfer. If H rounds are assigned to the writer, their NoC1 completion remains the writer's responsibility. In the optional `H_MCAST_POSTED=true` configuration, a write-ACK barrier is not itself a posted-write counter drain; the H payload is linked to the always-nonposted terminating VALID flag (`reader.cpp:232–264`). Completion of that flag supplies the existing payload-arrival ordering. The selected configuration has `H_MCAST_POSTED=false`. No datatype, fidelity, arithmetic, tensor layout, routing, sampling, cache ownership, trace registration, or token-feedback code changes in this diff. It adds only a final completion wait, so performance impact must be measured by the normal acceptance runs, not inferred from these diagnostics.

Read-only inspection of the completed evidence establishes:

- `readiness_vllm/noc_boundary_probe/synthetic_comparison.json`: baseline and drained variants each pass 5,000 retained replays. The sampled maximum outstanding count before the optional drain is 248 in both. The maximum after the optional drain is 245 in the baseline and zero in the drained variant. Both report zero next-kernel initialization delta. This demonstrates that sent-only completion can leave ACKs outstanding and that the added barrier drains them; it **does not reproduce next-program overshoot or the original stall**.
- `readiness_vllm/noc_boundary_probe/native_baseline.json` and `native_drained.json`: each passes 2,000 native fused-SwiGLU → zero-helper replays, split into 1,000 all-zero and 1,000 one-nonempty-expert fixtures. Both have one capture/release, closed meshes, and ten stable program entries. At all recorded checkpoints, all four chips have exact zero-helper output; the nonempty expert output has the same reported maximum analytic absolute error, `2.7990201488137245e-05`, in both variants. This is not a claim of exact equality against an analytic expert result or a separately saved elementwise baseline/variant comparison.

These native fixtures use replicated synthetic expert inputs and sparse weights, omit dispatch and full combine routing, and inspect checkpoint outputs rather than every intermediate replay. They exercise the actual reader and its immediate zero-helper transition but not all model traffic. Both unpatched controls passed. The correct conclusion remains: **minimal completion-contract repair with focused regression evidence; original recurrent-hang causality unproven**. The full 12-output model run was still owned by the parent and in progress at this review; this addendum claims no result for it or for subsequent serving acceptance.
