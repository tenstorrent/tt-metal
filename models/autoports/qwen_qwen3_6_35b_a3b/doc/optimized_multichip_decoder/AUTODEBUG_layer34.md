**1. Trace of the leading discrepancy through the selected source path.**

The B1 linear call reaches `LinearTP4Mixin._linear_attention` through `decode_batch` → `decode_forward` → `_forward` → `_attention_residual`. The attention output is a rank-local FP32 partial, not a replicated complete projection:

- Local gated width is 1024, corresponding to eight value heads of width 128. `multichip_decoder.py:649–669` forms two K512 ordered scan partials, reduces them with `fast_reduce_nc`, and returns FP32 for `linear_attn.out_proj.weight`.
- `_attention_residual` calls `_reduce(attention)` and then adds the BF16 hidden residual (`:1479–1491`). `_reduce` selects the direct path for one row and FP32 input because `replicated_collective="direct"` and `direct_ar_fp32=True` (`:888–895,1204–1233`). It requests BF16 output and `fp32_dest_acc=True`.
- The scratch-tensor overload selects the minimal direct implementation, not a generic composite all-gather/reduce (`AR/all_reduce_async.cpp:541–572`). `cluster_axis=1` is the four-device axis of the required 1×4 mesh; there is no axis0/EP ownership issue on this B1 path.
- The factory binds reduction CB1 with **input Float32** and output CB2 with **BF16** (`AR/device/all_reduce_async_program_factory.cpp:401–433`). Its compute descriptor sets HiFi4, nonapproximate math, FP32 destination accumulation, and full destination synchronization, but **no unpack-to-DEST mode** (`:469–478`).
- `tt_metal/jit_build/genfiles.cpp:1069–1086` selects `Tf32` as the conditional Float32 unpack format when FP32 destination accumulation and B-family exponent formats coexist. `tt_metal/jit_build/data_format.cpp:211–217` preserves full Float32 only for an explicit nondefault unpack-to-DEST mode; this factory supplies none.
- The selected compute kernel calls `add_init(cb1,cb1,true)` and `add_tiles` for rank pairs (`AR/device/kernels/compute/reduction.cpp:29–60`). `tt_metal/hw/inc/api/compute/eltwise_binary.h:265–274` lowers `add_tiles` to `llk_unpack_AB`, placing inputs in SrcA/SrcB. Blackhole's contract explicitly distinguishes FP32→TF32 on that path from FP32→FP32 identity into DEST (`tt_metal/tt-llk/tt_llk_blackhole/common/inc/cunpack_common.h:278–287,311–340`). TF32 has ten fraction bits; FP32 has 23.

**FP32 destination accumulation protects the accumulator, not the low 13 bits of each input partial. HiFi4 and BF16 output do not restore those bits after cancellation.** The flag describes destination accumulation, so this finding is a model precision mismatch with its single-chip reduction boundary; it is not evidence that the generic API promises lossless Float32 inputs. The callee owns the conversion and needs a full-input-precision implementation branch to preserve these model partials.

The single-chip contrast is explicit. `fused_decoder.py:758–777` produces eight K512 ordered output-projection scan partials and reduces them together. `self.compute` has FP32 destination accumulation enabled (`:327–333`). For Float32 input, `FR/device/fast_reduce_nc_program_factory.cpp:289–302` selects `REDUCE_FP32_IN_DEST` and `UnpackMode::UnpackToDest`. `FR/device/kernels/reduce_nc.cpp:38–56` copies full FP32 tiles into DEST and sums with SFPU `add_binary_tile`. Thus baseline does not pass its output scan partials through the TF32 SrcA/B path.

Both implementations eventually round the attention result to BF16 **before** residual addition. Baseline's `linear` default dtype is BF16 (`fused_decoder.py:619`), and the ordered-output return typecasts to that dtype (`:777`), as called at `:1320–1325`. Claiming that final BF16 rounding alone is a TP-only bug would be false. The actual differences are input narrowing plus a different sum hierarchy.

A cheap CPU arithmetic illustration, not a device result: rank partials `[1+2^-12, -1, 0, 0]` sum exactly to `2^-12`, which BF16 can represent. Narrowing the first input to TF32 with ordinary nearest rounding or truncation makes it 1, so the sum becomes 0. This shows why a later BF16 pack does not make earlier TF32 input loss harmless. It does not assert that these are the model's captured partials.

**Concrete buffer/work ledger.** For B1 linear attention, input is padded to `[1,1,32,2048]`, width-sharded over 32 cores with per-core `[32,64]` (`multichip_decoder.py:1056–1062,1212–1216`). Each core owns two tiles, for 64 total input tiles. Scratch is FP32 `[1,1,32,8192]`, per-core `[32,256]`, exactly eight Float32 tiles / 32,768 bytes per core (`:1064–1093`); output is two BF16 tiles / 4,096 bytes per core. Factory compile arguments give eight reduction tiles; runtime arguments give four blocks and two tiles/block (`AR/device/all_reduce_async_program_factory.cpp:402–404,444–447,480–481`). Compute waits for all eight slots, accumulates rank-block pairs 0/1 and 2/3 into two FP32 DEST tiles (physical tile-index pairs `(0,2)/(1,3)`, then `(4,6)/(5,7)`), and packs two BF16 output tiles once. There is no intermediate BF16 pack between rank pairs and no exposed partial-block boundary for these dimensions.

Writers place rank `r` at `r * num_tiles_per_core * input_page_size` (`AR/device/kernels/dataflow/worker_writer.cpp:117–131`); the receiver waits for all contributions before pushing the input CB (`reduction_receiver.cpp:31–36`). Arrival-order summation is not supported by this source. For these shapes there is no demonstrated wrong buffer extent, dropped contribution, rank misordering, or queue mismatch. The demonstrated issue is the math path consuming the correctly transported Float32 values through TF32.

**How this could produce the reported symptom.** The first model operation after this reduction is BF16 residual addition, followed by post-attention norm and the gate projection. If a narrowed sum crosses a BF16 rounding midpoint, it changes the normalized router input. Close eighth/ninth expert scores can then change membership and cause a much larger output difference than the collective's original error. Restoring the BF16 selector policy cannot undo a changed input to the router. This predicts a downstream spike with unchanged attention caches and is consistent with the observed recovery on the next fixed input. The missing evidence is whether those residual/logit/ID changes actually occur at 18/41/53/70/77. Do not present that causal link as measured.

**3. Router restoration is a useful contrast, not a complete fix.**

The baseline linear singleton router requests BF16 logits and calls inherited InlineSelector (`optimized_decoder.py:238–254`). Mesh requests FP32 logits and top-k/softmax, then BF16 scores (`multichip_decoder.py:1320–1333`). Selected-value softmax is mathematically equivalent to softmax-all then renormalize, but finite-precision BF16 logits and cutoff ties need not select the same experts. HF performs a BF16 linear, FP32 softmax/top-k, renormalization, and casts scores to router-logit dtype (`python_env/lib/python3.12/site-packages/transformers/models/qwen3_5_moe/modeling_qwen3_5_moe.py:784–792`). The current exact-FP32 selector matches the mesh's existing FP32 policy; that does not establish agreement with the BF16 baseline/HF boundary.

`mesh_baseline_router_probe.py:40–55` restores BF16 rounding, inherited partition selection, and already-normalized BF16 scores without an extra softmax. It expressly preserves the mesh router projection/input (`:9–10,90–94`). Its remaining HF failures 41/53 refute “selector precision/ties alone explains the whole problem”; they do not prove routing is now identical to single-chip on those rows. A preceding residual difference can still produce different BF16 logits. An unsorted permutation of paired IDs and weights is not itself a semantic bug; compare sets and paired scores before blaming order.

**4. TP expert arithmetic is a real secondary boundary.**

The weight partition is logically valid (`multichip_decoder.py:933–945`): rank-local gate/up shape `[1,256,2048,256]` contains paired 128 gate and 128 up channels; down is `[1,256,128,2048]`. All eight selected global expert IDs execute on each rank. This B1 path is indexed tensor parallel sparse matmul, not grouped EP dispatch. Grouped routing axis bugs cannot explain this execution.

Baseline builds each expert's full K512 down output, rounds it, multiplies its score, reduces eight experts, and adds the shared expert (`optimized_decoder.py:289–298,355–363`). TP first builds a local K128 down output and rounds it to BF16, multiplies the score and rounds, reduces eight experts and rounds, then adds the local shared branch and rounds before rank reduction (`multichip_decoder.py:1300–1306,1368–1380,1505–1512`). In ideal arithmetic these commute. In finite precision they do not. In notation with `B` denoting BF16 rounding, TP effectively moves `sum_rank` outside expressions containing `B(down_rank)`, score products, expert sums, and shared addition, where baseline rounds only after the full down contraction. No final collective can recover the discarded local bits.

There is also a GU accumulation-geometry contrast: TP uses one 64-tile K block on 8 cores, baseline four 16-tile K blocks on 32 cores. Both use FP32 destination accumulation and BFP8 expert weights (`optimized_decoder.py:44–49`; mesh sparse configuration `multichip_decoder.py:1337–1366`). The sparse factory explicitly preserves Float32 intermediate reloads with unpack-to-DEST (`ttnn/cpp/ttnn/operations/matmul/device/sparse/factory/sparse_matmul_multicore_reuse_mcast_1d_optimized.cpp:814–840`). Do not generalize the direct all-reduce TF32 finding into a claim that every sparse accumulator reload truncates.

The failing-token contribution of these MoE differences is unknown. Fixed postnorm input and matched IDs/scores are required to separate them from routing. If those controls show significant error, the smallest numerical repair boundary is to preserve rank-local down partials in FP32 through rank reduction **before each baseline BF16 boundary**, then score/combine in the baseline order. That may require per-expert communication or a fused reduction/combine. It preserves sharded expert work, but its cost is unmeasured; blindly widening after local BF16 down cannot restore lost information.

Account for DEST capacity: the current kernel permits eight accumulator tiles; a new FP32 SFPU branch cannot require eight accumulators plus eight temporary tiles. Use one accumulator plus one temporary, or a verified four-plus-four schedule, with the matching pack indices and completion boundaries.
