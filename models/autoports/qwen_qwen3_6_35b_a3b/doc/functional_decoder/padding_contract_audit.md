# AutoFix competing-hypothesis audit: page padding and planning

Source-only inspection of the current functional decoder, plus host-only execution of its extracted planner AST. This is not stage review and makes no new device-pass claim. No device tools or implementation edits were used.

**Conclusion:** the hypothesis that final-owned-page aliases intrinsically leak future values or write another owner's page is refuted for the documented valid-input contract: finite cache contents, disjoint owned pages, positions below the state's logical capacity, and a well-formed plan from `prepare_prefill`. The revised full-attention planner satisfies the native scalar chunk alignment requirements. I found no correction required in this narrow area. The alias table does not itself enforce logical capacity; that remains a caller precondition for device-tensor decode positions, already documented in README.md:28.

## Read and write bounds

Let C be logical capacity, B=ceil(C/32) owned pages, and P=8*ceil(B/8) table entries. `tt/functional_decoder.py:213` builds P entries, preserving distinct physical IDs in the first B and repeating the final owned ID afterward. It requires a physical pool at least P pages wide. That latter requirement matches native `paged_update_cache_device_operation.cpp:195` (under `ttnn/cpp/ttnn/operations/experimental/paged_cache/device/update_cache`), which compares table width against physical page count rather than counting distinct mapped pages. Each alias points to an allocated, request-owned physical page; no alias names a different request's page.

Decode reads complete 256-token key chunks, including virtual pages beyond the last valid token. The paged reads in `ttnn/cpp/ttnn/operations/transformer/sdpa_decode/device/kernels/dataflow/dataflow_common.hpp:753` map each virtual tile row through the table. For position p<C, the last read chunk ends at ceil((p+1)/256)*256 <=32P; table padding is therefore sufficient. The writer loads current position from its device tensor (`writer_decode_all.cpp:109` in the same dataflow directory), and generates the last-chunk mask at line256. `dataflow_common.hpp:215` generates zero through current position and negative infinity afterward, including full later tiles. Compute applies that mask before exponentiation (`../compute/sdpa_flash_decode.cpp`, mask logic before line490). Thus alias copies of existing finite K/V do not become visible attention history. Finite contents matter: a NaN-valued K/V cache is not repaired by causal masking and is outside this reasoning.

Prefill does not require speculative alias reads for its rounded tail. `sdpa/device/sdpa_program_factory.cpp:1235` sets scalar-chunk effective K length to start+Q length and rounds scheduling geometry at line1250. `sdpa/device/kernels/dataflow/reader_interleaved.cpp:670` clamps readable rows to this valid extent; its paged read at line702 calls `dataflow_common.hpp:256`, which reads only `src_rows` and zero-fills remaining chunk tiles. These paths are under `ttnn/cpp/ttnn/operations/transformer`. Causal masking still excludes later positions inside the valid prefill chunk.

Cache writes have separate bounds from attention reads. The prefill writer maps only the input's tile rows through the sliced table (`experimental/paged_cache/device/kernels/dataflow/writer_fill_cache_interleaved.cpp:239` onward), and the decoder supplies only complete 32-row inputs to this operation. Its start is 256-aligned, hence page-aligned. With end<=C, every page it writes lies among the B owned pages; it cannot reach table aliases. The one-token update writer selected by `paged_update_cache_program_factory.cpp:430` is `writer_update_cache_interleaved_start_id.cpp`: lines98–115 choose exactly page_table[p/32] and byte row p%32; lines135–164 replace that row in the existing tile before writing it back. For p<C, that index is <B. Read-only aliases are not write targets for valid calls, and rows after the logical end are preserved.

Out-of-contract decode positions are materially different: `decode_forward` cannot inspect the device scalar on the host, and `prepare_positions` validates HF capacity rather than the particular state's capacity. A position p>=C could overwrite an owned final-page row or access beyond the table. This is an explicit caller precondition, not a protection provided by padding. The README already states it; consumers must retain it when wrapping this class.

## Planner alignment

Native scalar chunked SDPA requires start divisible by both q_chunk_size and k_chunk_size (`sdpa_device_operation.cpp:389–403`). The configured values are32 and256. `FunctionalDecoder.prepare_prefill` uses chunked full attention only at absolute positions divisible by256, with a positive multiple-of32 input length no larger than256; all other starts use the one-token decode path. After a short aligned chunk (for example chunk_size32), it correctly advances with single tokens until the next256 boundary. This is potentially slower, but correct. The native factory pads K scheduling internally, so a32/64/224-row final chunk need not end at a256 boundary.

Host-only check executed the actual extracted `prepare_prefill` AST with a dummy position uploader; no TTNN import occurred. It checked **87,368** combinations: starts0..513 plus ten near-HF-limit starts, lengths1/2/7/31/32/33/63/64/65/127/128/129/223/224/225/255/256/257/511/512/513, and requested chunk sizes32/64/96/128/224/256/288/512, omitting combinations beyond262144. All plans exactly covered the logical input with no gaps/overlap, all multi-token starts were256-aligned, all multi-token lengths were32-aligned and<=256, and fill-page indices stayed within the logical page extent. This checks planner structure, not device numerics.

## Trace and remaining discriminating checks

All page-table allocation/padding and position uploads happen in setup. A captured decode retains the original tensor addresses; the caller must refresh those buffers in place, keep padded table shape fixed, and keep input/state/RoPE buffers alive. Replacing a Python state dictionary entry with a newly allocated tensor does not retarget a captured trace. Current `tests/trace_reuse.py:44–136` allocates persistent buffers before capture, prewarms all prefill paths, updates the same page-table and position buffers, and releases the trace only after requests finish. The modified padding does not add a runtime host operation or allocation.

Existing `page_extent_regression.json` records capacities1/31/32/33/255/256/257/511/512/513 with both PCCs>=0.99968 and unowned/future-row guards passing. Those results support the source proof; this audit did not rerun them. Two focused checks would discriminate remaining edge assumptions, without implying a discovered failure:

1. Fill future rows in the final owned page with large finite nonzero sentinels, then compare prefill/decode against an otherwise identical zero-tail cache. This directly tests mask exclusion and preservation of finite stale values; zero guards primarily prove absence of writes.
2. Reuse a single tracked decode trace with a padded table (e.g. capacity33, width8) across two disjoint page assignments, refreshing both owned entries and all final-page aliases in place. Existing refreshed trace testing uses capacity512, width16, which has no alias tail. Check last valid position32 and unchanged other-owner pages. This specifically joins alias padding to the already-tested stable-address replay mechanism.

These are narrow strengthening checks, not substitutes for the active full-context correctness run, watcher, performance, or independent stage review.
