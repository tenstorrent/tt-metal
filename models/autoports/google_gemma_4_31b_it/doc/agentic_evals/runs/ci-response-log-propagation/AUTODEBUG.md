## Source trace and ruled-out hypotheses

Pinned TTIaf1ef17abfecb059da13d0a1287c00eace0f210e adds VLLM_DEBUG_LOG_API_SERVER_RESPONSE="true" at the model device env and the two request flags. ModelSpec.__post_init__ merges device env into serialized top-level env. run_vllm_api_server._model_spec_env_vars merges both locations; set_runtime_env_vars exports them before runtime_settings and same-process runpy API startup. The actual CI command confirms the request flags, but no live artifact independently exposes the final API process environment. Absence of the env's INFO setup message is not proof it was absent: other INFO setup messages are also missing.

Stock vLLM response env parser accepts case-insensitive "true". middleware/register.py conditionally installs response logging and emits a CAUTION warning. request_logger.py slices prompt/detail strings at max_log_len, but emits Received request INFO independently of that limit. Thus max_log_len0 cannot suppress the request-ID record; changing it to a larger prompt length is not a justified fix. Duplicate --max-log-len32 then --max_log_len0 is visible and warrants exact parser confirmation, not invented suppression semantics.

TTI installs a custom AsyncLogHandler with one QueueListener. Python logging dictConfig closes existing handlers; AsyncLogHandler.close stops its listener. Host-only discriminator reproduces a concrete failure: after a working TTI custom config, uvicorn.Config with default logging closes the listener, and a subsequent Received request INFO produces zero records. Three repeated TTI custom dictConfigs alone each emit correctly. This is a viable mechanism for API logging disappearing while a separate engine process keeps its own handler.

However, stock vLLM get_uvicorn_log_config should carry its parsed pylogging_config_file through to uvicorn. A second host-only probe using the real vLLM argument parser, environment path, configure_logging_from_args and get_uvicorn_log_config preserves the custom path, envtrue and emits the record. Therefore the first discriminator is **not sufficient to claim the actual CI path used uvicorn defaults**. The exact CI point losing the handler/path remains unproven from this snapshot. No env/config repair has been accepted or implemented on this evidence.
