# Full-phase roofline method

The benchmark collector reports modeled useful work divided by observed whole-phase host wall time and a theoretical peak. These percentages are estimates, not measurements of device instruction occupancy or bus counters. No performance minimum is applied.

## Completion timeline

`QWEN_BENCHMARK_PHASE_LOG` enables the model-owned instrumentation. Otherwise the adapter has no timing state, extra events, or writer thread. Setup saves the actual imported adapter path, full layer indices, selected precision, topology, tensor dtypes and padded per-rank shapes in `.ready.json`.

Each forward records a `perf_counter` submission marker before adapter validation, uploads and telemetry. Every prefill call, including intermediate scheduler chunks, records a CQ completion event after the existing forward returns. A CPU observer polls the existing nonblocking `distributed::EventQuery` through `ttnn.event_query` every 0.5 ms. This reads completion counters; it does not synchronize the device, add a command-queue barrier, collect the live device profiler or change the scheduler. The only extra device command is a lightweight completion marker. Final sampled prefills already perform token readback; the marker also covers their remaining sample-mask restoration.

Decode carries its submission identity through `DecodeOutput` and `read_decode_output`. The observer queries the *existing* async readback event independently of when the plugin later processes that output. Synchronous reads mark completion after their existing blocking transfer. The adapter separately records entry and exit of `process_decode_output_host`, including conversion and validation. The plugin's `finalize_decode` has already synchronized the existing readback event before that callback. Thus a trace enqueue is never treated as completed device work, and delayed callback scheduling never hides a prefill completion.

Events may be registered out of order. The observer stores them by submission sequence and emits completion records in command-queue FIFO order, requiring each earlier CQ boundary to be observed. The collector partitions a single timeline from first measured submission through last observed completion. An interval ends at the current CQ completion and starts at the preceding completion; it is initially charged to the current phase. Actual decode host-conversion intervals are then charged to decode: any overlap is subtracted from prefill, and a final host-processing tail extends decode. The host intervals are unioned before subtraction. This includes communication, sampling, readback, conversion and host scheduling gaps, without adding overlapping request latencies or trace enqueues. Interleaved prefill/decode remains separately identifiable even when an older decode callback runs during a newer prefill. This explicit ownership convention resolves CPU/device overlap; it does not claim both overlapping activities each occupied the same wall-clock second.

Event polling and host thread scheduling delay are included, and the retained timeline records completion-observation minus marker-registration time (which includes device execution and is not observer overhead); this is a host-observed completion estimate with 0.5 ms polling granularity, not an exact hardware timestamp. The raw events, CQ timeline, host-conversion interval union, time reassigned from prefill and final host tail are all retained.

The observer buffers records and flushes JSONL off the serving thread every 0.2 seconds. A nonce/acknowledgement sidecar requests a flushed snapshot before the server stops. `check` requires the same live PID, selected policy, full layers, capacities, generated-module import, actual weight metadata and both prefill/decode completion events from the setup preflight.

## Measured-request selection

The vLLM 0.26 client and server share the Linux monotonic clock. Detailed client `start_times`, `ttfts` and `itls` delimit measured requests. The initial vLLM probe precedes this window and is excluded, as are previous warmups and eval traffic. Synthetic request IDs are created on first prefill and follow state-slot remaps. Events retain active slots, prompt chunk start/end, original prompt length, sequence positions and a first-64-token hash. Every selected request must have distinct prompt-prefix hashes, contiguous prefill chunks, all completed decode positions and measured input/output counts. Missing completion boundaries or interleaved unmeasured requests fail collection. Extra executed asynchronous outputs are retained separately rather than confused with HTTP output tokens.

## Prefill work and compute peak

Useful projection FLOPs use `2*M*K*N` on logical tokens and model dimensions: all 64 MLPs, 48 GDN input/output projections, 16 gated attention input/output projections and each executed terminal projection. Full attention adds causal QK and AV work using each chunk's real starting position. GDN adds the recurrence's decay, prediction, rank-one update and readout, plus causal convolution. No triangular masked attention or padded token rows are credited. GDN projection correction and padding overhead remain in elapsed time without inflating useful architecture FLOPs.

Projection FLOPs use each selected group/layer fidelity, including layer 0 and 63 exceptions and the LM head. Attention uses its selected LoFi kernel; GDN recurrence/convolution uses a conservative HiFi4 matrix-reference equivalent. The latter is an architectural compute roofline comparison, not a claim that the SFPU achieves matrix throughput. Mixed-policy peak is a work-weighted harmonic mean: `sum(F_i) / sum(F_i / peak_i)`.

Official [p300c specifications](https://docs.tenstorrent.com/aibs/blackhole/p300.html) describe 120 cores per ASIC and a 1.35 GHz clock. Four participating ASICs give a nominal LoFi peak of `4*120*1.35e9*4096 = 2.654208e15 FLOP/s`. The official [tt-perf-report reference](https://github.com/tenstorrent/tt-perf-report#additional-fields) supplies Blackhole phase divisors: LoFi 1, HiFi2 2, HiFi3 3, HiFi4 4. The collector records the observed usable compute grid separately; the roofline denominator uses the full advertised participating-chip peak, not just kernels' selected cores.

## Decode traffic and DRAM peak

Weights are counted once per executed decode step across all four TP ranks, sharing each weight read across the batch. The setup inventory records actual selected decode tensors and physical padded shapes. It excludes embedding-table bulk reads, prefill-only `swiglu_weight` and `row_parallel_weights` copies, and transformed-but-unused `A_log`; it includes the executed packed GDN primary/correction weight, packed gate/up, output/down projections, norms, transformed decay and convolution taps. Terminal decode calls the first layer norm with decode=True; its gather-norm decode path reads the full replicated final_norm weight, not the retained sharded prefill copy. BF8 and BF4 tile sizes include shared exponents: 1088 and 576 bytes per 1024 elements; BF16 is 2 bytes and FP32 is 4 bytes. Each participating rank's replicated data is counted. There are no MoE experts and no data-parallel replicas.

KV reads use actual active sequence positions, rounded to page32; both K/V are counted at selected BF8 storage. New KV updates conservatively count one page read and write. All executed trace rows contribute recurrent and convolution-state traffic, including inactive padded batch slots. The B1 trace has one state read and write (2 volumes). For B>1, Model.decode preserves inactive state unconditionally: core update (2), clone (2), where(old,updated) (3), copy (2), totaling 9 recurrent-state volumes. Convolution preservation additionally changes ROW_MAJOR [B,3,2560] to padded TILE [B,32,2560] on each rank: two tiled conversion writes, three tiled where passes and one tiled conversion read add 6 padded tile volumes, beyond 9 logical volumes. The two state-preservation masks per layer/rank include source reads, tiled writes and ideal single tiled reads. This counts the implemented path even when every row is active. Material activation traffic explicitly models BF16 residual/normalization, MLP, attention/CCL staging and logits/sampling buffers at padded 32-row matrix granularity. Embedding reads count every executed physical batch row, including inactive rows, rather than the full vocabulary table. Component totals are retained for each profile. This is an ideal material-traffic model: repeated kernel reads, cache effects, implementation-specific overfetch and firmware traffic are not measured and can make physical traffic differ.

The official [QuietBox 2 specification](https://docs.tenstorrent.com/systems/quietbox/quietbox-bh-2/specifications.html) gives 512 GB/s per ASIC, hence `4*512e9 = 2.048e12 byte/s` across the participating TP4 mesh. Ethernet is not added to DRAM peak bandwidth.

## Host validation

Run `python models/autoports/qwen_qwen3_6_27b/tests/test_benchmark_accounting.py`. Tests cover BF exponent storage, batch-shared weights, active KV versus physical embedding rows, nine-pass B>1 recurrent preservation and padded convolution conversions, replicated terminal norm selection, mixed-fidelity FLOPs, delayed nonblocking completion and reversed callback registration, resident-position/remap tracking, interleaved chunks/decode, exclusion of a preflight probe, nonoverlapping elapsed time and rejection of missing completion evidence. These tests do not establish measured hardware results; the live setup preflight and every profile's collector do that.
