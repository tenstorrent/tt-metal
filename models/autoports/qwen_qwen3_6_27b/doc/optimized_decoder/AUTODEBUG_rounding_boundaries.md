# Actual-input convolution and GDN norm rounding boundaries

Both proposed HF boundaries are confirmed, but matching them alone is **not demonstrated to repair the remaining sequence gate**. A further source correction matters: TTNN's fused **input** SiLU activation already packs an intermediate in the input dtype. With BF16 z, its gate is BF16 even without a separate `ttnn.silu` operation.

Evidence: `rounding_boundaries_cpu.json`, generated by `candidates/rounding_boundary_probe.py`. Nine actual input captures were inspected: chunk/direct/sfpu10 at steps19/58/99. No hardware or main-source edits.

## Convolution: exact same-input validation

Installed HF `torch_causal_conv1d_update` calls `F.conv1d` with BF16 history/weights, then applies `F.silu` to its BF16 output (`modeling_qwen3_5.py:222-237`). The CPU probe verifies that this equals:

```text
four BF16 inputs and taps
→ FP32 products and FP32 sums
→ BF16 completed convolution sum
→ SiLU with BF16 input/output
```

This explicit implementation is **bit-identical** to CPU BF16 `F.conv1d` plus SiLU on all nine captured TT histories/current QKV projections, across all10240 channels. Thus it is a fixture-verified boundary, not an assumption about PyTorch internals.

Current `conv_functional` rounds every product and every sum to BF16; `conv_round_products` also rounds products prematurely. Neither is the HF control. Native/batched fused-SiLU applies SiLU to the unrounded FP32 sum, then packs BF16. Those are different numerical contracts.

For the chunk/direct captures (their convolution inputs are identical), relative output error versus same-input HF convolution is:

| Recipe | step19 | step58 | step99 |
|---|---:|---:|---:|
| FP32 products/sum → BF16 → SiLU | 0 | 0 | 0 |
| FP32 sum → SiLU → BF16 | .003297 | .002769 | .003898 |
| BF16 products, FP32 sum → BF16 → SiLU | .003827 | .004055 | .003186 |
| BF16 products and sums → SiLU | .004137 | .005132 | .003214 |

The CPU fused-SiLU version reproduces captured TT convolution almost exactly: relative errors≤2.15e-5, with bit equality at step58. This localizes the observed difference to the intended rounding boundary rather than a history/channel ordering defect.

Because the TT projections/history already differ from HF, matching the boundary does not uniformly improve agreement with the actual HF upstream run. For example, step19 actual-HF QKV relative error changes .01147→.01184 when only this boundary is corrected. That does not invalidate the exact same-input result; it shows why a full prefix/decode test is necessary.

Minimal decode change: keep all four products and partial sums FP32; make the final add BF16 **without** activation; then apply BF16 SiLU. Do not enable product rounding. A full HF-parity control should apply the same contract during prefill: correcting only decode retains the existing prefix state mismatch. The native prefill convolution API hardcodes its fused SiLU behavior, so a local alternative would be needed if that prefix discrepancy proves material; no shared kernel change is implied.

## GDN RMSNorm and gate: two distinct boundaries

HF `Qwen3_5RMSNormGated.forward` (`modeling_qwen3_5.py:193-202`) does:

```text
x_BF16 → normalize in FP32 → BF16
→ multiply BF16 norm weight, producing BF16
→ multiply SiLU(z.float()) in FP32
→ final BF16
```

The weight multiplication must follow the BF16 normalization boundary. Current TTNN weighted RMSNorm instead keeps its normalized intermediate in Float32 when `fp32_dest_acc_en=True`: `layernorm_op_multi_core.cpp:490,738` assigns the `FUSION` buffer that format. `kernels/compute/layernorm.cpp:305-378` packs normalized values to that buffer and applies gamma before the output BF16 pack. This is a genuine mismatch with HF's explicit BF16-before-weight step, not merely naming an operation “fused.”

### Fused input SiLU still has a BF16 intermediate

`binary_ng_program_factory.cpp:1197-1210` allocates activated LHS buffer c3 in the LHS input data format. Both `eltwise_utils.hpp::preprocess_fpu_impl` and `eltwise_utils_sfpu.hpp::preprocess_sfpu_impl` run the unary operation, then `pack_tile` into that intermediate before the binary operation consumes it. `eltwise_binary_no_bcast.cpp:20,39-52` reads that post-activation buffer for the multiply.

Therefore `multiply(z_BF16, norm, input_tensor_a_activations=[SILU])` has a BF16 gate rounding boundary already. `round_silu=True` changes scheduling/topology but does not introduce that boundary for the first time. The captures closely match the CPU folded-norm/BF16-gate model, consistent with the source.

To match HF GDN, first widen z to FP32 before its SiLU/input-activation preprocessing, then multiply with the BF16 weighted norm and pack the final BF16 output. The explicit float32 input also makes the intermediate Float32. Verify the selected kernel's FP32 unpack path and result against the real device; an FP32 dtype name alone is not proof of full operand precision.

Do **not** blindly apply this change to MLP SwiGLU: HF's MLP computes SiLU on a BF16 gate projection, and its returned gate is BF16 before multiplication. GDN and MLP intentionally have different gate precision contracts in this installed model.

## Measured impact of the norm boundary alone

The CPU probe feeds each captured TT core/z through four norm/gate boundary variants. It also feeds those results through the **same real-weight CPU HF output projection, residual, post-attention norm and MLP**, holding the downstream implementation fixed. This is an attribution counterfactual, not a predicted device PCC. Reconstructing the full HF output from captured HF gated values gives PCC≥.999999517 across all controls.

For the direct-recurrence captures:

| CPU HF downstream input | step19 final PCC vs HF | step58 | step99 |
|---|---:|---:|---:|
| Captured TT gated output | .994228 | .999265 | .999161 |
| Correct HF pre-weight BF16 boundary + FP32 gate | .993847 | .999493 | .999489 |
| Folded weight + FP32 gate | .993844 | .999264 | .999175 |
| HF pre-weight BF16 boundary + BF16 gate | .994270 | .999267 | .999561 |

Thus exact HF GDN boundaries can improve margin at58/99 but do not rescue captured direct step19. The remaining core/upstream differences dominate that failure. At the older chunk step58, exact boundaries improve the same CPU-tail PCC .973019→.977420, still far below .995; they cannot repair the accumulated native state attenuation.

Whole gated-output PCC versus HF changes only .999265915→.999266121 for direct step19, .999790756→.999794106 at58, and .999850862→.999852925 at99. Small local changes can nevertheless move final PCC materially because of downstream sensitivity, so a real full-sequence control is warranted if combined with corrected input/state precision. No threshold or weight dtype should be altered on this evidence alone.

## Decoder-local candidate sequence

A precise GDN post-core control is:

```python
# out already BF16, shape ending in128
normalized = ttnn.rms_norm(out, epsilon=eps, compute_kernel_config=ckc)  # no weight; BF16 output
weighted = ttnn.multiply(normalized, norm_weight_bf16, dtype=ttnn.bfloat16)
z32 = ttnn.typecast(z, ttnn.float32)
result = ttnn.multiply(z32, weighted, input_tensor_a_activations=[ttnn.UnaryOpType.SILU], dtype=ttnn.bfloat16)
```

Shape folding/head concatenation must preserve the existing head order. This adds operations/data movement relative to weighted RMSNorm, so keep it only with measured quality/performance evidence or fold the exact boundaries into an already-legal decoder-local composite. No hardware validation is claimed for this snippet.

The convolution control and GDN control are independent. Evaluate them separately and combined with the corrected recurrent arithmetic; include prefix and the same128-token random fixture. Their correct HF boundaries are established, but a complete ordinary-single-BFP8 pass remains to be measured.
