# Terminal profiling analysis

CPU-only analysis of the successful fixed reduced Tracy capture, using
`tt-perf-report`1.5.0 with advice enabled. No TT devices were opened and no
production source was edited. Exact commands, tool version and input path
are in `command_receipt.json`; `render_reports.py` reproduces the reports.
The raw CSV remains unchanged at
`../tracy_terminal_fixed/reports/2026_11_14_03_14_06/ops_perf_results_2026_11_14_03_14_06.csv`.

**The LM head is the largest terminal cost; sampling does not dominate token-out
decode.** The vocabulary-sharded BF16/HiFi4 LM head costs approximately1.55–1.57ms
per token. Sampling plus token readback costs0.589ms, approximately18.4% of the
reduced model's3.197ms/token. The DRAM-sharded LM-head advice was subsequently tested by the parent at
unchanged precision: both legal adapted candidates were slower. Retain the
current head; `lm_head_decision.json` records the measured decision separately
from the frozen decoder rejection ledger.

## Scope and timing interpretation

The source workload is `tests/profile_full_terminal.py`, real layers[0,3],
B1, prompt128, cache2048, exact terminal norm/head/common sampler, three decode
replays per measured window. Diagnostic preparation covers length128 only.
This is reduced instrumented evidence, not all64 throughput or final trace
allocation acceptance. The matching receipt is `../terminal_profile_fixed.json`.
Its source hashes, three stable trace IDs, stable buffer addresses and unchanged
213 program-cache entries are preserved there.

| Window | Included work | Instrumented wall time | Per-device summed kernels |
| --- | --- | ---: | ---: |
| PERF_PREFILL | Request reset/config, eager bounded128 prefill, terminal norm/head, one traced greedy sample, token readback |8.133ms TTFT |4.263–4.277ms |
| PERF_DECODE | Traced model and sampler, persistent token feedback, one token readback per step |3.197ms/token;312.75t/s/u |2.975–2.979ms/token |
| PERF_LOGITS_ONLY | Model trace including terminal, fixed initial token with advancing positions, one end synchronization |2.626ms/step |2.521–2.532ms/step |
| PERF_SAMPLING | Sample trace repeatedly consuming the same resident logits, plus each token readback |0.589ms/sample |0.452–0.454ms/sample |

Logits-only is neither teacher forcing nor autonomous token generation. The
0.572ms difference between decode and logits-only wall times is consistent
with the separate0.589ms sampling/readback measurement, but their synchronization
patterns differ, so it is not an exact component subtraction. All sampled IDs
remain on-device feedback; observed token reads do not feed the next iteration.
Counter checks show zero full-logit readbacks, token refreshes or per-token
position/RoPE/page-table refreshes in these decode windows.

The profiler drains occur outside signposts. Nevertheless raw first-op
`OP TO OP LATENCY` spans the previous device work and profiler-drain boundary:
the report counts a77.809ms gap in a decode window whose host signpost span is
10.227ms and measured replay body is9.592ms. Prefill's advice similarly claims
118.936ms of removable gaps inside an8.637ms signpost span. These gap totals,
report `Total %`, and resulting claimed tracing savings are invalid as in-window
performance accounting. Preserve the report, but do not publish its percentage
ranking or use those gaps to infer a runtime stall. The already traced decode
cannot gain89.3% merely by “running with tracing.”

Raw individual kernel durations are consistent with measured wall time.
`kernel_accounting.json` and `kernel_categories.csv`, generated by
`summarize_kernels.py`, sum `DEVICE KERNEL DURATION [ns]` separately on each
rank and convert to microseconds. They exclude the invalid inter-window gap.
Do not sum four TP ranks into one latency. Kernel sums describe additive work;
they are not an independently measured critical-path interval. The report also
shows some decoder FLOPs percentages above100%, so its generic small-M fidelity
roofline estimates must not be treated as demonstrated hardware utilization.
No full-model roofline percentage is asserted here.

## Terminal decomposition

| Decode component | Per-token kernel work across ranks | Interpretation |
| --- | ---: | --- |
| Final hidden all-gather plus3 normalization primitives |30.1–37.4us | One terminal gather of the fractured1280-wide residual into5120; no added inter-layer gather |
| LM head `[1,5120] @ [5120,62080]` per rank |1547.5–1568.0us | Vocabulary TP4, BF16 weights/output, HiFi4,110-core generic interleaved matmul |
| Logits FillPad plus stable-buffer Copy |44.8–45.4us | Prepares the common sampler's32-row persistent storage |
| Local TopK route-prep/large-indices/route-finish family |324.9–325.5us | Physical localk32,65536-wide masked/padded vocabulary shard |
| Complete sample trace, separately measured |451.8–454.4us | Includes candidate CCL, greedy tie handling, RNG, selection, feedback |

The head is approximately49% of the reduced token-out wall time and61–62% of
its logits-only kernel work. The large-indices TopK kernel itself is about
278.4us; with preparation/finish it dominates *the sampler*, but not the whole
token-out path. This is the110-core Blackhole large-indices family, not a
multi-millisecond one-core generic `TopKDeviceOperation` fallback. No
`ArgMaxDeviceOperation` appears. Sampling gathers only the local32 candidates
and their indices, not the full vocabulary. The report's sampler AllGather
operations are two small candidate exchanges per step, about6us each.

Sampling remains the existing common `SamplingGenerator/TTSampling` contract:
physical local32 candidates with semantic greedy k1/p0/temp1, persistent token
output, traced RNG/state updates, masked65536-wide local input. This evidence
does not justify replacing it with full-vocabulary gather, host argmax, or a
custom sampler. Existing `sampler_ties.json` supplies semantic-greedy proof;
this deterministic synthetic prompt is not an accuracy or language-quality test.

The parent ran the focused LM-head followups; this author only prepared and
analyzed them. The initial L1 failure was adapted into two legal candidates
with passing logits/greedy and strict trace checks. Both regress terminal
latency, so this advice item has a measured disposition and no production
change is selected. This is a B1 same-precision comparison under allocation
tracking, not a B32 throughput result or exhaustive rejection of every possible
DRAM-sharded geometry. Final all64 uninstrumented TTFT/token-out and teacher-
forcing timing remain separate parent-owned evidence; reduced instrumented
rates must not replace top-of-README full-model measurements.
