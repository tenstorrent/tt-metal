# Full-phase collection design (source inspection)

This is a proposed instrumentation contract, not collected evidence. No hardware or implementation changes were made for this inspection.

## Actual implementation and completion hooks

`importlib.util.find_spec('vllm_tt_plugin')` resolves to `/workspace/tt-metal/vllm/plugins/vllm-tt-plugin/src/vllm_tt_plugin/__init__.py`. A second checkout under `/home/container_app_user/vllm-tt-plugin` differs and must not be used as the source of line numbers or claims.

- Autoport `tt/generator_vllm.py:169` `prefill_forward` encompasses sampling setup, all generator prefill, sample_prefill, and blocking output conversion. Timestamp entry and successful return. Actual host tokens exist at its return; no additional synchronization is necessary. Capture prompt lengths and compact rows before dispatch.
- Adapter `decode_forward` entry starts dispatch work. `_decode_inputs` trims trailing unused slots but retains interior inactive slots. Record executed row span as well as active row indices.
- Adapter `read_decode_output:291` issues `cpu(blocking=False)` and an event. It is a **submission**, not completion. Associate immutable submission metadata with the returned host tensor's identity, not the persistent device-output tensor, which is reused across steps.
- Actual plugin `async_decode.py:675` already calls `ttnn.event_synchronize` before `:682` invokes `process_decode_output_host`. An adapter hook at successful `process_decode_output_host` return is therefore an actual asynchronous completion boundary for device sampling/readback/host tensor conversion. Do not add event waits, device synchronization, `.cpu()` calls, or profiler instrumentation.
- The stronger full plugin boundary is `TTAsyncDecodeController.complete_decode_step:406`: it calls finalize_decode, performs `_get_output_tokens` (including host sampling where selected), and returns `CompletedDecodeStep` with `completion_time_ns` at line 451. `AsyncTTModelRunnerOutput._get_output_impl:156` subsequently enqueues and builds runner output. A model-owned opt-in instrumentation module can install wrappers around these methods at adapter import time, without editing shared plugin files. Wrappers must preserve signatures, exception behavior, returns, and existing finalization locks; invoke originals exactly once.
- `TTModelRunner.submit_prefill:2689` has runner state and input metadata; wrapping it captures stable request IDs together with the synchronous prefill completion. For complete host sampling coverage, wrap the prefill extraction/sampling caller as well or restrict verified benchmark protocol to device sampling and explicitly define the boundary.

## Request identity and batch positions

The adapter signatures contain no request IDs. The plugin owns them in `runner.input_batch.req_ids` and `req_id_to_index`. `capture_submitted_step_context:211` makes an immutable snapshot, including `request_states` and `submit_time_ns`; `complete_decode_step` receives that exact context. Use this context rather than consulting mutable current batch state during async completion. Request IDs must be copied at prefill submission from the matching runner/input batch, not inferred from token counts or completion order.

`generator.py:454` refreshes host-supplied positions only when `device_feedback=False`; trace replay increments device positions. Consequently a repeated `start_pos` argument under `reset_batch=False` cannot be used directly for KV-byte accounting. Maintain shadow positions per executed slot, seeded from the effective positions on binding/reset and incremented exactly once per successful decode submission. Snapshot them before incrementing. Preserve `-1` inactive rows, rebinding and slot remaps; fail accounting rather than guessing after an unsupported transition. Cross-check active output counts against 128 tokens per measured request and account for any extra speculative/pipelined submissions explicitly.

## Nonoverlapping full-phase denominators

Do not sum each submit-to-completion duration: asynchronous steps overlap. Collect raw submission and completion timestamps and build a single server timeline offline. Preserve intervals between steps so dispatch, communication, host processing and scheduler gaps remain in the denominator. For an uninterrupted phase, use earliest dispatch to final actual completion, including gaps; report dispatch/finish bounds and operation count. For interleaved prefill/decode, retain the raw overlap intervals and publish a deterministic nonoverlapping partition policy rather than double-counting or silently omitting time. One conservative policy is completion-ordered segments: each segment begins at the previous observed completion and ends at the next, attributed to the completing phase; first segment starts at the first model dispatch. State explicitly that this is host completion accounting, not isolated hardware service time, and expose any phase overlap. Final postprocessing/idle gaps can be attributed to the next phase; report the last completion-to-client-end tail separately. Do not claim every unit of phase-specific device work occurs inside its allocated segment under asynchronous overlap.

For a stricter complete serving envelope, bracket with client request start and completion and retain initial queue time and final transport time as separate host overhead. Distinguish those from model phase estimates. Entire work accounting must use the same included submissions; pending/unmatched operations invalidate collection.

## Excluding warmup/probes and matching bench output

`vllm/benchmarks/serve.py:984` retains `start_times`; endpoint request functions set these from `time.perf_counter()` just before HTTP dispatch. The client and server must share the same host monotonic clock; store hostname/boot identity and paired wall/monotonic timestamp anchors to validate that assumption. Select completed serving operations inside each measured benchmark window, not all operations since startup. Warmup and the benchmark's initial probe precede the minimum measured `start_times` and must be excluded. Include all measured request lifetimes through final completion; reject a window containing unrelated requests.

`RequestFuncInput.request_id` is sent as `x-request-id` (`endpoint_request_func.py:138`), but the saved bench result shown here contains times rather than request IDs. Preserve a request-ID sidecar or capture the generated benchmark IDs and validate how API-generated IDs map to engine request IDs. With model-local adapter hooks only, timestamps provide window attribution but not proof of individual request identity. Do not assert exact ID mapping without the plugin snapshot or a verified HTTP ID chain. Distinct prompt hashes plus row metadata can provide another consistency check without logging raw prompts.

## Storage and validation

Append compact immutable records in memory under a short lock; no disk writes on every token in measured work. Async completion and submit may run on different threads. Use per-submission IDs and host-tensor identity to match outputs, retaining duplicate/missing detection. Flush only after benchmark completion and natural drain, before server stop, via a model-local control path that does not run inference. A signal handler may request a snapshot/flush but should not perform blocking work inside measured callbacks. Include a schema/version, monotonic anchors, model policy/source identity and explicit flush cutoff. Validate all submissions have corresponding completions and no active measured requests remain before switching profiles.

This design cannot by itself establish FLOP/DRAM estimates; those require model shapes, precision, actual active experts/tile work assumptions, KV lengths, sharing assumptions and aggregate participating-device peaks. Host-wall percentages must never populate telemetry device-time fields.
