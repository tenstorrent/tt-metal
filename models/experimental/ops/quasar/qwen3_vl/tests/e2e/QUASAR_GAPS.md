# Qwen3-VL e2e: Quasar gaps and other failures

Gaps that block or shape the Qwen3-VL bring-up on Quasar today: open, not fixable, or with a fix still in review.
Section 1 lists ttnn ops/paths that work on WH/BH but not on Quasar. Base ops that the e2e routes to their
`ttnn.experimental.quasar` ports (`op_overrides.py`) are not listed.

Status values: `open` (not fixed in ttnn), `worked-around` (harness/model avoids it; still open in ttnn),
`unverified` (suspected from precedent, not yet reproduced on Quasar).

## 1b. Small-grid limits (any arch; block the 2-core emulator grid)

| # | Op / config | Failure on a 2x1 grid | Workaround in this branch | Status |
|---|---|---|---|---|
| G1 | `ttnn.experimental.nlp_concat_heads_decode` | `work_split.cpp:99: Target number of cores 32 is greater than total number of available cores 2` — one head per core | workaround `concat_heads_decode_small_grid`: device-only deshard → untilize → reshape → pad → tilize (same approach as llama32_1b_quasar `_install_quasar_concat_heads_grid_agnostic`) | worked-around |
| G2 | `tt_transformers` prefill matmul program configs sized for 8x8 (QKV, WO, FF1/3, FF2) | `compute_with_storage_grid_size (8, 8) must fit within device grid (2, 1)`; then `per_core_M (8) exceeds Mt (4)`; then L1 overflow (1.9 MB > 1.5 MB) | `fit_matmul_config`: grid clipped, per-core blocks from real M/N tiles, `in0_block_w=1`, `out_block_h/w` blocking | worked-around (config, not op) |
| G3 | LM head width-sharded input/output configs | prefill: sharded input clashes with matmul CBs in L1; `Unsupported op for output sharding` with interleaved input | LM-head input (prefill) and outputs DRAM interleaved on grids < 8x8 | worked-around (config) |
| G4 | decode linears fed by L1 width-sharded norm outputs with no program config (DRAM-sharded configs dropped, Q2) | `Statically allocated dataflow buffers ... clash with L1 buffers on core range [0-0 - 1-0]` (decode FF1 2560 → 9728) | workaround `small_grid_unshard_linear`: unshard input to DRAM, matmul to DRAM, reshard to the requested sharded output (completing a missing shard spec, which ttnn's default matmul cannot do: `Unsupported op for output sharding`) | worked-around (config) |
| G5 | `ttnn.untilize` (multicore, interleaved) of the decode logits `[1,1,32,151936]` | `Statically allocated dataflow buffers ... clash with L1 buffers on core range [0-0 - 0-0]`: the L1 check (`is_enough_space`) sizes CBs for a full 4748-tile row without counting live L1 buffers | workaround `small_grid_untilize_single_core`: `use_multicore=False` (single-core factory caps CBs at half of L1) | worked-around (config) |
| G6 | `models/tt_transformers` `ModelArgs.find_prefill_grid` returns `(rows, cols)` but every consumer (`matmul_config`, `MinimalMatmulConfig`, `VISION_WO_PREFILL_PROGCFG`) reads it as `(x, y)`; invisible on the square 8x8 grid (shared code, not fixed there) | on a 2x1 grid: `compute_with_storage_grid_size (1, 2) must fit within device grid (2, 1)` in vision WO | `_QuasarArgsMixin.find_prefill_grid` returns `(x, y)` | worked-around (config) |

## 2. Simulator and emulator issues — not Quasar op gaps, but they block a target

| # | Issue | Error | Repro | Workaround | Status |
|---|---|---|---|---|---|
| S1 | Any WH op that unpacks fp32 to DEST on ttsim WH: multi-K-block matmuls with `fp32_dest_acc_en=True` (partials reload), fp32 unary ops, fp32 tilize (S2). Single-K-block fp32 dest-acc matmuls pass (PCC 0.99999) | `UndefinedBehavior: tensix_unpacr: unpack_to_dst=0 in_data_format=0 out_data_format=0`. Root cause: after each unpack-to-DEST tile the WH LLK issues a dummy SrcA unpack (TEN-3868 workaround, `cunpack_common.h:964-984` `unpack_to_dest_tile_done`; ZeroWrite2, no data-valid) while fp32→fp32 formats are still loaded; ttsim enforces the ISA rule that fp32→fp32 is DEST-only (`ttsim src/tensix.cpp:3040-3042`). Real WH runs the dummy harmlessly | `tests/e2e/repros/fp32_dest_acc_linear.py` on ttsim WH (aborts; `fp32_dest_acc_linear.py 0`, bf16 dest acc, passes) | ttsim WH runs use `fp32_dest_acc_en=False` | open: fix belongs in tt-llk (SrcA-legal format, e.g. Tf32, around the dummy) or ttsim (exempt the dummy); not a tt-metal matmul bug |
| S2 | `ttnn.from_torch(fp32 → bf16, TILE, mesh_mapper=Replicate)` on ttsim WH | same as S1: WH fp32 tilize correctly unpacks to DEST (as Quasar does since #61421 fixed #57780) but trips the TEN-3868 dummy check | `ttnn.from_torch` of an fp32 tensor to bf16 TILE through a 1x1 mesh on ttsim WH (the e2e's first op, the rope transformation matrix, aborts) | workaround `ttsim_wh_host_cast_fp32_upload`: on a simulator and a non-Quasar device only, cast the torch source to bf16 on the host (until 2026-10-27 `host_cast_fp32_upload`, also applied on Quasar) | open (same root as S1) |
| S3 | `ttnn.scatter` (INT32 index) on ttsim WH; more generally any int32 unpack to DEST on ttsim WH: scatter's index transpose (permute row-major, `transpose_xw_rm_single_tile_size`), an int32 `ttnn.add` | `UndefinedBehavior: tensix_unpacr: unpack_to_dst=0 in_data_format=8`. With only that dummy disabled locally, an int32 transpose with full-range values, an int32 add and both `repros/scatter_merge.py tiny` layouts are bit-exact on ttsim WH, so no value passes through 19-bit SrcA. Not a WH bug | `tests/e2e/repros/scatter_merge.py tiny tile` on ttsim WH (aborts within seconds); `qwen3_vl_ops/test_scatter.py` | WH/BH keep the host merge (`QuasarModelArgs.device_scatter` is on only on Quasar); ttsim BH cannot run it either (`tensix_cfg_wr32: reg=19`, tt-blaze#5898) | open (same root as S1): fix belongs in ttsim (handle ZeroWrite2 before the format checks); WH silicon not yet checked |
| S4 | ttsim WH with the watcher on, on main e414373260f | no error, but very slow: a single `ttnn.add` took more than 10 minutes | e2e on ttsim WH with the default debug settings | `run_wh_bh.sh --debug fast` (watcher off) | open (not investigated) |

| S7 | emu-quasar-2x3: the soc descriptor declares 1 GiB of DRAM per channel, but the emulator backs only 64 MiB; addresses past 64 MiB wrap onto the bottom of the bank.
