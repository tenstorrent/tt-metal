# Qwen3-VL e2e: Quasar gaps and other failures

Gaps that block or shape the Qwen3-VL bring-up on Quasar today: open, not fixable, or with a fix still in review.
Section 1 lists ttnn ops/paths that work on WH/BH but not on Quasar. Base ops that the e2e routes to their
`ttnn.experimental.quasar` ports (`op_overrides.py`) are not listed.

Status values: `open` (not fixed in ttnn), `worked-around` (harness/model avoids it; still open in ttnn),
`unverified` (suspected from precedent, not yet reproduced on Quasar).

## 1. Ops supported on WH/BH but not on Quasar

| # | Op / path | Quasar failure | How found | Repro | Workaround in this branch | Status |
|---|---|---|---|---|---|---|
| Q1 | Matmul / `ttnn.linear` with `fp32_dest_acc_en=True` | Not yet reproduced on Quasar. The llama Quasar e2e forces `fp32_dest_acc_en=False` on every compute config. WH silicon does not need it | precedent (llama32_1b_quasar `test_llama_e2e.py:248-270`) | — | Quasar config uses `HIFI4_FP16` and strips fp32 dest acc from every `compute_kernel_config_*` (`tt/quasar_config.py::strip_fp32_dest_acc`); `ttnn.rms_norm` keeps the fp32 dest acc `models/common/rmsnorm.py` asks for (since 2026-10-27; craq-sim before #419 aborted on its bf16 -> Tf32 unpack, craq-sim#403) | unverified on hardware |
| Q2 | DRAM-sharded weights + `MatmulMultiCoreReuseMultiCastDRAMShardedProgramConfig` (captured layout for decode/lm_head linears) | not attempted: the 2-core emulator grid has fewer cores than DRAM banks on WH (12), and Quasar DRAM-sharded matmul is pending [#58912](https://github.com/tenstorrent/tt-metal/pull/58912) | design decision | — | Quasar config keeps weights DRAM interleaved and lets `ttnn.linear` pick the program (`create_dram_sharded_mem_config` / `dram_matmul_config` overrides) | worked-around (revisit when #58912 lands) |
| Q3 | DRAM capacity: bf16 weights of Qwen3-VL-4B (V=2, T=2) on Quasar's 2 x 1 GiB DRAM (craq-sim `dram_bank_size: 1073741824`, same as `tt_metal/soc_descriptors/quasar_32_arch.yaml`) | `TT_FATAL ... bank_manager.cpp:495: Out of Memory: Not enough space to allocate 6553600 B DRAM buffer across 2 banks` while loading the LM head splits: bf16 token embedding `[151936, 2560]` (~778 MB) + bf16 LM head (~778 MB, untied copy of the same tied weight) + 2 text layers (~0.4 GB) exceed 2 GiB. On WH/BH the captured config uses bfloat8_b and more DRAM; Quasar has no bfp8. Quasar lists `Fp8_e4m3`, but ttnn allows FP8_E4M3 tensors only in ROW_MAJOR (`tensor_spec.cpp:141`), so FP8 matmul weights cannot be created (`tests/e2e/repros/lm_head_fp8.py`) | craq-sim 2x1 e2e, LM head load | e2e on craq-sim | memory placement (not a host op fallback; runs stay PASS-eligible): `QuasarModelArgs.host_embedding=True` keeps the table in host memory and uploads only looked-up rows (`tt/model.py::HostEmbedding`); prefill already embeds on the host; same as the llama Quasar port's `_install_quasar_host_embedding` (there for setup time) | worked-around (placement) |

## 1b. Small-grid limits (any arch; block the 2-core emulator grid)

| # | Op / config | Failure on a 2x1 grid | Workaround in this branch | Status |
|---|---|---|---|---|
| G1 | `ttnn.experimental.nlp_concat_heads_decode` | `work_split.cpp:99: Target number of cores 32 is greater than total number of available cores 2` — one head per core | workaround `concat_heads_decode_small_grid`: device-only deshard → untilize → reshape → pad → tilize (same approach as llama32_1b_quasar `_install_quasar_concat_heads_grid_agnostic`) | worked-around |
| G2 | `tt_transformers` prefill matmul program configs sized for 8x8 (QKV, WO, FF1/3, FF2) | `compute_with_storage_grid_size (8, 8) must fit within device grid (2, 1)`; then `per_core_M (8) exceeds Mt (4)`; then L1 overflow (1.9 MB > 1.5 MB) | `fit_matmul_config`: grid clipped, per-core blocks from real M/N tiles, `in0_block_w=1`, `out_block_h/w` blocking | worked-around (config, not op) |
| G3 | LM head width-sharded input/output configs | prefill: sharded input clashes with matmul CBs in L1; `Unsupported op for output sharding` with interleaved input | LM-head input (prefill) and outputs DRAM interleaved on grids < 8x8 | worked-around (config) |
| G4 | decode linears fed by L1 width-sharded norm outputs with no program config (DRAM-sharded configs dropped, Q2) | `Statically allocated dataflow buffers ... clash with L1 buffers on core range [0-0 - 1-0]` (decode FF1 2560 → 9728) | workaround `small_grid_unshard_linear`: unshard input to DRAM, matmul to DRAM, reshard to the requested sharded output (completing a missing shard spec, which ttnn's default matmul cannot do: `Unsupported op for output sharding`) | worked-around (config) |
| G5 | `ttnn.untilize` (multicore, interleaved) of the decode logits `[1,1,32,151936]` | `Statically allocated dataflow buffers ... clash with L1 buffers on core range [0-0 - 0-0]`: the L1 check (`is_enough_space`) sizes CBs for a full 4748-tile row without counting live L1 buffers | workaround `small_grid_untilize_single_core`: `use_multicore=False` (single-core factory caps CBs at half of L1) | worked-around (config) |
| G6 | `models/tt_transformers` `ModelArgs.find_prefill_grid` returns `(rows, cols)` but every consumer (`matmul_config`, `MinimalMatmulConfig`, `VISION_WO_PREFILL_PROGCFG`) reads it as `(x, y)`; invisible on the square 8x8 grid (shared code, not fixed there) | on a 2x1 grid: `compute_with_storage_grid_size (1, 2) must fit within device grid (2, 1)` in vision WO | `_QuasarArgsMixin.find_prefill_grid` returns `(x, y)` | worked-around (config) |

## 2. Emulator issues — not Quasar op gaps, but they block a target

| # | Issue | Error | Repro | Workaround | Status |
|---|---|---|---|---|---|
| S1 | emu-quasar-2x3: the soc descriptor declares 1 GiB of DRAM per channel, but the emulator backs only 64 MiB; addresses past 64 MiB wrap onto the bottom of the bank. Adding a second 1 GiB channel in the descriptor (local, uncommitted tt-umd-simulators edit) does not help: each channel still wraps at 64 MiB. Usable space above the allocator base (~23 MiB) is ~41 MiB per channel; Qwen3-VL tiny needs ~1.3 GiB, vision-only V=1 ~131 MiB | no error: later uploads silently overwrite earlier tensors. Vision-only V=1 run: the first ~1 MiB per bank (`transformation_mats`, `wqkv_bias`, the first 1056 tiles of block 0 `wqkv`) differs from craq-sim when read back before the forward; the QKV linear then gives PCC 0.37 and every vision stage fails (full V=2/T=2 run: PCC ~0 from `vision.block0.attn`, NaN from `text.layer1`). The same ops with the same weight file and input pass on the emulator when run alone | `tests/e2e/repros/dram_alias.py` on the emulator: X at the bank bottom is overwritten by a write S MiB above it for S = 64/128/256/512, not for 16/32 (craq-sim: never) | since #60444 (in main 2026-10-26) tt-metal clamps each emulator channel to the 64 MiB it backs (~41 MiB usable per bank), so the e2e now fails at weight upload with an OOM instead of wrapping. Trial workaround (open decision, see the README's Run section): a copy of the emulator build dir under a name tt-metal does not recognise (`emu-quasar-2x3-uncapped`, passed as `QWEN_EMU_DIR`) restores the descriptor's 1 GiB; with it the 2026-10-26 e2e ran every stage (1212 device ops, no hang or crash; 203 min of ops after a 13 min Zebu queue) with PCC wrong from `vision.block0.attn` on, accepted as the wrap effect | open: #55417; #60444 makes the limit explicit; the e2e weights (~1.3 GiB) cannot fit 2 x 64 MiB |
