## Context

Fusing MSDA is a net win — it deletes the surrounding stack, multiply and reduction work — but the fused op then accounts for 59.9% of the remaining layer kernel time. Once the surrounding costs are gone it is the dominant component, so kernel-level work there has high leverage.

Two of the three candidate explanations are already answered. A profiling branch measured `CB-COMPUTE-WAIT-FRONT` at 36.1 ms on a 36.0 ms call: the compute kernel was idle for the whole op, waiting on a reader doing coordinate arithmetic in soft float. So the op was not slow sampling and not launch overhead, and the "fused MSDA is ~45% slower than bare `grid_sample`" figure was measuring that reader. Fixing it is #55231.

What is left for this ticket: measure what remains after #55231, and gate #55201.

## Problem

- [BEVFormer uses `grid_sample` rather than the fused op](https://github.com/tenstorrent/tt-metal/blob/main/models/experimental/bevformer/tt/tt_ms_deformable_attention.py#L78-L124), so fused-op behaviour at model shapes is not covered here.
- Kernel cost is entangled with the benefit of deleting the concat/reshape/multiply/reduce tail, so neither can be attributed alone.
- SCA invokes the op once per feature level. Whether that repetition is worth changing the TTNN contract for is unmeasured — and it is the whole decision for #55201.

## Proposed direction

Benchmark at TSA and SCA per-level shapes, including `N=48, Q=2496, P=4, D=32`, **after #55231**:

- Three configurations over the same sampled points: bare `grid_sample` (sampling only), the complete decomposed path (sampling + weighting + reduction — what the fused op replaces), and fused MSDA. Fused is not expected to beat bare `grid_sample`; it does strictly more work. The useful comparison is fused against the decomposed path.
- Four single-level calls against one call over the same total points. This is the decision gate for #55201, not general benchmarking.
- Report `CB-COMPUTE-WAIT-FRONT` alongside op duration. Reading only the total is what produced the earlier wrong conclusion.

## Acceptance criteria

- [ ] All three configurations are reported, each labelled by the work it covers.
- [ ] The four-single-level versus one-multi-level difference is reported separately.
- [ ] Results include warm-up, repeated samples, variance, device/configuration and exact input layouts.
- [ ] The ticket concludes with one of: remaining kernel overhead is significant, so file a minimal reproducer; repeated invocation overhead is significant, so #55201 is justified; or neither, so no upstream change is warranted.
