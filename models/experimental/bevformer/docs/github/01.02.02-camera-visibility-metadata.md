## Context

`bev_mask` records whether each projected BEV query is visible to each camera at each sampled depth. SCA reduces the depth dimension to obtain one Boolean value per camera and BEV query: `visible_per_camera`.

This visibility information has two uses:

- select the visible queries that each camera should process;
- count how many cameras contributed to each BEV query so their outputs can be averaged.

Ticket #55193 first moves the complete rebatch plan out of the layer loop. This follow-up is then a structural cleanup: it gives the device-side visibility reduction introduced by #55195 one producer and three consumers. Moving the code alone is not expected to improve performance.

## Problem

- [SCA reduces `bev_mask` to build per-camera query lists and calculate `max_len`](https://github.com/tenstorrent/tt-metal/blob/main/models/experimental/bevformer/tt/tt_spatial_cross_attention.py#L152-L164).
- [The same reduction is repeated later to count camera contributions](https://github.com/tenstorrent/tt-metal/blob/main/models/experimental/bevformer/tt/tt_spatial_cross_attention.py#L317-L321).
- Both calculations run inside every encoder layer even though [`bev_mask` is produced once per frame](https://github.com/tenstorrent/tt-metal/blob/main/models/experimental/bevformer/tt/tt_encoder.py#L464-L497).
- After the parent tickets hoist planning and move reductions to device operations, leaving these results inside SCA would split ownership between the mask producer and its consumers.

## Proposed direction

- After point sampling, reduce the depth dimension of `bev_mask` once on device to create `visible_per_camera`.
- Store `visible_per_camera` in the frame-level SCA rebatch plan.
- Use the same tensor to build per-camera query indices, calculate `max_len`, and count contributors for output averaging.
- Keep the full `bev_mask` only where depth-level visibility is still required.

## Acceptance criteria

- [ ] `visible_per_camera` is computed once per encoder forward, before the layer loop.
- [ ] Per-camera query indices, `max_len`, and contributor counts are all derived from that shared tensor.
- [ ] The shared results exactly match the existing Torch calculations, including empty-camera and multi-camera cases.
- [ ] No additional device-to-host synchronization is introduced.
- [ ] Existing point-sampling, SCA, layer, and encoder tests pass at their configured PCC thresholds, including PCC >= 0.997 for the base encoder.
- [ ] Profiling confirms that the refactor does not add device operations or measurable runtime.
