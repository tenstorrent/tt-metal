## Context

A fixed camera rig provides a realistic and reproducible geometry for encoder PCC testing. Testing `max_len` reuse across frames additionally requires a sequence whose projection geometry changes in controlled ways.

Parent issue #55187 removes arbitrary random 4x4 `lidar2img` matrices and establishes the valid camera rig. This issue builds on that geometry and must not reintroduce random matrices to vary `max_len`.

## Problem

- After issue #55187, [encoder tests](https://github.com/tenstorrent/tt-metal/blob/main/models/experimental/bevformer/tests/pcc/test_encoder.py#L46-L69) run on a single static camera rig; there is no multi-frame sequence whose projection geometry changes between frames.
- [`lidar2img` determines `reference_points_cam` and `bev_mask`](https://github.com/tenstorrent/tt-metal/blob/main/models/experimental/bevformer/tt/tt_encoder.py#L436-L470), which in turn determine the per-frame SCA `max_len`.
- Random feature tensors do not change `max_len`; repeating one fixed camera geometry therefore cannot test high-water-mark growth, reuse, or reallocation.
- Synthetic geometry cannot establish how quickly the high-water mark stabilizes on real data or its representative steady-state cost.

## Proposed direction

- Build deterministic frame sequences from each supported valid camera rig.
- Apply bounded, reproducible changes to projection geometry, such as camera pose or image-transform variations, instead of generating arbitrary matrices.
- Include sequences where `max_len` stays unchanged, falls below the cached mark, and exceeds it.
- Record reference per-camera visibility counts and `max_len` for every frame so cache behavior has an explicit oracle.
- Keep synthetic cache-correctness validation separate from measurements that require a representative dataset.

## Acceptance criteria

- [ ] Each supported camera rig has a deterministic multi-frame sequence generated from valid projection matrices.
- [ ] Repeating the same seed produces identical frame metadata, visibility counts, and `max_len` values.
- [ ] Test sequences cover high-water-mark initialization, reuse, monotonic growth, and reallocation.
- [ ] Expected per-camera visibility counts, per-frame `max_len`, and the resulting high-water mark are recorded for every frame.
- [ ] No frame allocates less rebatch space than its observed `max_len`.
- [ ] Encoder PCC remains at the configured thresholds for every generated frame.
- [ ] Synthetic results are not used to claim representative stabilization, memory use, or steady-state cost; those measurements remain blocked until representative data is available.
