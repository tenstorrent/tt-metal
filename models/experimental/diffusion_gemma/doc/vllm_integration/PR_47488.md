## Title

`[Model-Bringup] Block-granular runner + scheduler for DiffusionGemma (#47488)`

## Motivation

DiffusionGemma 26B-A4B-it is a discrete **text-diffusion** LLM (`DiffusionGemmaForBlockDiffusion`).
It does not generate token-by-token: per 256-token canvas it runs an on-device denoise loop
(Gumbel-max → entropy-budget accept → renoise, ≤48 steps) inside the tt-metal model forward and
**commits a whole 256-token block per decode step**.

Two places in the TT plugin hard-assume one committed token per decode step:

1. **Runner** (`model_runner.py`) — asserts the sampled-id tensor is `[num_reqs, 1]`, collapses the
   device sample to a single token, and advances host token state by exactly 1. A 256-token canvas
   trips `RuntimeError: shape '[1]' is invalid for input of size 256` (reproduced live).
2. **Async scheduler** (`scheduler.py`) — `AsyncScheduler` reserves exactly one output placeholder
   per scheduled step (`_update_after_schedule: num_output_placeholders += 1 + spec`) and asserts
   `num_output_placeholders >= 0` after subtracting the committed count. Any step committing more
   than one surviving token underflows and kills the engine (`async_scheduler.py:53 AssertionError`,
   reproduced live on an ordinary completion, not only under `ignore_eos`).

The whole change is keyed on `num_out_tokens = sampled_token_ids.shape[1]`, so **`N == 1` is
byte-identical to today's behavior** and no autoregressive TT model changes. It also registers the
architecture. Note vLLM v1 core already supports a per-request token *list*
(`update_from_output → _update_request_with_output` appends all and trims at the stop point), so a
single 256-token block satisfying `max_tokens <= 256` needs **no** scheduler change — only
multi-block does.

## What each file changes

### `platform.py` — register DiffusionGemma
`register_tt_models()` maps the HF arch `DiffusionGemmaForBlockDiffusion` (plus the
`DiffusionGemmaForCausalLM` / `TT*` aliases) to
`models.experimental.diffusion_gemma.tt.generator_vllm:DiffusionGemmaForCausalLM`, via the existing
`_register_model_if_missing` helper — additive, cannot shadow an already-registered arch.

### `model_runner.py` — accept and emit N-token blocks

| edit site | where (fork head `6b4a3a7`) | change |
|---|---|---|
| `sample_tokens` DP-pack | :2252 | accept `[num_reqs, N>=1]` instead of asserting `shape[1] == 1` |
| `_get_output_tokens` | ~:2757 / :2760 | keep the full `[sz, num_out_tokens]` via `reshape(sz, -1)` instead of `reshape(sz)` |
| `_build_runner_output` | :2839 | emit all `num_out_tokens` per request in the `ModelRunnerOutput` token list |
| `_apply_sampled_tokens_to_state` | :2887 | drop the `== 1` assert; write `[start : start + N]` into `token_ids_cpu`, advance `num_tokens` by N, extend the output list by N in **both** the sync and captured/async paths; context bound becomes `start_idx + N <= max_model_len` |

**MEASUREMENT TRAP:** an earlier scope table for the same four concerns was written against the
stale ghcr image and reads `model_runner.py:2471` (`assert num_out_tokens == 1`), `:2378`
(`view(sz,1)`), `:1878-1880` (`shape[1]==1`), `:2437`/`:2444` (one-token output lists),
`:2479-2489`/`:2508-2518` (`+1` advances) and `:931-934` (decode read of the single last token).
**A scope table without its plugin revision is unusable** — the two revisions' line numbers differ.

The per-token device-logprobs path still collapses to `[sz]` and is now explicitly guarded with
`assert next_token_ids.shape[1] == 1` when logprobs are requested; block-diffusion serving requests
no logprobs.

### `scheduler.py` — N-token async accounting
`TTScheduler._update_request_with_output` calls the **grandparent**
`Scheduler._update_request_with_output` for the append plus stop-trim, then replaces only the
placeholder / `num_computed` math: clamp `num_output_placeholders` at 0 instead of asserting;
advance `num_computed_tokens` by the extra `n - 1` so it keeps lagging committed output by exactly
one position (the invariant the running-loop scheduler math needs to schedule the next decode step
with `num_new_tokens == 1`); skip the prefix-cache `cache_blocks` bookkeeping for `n > 1`. For
`n == 1` it is byte-identical to `AsyncScheduler._update_request_with_output`, including the
`discard_latest_async_tokens` early-return.

Device QB2 `bh-qbge-06`, 4x Blackhole (P150x4), TP=4, `(1,4)` mesh; vLLM built fresh on host against
the current tt-metal `ttnn` (`VLLM_TARGET_DEVICE=empty`), branch `dev` @ `6b4a3a7`, this plugin as
the editable `vllm-tt-plugin` package. Import sanity:
`flock /tmp/dg-mesh.lock timeout 300 ... VLLM_TARGET_DEVICE=empty python -c "import vllm; import
vllm_tt_plugin"` → `PLUGIN_OK`.

Both blockers were reproduced live and then fixed live; a request with `ignore_eos` +
`max_tokens 512` then emitted **two real committed 256-token denoise blocks** —
`prefill block0 32→288 (35 steps)` then `decode block=1 288→544 (48 steps, stop=False)`, position
`32→288→544 = cache_len + 2x256`, 512 committed tokens, HTTP 200 — alongside a 7-request live
OpenAI suite and a device-gated `pytest tests/test_serving_block_contract.py` → 7 passed. Full
evidence and per-block metrics: `models/experimental/diffusion_gemma/doc/vllm_integration/`
([README](README.md), `serving_test_suite.json`, `live_vllm_serving.json`).

Launch flags that mattered: `--block-size 64`, `sample_on_device_mode: all`,
`enable_model_warmup: false`, `--generation-config vllm` (drops the model's `max_tokens=256` default
cap for multi-block). The adapter-side `stop_token_ids=[]` session-stop deferral and
`--generation-config vllm` live in the tt-metal adapter/launch docs, **not** in this plugin PR:
without the deferral a committed block containing an EOS forced `session.finished=True` and the next
decode step returned synthetic `256 x stop_id` padding, so a "2-block" request returned 512 tokens
with only ONE real block.

## Risk / compatibility

- **AR parity** is the primary regression-safety claim: every changed path is keyed on `shape[1]`,
  and for `N == 1` the runner writes/advances/emits exactly as before while the scheduler override is
  byte-identical to `AsyncScheduler`. **REVIEWER ASK:** worth a spot-check on a Llama/Qwen decode run.
- **No silent corruption:** DiffusionGemma owns its own KV and position (`page_table=None`,
  contiguous model cache), so vLLM's `num_computed_tokens` governs only stop/bound/bookkeeping — a
  mis-count can only mis-schedule (caught by the live block-count checks) and can never silently
  corrupt generated tokens.
- **Logprobs:** the device path is explicitly asserted to 1-token; AR logprobs unchanged.
- **Prefix caching:** `cache_blocks` is skipped only for `n > 1`, and APC is already force-disabled
  for sliding-window models on this platform.
- **Registration:** additive; the adapter target module lives in tt-metal, so the arch is only
  usable when that PYTHONPATH is present.
- **OUT OF SCOPE (follow-ups):** the cache-ownership half of #47488 (paged cache + per-request block
  tables for concurrent batched serving) and batched canvas decode #47557. This PR is
  `--max-num-seqs 1`, one contiguous model cache per active sequence.
