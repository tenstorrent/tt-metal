Gemma4 packed prefill under load — 2026-10-08

Blackhole Galaxy · CP8/TP4 · Gemma4-31B-it · 60 decoder layers

Measured conclusion

The current packed implementation is slower under load. Four complete 256K prompts took 70.89 s packed with DRAM activations versus 28.07 s with regular 8K chunks (2.53× the time). The default packed L1 configuration cannot run four full 8K chunks.

  • Regular 8K is the best full-context baseline: 37,702 useful tokens/s, versus 33,272 for 4K and 21,930 for 2K.
  • Even when four 2K final tails fill an 8K pack, packed/native-8K time is 1.29× early, 1.15× mixed, 1.07× late. The relative gap narrows at long context because both paths still run 8K attention for each request.
  • For mixed-history 2K tails, the first request completes in 67 ms with native 2K, 131 ms with native 8K, and 917 ms packed. Packed outputs wait for the whole batch, including its long-history requests.
  • Shape changes require another trace capture even for previously compiled shapes. Returning to four 2K tails costs 10.20 s for the first call, versus 0.67 s for a resident replay.
  • The underfilled 1K + 32-token batch is a small exception: at long history, packing takes 588 ms versus 629 ms for native 8K. Native 2K still takes only 239 ms. These tiny tails fill only 13% of the 8K target; this is not a fully loaded batch win.

The data supports keeping regular 8K as the current throughput baseline. Packing's tokenwise savings are outweighed by the current fixed-FP32 reductions, CP redistribution, and padded attention work. The controls below separate measured causes from possible improvements.

What was measured

The three requested canonical runs process a complete 262,144-token text prompt with native ring reductions, one KV slot, and the original demo's direct trace replay. The loaded study uses the runtime API with four allocated 256K slots in every mode, comparing identical useful request lengths and prefixes against regular 2K, 4K and 8K paths plus an independent fixed-FP32 control. All histories are populated by model execution. No external server, fabricated valid-length-only history, or prefix sharing is used.

Regular paths use round-robin chunk scheduling. Repetitions rewrite fixed boundaries and restore host bookkeeping; they do not simulate request arrivals.

Shorter-than-8K packed chunks are final: they model short prompts or final tails, not arbitrary 2K progress steps in an ongoing 8K-geometry request. Four ongoing requests therefore contribute 32K useful tokens. All packed runs use fixed-order FP32 TP reductions. The original GPU-accuracy qualification gap remains; this report measures performance, not model quality.

Default L1 storage failed at the MLP gate projection for four full packed chunks, both after smaller shapes and in a fresh process. Full packed batches explicitly use GEMMA4_ACTIVATIONS_DRAM_ONLY=1; every such plot marks the fallback. All smaller matrix cases use default L1. This is a configuration limitation, not a measured default-path throughput number. See failure evidence.

3. Does packing improve throughput?

Why measure this: Separate comparison with the current 8K default from comparison with an appropriately chosen native chunk size.

What it shows: Cells are packed batch time ÷ native batch time. Below 1× favors packing (blue); above 1× means packing is slower (red). Four full packed chunks require the measured DRAM fallback. The best regular chunk is selected separately for each workload; changing chunk size within a live request would require compatible cache geometry, and is not a free scheduler decision.

4. What if most requests are late in their context?

Why measure this: Hold useful tokens, number of requests, and packing shape fixed; vary only how many prefixes are long.

What it shows: Moving one request from start 0 to 248K adds about 166.5 ms in the packed path versus 54.2 ms with native 2K chunks (endpoint-average increments). Prefix changes reuse the resident trace, so this increase is execution work, not recapture. Mixed batches pay approximately the sum of their separate history costs, not the longest history for every request. Per-request 8K attention still executes on the packed path, including padded queries; shared projections do not eliminate this history-dependent work.

5. Where does the extra cost come from?

Why measure this: Use a single full request so packing saves no rows, then isolate the stable-reduction choice from the remaining packed machinery.

What it shows: The first-to-second difference measures replacing native TP ring reductions with rank-ordered FP32 additions: 176 ms extra at the early prefix. The second-to-third difference includes CP redistribution, splitting/concatenating, and the packed cache/metadata path. For four early 2K tails, packing takes 668 ms versus 1229 ms with independent fixed-FP32 execution, but the default native path takes only 520 ms. The saving against the FP32 control is real; it does not establish a win over the default. This is an end-to-end ablation, not a kernel-profiler attribution. Numerical equivalence to GPU is not established by this performance study.

6. Does packing help individual request latency?

Why measure this: Avoid mistaking aggregate throughput or batch time divided by request count for actual request completion latency.

What it shows: All requests are ready at time zero. Native paths visit active slots round-robin by their chunk size; packed outputs become available only after the entire graph completes. Earlier requests therefore inherit the long-history work of other requests in their packed batch. Arrival queueing and downstream transfer would add further latency.

7. What happens when shapes vary under load?

Why measure this: Revisit shapes whose kernels have already run, after their traces have been released.

What it shows: These are warm-process shape switches, not weight loading. Only one graph is resident, so returning to an old shape still triggers warmup/capture. Fixed-shape replay throughput is an optimistic bound for a heterogeneous queue; frequent shape changes can dominate service time.

8. Does the result hold for four complete long prompts?

Why measure this: Measure a real continuous prefill stream instead of extrapolating fixed-prefix tail measurements.

What it shows: Each path runs all four prompts from 0 to 256K with real contiguous KV writes. Native 8K took 28.07 s (37,353 useful tokens/s); packed with DRAM activations took 70.89 s (14,792 tokens/s). Native 8K with DRAM took 29.29 s; independent fixed-FP32 execution with DRAM took 51.55 s. These controls separate storage placement and reductions from the remaining packing costs. This is one complete stream per mode, excluding initial warmup/capture. The packed default L1 configuration failed before this stream could run.

What to investigate next

First reduce the fixed-FP32 collective cost without losing the required numerical behavior, and measure attention with true query lengths while preserving the existing cache mapping. Then test less expensive CP redistribution and bound the lifetime of MLP slab outputs so full batches fit. Finally evaluate a small set of reusable trace shapes. These are hypotheses suggested by the controls, not optimizations measured here.

Reproduce and interpret

reproduce.sh contains the exact model/cache environment, three canonical nodes, five loaded modes, four continuous streams, and report generation. Run it from the repository root with the Python environment activated and exclusive access to the device. GEMMA4_LOAD_CASES can filter scenarios for exploratory runs; this report requires all 19 scenarios and five repetitions. OMP_NUM_THREADS=16.

Implementation measured: commit 8fc27f0c760, plus the accompanying benchmark harness; production model code was unchanged during the study. Device tests ran sequentially on one Blackhole Galaxy. There is one canonical run per chunk size, five fixed-boundary replays per loaded cell, and one full continuous stream per mode. Min–max whiskers describe those samples, not a statistical confidence interval. The native 2K/4K comparisons require that cache geometry from the start of the request; they do not imply free switching at a final tail. The study excludes arrival queueing, output download and external KV migration, so it does not establish server-level throughput or latency.
