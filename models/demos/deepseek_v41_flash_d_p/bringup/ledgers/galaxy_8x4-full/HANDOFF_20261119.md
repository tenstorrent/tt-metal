## 1. FAST ITERATION IS THE FIRST RULE

The owner spent this whole day waiting on slow loops. Treat iteration time as the main constraint of every step:

- **Never load what you do not need.** Before any load ask: can a piece answer it (CPU only, data already measured,
  one layer, the layers the question touches, one head, a row slice, a synthetic table in the same format, a short
  history)? Iterate on the piece in seconds; the full model / full tables only once, for the final measurement. Write
  the one-line reason before any full load.
- **Every device open leaks 10-27 GiB of host RAM** (driver) until a reboot, and a model load costs 2-4 min (+6 min with
  the engram device tables). Measured today: a pure measurement through an orchestrator agent took ~1 h and 6 model
  loads; the same measurement run directly on the resident runner took 5 s to 5 min.
- **Use the resident runner for everything on the device**, op tests and probes included:
  `python -m models.demos.common.bringup.resident start|status|submit|stop --spec <spec>`;
  `submit --cmd "<safe-runner command(s), && joined>"` runs them in the held process (one load; later requests reach
  their first chunk in ~1-2 s). A direct `scripts/run_safe_pytest.sh` makes the runner step aside = a fresh device
  open. Mark new test files `BATCH_SHARED = True` (+ `BATCH_ITEM_VARS` for per-run env, `BATCH_LAYERS`).
- **Measurements: run them yourself on the runner**, not through an orchestrator agent (agent overhead 30-40 min).
  Agents only for code changes, and they too submit to the runner (bringup-engineer.md rule).
- Make A/B switches **call-time** (read per chunk; listed in `bringup/hooks.py batch_call_settings`), so both sides
  run in one load. A load-time switch = a reload per side.
- New kernels hung the box twice today (bad L1 pointer; unbounded waits): bounded waits, every awaited semaphore
  signalled, NOC writes inside buffers, fabric payloads <= 6208 B; smallest shape first.
- Judge perf by the device profile (walls are noisy by several ms); keep a change only at >= 1 ms device a chunk.

## 5. Facts that matter for packing

- A request of ~1.6k new tokens today pays a whole 5120-token chunk (~80 ms): ~19k new tok/s per request; packing
  is what turns the 66-68k packed-equivalent into real per-request throughput.
- Chunk geometry on 8x4: the chunk must be a multiple of 1024 (32 tile rows on every chip, DS41-297); 8192 measured
  +15 % tok/s over 5120 at ~142k (X.8), host time grows with the chunk (+7 ms).
- Per-slot served state the model already reads from tt-d-gen's caches every chunk (compressed KV, index keys, window
  snapshot); the engram 3-id tail and the 128-row window replay need tt-d-gen asks 1/2 (drafts in
  /data/dnijemcevic/bringup/handoff_20261118/drafts/tt_d_gen_asks.md). A packed chunk mixes slots: every per-row
  quantity (positions, slot, write_start, engram tail, window) becomes per-segment.
- Exposed host ~13-14 ms a chunk at <= 256k (layer-2 launches ~4.9, chunk end ~3, engram ~2-5) shrinks with context.
