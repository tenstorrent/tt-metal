# Llama-3.1-8B-Instruct Prefill (`llama_3_1_8b_d_p`)

Long-context **prefill** for Llama-3.1-8B-Instruct on a **Blackhole Galaxy (8×4)** at **SP=8 × TP=4**,
on the model-agnostic `models/demos/common/prefill` engine. Bring-up follows
`.claude/skills/prefill-model-bringup/SKILL.md` and **ends at P2** (chunked prefill); serving,
KV migration, perf tuning and decode are out of scope.

**Weights are REAL**, not synthetic: `/mnt/models/meta-llama/Llama-3.1-8B-Instruct` (bf16,
unquantized, 4 safetensors shards + index, 32 layers). Resolved per recipe §4 step 0 from the shared
store — no download, no HF token. No golden trace existed for this model, so one is generated by
`scripts/generate_golden_kv_cache.py` and written beside the weights.

## The four things that cost real time

Each of these fails **silently** — plausible numbers, nothing raised — and each is now pinned by a
test so the next bring-up inherits the knowledge rather than the bug.

### 1. Two KV heads per chip

`num_kv_heads // tp = 8 / 4 = **2**`. Every prefill package on this engine has exactly **one**
(minimax_m3: 4 kv heads at TP=4; gpt_oss_d_p: 8 at TP=8), and their KV-cache code hardcodes the
literal `1` while their *write* docstrings describe a parametrized `n_kv_local`. The per-chip cache
here is `[num_users*num_layers, 2, seq_local, 128]`.

`update_padded_kv_cache` turns out to be genuinely head-agnostic on this path — its single-head
constraint fires only when `tp_axis` is set, which K/V do not use. **Verified**, not assumed:
`test_kv_cache_gqa_sp_vs_ref.py` writes and reads back all 8 heads at PCC 0.99997 with 2 per chip.

### 2. The RoPE convention: Meta tables, permuted q/k weights

`rotary_embedding_llama` and `rotary_embedding_indexed` consume **Meta interleaved** cos/sin
(`[c0, c0, c1, c1, …]`), which is what `tt_transformers`' `RotarySetup` builds. The HF checkpoint and
the reference are **half-split** (`emb = cat(freqs, freqs)` + `rotate_half`). Feeding HF tables to
these ops measures **PCC 0.75** — plausible output, silently wrong.

Fix: permute `q_proj` and `k_proj` weight rows HF→Meta at load (`utils/weight_conversion.py`).
Nothing else changes — attention scores are a dot product over the head dim and are invariant under
a permutation applied to both operands, while `v_proj` and `o_proj` are never rotated. The
alternative (HF tables + `rotary_embedding_hf`) has no counterpart for `rotary_embedding_indexed`,
which P2's chunked path needs.

**Consequence:** the on-device KV cache stores **K in Meta head-dim order**. Every comparison
against an HF-order golden — including the golden trace — must permute one side. Getting it wrong
reads as *uncorrelated* (PCC 0.008), not as a near miss.

### 3. RoPE tables must be SP-sharded, not replicated

SP row `r` holds sequence positions `[r·seq_local, (r+1)·seq_local)`, so it needs exactly those rows
of cos/sin. `rotary_embedding_llama` has **no prefill-mode check** that the table length matches the
input, so a replicated full-length table silently rotates every row at positions `[0, seq_local)`.

The failure is asymmetric and that asymmetry is the useful part: the whole-model **logits** check
still read PCC 1.0 with replicated tables, while the per-layer **KV** check dropped to 0.59. That is
why the KV comparison, not the logits, is the artifact this bring-up is graded on.

### 4. `fp32_dest_acc_en` on the ring SDPA

The donors pin the ring SDPA to `fp32_dest_acc_en=False`, and the recipe warns that this constraint
is local to the ring cache-read op rather than a property of SDPA. Measured here:

* On the **cache-read** path it is a hard kernel constraint, not a preference — `True` fails with
  `kv_actual_isl requires the ring-joint streaming compute path; the compute_common.hpp path
  selected by fp32_dest_acc_en=true is not supported`. fp32 dest accumulation selects a compute path
  that cannot do the KV-pad rotation chunked prefill depends on.
* On the **no-cache** path it is allowed and worth **+7e-5** PCC.

So `False` costs nothing measurable and is required for P2 to work at all. Every projection matmul
and the plain SDPA still use HiFi4 with `fp32_dest_acc_en=True` (the bring-up default).

> An earlier note in this file attributed a 0.9899 attention PCC to the ring SDPA's bf16
> accumulation. That was wrong: the cause was finding 3 above, and with SP-sharded rope tables
> attention measures **1.000000**.

## Exploration (stage E): what was borrowed, and the envelope it was measured at

Candidates were gated on `ADAPTER_PATHS` in `models/demos/common/prefill/adapter.py` (a package not
in it has never run on this engine) and then on the spec's target hardware. Survivors: `minimax_m3`,
`gpt_oss_d_p`, and the `deepseek_v3_d_p` family. `mistral_3_5_d_p` is not in the registry and the
package is empty; `gemma4` is not in the registry either (source for the LM-head *test shape* only).

Ranked by attention family → MLP density → checkpoint quantization:

1. **`minimax_m3`** — measured at **hidden 6144, head_dim 128, chunk 5120, sp8×tp4 on a BH Galaxy
   8×4**. Same target hardware, same mesh orientation, same SP×TP, same chunk size, same head_dim.
   Its **dense layers 0-2 are GQA + `ring_joint` SDPA + dense SwiGLU MLP** — structurally the same
   block as a Llama layer. Primary source for every part.
2. **`gpt_oss_d_p`** — GQA, so the right *cache count*, but hidden 2880, head_dim 64, chunk 1024,
   sp4×tp8 (transposed mesh), with sinks and sliding-window alternation. Math-only source.
3. **`deepseek_v3_d_p`** — MLA + MoE. Imported, never copied: the NdShard spec behind
   `init_kvpe_cache`, `update_padded_kv_cache`, `rotary_embedding_indexed`, `rotated_chip_positions`,
   `get_num_dram_banks`, and the whole-model reference cache helpers.

Per-part records with what was rejected and why are in [`bringup_log.jsonl`](bringup_log.jsonl)
(`ev: "source"`).

| Part | Source | Structural (copy + verify) vs re-derived |
|---|---|---|
| Weight loading | `minimax_m3` `tt/model_config.py`, `utils/substate.py` | safetensors walk + prefix filter + single dtype exit copied; loader body fresh (plain `LlamaForCausalLM`, keys already match the reference) |
| Dequant | **none needed** — unquantized bf16 checkpoint | — |

| Embedding | `minimax_m3/tt/parallel_embedding.py` | both sharding modes copied; vocab 128256 needs no padding (16032/SP row, 32064/TP col) |
| MLP | `minimax_m3/tt/dense_mlp.py` | col/row-parallel split + CCL tail copied; **activation replaced** — plain SiLU SwiGLU, not clamped swigluoai |
| Attention | `minimax_m3/tt/attention/` | head split, projection sharding, o-proj CCL tail, `ring_joint` call copied; **q/k permutation added** |
| RoPE | `minimax_m3:create_rope_setup` + `tt_transformers/tt/rope.py:RotarySetup` | `rope_scaling_model_factory` already carries llama3 scaling; full-width rotation, so the donor's partial-rotary slice/concat is never entered |
| KV cache | `minimax_m3/tt/attention/kv_cache.py` — **one** package for all five coupled roles | layout copied verbatim; `index_k` dropped, `n_kv_local` 1 → **2**, capacity rounded up to a whole chunk |

reason rather than by inheritance**: the donor was measured at head_dim 128 and chunk 5120 on sp8,
giving chunk_local 640 — and this spec's head_dim and chunk_size are the same, so chunk_local is the
same 640. Change either and they must be re-derived.

## Status

**E ✅ → D1 ✅ → D2 ✅ → D3 ✅ → M1 ✅ → M2 ✅ → M3 ✅ → P1 ✅ → P2 ✅**

Bring-up complete. Both graded stages ran at **full depth (32 layers), full width, real
Llama-3.1-8B-Instruct weights**, sp8 × tp4 on the Blackhole Galaxy, **linear** fabric, per-layer KV
against the CPU golden trace `golden/synthetic_5120b`:

| Run (32 layers, 5120 tok) | min K | min V |
|---|---|---|
| **P1** — one-shot, 1 × 5120 | **0.994016** | **0.980986** |
| **P2** — chunked, 2 × 2560, ring cache-read | **0.993996** | **0.980725** |

Both are above `pcc_lower_bound` 0.85 on every one of the 32 layers. K clears `pcc_target` 0.99; V
sits between target and bound (see below). Throughput 156 tok/s one-shot, 81 tok/s chunked (first
runs, kernel compilation included; perf tuning is out of scope).

**P2's acceptance criterion is that chunked matches one-shot, and it does**: the two rows agree to
2.0e-5 on K and 2.6e-4 on V, and layer by layer they match to four decimal places. The chunked run
attends the prefix that earlier chunks left in the block-cyclic cache and reproduces the KV of a
single pass over the whole sequence.

One caveat, stated rather than buried: this chunked run used a **2560-token chunk, not the spec's
5120**. A 2-chunk run at the spec's chunk size needs a 10240-token golden trace, and a full-depth
fp16 CPU forward at that length takes hours (see *Known gaps*). Using P1's own 5120-token trace
instead makes the P1↔P2 comparison above *exact* — same tokens, same golden — and exercises more
chunk boundaries per token, but it is not the production chunk size. The spec-exact 2 × 5120 run is
the one remaining confirmation; the shipped code defaults to the spec's 5120 either way.

**Why V is below `pcc_target`, and why it is accepted.** Not the bf8 KV cache: re-running P1 with a
bf16 cache gives min K 0.993981 / min V 0.980903 — identical within run-to-run noise, so cache
quantization costs essentially nothing. The gap is **error accumulating through the residual
stream** at the spec's bf8 weights and bf16 activations. It is depth-shaped rather than
layer-specific: V is 1.000000 at layer 0, bottoms out at ~0.981 around layers 12-13, and recovers to
0.994 by layer 31. Every knob the spec leaves open was tried, and the dtypes themselves are
spec-bound. For scale, the donor this package borrows from reports min 0.96289 K / 0.87884 V across
its 60 layers.

`PREFILL_KV_DTYPE` exists only for that attribution; any number it produces is labelled a
diagnostic, not a grade.

### Fabric topology

This Galaxy is a plain **8×4 grid, not a torus**: `FABRIC_1D` +
`single_bh_galaxy_mesh_graph_descriptor.textproto` + `ttnn.Topology.Linear`, selected in
`conftest.py` before the cluster initialises.

**The torus is unavailable here, and that is an `env` finding rather than a blocker.** Every torus
mesh-graph descriptor shipped for a Blackhole galaxy spans multiple galaxies or hosts
(`dual_bh_galaxy_torus_xy`, `32x4_quad_bh_galaxy_torus_xy`, `bh_galaxy_sp4_torus_xy`, …), so
selecting one fails at control-plane init with `Mesh 0 has 4 host ranks, expected 1`. A single-host
8×4 torus descriptor does not exist. `LLAMA31_8B_FABRIC_TORUS=1` therefore raises rather than
silently running linear.

**Every number below was measured on the LINEAR fabric.** Correctness is topology-independent;
collective *cost* is not, so linear and torus numbers would not be comparable.

## Known gaps

- **The spec-exact chunked run (2 × 5120) is outstanding.** P2 is measured at full depth with a
  2560-token chunk; the 10240-token golden it needs takes hours of CPU to generate. See the P2
  section — the shipped code defaults to the spec's 5120 chunk regardless.
- **V is below `pcc_target`** (0.9810 vs 0.99), attributed and accepted — see the P2 section.
- The golden trace is generated by this package; none existed on the shared store.
  (`/mnt/models/meta-llama/llama-3.1-8b-cache/llama31_decoder_L*.pt` are per-module `.pt` goldens
  from an unrelated earlier effort — no `metadata.json`, no `kv_cache/layer_N.safetensors`.)
- **The cached K is in Meta head-dim order.** Any downstream consumer that expects HF order — a KV
  migration to a decode engine, for instance — must permute. Follow-on, not a bring-up gate.
- **The CPU golden generator is the slowest thing in the bring-up.** fp16 on CPU parallelises
  poorly (~4 of 64 cores), so a full-depth 5120-token trace takes ~50 minutes and 10240 several
  times that. Generate it detached (`setsid`) and without a `timeout`: a 50-minute cap killed the
  first attempt outright, and the trace is only written at the very end, so a kill loses everything.
  If this becomes a recurring cost, computing the reference in fp32 and casting to fp16 on write
  would be far faster and no less accurate — but it would deviate from the recipe's fp16 convention,
  so it is flagged here rather than done unilaterally.
- **`/opt/venv` does not survive a box reallocation.** Mid-bring-up the venv was reprovisioned:
  `torch` and `transformers` were still installed but the editable `ttnn` was gone, so `import ttnn`
  silently resolved to the repo's `ttnn/` directory as an empty namespace package and
  `ttnn.SDPAProgramConfig` vanished. `ttnn.__file__ is None` is the tell. Re-run
  `uv pip install setuptools_scm==8.1.0 && uv pip install -e . --no-build-isolation`, and check
  `check_runtime_env.sh` after any session restart before blaming a code change.
- Top-1 / logits agreement with HF **on device** is explicitly not a bring-up gate (recipe §8); KV
  PCC is the proxy. Note the *reference* does agree with HF on argmax (above).
- Serving (adapter manifest, two-process runner) and KV migration are a separate follow-on. This
  package is not yet registered in `ADAPTER_PATHS`.
