## (a) U=8 (B=32) TT_THROW "Statically allocated circular buffers ... clash with L1 buffers"
Reproduced in demo/text_demo.py (prefill_128_b32, DSV41_LAYERS=0-1/0-3, host .46, logs prefill2_u8p3_a.log / u8p4.log): grouped moe_compute (T=256) in layer 0's first prefill MoE: L1 buffer at 615616 vs static CB end 685584;
L1 free 1,405,312 B before, 784,128 B after the op's own ~650 KB L1 output. It does NOT reproduce in tests/test_prefill_scen_device.py at U=8 (40 layers, G=8 + colsplit passed earlier, prefill2_u8_smoke3.log), so the extra L1 need is specific to the demo/dsv41_model build at 8 users/row;
I did not find the U-dependent term (moe_compute's config does not depend on U; 0 live L1 tensors are reported at failure).
IMPORTANT finding: catching the TT_THROW and falling back is NOT possible: the failed op has already allocated its L1 output, which leaks, and the next L1-heavy op (SDPA, 1.3 MB static CB) clashes too (prefill2_u8p3_a.log). So the guard is static:
`DSV41_MOE_G` default "auto": G=8 only for users-per-row in GROUPED_USERS = (1, 4, 16) (the verified sizes); every other U uses the T=32 path (the old behaviour, no throw). Explicit DSV41_MOE_G=1/2/4/8 overrides for all U (=8 at U=8 will throw until the cause is fixed).
Verified after the guard: demo prefill_128_b32, 4 layers: TTFT 372 ms, decode 91 ms/token, passes; scen test 40 layers U=8 (prefill2_u8_40.log): ISL 128 TTFT 2.77 s (1479 tok/s), ISL 1024 chunk 256: 21.06 s (1556 tok/s). Cost of the guard at U=8: ~2x slower than the G=8+colsplit scen run (1.42 s / 10.59 s).
4 layers: U=16 (G=8, colsplit) ISL 256/1024: 1.00 s / 3.12 s; U=2 (G=1) 0.25 s / 0.73 s: both pass.
## Which shapes use what (after this diff)
* G=8 grouped MoE (T=256 front-end): users/row U in {1, 4, 16}. Within those: COLSPLIT when U*C % 256 == 0: U=4: every chunk (C multiple of 128 -> 512...), U=16: every chunk, U=1: C = 256, 512, 1024, ... (C=128 and C=384/640/... fall back).
  Replicated (no colsplit) fallback inside G=8: the chunk count U*C/32 not a multiple of 8 (U=1, C=128: 4 chunks) -> the T=32 front-end `pmoe.g1` (same experts, shared small buffers); a count that is a multiple of 8 but U*C%256!=0 cannot occur.
* T=32 path (old behaviour, G=1, no colsplit): U = 2, 3, 5, 6, 7, 8, 9..15, 17+ (incl. U=32 / B=128), and anything with DSV41_MOE_G=1 or DSV41_COLSPLIT=0 (COLSPLIT=0 forces replicated, G stays grouped for the allowed U).
