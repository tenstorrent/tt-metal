# DeepSeek-V4.1-Flash: optimizations

This file is the record of the changes that **improved a measured number** for this model on Blackhole Galaxy (4x8 mesh, branch `ssinghal/dsv4p1`). Each entry says what changed, why it helps, what was measured before and after (setting, host, how), the correctness gate, where the code is (file, commit) and where the number comes from (log or note). A change that did not improve a number, or failed its correctness gate, does not get an entry (it can appear under "Tried, not kept" in one line). Future ideas that are not done stay in `FUTURE_WORK.md`.

How to add an entry: measure before and after on the same host and settings (4 concurrent cold prompts for TTFT, GSM8K chat prompts for decode, traced clock for kernels), keep the correctness gate (logits PCC, needles, GSM8K), commit the change, then add a row to the table of its area and a block under "Details" with the log paths. The optimization loop (`tt-opt`, `dsv4-logs/ttopt/`) writes a standalone `keeps/NN.patch` for every kept edit; its entries go in section 8.

Conventions. `L` = `/mnt/tt-data/ssinghal/dsv4-logs`, `D` = `models/demos/blackhole/deepseek_v41_flash`. Source tags in the Details: **[log]** the number was read in the raw log named; **[doc]** the number is in a note of this directory and was not re-read in a raw log; **[commit]** the number is only in a commit message. Numbers are copied, not rounded. Where two sources disagree both are given. B is the batch (users), k the number of drafted tokens, "batch TTFT" the time until every user of the batch has its first token.

Entry counts: server and scheduling 12, prefill 17, decode 6, speculative decoding 10, sampling 3, memory/DRAM and tracing 15, tt-opt 0 (section 8.1-8.10 are lever blocks, 8.7-8.10 are the B=8 levers), branches not merged 4, tried and not kept 17, known regressions 13. Items that are not accepted yet are not entries: they are listed in "Pending (not in this release yet)" with owner branch and status only. Paths starting with `tt/` or `tests/` are under `D`.

## 8.6 Bounded prefill replay: layers 21-39 only on the last 2560 tokens of a prompt (`DSV41_PF_REPLAY`, default 2560; 0 = off)

**What changed.** The checkpoint shares one compressed KV and one set of index keys between the layers 20-39 (`kv_source_layer_ids` [.., 20], `index_source_layer_ids` [.., 20, 24, 28, 32, 36]): layers 21-39 only READ the entries layer 20 writes from the output of layer 19, and keep their own 128-token window KV. A chunk of a cold prompt that is more than 2413 tokens (19 layers x 127 window positions) away from the end of the prompt therefore needs layers 0-20 only: nothing that layers 21-39 compute for it is read by any later token or by decode. The chunk trace is captured as two halves joined by persistent bridge buffers: trace A = embedding, Engram, layers 0-20; trace B = layers 21-39 + taps + ragged head (+3.3 / +2.8 MiB per DRAM bank, the same 6.1 MiB as the single trace). A window replays A only unless one of its rows is in its replay zone (chunk starts >= `floor((S - R) / C) * C` for a prompt of S tokens, R = 2560, C = 512), then A and B. For the first zone chunk of a row the window of layers >= 21 starts empty (a second set of "first chunk" window tensors, `ctx.sp_perm_b`, `ctx.pg.win_b`); every later chunk of the zone has run B before, so the halo is valid. Exact: with R >= 2414 the replayed rows, the decode ring and the drafter taps are bit-identical to running all 40 layers on every chunk (a smaller R is window-clipped, an approximation: do not use). Code: `tt/replay_cfg.py` (switches), `tt/prefill_model.py` (`_forward_device(part)`, bridge, `_capture_dyn_trace_split`, `replay_window(back=)`, `set_zone`), `tt/dsv41_model.py` (`prefill_interleaved(totals=)`, zone per mesh row, A-only windows, APC), `tt/prefix_cache.py` (partial snapshots), `tt/generator_vllm.py` + plugin `prefill_total` (the whole length of every request, next to `prefill_final`; a model run without it never skips), `tt/dsv41_model.py` window build: Engram row gathers of the next `DSV41_PF_BUILD_AHEAD` (2) windows in a thread pool (an A-only window is shorter than the host's build of a window: 0.27-0.31 s -> 0.19 s per window with it).

**Switches.** `DSV41_PF_REPLAY=R` (default 2560; 0 off) is honoured only where it is supported: paged read mode (`DSV41_PF_PAGED=read`) and the per-user state mask (`DSV41_PF_UMASK=1`), i.e. the server and the demo recipes; at boot it decides whether the chunk trace is split. `DSV41_PF_REPLAY_FILE=<path>` makes R live (file content; 0 = both halves on every chunk, numerically the single trace) for same-session A/B runs. `DSV41_PF_BUILD_AHEAD` (default 2; 1 = previous host build).

**APC.** A snapshot taken while layers >= 21 skipped chunks has stale halos for them: it is marked partial (`PrefixSnapshot.full` False) and only restored at `s <= p0` of the new prompt (the first zone chunk ignores those halos); a snapshot of a prompt shorter than R + C (every chunk ran every layer) stays full and usable as before. Cold == hit outputs stay bit-equal.

**Measured (same host .45, same server session, replay ON vs `DSV41_PF_REPLAY_FILE`=0, catalog default B=4 / 1M build, rebased v3 tip):** 4 concurrent cold prompts, batch TTFT 8k / 32k / 64k / 128k: 4.64 / 13.55 / 25.86 / 50.43 s against 8.43 / 32.12 / 64.22 / 129.79 s (the scheduler starts the first request alone in some runs: a pure image without any of this shows 5.76 / 21.08 / 42.05 / 84.80 s in a good run and 8.4 / 32.1 / 64.3 / 129.7 s in the others; good-run vs good-run is -19 / -36 / -38 / -41 %, bad vs bad -21 / -39 / -41 / -42 %). ## 8.10 Host-side serial work of a speculative round (`DSV41_HOSTOPT_*`)

**What changed.** Six switches, all default OFF (`tt/hostopt.py`; call sites in `tt/spec_model.py`, `tt/spec_decoder.py`, `tt/decoder.py`, `tt/device_sampler.py`): `FORCE` (`SpecDecoder.set_force` skips the host-to-device copy when the value is unchanged), `ENGRAM` (numpy n-gram hash and LUT fp8 dequant straight into one reused bf16 buffer), `PACK` (with ENGRAM: the two host tensors of the packed upload are built once and refilled in place; sampler params: only the uniforms are rebuilt per round), `READBACK` (read-back enqueued right behind the trace, one synchronize instead of two), `POST` (vectorised post-process loop), `WARM` (an idle-priority busy loop in a separate process, pinned to the core of the round thread). The module docstring states that no result bit changes. Commits (this branch): d852075dec3 (framework), 9836f021d63, 154400fb658, 603ed48474b, 78f4714d676, 767b1faab4c, 64001bf647a, and the two server fixes 264a602b690 (ENGRAM falls back to the shipped path on error; WARM pins every round thread and pauses during prefill calls; `DSV41_VLLM_SPEC_KFILE` test hook, default unset; first 8c30a8719d6 on `ssinghal/dsv4p1-hostopt-srv`) and 332540b5ff9 (PACK: the sampler-params template applies only to `DSV41DeviceSampler`, the server's `SharedSamplerAdapter` keeps the shipped path, it raised AttributeError on the first sampled round; first d10897be4ac, the tip of `ssinghal/dsv4p1-hostopt-srv`). Restore: unset the switches.

**Root cause of the WARM gain** (docstring of `DSV41_HOSTOPT_WARM`, quoted in `L/host_opt/runs/sm6_cyc.log`; no separate report file exists): the host thread sleeps about 50 ms of every 55 ms round inside the device wait; on these hosts (AMD EPYC, `acpi_idle` C2) the core's deep idle state has a 0.8 ms exit latency and the core's caches are lost, so every host phase runs cold: the same Engram hash takes 0.55 ms after a sleep, 0.29 ms after a busy wait, 0.13 ms back to back. A `SCHED_IDLE` busy loop pinned to the same core (separate process: no GIL, it never runs while the round thread is runnable) keeps the core out of C2.

**Measured, demo loop** (`L/host_opt/tables_final.md` [log], round-timeline period, switches cycled every 4 rounds on the same token stream, instrumentation off, 1M / B=4 and 512k / B=8, fixed k and adaptive frozen table 3:47, 5:58, greedy and sampled): all switches against none, saving per round B=4 3.61-4.89 ms (6.5-8.5 %; k=3 greedy 53.64 -> 50.03 ms, k=5 greedy 58.52 -> 54.71 ms, adaptive 3.87 / 4.67 ms), B=8 4.07-5.40 ms (5.6-7.6 %; k=3 greedy 64.65 -> 60.59 ms, k=5 greedy 87.33 -> 82.42 ms); without WARM 2.25-3.78 ms.
