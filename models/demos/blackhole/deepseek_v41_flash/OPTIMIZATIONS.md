# DeepSeek-V4.1-Flash: optimizations

This file is the record of the changes that **improved a measured number** for this model on Blackhole Galaxy (4x8 mesh, branch `ssinghal/dsv4p1`). Each entry says what changed, why it helps, what was measured before and after (setting, host, how), the correctness gate, where the code is (file, commit) and where the number comes from (log or note). A change that did not improve a number, or failed its correctness gate, does not get an entry (it can appear under "Tried, not kept" in one line). Future ideas that are not done stay in `FUTURE_WORK.md`.

How to add an entry: measure before and after on the same host and settings (4 concurrent cold prompts for TTFT, GSM8K chat prompts for decode, traced clock for kernels), keep the correctness gate (logits PCC, needles, GSM8K), commit the change, then add a row to the table of its area and a block under "Details" with the log paths. The optimization loop (`tt-opt`, `dsv4-logs/ttopt/`) writes a standalone `keeps/NN.patch` for every kept edit; its entries go in section 8.

Conventions. `L` = `/mnt/tt-data/ssinghal/dsv4-logs`, `D` = `models/demos/blackhole/deepseek_v41_flash`. Source tags in the Details: **[log]** the number was read in the raw log named; **[doc]** the number is in a note of this directory and was not re-read in a raw log; **[commit]** the number is only in a commit message. Numbers are copied, not rounded. Where two sources disagree both are given. B is the batch (users), k the number of drafted tokens, "batch TTFT" the time until every user of the batch has its first token.

Entry counts: server and scheduling 12, prefill 17, decode 6, speculative decoding 10, sampling 3, memory/DRAM and tracing 15, tt-opt 0 (section 8.1-8.13 are lever blocks, 8.7-8.13 are the B=8 levers), branches not merged 4, tried and not kept 19, known regressions 14. Items that are not accepted yet are not entries: they are listed in "Pending (not in this release yet)" with owner branch and status only. Paths starting with `tt/` or `tests/` are under `D`.

## 8.6 Bounded prefill replay: layers 21-39 only on the last 2560 tokens of a prompt (`DSV41_PF_REPLAY`, default 2560; 0 = off)

**What changed.** The checkpoint shares one compressed KV and one set of index keys between the layers 20-39 (`kv_source_layer_ids` [.., 20], `index_source_layer_ids` [.., 20, 24, 28, 32, 36]): layers 21-39 only READ the entries layer 20 writes from the output of layer 19, and keep their own 128-token window KV. A chunk of a cold prompt that is more than 2413 tokens (19 layers x 127 window positions) away from the end of the prompt therefore needs layers 0-20 only: nothing that layers 21-39 compute for it is read by any later token or by decode. The chunk trace is captured as two halves joined by persistent bridge buffers: trace A = embedding, Engram, layers 0-20; trace B = layers 21-39 + taps + ragged head (+3.3 / +2.8 MiB per DRAM bank, the same 6.1 MiB as the single trace). A window replays A only unless one of its rows is in its replay zone (chunk starts >= `floor((S - R) / C) * C` for a prompt of S tokens, R = 2560, C = 512), then A and B. For the first zone chunk of a row the window of layers >= 21 starts empty (a second set of "first chunk" window tensors, `ctx.sp_perm_b`, `ctx.pg.win_b`); every later chunk of the zone has run B before, so the halo is valid. Exact: with R >= 2414 the replayed rows, the decode ring and the drafter taps are bit-identical to running all 40 layers on every chunk (a smaller R is window-clipped, an approximation: do not use). Code: `tt/replay_cfg.py` (switches), `tt/prefill_model.py` (`_forward_device(part)`, bridge, `_capture_dyn_trace_split`, `replay_window(back=)`, `set_zone`), `tt/dsv41_model.py` (`prefill_interleaved(totals=)`, zone per mesh row, A-only windows, APC), `tt/prefix_cache.py` (partial snapshots), `tt/generator_vllm.py` + plugin `prefill_total` (the whole length of every request, next to `prefill_final`; a model run without it never skips), `tt/dsv41_model.py` window build: Engram row gathers of the next `DSV41_PF_BUILD_AHEAD` (2) windows in a thread pool (an A-only window is shorter than the host's build of a window: 0.27-0.31 s -> 0.19 s per window with it).

**Switches.** `DSV41_PF_REPLAY=R` (default 2560; 0 off) is honoured only where it is supported: paged read mode (`DSV41_PF_PAGED=read`) and the per-user state mask (`DSV41_PF_UMASK=1`), i.e. the server and the demo recipes; at boot it decides whether the chunk trace is split. `DSV41_PF_REPLAY_FILE=<path>` makes R live (file content; 0 = both halves on every chunk, numerically the single trace) for same-session A/B runs. `DSV41_PF_BUILD_AHEAD` (default 2; 1 = previous host build).

**APC.** A snapshot taken while layers >= 21 skipped chunks has stale halos for them: it is marked partial (`PrefixSnapshot.full` False) and only restored at `s <= p0` of the new prompt (the first zone chunk ignores those halos); a snapshot of a prompt shorter than R + C (every chunk ran every layer) stays full and usable as before. Cold == hit outputs stay bit-equal.

**Measured (same host .45, same server session, replay ON vs `DSV41_PF_REPLAY_FILE`=0, catalog default B=4 / 1M build, rebased v3 tip):** 4 concurrent cold prompts, batch TTFT 8k / 32k / 64k / 128k: 4.64 / 13.55 / 25.86 / 50.43 s against 8.43 / 32.12 / 64.22 / 129.79 s (the scheduler starts the first request alone in some runs: a pure image without any of this shows 5.76 / 21.08 / 42.05 / 84.80 s in a good run and 8.4 / 32.1 / 64.3 / 129.7 s in the others; good-run vs good-run is -19 / -36 / -38 / -41 %, bad vs bad -21 / -39 / -41 / -42 %). ## 8.17 Unified-MoE row topology linear (`DSV41_UNI_TOPO=linear`), fix of an intermittent combine deadlock in 8-user 8k prefill

`DSV41_UNI_TOPO` (read per call in `tt/prefill_unified_moe.py::row_topology`) selects the topology of the prefill dispatch / combine over the 4 mesh rows; default `ring` (wrap link), the B=8 catalog now sets `linear`. **Failure (default ring, 2 links).** 8 concurrent fresh random-token 8k prompts on an idle B=8 server (image `afb78699c8b-5b6f9268-dd4fbc6`, catalog = b8_final): device timeout after 3 / 5 / 7 clean iterations on .32 / .34 / .44 (3 of 3 hosts; the earlier runs on .33 / .47 hung at iteration 1, 4 of 4 boots). **Fix and cost.** Each of `DSV41_UNI_TOPO=linear` and `DSV41_UNI_LINKS=1` removes it on its own (a cold server, 8 x 8k fresh prompts per iteration, osl 2, then 4 x 8 x 32k): linear 80/80 clean 8k iterations (.34 20 + 30, .44 30; 4 + 4 x 32k on .34), links=1 with ring 54/54 (.32: 20 + 30 + 4 x 32k). Default hazard on the same protocol is about 1 in 6 iterations, so 30 clean iterations are at the 0.5 % level per run. Cost (8 users, real-text prompts, idle server, mean of 2, same host .34 unless noted): default 8k 9.02 s / 32k 27.40 s; linear 9.09-9.14 s (+0.8 to +1.3 %) / 27.64-27.84 s (+0.9 to +1.6 %); (.44: 9.27 / 27.88); links=1 9.37-9.54 s (+4 to +6 %, .32) / 28.7-28.9 s (+5 %). Random-token 8k iteration means: default 8.93 (3 clean iterations), linear 8.88 / 8.88 / 8.97, links=1 9.43 / 9.33. Decode at ISL 1024 c8 is unchanged (45-49 tok/s/user in 64-200 token windows for default, linear and links=1; the setting is not on the decode path). Linear is therefore the fix (< 3 %); links=1 costs about 5 %.

**Suspected kernel cause (not rebuilt, not proven).** The hang is the pattern fixed upstream for `reader_worker_dispatch` / `reader_combine` in 12b1eb51481: on Blackhole every NOC atomic is non-posted, NCRISC snapshots the atomic-response counter at kernel start, and a response that lands after the next kernel's snapshot leaves the hardware count one ahead, so a later barrier on that RISC never completes. The final tree already has the exit `noc_async_atomic_barrier()` in `reader_combine`, but other kernels that run on the same cores just before combine still end with an increment and no atomic barrier: `unified_routed_expert_ffn_reader.cpp`, `moe_fused_swiglu_reader.cpp`, `masked_bincount/reader_masked_bincount.cpp` (grep: `noc_semaphore_inc` / `.inc(` / `.up(` without `noc_async_atomic_barrier`). A leaked count in front of `reader_combine.cpp:254` fits the stuck write barrier, and the 3-of-4 devices waiting at exit semaphore 2 of 3 is just the missing 4th arrival. Why ring / 2 links matters: the exit handshake (`send_init_semaphore_to_configured_targets` with the compile-time `topology`) and the data routes (`get_route<topology>`) differ, so with ring + 2 links more packets cross the wrap link and the leak window (last atomic of the previous op landing late under fabric load) is hit more often; linear or one link shifts timing, it does not remove the cause. To prove it: run the 1-layer unified MoE test with the watcher and check `DebugAssertNCriscNOCNonpostedAtomicsFlushedTripped` on the expert-FFN / bincount readers, or add `noc_async_atomic_barrier()` at their exit and rerun the ring reproducer.

Logs: `dsv4-logs/hang2/` (`srv/<run>/server_full.log`, `res/<run>/drive.log`, `costA.json`, `dec1k.json`; runs: baseA32 / baseA34 / baseA44 hang, base34 cost, toplin / linB / linC linear, lk1ring / lkB links=1; scripts hold.sh, drive3.sh, drive4.sh).

## 8.19 APC with images (`DSV41_APC_IMAGES=1`)

**What changed.** Image prompts take part in the model-owned automatic prefix cache (before: 8.18 skipped prefix-cache reads for them). **Measured** (device runs on host .46, rc2 image with worktree mounts; rc3 end to end pending): cold -> repeat TTFT with 10 / 50 / 100 / 250 images: 3.3 -> 1.5 s, 8.8 -> 6.0 s, 16.3 -> 11.1 s, 41.1 -> 22.8 s.

## 8.20 APC host tier on the 512 grid (M0', `DSV41_APC_GRID=512`)

**What changed.** The prefix cache snapshots on the 512-token grid instead of only at powers of two: a tip snapshot at the end of every prompt (and a second tip), a zone point per prompt (honouring the bounded-replay zone rule: a snapshot past the zone start is only partial), and a divergence point where the prompt leaves a chain seen before (lineage thinning: a new tip supersedes older tips of its own chain). The snapshots live in a host store (budget 50 GiB). `tt/apc_grid.py` (`GridPolicy.plan`), `tt/prefix_cache.py`; CPU tests `tests/test_apc_grid.py`, `tests/test_prefix_store.py`. Needs `DSV41_APC_DEFER=1` (the code default; the plan is consulted in `begin_snapshot`, no extra host sync). `DSV41_APC_GRID_LADDER` (extra divergence points) stays 0; `DSV41_APC_GRID_FILE` (live switch file, 0 = grid snapshots off) is not set.

**With images (8.19).** The plan of an image prompt is made on the image-aware key chain (token chain with one content-hash value per image span), the chain `begin_snapshot` keys with, so image prompts get tip / zone / divergence snapshots too. Text-only plans are identical with the image code present (`tests/test_apc_grid_images.py`). The combination of image keys and the grid is verified on CPU only; device verification is part of the rc3 end to end.

**Measured** (host .45, rc2 image): shared 30k-token system prompt 10.6 -> 3.75 s per request after the first; 32k resend 10.8 -> 3.2 s; 8 agents with 6k + 3.9k per turn 16.7 -> 11.0 s mean TTFT after turn 1. Cold prefill costs +0.28 s at 16k and +0.5 s (2.5 %) at 32k. Host store: 22 GiB at 506 snapshots of the 50 GiB budget.

**Limits.** Hits only at or below the new prompt's zone-start floor ((end - 2560) / 512) * 512, so a prompt that grows by less than about 2.6k tokens per turn gains little.

**Boot cost, not measured.** `warm_apc` compiles every multiple of 512 up to `DSV41_WARM_APC_GRID_MAX=32768` (default); the extra boot time is unmeasured and must be checked at the rc3 boot.

**Catalog.** `DSV41_APC_GRID: "512"` in all deepseek_v41 entries (B=4, B=8, B=16; text and vision).

## 8.23 Device-resident block-paged APC (`DSV41_APC_PAGED=1`, default off)

**What it is.** A second prefix cache next to the host snapshot tier (8.x, `DSV41_APC`): the cached state stays in device DRAM and a hit is a device-local copy (design: `APC_PAGED_DESIGN.md`, code `tt/apc_paged.py` (CPU block index), `tt/apc_paged_store.py` (stores + 3 JIT copy kernels), `tt/apc_paged_model.py` (wiring), plugin `prefix_hooks`, `prefix_cache_hit_policy = "model"`). Hit grid = the 512 chunk, hit <= prompt end - 128. Per mesh row: the pool pages (shared, refcounted, a committed 512-block hands its 4 pages to the cache: no copy), a key store (40 KiB per chip per block, 2048 blocks), a halo store (part A layers 0-20: 128 slots; part B layers 21-39, only inside the bounded-replay zone: 48 slots). Stores are allocated at build before the first trace capture (`warm_serving`, after the decode buckets compile; 530 MiB per chip = 65 MiB per bank at B=8: free after boot 348 vs 413 MiB per bank) and their 3 kernel programs are compiled then. No save runs inside a trace: after the replay of a window is enqueued, the keys and halos of the chunk ends that the index wants are saved with eager launches queued behind it (before the next replay), so the chunk trace and its layout are unchanged. A hit: the scheduler asks the model (`plan_hit`: deepest hit on a row that has a free user, reserves that user), `prefill_forward` binds the reservation (page table = shared pages + private pages), enqueues `key_load` + halo restore (about 2 ms host), continues from `s` with the existing continuation path. A reservation lost (reset, expiry, race) recomputes from 0 (counted). Image prompts never take part (host tier, as before). A text request the paged cache owns does NOT use the host tier (no restore, no snapshot, `DSV41_APC_PAGED_HOST=0` default): a host restore turns the request into an anonymous one (`restore_users` releases and re-admits the user), so its chunks are never committed and the paged cache starved (hold h1/h2: every commit on the one row that computed cold, hits only on users 0 and 1); `DSV41_APC_PAGED_HOST=1` keeps the old fallback (index miss -> host snapshot) at that price, until a commit-after-restore exists; `DSV41_APC_PAGED` off = exactly the previous behaviour. Needs the single chunk trace, chunk 512, `Up == U` (B=8, B=4); B=16 (`Up < U`) stays on the host tier.

**Switches.** `DSV41_APC_PAGED_HALO_A/B/KEYBLOCKS` (store sizes per mesh row), `DSV41_APC_PAGED_HALO_BUDGET` (default 32: at most about this many halo A records per prompt, thin = ceil(blocks / budget), the tip always; a long cold prompt must not wipe the halo store of its row), `DSV41_APC_PAGED_ZONE_EQ=1` (halo B valid only if the donor's zone start equals the new prompt's; default `<=`, see below), `DSV41_APC_PAGED_LOG_EVERY`.

**Exactness.** Device test `tests/test_apc_paged_hit_equals_cold.py` (B=8 geometry, fp8 pool, bounded replay, layers 0-23): last-token logits of a hit are BIT-IDENTICAL to a cold prefill (and cold vs cold: 0 difference) and 8 greedy decode tokens are identical, for hits at 512 .. 6144 tokens with halo A only and with halo B (cases around p0), including `b_zone < p0_new` (a donor shorter than the prompt by 1556 tokens, hit at 6144 > p0(new) = 5120): bit-identical, so the default `b_zone <= p0_new` rule stays. Logs `dsv4-logs/apc_paged/m1b/out/t2.log`.

**Found and fixed on the way.** (1) Two requests that planned a halo record for the same block while it had none overwrote each other's slot (a leaked halo slot per race; the index's thread test failed one run in three): the second now gives its slot back (`test_two_dup_commits_...`). (2) The scheduler plans the hit of a new request in the step that also carries the release of a request that just finished, but the model only learns about the release at the start of that step: the users of just-finished requests looked busy, so 6 of 8 concurrent repeats missed. The plugin hook now receives `finished_ids` and the index treats those users as free (`BlockIndex.plan_hit(finished_ids=...)`).

**Measured** (host .46, rc2 image with the m1b model + plugin worktrees mounted, B=8 / 1M baked catalog, hold h3 of `dsv4-logs/apc_paged/m1b/`; M0' = host tier numbers of `dsv4-logs/apc_m0p/res`):

Restore cost per hit: about 2 ms of host time (3 table uploads + 6 launches, `restore enqueued in 1.7-2.5 ms`), the device copy rides in the first replay of the hit (a 128k hit is one 0.49 s replay of the last chunk, 0.65 s per call); commit cost 1.5-2.2 ms per chunk on the host (saves queued behind the replay). cache_salt isolation holds (cold for another salt and for none), aborts mid-prefill leave a consistent cache (resend text equal to the reference, 0.7-2.3 s), header burst of 16 fine, hang canary 8 x 8k fresh prompts x 30: 0 errors, 8.5 s per iteration (9.7 s with the host snapshots), pressure (24 x 32k, 736 block + 5457 halo-A evictions, 0 out_of_pages): 24/24 needles right, a cyclic re-send of a working set larger than the halo store misses (LRU, as expected: the halo store, 128 A slots per row, is the binding resource; `DSV41_APC_PAGED_HALO_A`), image prompts unchanged (host tier, answers right). **What the holds taught** (h1, h2 -> h3). **Memory and limits.** +65 MiB per bank; free DRAM at B=8 is 348 MiB per bank. The halo-A store (128 slots per mesh row) is the binding resource. Hit logits are bit-identical to a cold prefill including the `b_zone < p0_new` case; no regression in cold prefill.

## 8.24 Image-cut piece lag (`DSV41_PIECE_LAG=1`)

**Problem.** vLLM cuts a long prompt into prefill pieces; a piece end that is not on a chunk boundary, or that lands inside an image span, made the next piece recompute from position 0 (wasted prefill, worst for image prompts).

**Fix** (`IMAGE_CUT_NOTES.md`; `tt/generator_vllm.py`, `tt/vllm_state.py`): a piece that does not end its prompt is cut back to a chunk boundary (and before a straddling image span), and the next piece resumes at the carried end (the end vLLM believes the user has reached is tracked separately). `DSV41_PIECE_LAG_FILE` is a live switch file for A/B in one boot.

**Measured** (device A/B, branch owner): wasted recompute 32.6 % -> 2.0 %, no errors. **Catalog:** `DSV41_PIECE_LAG: "1"` in all deepseek_v41 entries.

## 8.25 Delta / block host snapshots (`DSV41_APC_DELTA=1`, default off)

**What changed.** The host snapshot store keeps the position-indexed state (pool latents of the 4 kv sources, index keys of the 4 owners) in refcounted blocks of one chunk, keyed by the token chain at the block end (`DeltaStore`, `Block`, `tt/prefix_cache.py`); a record keeps only the halos (5 MiB), the tokens and the chain of block keys. The device read of a snapshot is a delta too (`snapshot_begin(..., s_lo)`: only the rows since the end of the cached run of blocks). `restore_users` is unchanged: `DeltaStore.assemble` concatenates the blocks into the full-form snapshot first (0.04-0.08 s at 46-62k tokens). Switches: `DSV41_APC_DELTA` (off: byte-identical behaviour), `DSV41_APC_DELTA_STEP=N` (also snapshot every N chunks: one halo per extra point), `DSV41_APC_DELTA_CHECK=1` (debug: whole snapshot at the same moment, assert bit-identity). Design: `APC_DELTA_DESIGN.md`. Tests: `tests/test_prefix_delta.py` (CPU), `tests/test_apc_delta_device.py` (device, part A).

**Exactness.** Server (host .44, rc3 image + worktree mounted, B=8 / 1M catalog with `DSV41_APC_PAGED=0` so the host tier owns text): 67 of 67 assembled records bit-identical to the whole snapshot (`dsv4-logs/apc_delta/srv/dA`, `DSV41_APC_DELTA_CHECK=1`); hit == cold greedy text 9 of 9 on base / extended / branching prompts of 3k, 9k, 20k tokens, with and without the check (`res/correct_dA.json`, `correct_dB.json`; cold = the live switch file `DSV41_APC_FILE` = 0). Device unit test (layers 0-23, B=8 geometry, `out/t_delta.log`): 8 of 8 snapshots bit-identical, hit at 2560 of a 4700 token prompt: last-token logits bit-identical to cold (max diff 0.0), cold vs cold 0.0.

**Measured** (same host, same prompts, `res/multiturn_dB.json` vs `multiturn_dC.json`; one conversation, prompt = previous prompt + answer + 4096 new tokens, 8.2k -> 66.4k tokens, 15 turns): host store growth 325 MiB (delta, 36 records, mean record 5.0 MiB) against 2,487 MiB (whole snapshots, 35 records, mean 105 MiB), i.e. 7.7x less; container RSS growth 0.5 GiB against 2.5 GiB (RSS baselines of the two boots differ by 20 GiB, only the growth is comparable); per-turn TTFT 4.15 -> 5.25 s against 4.17 -> 5.50 s (turn 0 cold 6.15 / 6.36 s). Cold prefill with the cache on, 3k / 9k / 20k: 2.99 / 6.45 / 12.79 s against 3.17 / 6.43 / 12.75 s with it off (no regression; the check flag costs +1.8 s at 20k and is debug only). Snapshot enqueue 12-20 ms as before.

**Limits.** Only the host tier uses it (images, B=16, `DSV41_APC_PAGED=0`; text on B=4 / 8 is owned by 8.23). A record still costs its halo, so `DELTA_STEP=1` (a point per 512 tokens) costs 10 MiB per 1k tokens: the halos, not the blocks, bound the grid. The 62k multi-turn restore point is the grid point below the prompt (tip), unchanged policy.

## 8.26 Cache the decode output for the next turn (`DSV41_APC_DECODE=1`, needs 8.25, default off)

**What changed.** At the end of a request the decode state is converted into a carried-state snapshot at the last chunk multiple s of the tokens whose KV the model holds, so the next turn (old prompt + answer + new message) hits including the answer. Pool latents are read from the pool as for a prefill snapshot; the index keys are the decode slab rows (a column-sharded decode slab has the same per-column layout as the single-trace prefill slab, a replicated one is re-interleaved on the host); only the sliding-window ring survives decode, so the halo of s is gathered from the 40 rings (one `paged_gather_rows`, 5 MiB, non-blocking) when the committed length crosses a multiple of 512 (hooks `_apc_dec_poll` after every plain step and spec verify round in `tt/generator_vllm.py`, `PrefixCache.decode_poll`; the latest crossing per user is kept; a capture is taken only while `n - s <= ring_rows - 144`, at `n == s` for a 128-row ring). `decode_finish` runs in `release_request` before the pages are released, 0.01-0.02 s. Tests: CPU flow in `tests/test_prefix_delta.py`, device part B of `tests/test_apc_delta_device.py`.

**Measured.** Device unit test (`out/t_delta2.log`, 3000-token prompt, 700 decode steps, next turn +300 tokens): hit at 3584 = the last chunk multiple of the decoded sequence; last-token logits against a cache-off run: max diff 1.72, mean 0.27, argmax equal (not bit-identical by construction: decode kernels, fp8 ring for the halo); 8 of 9 greedy decode tokens equal. Server (`res/dec_needle_dB.json`, 10 conversations, 7-9k token turn-2 prompts with 1200 new tokens, code word written at the START of a 700-token answer and asked for again): 10 of 10 correct with the decode snapshot (hit past the answer) and 10 of 10 with the cache off; mean TTFT 1.92 s against 5.77 s cache off and 3.71 s with decode caching off but prompt snapshots on (`dec_needle_dC.json`). Turn-2 greedy text equal to the cache-off text in 2 of 3 conversations (`res/dec_correct_dB.json`; the third differs on an ill-posed counting question, 1,000 against 500; the whole-prefix baseline `dec_correct_dC.json` is equal 3 of 3). Multi-turn with 4k new tokens per turn gains little (the new message dominates); the gain is the answer length (about 0.7-1k tokens) per turn.

**Limits / open.** No task-level accuracy run (GSM8K style multi-turn) yet: the converted state is approximate (see above), the needle result shows retrieval from decode-written positions works. Not applicable to the paged device cache (M4 of its design: copy-on-write at the block boundary). Requests whose answer never crosses a chunk multiple beyond the prompt's own tip store nothing. Image prompts are skipped.

## 8.27 Cross-row hits of the paged APC (`DSV41_APC_PAGED_XROW=1`, needs 8.23, default off)

**What changed.** When the deepest hit sits on a mesh row without a free user, the index plans the request on a row that has one (fresh private pages there, donor blocks pinned, `plan.xrow_src`), and the model copies the blocks host-staged (`PagedApc.xrow_copy`): latents of the donor pages and the key-store slots / tip halo slots of the donor row are read to the host (one chip per column), the latents scatter into the new pages, keys and halos go into freshly allocated store slots of the receiving row through the existing `key_save` / `halo_copy` kernels from staging tensors, one copy chunk per block (`begin_chunk(copy=...)`), the blocks are published in the receiving row's index and the request continues as a LOCAL hit (`xrow_finish`). No CCL. Switches: `DSV41_APC_PAGED_XROW`, `_XROW_MIN` (copy only if it gains at least 2048 tokens over the best local hit), `_XROW_MAX` (65536 tokens). Design and the vLLM connector question: `APC_DELTA_DESIGN.md` section 3. Tests: `tests/test_apc_paged_xrow.py` (CPU, index), `tests/test_apc_paged_xrow_device.py` (device).

**Exactness.** Device unit test (`out/t_xrow2.log`, layers 0-23, B=8, row 0 full): hits of 5120 / 10240 / 3072 tokens copied row 0 -> row 3: last-token logits BIT-IDENTICAL to cold (max diff 0.0, cold vs cold 0.0) and 8 greedy decode tokens identical in all 3 cases; a later request finds the blocks on the receiving row (local hit).

**Measured** (host .44, rc3 image + rc3 plugin worktree mounted, B=8 / 1M catalog, paged APC, 16 conversations on the 8 users, 6 turns, the m1b agents workload twice per arm, `res/agents_dX*_n16.json`, `srv/dX0`, `srv/dX1`): XROW off: lookups 190, hits 178 (2.00 M tokens), busy-row loss 68 lookups (428,544 tokens), cached fraction 0.666 / 0.595, mean TTFT of turns > 0 35.2 / 43.0 s, wall 355 / 412 s; XROW on: 116 local hits (1.43 M tokens) + 59 cross-row hits (1.03 M tokens, mean 17.4k tokens, 14 ms per block, 478 ms per hit; the first copy of a boot 1.8 s because its programs compile then), 2 copies failed ("a receiving block is missing": the request recomputed from 0), cached fraction 0.769 / 0.767, mean TTFT 32.1 / 34.5 s, wall 312 / 340 s (-12 % / -17 %). TTFT here is dominated by queueing (16 conversations on 8 users); text equality of server hits was not compared (unit test above is).

**Limits.** Copies up to 65,536 tokens (the slot reads are per block), no copy at B=16 (no paged cache there). The copy programs are not in the boot warm-up. Only the tip of the copied path keeps a halo record on the receiving row.

## 8.28 One-slot (Up=1) prefill context for short prompts (`DSV41_PF_UP1_SHORT=1`, default off; under test, not in the catalog)

At B=8 (`DSV41_PREFILL_UP=2`) a lone short prompt pays for an idle second slot in every chunk replay (window 0.4-0.5 s at 40 layers; 150 ms vs 90 ms replay in the 10-layer probe). A second prefill context with one slot per mesh row (`PrefillModel.compile_dyn_up`, `tt/pf_up1.py`) serves from-scratch prompts that fit one chunk, at most one per mesh row, no image, no host-tier restore; anything else runs the Up=2 trace unchanged. `DSV41_PF_UP1_SPAD`, live A/B file `DSV41_PF_UP1_FILE`. Design, selection rules and results: `PF_UP1_NOTES.md`; CPU tests `tests/test_pf_up1_cpu.py`. **Fixed in rc4c (found in the rc4b validation).** The "clear the vision buffers after an image window" flag (`PrefillModel._vis_dirty`) was keyed by chunk size and reset at prep time, so a call on the one-slot context cleared it while the Up=U context kept a stale image mask / embedding override; the next text-only window of the Up=U context (any prompt >= 512 tokens, or two users in a row) then saw image rows (text chats answered with grounding text; 1-2 % of multi-turn chats in a mixed image + text run). The same latent gap exists in rc3 / rc4 without the lever whenever two image / text contexts alternate; the fix is on the code path itself: the flag is now per vision buffer, decided at upload, and discarded lookahead uploads re-arm the clear (needle repro lost 24/24 before, 0/24 after, also with the lever off). The ISL >= 512 cost is removed too (`pf_up1.prebuild_other_ctx` prebuilds the fresh-prompt tables of every other context at the last window of a call). Soak on the fixed code (.34, B=8/1M, paged): 2000 requests with the lever on and 1871 with it off, 0 wrong / 0 errors; canary 30/30 iterations on, 0 bad; GSM8K 247/250 on and off. Tests: `tests/test_pf_up1_ctx_cpu.py`, device regression `tests/test_pf_up1_vis_stale_device.py`; hazard table in `PF_UP1_NOTES.md`. `DSV41_PF_UP1_SHORT` stays default OFF and out of the catalog until the user decides after the rc4c validation.

The APC delta / decode-output / cross-row switches of 8.25-8.27 are likewise off by default and not in the catalog (tests turn them on by environment override).
