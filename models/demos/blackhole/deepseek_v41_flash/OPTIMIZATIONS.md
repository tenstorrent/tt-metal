# DeepSeek-V4.1-Flash: optimizations

This file is the record of the changes that **improved a measured number** for this model on Blackhole Galaxy (4x8 mesh, branch `ssinghal/dsv4p1`). Each entry says what changed, why it helps, what was measured before and after (setting, host, how), the correctness gate, where the code is (file, commit) and where the number comes from (log or note). A change that did not improve a number, or failed its correctness gate, does not get an entry (it can appear under "Tried, not kept" in one line). Future ideas that are not done stay in `FUTURE_WORK.md`.

How to add an entry: measure before and after on the same host and settings (4 concurrent cold prompts for TTFT, GSM8K chat prompts for decode, traced clock for kernels), keep the correctness gate (logits PCC, needles, GSM8K), commit the change, then add a row to the table of its area and a block under "Details" with the log paths. The optimization loop (`tt-opt`, `dsv4-logs/ttopt/`) writes a standalone `keeps/NN.patch` for every kept edit; its entries go in section 8.

Conventions. `L` = `/mnt/tt-data/ssinghal/dsv4-logs`, `D` = `models/demos/blackhole/deepseek_v41_flash`. Source tags in the Details: **[log]** the number was read in the raw log named; **[doc]** the number is in a note of this directory and was not re-read in a raw log; **[commit]** the number is only in a commit message. Numbers are copied, not rounded. Where two sources disagree both are given. B is the batch (users), k the number of drafted tokens, "batch TTFT" the time until every user of the batch has its first token.

Entry counts: server and scheduling 11, prefill 16, decode 6, speculative decoding 10, sampling 3, memory/DRAM and tracing 13, tt-opt 0, branches not merged 4, tried and not kept 14, known regressions 7. Paths starting with `tt/` or `tests/` are under `D`.

## 0. Combined release comparison (mixed, not isolated)

Final image against `0.24.0-0655530-4743e01` (fixed k=5, dense prefill, APC off), B=4 / 1M server, 4 requests, `vllm bench serve`, random prompts, 128 output tokens, 3 repeats: ISL 8,192 TTFT 9059 -> 7792 ms, TPOT 120.9 -> 32.3 ms (output 20.2 -> 41.7 tok/s); ISL 1,024 TPOT 67.5 -> 30.6 ms but TTFT 1590 -> 2046 ms (regression R1). Source: `L/image_tests/new_text/bench.log` [log] (the "reference" numbers in it are the release's). This mixes S1-S4, S7, SP3, SP5, SM2 and more and is not a per-change gain. Against `0.24.0-c9cfb00-ffd1a57` the 4-user rows were -42 / -25 % (ISL 1,024 TTFT / TPOT) and -46 / -34 % (ISL 8,192), 16 users within +5 % (`RELEASE_NOTES.md`, `serving_bisect/README.md` [doc]).

## 11. Known regressions (not optimizations)

* R1. ISL 1,024 TTFT at B=4 is 2046 ms against 1590 ms in the previous release (+29 %): a short prompt needs several windows and the first-step cap adds a step (`FUTURE_WORK.md`, "Server prefill: host-side costs"; `new_text/bench.log`).
* R2. Per-row RoPE in plain decode (correctness: a user's latent no longer depends on its mesh-row mates): about +4.6 ms/token at B=16 (799a223987c [commit]).
* R3. Column-sharded RoPE tables: +0.39 ms per decode step at 1M (M2).
* R4. Unified MoE reading the ring weights: layer MoE section 3.45 ms against 2.71 ms with a second copy at N=512, 8.52 vs 7.72 ms at 4096 (M6, `PREFILL_UNIFIED_MOE_NOTES.md` [doc]).

APC snapshots inside the prefill call (before S6): 16 x ISL 1,024 TTFT +13.6 %, TPOT +20.6 %, tok/s -15.6 % against `c9cfb00` (V1 vs V0), and the 4,096-token budget 16 x ISL 8,192 +100 % / +71 % / -44 % (`L/serving_bisect/README.md` [doc]); APC on 16 x ISL 1,024 in the final specs was not re-measured after S6 (`FUTURE_WORK.md`).
