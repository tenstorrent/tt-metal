# DeepSeek-V4.1-Flash APC, next steps for rc4: delta snapshots, decode-output caching, cross-row sharing

Branch `ssinghal/dsv4p1-apc-delta` (off rc3 a08ff68fa07). All three items are default OFF behind env flags; one commit per step. Status and measured numbers are in the last section.

## 0. Survey (what exists, what we reuse)

* **vLLM automatic prefix caching** (`v1/core/kv_cache_utils.py`, `block_pool.py`): content-addressed blocks, key = chained hash over (parent hash, block tokens, extra keys: mm hashes, cache_salt), refcounted, free blocks kept in an LRU queue, a block is evictable only at refcount 0. This is the shape of the new `DeltaStore` (block = one 512-token chunk, key = our sha256 chain at the block end, `refs` = records that contain it, LRU over records, a block is freed with its last record). We do not use vLLM's blocks as storage (block ids are inert placeholders in the TT runner, `vllm_feature_gap.md` 1.1).
* **Other models in this repo** (llama3_70b_galaxy `prefix_caching_benchmark.py`, gemma4 `generator*.py`, qwen36 `qwen36_vllm.py`, deepseek_v3 `generator_vllm.py`): all rely on vLLM's own block table + `num_cached_tokens`: the cached KV is plain paged KV that attention reads in place, so a prefix is a list of page ids. None of them has non-additive carried state (window ring / halo, key FIFO) or a host tier. Nothing to reuse for DSV4.1 beyond that "hit = page table"; our paged APC (8.23) already does the same for the pool pages.
* **DeepSeek V4 paper (sec 3.2)**: compressed global KV is persisted whole and reused as a complete prefix; SWA KV is a separate small state ("host-DRAM pool", cached at the end of the prompt and the end of the output, decode SWA never cached otherwise). That is exactly the split used here: position-indexed rows (latents, index keys) are additive blocks, the 128-row halo is the tail record.
* **vLLM KV connector API / offloading** (coordinator report `dsv4-logs/research/vllm_feature_gap.md`): scheduler side `get_num_new_matched_tokens`, `update_state_after_alloc`, `build_connector_meta`, worker side `start_load_kv`, `wait_for_save`; pending state `WAITING_FOR_REMOTE_KVS`. Our TT plugin has no runner wiring for it and the lane scheduler hard-codes `connector=None` (`P/lane_scheduler.py:285`). See section 3 for how items 2 and 3 relate to it.

## 1. Delta / block host snapshots (`DSV41_APC_DELTA=1`)

What a whole snapshot holds (`tt/prefix_cache.py` docstring): halos (128 raw kv rows per layer, 5 MiB, NOT additive), and position-indexed rows: the pool latents of the 4 kv sources and the index keys of the 4 owners (single-trace slab: column c holds rows [Cc8 * k, ...) of chunk k, i.e. per column an append-only row sequence), kv-table rows on the dense path. Measured sizes: 6.6 MiB at 512 tokens, 105 MiB at 32k, 405 MiB at 128k (3.1 MiB per 1k tokens + the halo).

Design:
* `Block` = the rows of ONE chunk (512 tokens) of every tail tensor and every pool source, stored per mesh column (replicated tensors once). Key = the token-chain key at the block end (same `PrefixStore._chain` as the snapshots: signature, S_pad tag, position, sha256), so two prompts that share a prefix share its blocks, and image prompts use the image-aware key tokens as before.
* A record (`PrefixSnapshot`) keeps the halos (`full` kinds), the tokens and `bkeys` (the block keys of [0, s)); `refs` of the blocks are incremented at put. Eviction is LRU over records (as before); a block dies with its last record. `bytes` = halos + live blocks, budget `DSV41_APC_GB` unchanged.
* The device read is a delta too: `snapshot_begin(..., s_lo)` slices only rows [count(s_lo), count(s)) of the tail tensors and reads pool entries [s_lo / ratio, s / ratio). `s_lo` = end of the longest run of blocks already held (or pending from an earlier snapshot of the same call). So the read cost and host copy of a snapshot of an extended prompt are proportional to the new tokens, not the prompt.
* Layout independence: the store keeps LOGICAL per-column rows (oldest first). The device layout of the key FIFO depends on s (shifting FIFO) or on the slab geometry (single trace: start-anchored); both are reconstructed by `restore_users`, which still takes the full-form snapshot: `DeltaStore.assemble(record)` concatenates the blocks (a host copy of the prefix, measured below) and hands the unchanged restore path a normal `PrefixSnapshot`.
* Finer granularity: `DSV41_APC_DELTA_STEP=N` additionally snapshots every N chunks (cost per extra point: one halo, 5 MiB, plus nothing else because the blocks exist).
* Bounded replay: a partial snapshot (halos of layers >= 21 stale) is only partial in its halos. Blocks come from kv sources / index owners 2, 8, 14, 20 (all < 21, run on every chunk), so blocks are shared between partial and full records; `delta_unsupported` refuses delta mode if a tail tensor belonged to a layer >= 21 with the bounded replay on.
* Fallback: any model whose tail tensors do not split into whole chunks keeps the whole-prefix store (one log line).
* Debug: `DSV41_APC_DELTA_CHECK=1` takes the whole snapshot at the same moment and asserts the assembled record is bit-identical (logged per snapshot).

Exactness argument: a block row is written once by the chunk that owns it and never touched again (latents are appended, keys appended), so row j at snapshot s equals row j at any later snapshot; the check flag verifies that on device.

## 2. Cache the decode output for the next turn (`DSV41_APC_DECODE=1`, needs delta mode)

Why decode state is not the carried prefill state:
| state | prefill carried (what a record holds) | decode state at the end of a request |
|---|---|---|
| pool latents | rows through the user's page table | the same pool rows, decode appends them (a ratio-2 pair at a time); read with the same gather as the prefill snapshot, nothing to convert |
| index keys | single-trace slab, per column contiguous chunk-local split (column c holds entries [Cc8 c, Cc8 (c+1)) of every chunk) | `dec.k_cache` column-interleaved (entry e on column e % cols, slot e // cols) + a replicated head slab; the host re-splits the entry sequence into the per-column chunk blocks (pure permutation) |
| halo (kv rows s-128..s-1 of 40 layers) | persistent `halo` tensor updated by the chunk trace | only the sliding-window ring (ring rows 128, 288 in a spec build) survives: positions older than `end - ring_rows` are gone |

The ring is the constraint: the halo at a chunk multiple s can only be taken from the ring while `pos - s < ring_rows - 128` (160 tokens with the 288 spec ring). The design therefore captures the halo ON THE WAY: after a decode/verify round whose committed position crossed a multiple of 512, the host enqueues one `paged_gather_rows` of the 40 x 128 ring rows (non-blocking read, 5 MiB, bf16 even for an fp8 pool) and keeps only the latest capture per user. At the end of the request (before `release_user`) the model builds a record at the latest crossed s: halo from the capture, key rows and pool rows only for the blocks the store does not hold yet (`_delta_start`), converted as above, `full=True` (decode ran every layer). Next turn's prompt = old prompt + answer + new user message: the chain matches as far as the re-tokenised answer equals the generated ids; the hit is the deepest record on the matching chain (usual lookup rule s <= end - 128, `DSV41_APC_MARGIN`).
Not bit-identical to a cold prefill by construction (decode kernels, fp8 ring, spec numerics), so the gate is: same greedy text on the benchmark conversation and unchanged needle accuracy; prompt-part blocks (prefill-computed) are never overwritten by decode-computed ones (`_delta_start`).
Not covered: the device paged APC (8.23, M4 of its design needs copy-on-write at the block boundary); text requests owned by the paged cache bypass the host tier (`DSV41_APC_PAGED_HOST=0`), so decode caching applies to the host tier users: images, B=16, `DSV41_APC_PAGED=0`.

## 3. Cross-row block-paged APC (M3) and the vLLM connector

State: the paged cache (8.23) is per mesh row (pool pages, KeyStore, HaloStore per row). A hit needs a free user on the row that holds the blocks. 8.23 measured 233 of 266 lookups hit and 22 lost a deeper hit to a busy home row (31k of 2.4M tokens) for B=8 agent loads; it only matters above 8 conversations.

Options:
1. Device-to-device over the mesh row axis (send/recv, all_gather of a staging buffer): about 27 MiB per chip per 16k hit, ms-scale, but a fabric op on the serving path (hang class of 8.17) and bandwidth unmeasured. Not attempted without a device study.
2. Host-staged copy: read the donor blocks of row A (pool pages: one chip of the row, they are replicated over the 8 columns; key store: 8 columns; halo records) into host `Block`s (exactly the format of section 1), write them into row B's pages / key store / halo store with the existing eager scatter paths, register them in row B's `BlockIndex` as ordinary cached blocks. Cost is host bound (reads ~ the host-tier restore cost); it turns a busy-home-row miss into a hit and makes every later request on row B hit locally. This reuses section 1's block format, so the host tier and the cross-row path share one representation.

Integration point and deviation from the coordinator's preference (vLLM KV connector API): the cross-row copy is a pending load (the request must not run before the blocks are on row B), which is what `get_num_new_matched_tokens(load_async=True)` + `start_load_kv` express. We keep the device storage ours (per-row stores, window-slot halos: not representable in vLLM's hybrid allocator, see the gap report), and expose the copy through a connector-shaped class (`RowCopyConnector`: scheduler half `get_num_new_matched_tokens` / `update_state_after_alloc` / `build_connector_meta`, worker half `start_load_kv`) driven today by the existing `prefix_hooks` plan_hit path. Deviation: it is NOT registered as a vLLM `KVConnector`, because (a) the lane scheduler hard-codes `connector=None` and the TT runner never calls `start_load_kv` per step, so registering needs runner changes that affect every request path, not only the opt-in flag; (b) vLLM would pass vLLM block ids that address nothing on TT; (c) the load completes inside the same scheduler step on the host (ms), so `WAITING_FOR_REMOTE_KVS` buys nothing yet. The class keeps the method names and metadata types so that moving it onto the real interface later is a registration, not a redesign.
Status of this item is in the last section.
