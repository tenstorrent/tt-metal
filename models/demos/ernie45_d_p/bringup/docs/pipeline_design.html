A gated pipeline for bringing up transformer prefill on Tenstorrent

This page proposes a model-agnostic version of the process used to bring up ERNIE-4.5-21B-A3B chunked prefill on a 4-chip Blackhole box. Agents do the creative work in fixed steps. Tests that were written and checked before the implementation decide whether each step passed.

Evidence run ERNIE-4.5-21B-A3B, 28 layers, 55k@5k Box 4× p150b, mesh 1×4 Result 26 gates passed, 55k TTFT 4.4 s Code models/demos/ernie45_d_p/bringup

The one rule

An agent never writes the gate it has to pass. A separate step writes each test, checks the test against the reference, and freezes it before any implementation exists. The gate runner only executes frozen tests and compares their recorded numbers with thresholds that were fixed in advance.

The pipeline is a fixed sequence of agent calls. Between two calls sits a gate that a script runs without judgment. A gate either passes, and the pipeline commits the step and moves on, or fails, and the same agent gets the failure log and tries again.

What a model must look like to enter

The pipeline does not care about the attention flavor, the MLP type, or the number of layers. It needs five things from a model.

  • A checkpoint with a runnable reference, today a Hugging Face model, that the pipeline can run on CPU as an oracle.
  • A forward pass that is an embedding, a stack of blocks, and a head. Blocks may differ by layer, for example ERNIE's dense layer 0 followed by 27 MoE layers.
  • Blocks that decompose into components with a fixed order and residual wiring, where each component maps a named input tensor to a named output tensor.
  • Per-layer state that chunked prefill carries between chunks, such as a KV cache or a recurrent state, with a known shape per layer.
  • A deterministic CPU forward pass, so that chunked and one-shot prefill agree to about 1e-6 and every golden is reproducible.

The pipeline

Nine steps run in order. Five are agent calls, three are scripts with no agent, and people approve decisions at three points. Each arrow between steps carries a gate and the files that the next step reads.

Who runs the pipeline

A single orchestrator script runs every step in order. It writes each step's brief, starts the agent, runs the gate, commits on a pass and retries on a fail. It stops when a step needs a person: an approval at intake or plan, a debugger that gave up, or the opportunity list at the end. resume, rerun and fork are subcommands of the same script.

A person starts a run by talking to Claude, not by writing a config file. A companion skill, for example /bringup, asks for the model, the box, the target context and chunk size, and the layer subset if the model does not fit. It checks what it can on the spot, such as whether the checkpoint is reachable and how many chips the box has. It then writes a draft spec.yaml, shows it for approval, and launches the orchestrator. The same skill can report on a running pipeline and resume it after a stop.

How one agent step runs

Every agent step is a new claude -p process with the same model. It starts with no memory of earlier steps. It gets a brief, a small file the runner writes, which names the task id, the input files, the paths the agent may change, the gate it has to pass, and two shared documents that every agent reads first: the repo map and the known-issues file. The runner records the session id, the model id and the git hash of the agent definition in the task's state entry. That lets a step be replayed with the same inputs, and lets two runs be compared step by step after a fork.

Only scripts/run_safe_pytest.sh and scripts/tt-probe.sh may touch the device. Both hold a file lock on the device and reset it after each run, so several implement agents can work at once and queue for the same box. An agent that calls pytest or python directly on device code fails the gate, because the runner checks the command log in the step's output.

Test writing and implementation use the same agent definition with two roles. The test role may write only under tests/ and runs first. The implement role may write only the component's module and cannot change a frozen test, which the hash check enforces.

What each step does

Each step lists what it reads, what it writes, and the gate that must pass before the next step starts. The ERNIE task ids in brackets point to the gates that ran in the evidence run.

    Intake

    agenthuman approves

    A person picks the model, the box, the target, for example 55k tokens in 5k chunks, and optionally a subset of layers to bring up. The agent turns that into a model spec with the block types, the layer schedule, the per-layer state and the expected checkpoint tensors with their shapes. It downloads the checkpoint into the artifact folder.

    Writes

    Gate

  2. 1

    Reference

    agent

    The agent writes a standalone CPU implementation against a fixed interface: forward_chunk(tokens, start, state, recorder, layers). The recorder receives every tensor at a component boundary under a name such as L14.attn_out. The reference loads one layer's weights at a time, so a model larger than host memory still runs.

    Reads
    spec.yaml, HF modeling code, paper, repo map
    Writes
    reference.py
    Gate
    per-layer output matches HF at PCC ≥ 0.9999, and chunked prefill equals one-shot prefill [P1.2, P1.3]
  3. 2

    Goldens

    script

    A script runs the reference once per rung of the context ladder over a real long text. It stores every boundary tensor, the per-layer state and the top logits, in the serving layer's golden-trace format. Every later comparison reads these files and never reruns the CPU model. For ERNIE the longest rung took 61 minutes on CPU and every comparison after that took seconds.

    Reads
    reference.py, text, ladder and layer subset from spec.yaml
    Writes
    $ART/<model>/golden/ with a manifest and a content hash
    Gate
    manifest lists every layer and chunk; the hash is recorded for the tests to pin [P1.4 to P1.6]
  4. 3

    Plan

    agenthuman approves

    The agent maps every component to a TTNN op, tagged NATIVE, COMPOSED or CPU when no op fits, and checks the repo map before tagging anything COMPOSED. It writes the sharding plan in the reference format described below and the task ledger with one task per component swap, per integration rung and per contract check. A person approves the plan, because sharding and the choice of op are decisions the later gates cannot judge.

    Reads
    spec.yaml, repo map, reference plans, known issues
    Writes
    components.yaml, plan.md, tasks.yaml
    Gate
    schema valid; weights, caches and activations fit in per-chip DRAM [P2.2]; approval recorded
  5. 4

    Tests

    agent, test role

    The test role fills one template per component kind and one per swap in the block. A component test loads the golden input, runs the module, and records the PCC of its output against the golden output. Before freezing, the gate runs each test twice. With the CPU reference as the module it must pass. With a stub that returns zeros it must fail.

    Reads
    components.yaml, tasks.yaml, test templates, goldens
    Writes
    tests/, test hashes in tasks.yaml
    Gate
    passes with the reference, fails with the stub; then frozen
  6. 5

    Implement

    agent, implement role, one per component

    The implement role writes one TTNN module and swaps it into the block while every other component stays on the CPU reference. Swap tests run on one representative layer per block type; the other layers of that type are covered by the layer-stack tests in step 6. Components without dependencies on each other run in parallel. After three failed attempts the agent commits its current code as a work-in-progress commit and hands over to ttnn-expert-debugger, the repo's debugging agent, which gets the WIP commit, the three failure logs and the hang triage report. If the debugger also fails three times, the runner stops and pages a person.

    Reads
    frozen test, components.yaml entry, repo map, known issues
    Writes
    tt/<component>.py, a known-issues entry if it hit something new
    Gate
    the frozen component test, then the block test with this swap [P2.3 to P2.10]
  7. 6

    Integrate

    script

    Generic tests stack the device blocks: one layer, then the selected subset, then all layers if the model fits. Then they climb the context ladder. For ERNIE the rungs were 2k→2k, 8k→8k, the last chunk after a golden 50k prefix, and the full 55k in 11 chunks. Each rung records the per-layer PCC trail, the state PCC, the final hidden-state PCC and top-5 agreement. A failure points back to step 5 for the component whose layer first broke the trail.

    Reads
    tt/*.py, goldens
    Writes
    metrics, PCC trail
    Gate
    block ≥ 0.98, state and final hidden ≥ 0.97, top-5 ≥ 0.9 at every rung [P2.11 to P2.14]
  8. 7

    Serving contract

    agent

    The agent writes the adapter and runtime that tt-metal's prefill engine loads, and the per-layer state in the layout the engine migrates. The target is the contract the Blaze prefill CI checks. Generic tests read the state back through the engine's address table and compare it with the goldens using their own PCC. The tt-d-gen audit found two more checks in this scope that the ERNIE run missed: a layer is acknowledged only after its state is readable, and the runtime accepts the engine's uint32 input with a padded tail.

    Reads
    working model, common/prefill/docs/ADDING_A_PREFILL_MODEL.md, repo map
    Writes
    adapter, runtime, cache layout, manifest
    Gate
    layout, table round trip, producer read-back [P2.15, P2.16], ack timing, H2D input
  9. 8

    Performance review

    scripthuman picks

    A script profiles one long chunk per phase and per chip after a warm-up run, and writes an opportunity list. Each entry names a phase, its measured device time, a candidate change, and where in the repo a similar change already exists. The script does not apply anything. A person picks entries, and each picked entry becomes an implement task behind a switch. That task passes only if warm device time drops and every accuracy gate still passes. The person also decides on changes that trade accuracy for speed.

    Reads
    the model, profile, repo map
    Writes
    opportunities.md, per-phase and per-chip profile
    Gate
    profile complete [P3.3]; each picked item passes its own speed and accuracy gate [P3.1, P3.2, P3.4]

An example entry from the ERNIE run, in the form the script would write it: "SDPA, 1,328 ms of 1,570 ms per 50k→55k chunk. The compute config sets fp32_dest_acc_en=True, which turns off SDPA's streaming kernel on Blackhole (sdpa_program_factory.cpp:75). Candidate: HiFi2, fp32 accumulate off, approximate exp, k chunk 512, as in gemma4_d_p and minimax_m3." Picked and measured, this cut 55k TTFT from 10.9 s to 4.4 s.

Bring a block up one component at a time

Yes, this ordering makes sense, and the pipeline should enforce it. A block test that swaps in several device components at once cannot say which one broke the output. Swapping one component at a time, with the rest of the block on the CPU reference, means that when the block output drifts, the component just swapped caused it.

A swap test feeds the golden block input, runs the listed components on the device and the rest on the CPU reference, and compares the block output with the golden block output. The data crosses between host and device at every boundary. That is slow, but only the tests do it.

Bringing up a subset of layers

For a model that does not fit the box, spec.yaml lists the layers to bring up, for example one of each block type plus the first and last layer. The subset changes three things.

  • The golden step still runs every layer on CPU, because a layer's input depends on all layers before it, but it stores boundary tensors and state only for the selected layers.
  • The device runs the selected layers only. When the subset is not contiguous, each run of selected layers starts from its golden input, so the gaps never run on the device.
  • The ladder rungs, the contract tests and the profile use the subset, and every result records which layers it covers. A subset result is never reported as a full-model result.

Resuming and forking a run

A run is a directory with a task ledger, a state file and one git branch. Every passed step leaves a commit tagged with its task id, and an artifact manifest listing the hashes of the files it produced. Three operations use this.

  • resume starts from the first step that has not passed. A hang counts as a failed step: the harness kills the process, resets the device and attaches the triage report to the step's log.
  • rerun --from P2.6 reruns one step and everything downstream of it, keeping the earlier steps.
  • fork --from P2.9 --name runB starts a new branch at P2.9's commit and a new run directory. It reuses the upstream artifacts, such as goldens and weight caches, by reference. Use it after changing an agent definition, to compare the two runs from that step on.

One artifact folder, and what is cached in it

Every file the pipeline creates outside the git tree goes under one root, $ART, which defaults to /localdev/$USER/bringup/. Deleting $ART/<model> removes everything for that model. The ERNIE run spread these over the HF cache, generated/ and the scratch directory, which made cleanup manual.

$ART/<model>/
  hf/                 checkpoint, tokenizer
  golden/<rung>/      boundary tensors, state, logits
    manifest.json     layers, chunks, content hash
  tt_cache/<mesh>/<version>/
                      .tensorbin weights, per task
  profiles/           per-phase, per-chip JSON
  runs/<run>/         logs, triage, briefs, state

Two kinds of data are cached, because tests use them many times.

Weights on device. Every weight goes through ttnn.as_tensor(cache_file_name=...), which stores the tilized, bfp8-packed, per-device tensor as a .tensorbin file. A 4096×14336 weight loads in 0.01 to 0.02 s from the cache against 0.3 to 0.8 s from torch. The file name holds only the name, dtype and layout, so the path must add the mesh shape, the sharding and a version. The cache writes to a temporary name and renames, so an interrupted run cannot leave a half-written file. Source: tensor_caching_research.md.

CPU reference outputs. Goldens are recorded once per rung. Tests, swaps, ladder rungs and contract checks all read them and pin their content hash, so no gate runs the CPU model again.

What the planner starts from

The planner writes plan.md in a fixed shape: for each layer type, a table with one row per component that lists what each chip holds, the collective that follows it, and the per-chip memory. It closes with a per-chip memory total and the per-layer list of collectives. Two reference plans show the shape.

  • The Kimi K2.7 layer on a 4×4 mesh, from the artifact shared in this project. It shows rows splitting tokens and columns splitting weights, the dispatch and combine traffic per column, and a time per step.
  • ERNIE on a 1×4 mesh: models/demos/ernie45_d_p/SHARDING.md and bringup/plan.py. It shows one KV head per chip, 16 experts per chip, and the memory check that the plan gate runs.

The planner copies the table shape, not the numbers. A plan that departs from both references says why in one sentence per departure.

The repo map

The ERNIE run lost time searching for things the repo already had. It first wrote its own MoE and only later found unified_routed_expert_moe. The repo map is a checked-in file of pointers that every agent reads first, grouped by what they are for. Agents add rows when they find something new, and a person reviews the additions at the next approval point.

The known-issues file

Every agent reads the known-issues file before it starts, because the brief includes it. It has five sections: API behavior, accuracy, performance, infrastructure, and serving contract. Each entry names the symptom, the cause, the fix, the task where it was found, and the model. An agent that hits a new issue adds an entry in a proposed section at the end of its step. The gate checks the entry's format, and a person moves it into its section at the next approval point. Entries from the ERNIE run would seed it.

Inside one gate

The gate runner is a small script, gate.py in the ERNIE run. It never decides anything that was not written down before the step started.

Five rules came out of problems the ERNIE run hit. The runner enforces each one; none depends on agent instructions.

  • Tests compute PCC with their own function, because of the comp_pcc stub listed in the known issues.
  • The runner pins PYTHONPATH to the checkout. An inherited value pointed at a second checkout and mixed modules from both.
  • A commit stages only the task's declared paths. A background gate once committed files another step was still editing.
  • Performance gates measure a warm run. The first run with new SDPA kernels compiled one program per chunk offset and read 22 s instead of 4.4 s.
  • The runner locks the task ledger and the state file. Two gates running at once overwrote each other's verdicts.

Where it stops being model-agnostic

  • The reference parity gate needs an oracle. Models without an HF implementation need another trusted forward pass, or a reference a person reviews.
  • Chunked prefill of non-attention state is less uniform. Sliding windows, recurrent state and compressed caches each need a state template, and the chunked-equals-one-shot gate has to know which state to compare.
  • The Blaze contract assumes attention KV with one KV head per tensor-parallel column. Other state types need the engine to support them first.
  • Sharding depends on the model and the box together. The planner proposes it and a person approves it, because no gate measures whether a different split would have been better.
  • Missing TTNN ops end in COMPOSED or CPU tags. Composing an op well took the most judgment in the ERNIE run.
