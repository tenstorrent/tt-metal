models/demos/common/bringup

Gated prefill bring-up

A framework that brings up chunked prefill of a Hugging Face transformer on Tenstorrent hardware. A Python script walks a fixed list of tasks. Claude agents write the code for each task, and a test written before that code decides whether the task passed. A supervising Claude session watches the run and reports to a person.

Status in use, 4 bring-ups done Box 4x Blackhole p150b Updated 2026-09-28 Entry point /bringup skill

The one rule

No agent decides that its own work is correct. A step passes when a test that was written, checked against the CPU reference and frozen before any implementation existed says it passes.

Every test is frozen only after it passes with the CPU reference plugged in and fails with a module that returns zeros. After that, the runner refuses any change to it. An agent can retry within its budget, but it cannot change the test.

The goldens (the CPU reference's outputs for a fixed input text) are computed once per checkpoint and hashed. Every accuracy check in the run compares against them.

Who does what

script

Orchestrator

A plain Python loop (orchestrator.py). It reads tasks.yaml, picks the next task whose dependencies passed, writes a brief, starts an agent, runs the gate and commits. It makes no decisions of its own.

agent

Bring-up engineer

A fresh claude -p for every step, with one role (reference, plan, test, implement, fix, contract, perf, optests). It gets a brief, a list of files it may touch, and the log of its last failed attempt.

overseer

Supervising session

A Claude Code session running the /bringup skill. It writes the spec with the person, launches the run, reads every gate commit, rejects cheating, fixes the framework when it misbehaves, and publishes the dashboards.

person

Owner

Approves the spec, the sharding plan and the performance picks. Resets the board and pushes. Everything else the overseer decides and logs.

How one step runs

A gate is mechanical. It passes only when all of these hold:

  • every dependency passed, and every frozen file still has its recorded hash;
  • the command exits 0, every metric meets its threshold, and every expected result file exists;
  • the device ran only through scripts/run_safe_pytest.sh or scripts/tt-probe.sh;
  • the agent changed files only inside the paths its brief allowed.

The runner then formats the files, commits only the task's paths, and records the metrics in results/<task>.json and state.json. When a person is needed, the orchestrator exits with code 3 and waits. orchestrator resume continues from where it stopped.

The steps of a bring-up

The order below is the order the ledger runs. A 6-layer MoE model ends up with about 60 tasks; a 48-layer one with more component tasks, because each distinct block type gets its own.

  1. 1

    Intake

    overseerperson

    The overseer interviews the person, checks the checkpoint and the box, and writes spec.yaml: target length and chunk size, the ladder of test lengths, block types, owner rules for every agent, dashboard style. Nothing runs until the person approves it.

  2. 2

    CPU reference (R.1 to R.3)

    agent

    An agent writes a standalone CPU reference of the model, split into the steps a device version would swap one at a time. The gates check it against Hugging Face to PCC 0.9999, check that chunked prefill equals one-shot prefill, and check that each block's graph replays exactly.

  3. 3

    Goldens and box check (G.*, B.1)

    script

    A script runs the reference over each ladder rung (up to 56k tokens) and stores every layer's outputs and KV state with a content hash. Another opens the mesh and checks that the collectives are exact.

  4. 4

    Plan (PL.0, PL.1)

    agentperson

    An agent maps every component to TTNN ops and shards the model over the mesh. The gate recomputes per-chip memory from the real checkpoint shapes, so a plan that does not fit fails. The person approves it; any later edit to the plan voids the approval.

  5. 5

    Components and swaps (C.*, S.*)

    agent

    One component at a time (a norm, attention, the router, the experts). A test agent reviews the generated test, the runner freezes it, and an implement agent writes the device module. Then a swap test runs the whole block with steps 1 to n on the device and the rest on the CPU, so an error shows up in the step that caused it.

  6. 6

    Assemble and ladder (M.1, L.*)

    agentscript

    An agent builds one device model whose hidden state stays on the device from the embedding to the final norm. The ladder then runs it at growing lengths (4k, 16k, the last chunk after a 50k golden prefix, the full 56k) and checks every layer, the KV state and the top-5 tokens. A failure starts a fix agent.

  7. 7

    Serving contract (K.1)

    agent

    An agent makes the model servable by the shared prefill engine (models/demos/common/prefill): the adapter, the KV layout and address table, and the handover to decode.

  8. 8

    Performance (X.1, X.2, P.*, X.3)

    scriptpersonagent

    A warm profile, a ranked list of opportunities, the person's picks, one agent task per pick, and a final full-length accuracy and speed check. The next section covers this.

  9. 9

    Fork tests (O.1)

    agent

    Every call the model makes to a bring-up op gets a random-input test case in that op's folder. See the bring-up ops section.

The overseer

The orchestrator is fixed code, so something has to handle what it cannot: an agent that needs a file outside its paths, a framework bug, a board that stops responding. That is the overseer, a Claude Code session running the /bringup skill (skill/bringup/SKILL.md).

It decides routine things itself and logs each decision in supervision.md. It asks the person only for the spec, the plan, the performance picks, a board reset, a push, or when the data looks wrong (for example implausible accuracy or degenerate text).

It never edits the tree while an agent runs, because the path check would charge the edit to that agent. It pauses the orchestrator first.

It reads the diff of every gate commit, not only the verdict. It reverts a commit and reruns the task when the agent:

  • loosened a threshold or edited a frozen test, a golden or the ledger;
  • special-cased the test input or read the golden inside the model;
  • hid CPU work in a device module;
  • swallowed an error instead of fixing it;
  • faked an interface to get past a check.

It also republishes both dashboards (a standard page and a teletext page) after every gate.

Performance

Functional bring-up comes first, at HiFi4 everywhere and bfp4 weights only where the checkpoint itself is 4-bit. Speed work starts only after the full model passes every accuracy gate, and each speed change has to pass them again.

The profiler books every TTNN call to a layer and a section (L5.attention.sdpa) with its shapes and tensor placement (DRAM or L1, interleaved or sharded). It also records a pipelined timeline of the critical chip with each op's kernel time, the idle gap before it and the host dispatch time. The dashboard shows this per block type.

TaskWhat happens
X.1Warm profile of one long chunk (50k to 55k tokens), per section and per chip.
X.2A ranked list of sections by device time, each linked to the known issues and repo-map rows that apply. The run stops here.
P.*The person marks picks. Each becomes one perf task with the exact change in its brief, behind a switch so the old path stays selectable. Its gate reruns the frozen tests of every layer the change touches, an accuracy rung and the profile, with a time threshold below the baseline.
X.3Final check at the full 56k: per-layer accuracy, warm time-to-first-token, the per-op profile and timeline.

On MiMo-V2.6 (layers 0 to 5, mesh 1x4) the 50k to 55k chunk went from 1122 ms of device time at X.1 to 204.9 ms after the perf tasks and later fusions. The 2x2 run started at 278.5 ms and ended at 249.9 ms after one pick.

Bring-up ops

A bring-up never edits an existing TTNN op. When a model needs an op to behave differently (a missing feature, a precision option, a bug on one mesh shape), the agent copies the op into ttnn/ttnn/bringup/<op>/ with fork_op.py and changes the copy. The copy registers as ttnn.bringup.<op> next to the original, builds with ./build_metal.sh, and gets a CHANGELOG.md (source path, source commit, every change with its reason) and a row in INDEX.md.

Forks are shared. The next model reuses a fork before making a new one, and puts any new behaviour behind an option that is off by default, so the models already using the fork get the same program. A person decides later whether a change goes back into the original op.

Each fork carries two kinds of tests.

  • A best-effort selection of the source op's own tests, listed in tests/source.yaml and run in place with the original op's name pointing at the fork. A recorded baseline says which of them pass.
  • One random-input case for every distinct call a model makes, added by task O.1 (skill bringup-fork-tests). The O.1 gate runs every model's cases, so a change made for one model fails if it breaks another.

Extending a fork follows a fixed recipe in skill bringup-fork-op. Start from the recorded baseline, iterate on a few targeted cases and the model's own gate, then run the full regression once.

Prior bring-ups

A checkpoint that was already brought up can be brought up again on another mesh or configuration: new --prior <slug> --mesh R,C. The new bring-up shares the prior's checkpoint download, CPU reference and goldens. Its reference and golden tasks pass on their first check without an agent, and every brief gets a section pointing at the prior's matching files. Implement agents copy the prior's modules and adapt them; they never import them.

MiMo-V2.6 on a 2x2 mesh ran this way. All 60 tasks passed on their first attempt, and the accuracy matched the 1x4 run to four digits.

What every agent reads first

knowledge/repo_map.md lists, per problem, the best existing code to start from (a MoE dispatch on a 2D mesh, a sliding-window attention, a serving KV contract). knowledge/known_issues.md lists traps the earlier runs found, each with its symptom and fix. Agents add rows as they learn; a format check keeps both files parseable.

The spec's agents.rules hold the owner's rules for one model and appear in every brief. The agent definition (agents/bringup-engineer.md) holds the standing rules for all models, for example 2D fabric only, no edits to existing TTNN ops, and HiFi4 during functional bring-up.

What a run leaves behind

In git, per model

  • bringup/spec.yaml, tasks.yaml, state.json and results/
  • plan.md, plan.yaml, opportunities.md
  • BREADCRUMBS.md (what each agent learned) and supervision.md (every overseer decision)
  • tt/ (the device model) and tests/bringup/ (the frozen tests)

Outside git

Everything large lives under /localdev/$USER/bringup/<model>/: the checkpoint in hf/, the goldens, the weight cache, the profiles, and per run the orchestrator log, every brief and every agent transcript.

Where to start

In Claude Code, type /bringup and name the model. The skill does the interview, the spec, the launch and the supervision. To run the pieces by hand:

# the shell's default PYTHONPATH points at another checkout
export PYTHONPATH=$PWD
B="python -m models.demos.common.bringup"
$B new --model <slug> --hf-id <org/name>        # or: $B new --prior <slug> --mesh 2,2
$B approve intake --spec models/demos/<slug>/bringup/spec.yaml
python -m models.demos.common.bringup.plan.ledger_gen --spec <spec> --early --write
$B init-run run1 --spec <spec>
python -m models.demos.common.bringup.orchestrator run --spec <spec>
$B status --spec <spec>                             # approve plan|perf, rerun --from, fork, compare

Further reading in the repo: models/demos/common/bringup/README.md (layout and the rules the runner enforces), the three skills under skill/, ttnn/ttnn/bringup/INDEX.md, and dev/BREADCRUMBS.md (how the framework itself was built, changes F1 to F45).
