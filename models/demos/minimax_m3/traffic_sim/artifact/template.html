Feature priorities

Each scenario has two numbers per feature, measured from opposite ends:

  • G = gain when added (step #). Start from today's configuration, try every feature and keep the best; repeat from the new configuration until all features are in. "×1.65 #2" = this feature was the 2nd one added and multiplied goodput by 1.65 at that point. The order is a suggested build order; a gain depends on the features added before it.
  • LOO = loss if removed (leave-one-out). Start with every feature on and turn only this one off. "×1.96" = goodput drops 1.96x without it. ×1.00 = it adds nothing once everything else is on. That is usually because another feature does the same job: bounded dense gather and variable-size lanes both remove the whole-slot scan, and variable chunk already includes unaligned resume.

Columns: "4gx today" = 4 galaxies with today's kernels, "4gx roofline" = 4 galaxies with kernels at roofline targets, and the same for 8 galaxies (Method tab).

Order and tier come from the "8gx today" column (8 galaxies, today's kernels): the larger of its G and LOO, highest first. P0 ≥ 1.25x, P1 ≥ 1.07x, else P2. The other columns show how the value changes with fewer galaxies or faster kernels. Complexity is a rough low / med / high judgement of the implementation work (Method tab).

How the cost model is calibrated

Every layer is split into the ops the implementation runs. Each op has a roofline time from its FLOPs, DRAM bytes and ethernet bytes on the stage mesh (Blackhole: 608 TF LoFi / 304 TF HiFi2, 512 GB/s GDDR6, 100 GB/s bidirectional CCL per axis). What this page is

A planning tool for the MiniMax-M3 prefill service on Tenstorrent Blackhole galaxies. It asks which implementation features and which hyperparameters give the most overall system throughput on realistic agentic traffic, rather than on one benchmark cell. It combines three things:

  • Real traffic. The public AgentX corpus of Claude Code sessions, replayed request by request the way the SemiAnalysis InferenceX AgentX benchmark replays it.
  • A cost model of the M3 prefill pipeline: a per-op roofline whose efficiencies are fitted to hardware measurements (section "Cost model").
  • A KV-cache model that tracks which prefixes are resident, evicts them, and charges re-prefill when a prefix was lost (section "KV cache").

The Explore tab runs the same simulator in your browser for any configuration you choose. Roadmap shows a precomputed study that ranks features. Model & calibration shows how well the cost model reproduces measured runs.

Context: the system being modelled

  • Model. MiniMax-M3: 60 layers.
    • Layers 0-2 are dense: full-attention GQA plus a dense SwiGLU MLP.
    • Layers 3-59 are MoE with MSA sparse attention: 128 experts, top-4, plus 1 shared expert; the indexer selects 16 blocks of 128 keys per query.
    • Dimensions: hidden 6144, 64 query heads, 4 KV heads, head dim 128, max context 1,048,576 tokens.
  • Hardware. A galaxy is 32 Blackhole chips, each with 32 GiB GDDR6 at 512 GB/s. Prefill runs as a pipeline: the 60 layers are split over S stages, and each stage is a sub-mesh [SP, TP]. [2,4] means 8 chips: the sequence is split 2 ways (SP), heads and hidden are split 4 ways (TP), and MoE experts are spread over the stage. The measured deployment is 4 galaxies = 16 stages of [2,4].
  • How it works today:
    • Static slots. The KV cache is a set of fixed 1M-token slots, one per conversation. Resuming a conversation reuses its own slot's prefix and nothing else.
    • Fixed chunk, one request per chunk. Each chunk (5120 or 2048 tokens) carries one request, and the tail is padded. The chunk size is fixed because the KV cache is laid out block-cyclically over the SP axis with a period of chunk/SP.
    • Chunk-aligned resume. A resumed request must start at a chunk multiple; cached tokens past it are recomputed.
    • Whole-lane dense scan. The dense layers' ring-joint attention walks the whole slot capacity on every chunk.
  • Measured performance is tracked in tenstorrent/tt-metal issue #57827. The runs used here (Sep 27 2026, 4 galaxies, 16×[2,4], bf4 experts, bf16 index cache):
    • A: chunk 5120, even layer split.
    • B: chunk 5120, split 1,1,1,5,5,5,5,5,4,…
    • C: chunk 2048, same split as B.
    Each run measures a (new tokens × cached tokens) matrix, loaded and idle. The preset today-C is run C.
  • Features under consideration (defined in "Features" below): batching several requests per chunk; slot lanes plus a paged KV pool; variable chunk size with an all-to-all KV write; plus a few more the study adds (host-DRAM tier, index-cache layout, async stage handoff, bounded dense gather, and others).

The metric: goodput

Goodput = useful tokens per second, at the highest load where p90 TTFT stays at or below the SLO (default 10 s). Why each part:

  • Useful tokens, not processed tokens. A request's useful tokens are the ones an ideal system with an infinite prefix cache would still prefill: its input minus the longest prefix already seen earlier in the same session. Tokens recomputed because a cached prefix was evicted, because resume had to be chunk-aligned, or because they are padding count as processed but not useful. Processed throughput rewards a thrashing cache. In one configuration the pipeline processes 210k tok/s while only 50k tok/s of it is useful.
  • Only prefill work counts. Useful tokens exclude cached tokens and decode. For a fixed traffic mix, useful tok/s is proportional to requests served per second.
  • At an SLO, not at peak. In a closed-loop replay, throughput first rises with concurrency and then collapses. More live sessions stop fitting in the KV cache, evictions turn into re-prefill, TTFT grows to hundreds of seconds, and idle KV then gets evicted even faster (the "cache cliff"). The SLO picks an operating point a real deployment could run at.
  • The SLO is loose on purpose (p90 ≤ 10 s; today's single-request TTFT is about 1-2 s) because throughput is the priority. p90 is used rather than the median because p90 sees the queueing blow-up earlier. The collapse is sharp, so the best SLO-free throughput is almost identical to goodput (see the sensitivity table), and the ranking does not depend on the exact SLO. You can change the SLO on the Explore tab.
  • Finding the cliff. The throughput-vs-concurrency curve is steep near the cliff: two neighbouring grid points can differ by 10% or more. After the grid sweep, the simulator therefore bisects (in log concurrency) between the best point that meets the SLO and the next one that fails it, 4 more runs, which locates the cliff to about 1% in concurrency. If the failing point still has higher throughput, goodput is also interpolated to the SLO crossing. The page and the Roadmap study use the same rule.

Glossary

  • Concurrency / lanes (C). The number of simultaneous simulated agent users. Each lane replays one session: the main agent plus the sub-agents it spawns, so one lane can have several requests in flight.
  • TTFT. Time from when a request becomes ready (its predecessor finished and its recorded think time elapsed) to when its prefill finishes on the last pipeline stage. It includes queueing and any host-tier fetch.
  • Hit rate. Cached tokens / input tokens, token-weighted. The ∞-cache hit rate is the ceiling (98.3% on the whole corpus).
  • Re-prefill. New tokens that were not needed with an infinite cache: evicted prefixes, alignment loss, and history from before the replay's start point that was never materialised.
  • Padding. Tokens computed only to fill a fixed-size chunk.
  • ∞ cache. The same configuration with an unbounded KV cache. It separates cache losses from compute limits.
  • Stage, mesh, SP/TP, split, replicas. See "Context". The split is how many layers each stage holds; "auto" balances the stages for a representative mix of cached lengths. Replicas divides the galaxies into independent pipelines, each with its own cache; sessions stick to one replica.
  • Scenario labels. "Today's kernels" = op-efficiency 0 (k0); "roofline kernels" = op-efficiency 1 (k1). See the section on kernels.
  • Tiers. P0 / P1 / P2 = priority from the study; the rule is in "How the study works".
  • Complexity (low / med / high). A rough judgement of how much of the stack a feature touches. Low: one op or the scheduler, plus validation. Med: a new op or allocator, or changes across a few ops. High: cross-cutting changes to the runtime, KV layout, several kernels and the scheduler. Not validated with the code owners.

Traffic replay

The corpus is semianalysisai/cc-traces-weka-062126, full variant: 393 Claude Code sessions, 98,827 requests (56,798 main-agent turns and 42,029 sub-agent requests), 21.6B input tokens, inputs up to 990k tokens. Each request lists its input as a chain of 64-token block hashes. Equal hashes mean identical content, so the prefix a request shares with earlier requests is known exactly. The replay follows the rules of AIPerf's inferencex-agentx-mvp scenario, read from its source:

  • Start point. Each lane starts its session at a random instant t* anywhere in the session.
  • Primers and warmup. Every conversation active at t* first re-sends its last request before t* as a primer: a full prefill with max_tokens=1. That warms the cache the way the benchmark does. Measurement starts when all primers are done.
  • Think time. Each next request waits for its predecessor to end, then for the recorded gap: max(0, tk − tk−1 − api_timek−1). The gaps are not capped, as AgentX requires. Main-agent gaps have a median of 4.9 s but a mean of 395 s (p99 54 min), because humans think and tools run. The only cap is AIPerf's rule that if the whole system is idle, the next request fires within 10 s.
  • Sub-agents. A sub-agent starts when the main-agent turn that spawned it returns. The main agent's next dependent turn fires as soon as the last sub-agent in its group finishes.
  • End of a request. Prefill finishes, then decode runs for the recorded output length at a fixed decode speed (default 180 tok/s). The output's KV is not reused: the benchmark sends synthetic assistant text in the next turn, which is prefilled like any other new text.
  • Recycle. When a session's whole tree is finished, the lane moves to the next session in the corpus and starts at turn 0 with a fresh cache-bust marker, so different lanes never share cache.
  • Window. 1800 s of profiling (the AgentX default). Goodput counts requests whose prefill ends inside the window.

Consequence. Because the gaps are long, an AgentX lane is idle most of the time. Filling the prefill pipeline takes hundreds to thousands of lanes. Their combined KV then exceeds what the galaxies can hold, and KV capacity rather than compute becomes the limit. This is the main finding of the study.

Cost model and its calibration

Per-op roofline. Every layer is broken into the ops the implementation runs.

  • MoE/MSA layer: two norm all-gathers, QKV projection, index branch, all-gather of the cached K/V and index keys over SP, indexer, sparse attention, output projection + reduce-scatter, shared expert, router, dispatch, experts, combine, MoE reduce, misc.
  • Dense layer: ring-joint attention plus the dense MLP and its collectives.

For every op the model computes its FLOPs, DRAM bytes and ethernet bytes for the given mesh, chunk, request lengths and cache depth. From these it takes the time the op would need at peak hardware rates, its "roofline": 608 TFLOP/s LoFi / 304 HiFi2 per chip, 512 GB/s DRAM, 100 GB/s bidirectional ethernet per mesh axis.

Step 1: per-op efficiency from profiles. Profiles of one prefill chunk (5120 tokens attending a 51,200-token cache) give each op's measured time on [2,4], [8,4] and [4,2] stages. Each op's efficiency is roofline / (measured − fixed latency). Examples at [2,4]: experts_mm runs at 28% of its roofline and sparse_sdpa at 4% (Model tab). Other chunk sizes and cache depths are predicted by scaling each op's roofline at that fixed efficiency. [4,4] has no profile and uses the geometric midpoint of [2,4] and [8,4].

Step 2: pipeline-level fit. The profiles come from a single-stage harness with small cache capacity, so they miss a few things the real 16-stage pipeline shows. A small number of extra parameters is fitted to 7,840 per-stage, per-chunk-position timings of runs A/B/C:

  • MoE multiplier ≈ 1.03: MoE layers run about 3% slower in the pipeline. The pipeline uses the 2D fabric, where one dispatch fast path is disabled.
  • Dense attention = compute part + capacity-scan part, whichever is larger. Compute runs at 30% efficiency. The scan walks the whole slot capacity every chunk at 1.4% efficiency, about 100 ms per 1M-token slot per dense layer per chunk. The profiles cannot separate the two because their capacity was only 56k.
  • Handoff between stages.
    • Blocking send (about 18 ms per chunk at 5120, 7.5 ms at 2048): the stage stays busy after computing. Fitted as the measured loaded chunk period minus the slowest modelled stage.
    • Hop latency (about 16 ms / 14 ms): delays the chunk's arrival at the next stage. Fitted as idle TTFT minus the sum of stage times.
  • Embedding cost about 1.5 ms per chunk on stage 0.
  • Two structural facts:
    • Padding is cheaper in the MoE. Routing, dispatch, experts and combine only process a chunk's real tokens, so a 640-token request in a 5120 chunk costs 18% less than a full chunk.
    • Today's expert kernel costs weight read + compute, not the larger of the two.

Check. Replaying all 105 cells of the #57827 matrices with the fitted model gives a few percent median error on loaded throughput and idle TTFT (Model tab, full table). Anything far outside the measured range is extrapolation: batched chunks above 5120 tokens, meshes without a profile, stage counts other than 16.

"Today's kernels" vs "roofline kernels" (the op-efficiency knob)

  • Op efficiency 0 (k0, "today's kernels"). Every op keeps its measured efficiency from the calibration. For configurations that have been run, it reproduces measured performance. For configurations that have not (batching, a paged pool, other meshes), it projects how today's kernels would perform.
  • Op efficiency 1 (k1, "roofline kernels"). Every op runs at a realistic target, not raw peak: 70% of peak for matmul-type ops and 80% for DRAM- or link-bound ops. Latency floors drop from 0.04 to 0.02 ms per collective and from 0.01 to 0.005 ms per op. The expert kernel overlaps its weight reads with compute. The pipeline MoE multiplier becomes 1.0, stage overhead 0.3 ms and embedding 0.3 ms. The dense capacity scan runs at link rate. It is an optimistic bound for "kernels get fixed", not a forecast.
  • In between. Each op's efficiency is interpolated geometrically, so 0.5 is a middle case.
  • Not affected by the knob: the blocking stage handoff and hop latency (that is the separate "async handoff" feature), expert-load imbalance (fixed at 1.2×), KV memory sizes, and the traffic.

KV cache

  • KV size. Per token per layer: K and V cost 1088 B (bf8). The index-key cache costs 128 values × 2 B (bf16) and is today stored on all 4 TP columns, so 1024 B. Total 2112 B per token per layer, about 127 KB per token over 60 layers, about 133 GB for one 1M-token context. Four galaxies hold about 21.5M tokens of KV after weights and reserves, which is 20 static 1M slots.
  • Static slots (today). A conversation owns one 1M slot while it is resident. A new conversation takes a free slot or evicts the least recently used idle one. A hit is the prefix shared with that conversation's previous request, rounded down to a chunk multiple unless "unaligned resume" is on. Slots are never shared across conversations.
  • Slot lanes + paged pool. A few lanes per stage are the contiguous KV buffers the attention kernels run on (fixed 1M each, or sized per request in an arena). All other memory is a paged pool: content-addressed pages shared by every conversation that has the same prefix, evicted by exact least-recently-used order. Before a request runs, its cached prefix is copied from the pool into its lane; afterwards the new tokens are copied back. The copies are DRAM-bound, overlapped with compute, and charged 25% for bandwidth contention.
    • Lane scope. A lane is held per stage only while that stage works on the request (the per-stage scope). Today's slot_id is global, so a slot is held on every stage for the whole request.
    • How eviction is tracked. Each session's prefix tree is compressed into pieces. Every request touches whole pieces, so LRU over pieces is exactly LRU over 64-token pages.
  • Host-DRAM KV tier = offloading KV to the host servers' RAM.
    • Mechanism. When the device pool evicts a page, it is written to host RAM instead of being dropped. A later hit on it is copied back over PCIe into the request's lane while the request waits in the queue. Host RAM evicts least-recently-used too. Write-backs and fetches share the PCIe link.
    • Defaults: 1 TB of host RAM and 64 GB/s of PCIe per galaxy. Both are assumptions, not measured galaxy-host specs.
    • AgentX cap. The methodology caps host DRAM at 3 TB per system, except for a few standard rack systems, and a configuration may use only the share of host DRAM proportional to its accelerator allocation. A compliant submission may therefore have less than the default (4 TB at 4 galaxies). The sensitivity table shows 0.5 and 2 TB per galaxy.
  • Full paging (ideal). Kernels read paged KV directly: no lanes, no copies. It can have the host-DRAM tier behind it, like the pool; compare paging and pool with the same host setting.
  • Infinite cache. Nothing is ever evicted.

Pipeline and scheduling

  • Stages and chunks. Stages process chunks in order. A chunk's time on a stage is the sum of its layers' costs plus overhead; then the blocking send runs; then the hop latency applies before the next stage can start it. At most 2S+4 chunks are in flight.
  • Fixed layout (today). One request per chunk, padded to the chunk size.
  • Variable layout. Chunks of any size. Each request's segment is padded only to 32·SP tokens, and each layer pays an all-to-all that writes the new K/V rows to the SP rank that owns them. Resume is block-granular.
  • Batching. Several requests share a chunk, up to the token budget. Projections and MoE run on the whole batch; that is where the gain comes from, since expert weights are read once for more tokens.
    • Sequential attention runs once per request.
    • Fused attention runs once per chunk.
    • Both include a penalty for short segments that leave some of the 110 cores idle.
    With fixed layout, batching packs whole chunks.
  • Queue order. First-come-first-served, or shortest-first with 30 s aging.
  • Memory per stage. Weights (bf4 experts, bf8 attention, bf16 shared expert and dense MLP; embedding on the first stage, LM head on the last) + a reserve per chip (default 3 GB) + activation buffers for the largest chunk. The remainder is KV. A replica's KV capacity is the minimum over its stages, because every token needs KV in every layer.

Features in the study

  • Slot lanes + paged pool: replaces static slots (see KV cache): 4 fixed 1M lanes per stage.
  • Variable-size lanes (arena): lanes allocated at the request's actual length from a contiguous arena (2-8M tokens) instead of 1M each.
  • Host-DRAM KV tier: see KV cache. It requires the paged pool or full paging.
  • Bounded dense gather: the dense layers' ring-joint attention scans only the valid prefix [0, kv_len) instead of the whole lane capacity. The MSA layers already do this. Request-sized lanes (arena) remove the same cost, so the two are substitutes.
  • index_k stored once: the index-key cache is kept on one TP column instead of all four, and gathered when needed. This cuts KV size from 2112 to 1344 B per token per layer.
  • index_k bf8: the index-key cache in bf8 instead of bf16. It is the runner's default dtype, but the measured runs used bf16, and it needs an accuracy check.
  • Variable chunk / flexible SP layout: see Pipeline. It also makes resume block-granular.
  • Unaligned resume: resume at any 32-token boundary within fixed layout. In review as PR #57636. Variable layout subsumes it.
  • Multi-request batching: see Pipeline; 16k-token budget in the roadmap, 4k-32k in the grid.
  • Fused multi-user attention: one attention kernel over all requests in a chunk.
  • Async stage handoff: the send to the next stage overlaps with computing the next chunk. Removes the blocking send; the transfer then runs at link rate.
  • MSA SP-local indexer: each SP rank scores its local index keys, a small top-k merge follows, and only the selected K/V blocks are fetched. Removes the all-gather of the whole cached prefix.
  • Shortest-first scheduling: queue order by new tokens, with 30 s aging.
  • Each feature has a longer explanation (what it is, why it helps, what needs to be done, interactions): click its name in the Roadmap table.

How the study works (Roadmap tab)

  • Four scenarios: {4 galaxies, 8 galaxies} × {today's kernels, roofline kernels}.
    • Baseline, 4 galaxies: 16×[2,4], auto split, chunk 2048, static 1M slots. This is run C's shape.
    • Baseline, 8 galaxies: 32×[2,4], same settings.
  • Concurrency sweep. Each configuration is simulated at C = 8 to 4096 (28 points), stopping early once it is past the cache cliff, and summarised as goodput.
  • Greedy roadmap ("gain when added"). From the baseline, try every remaining feature, keep the one with the largest goodput, repeat. The order is a suggested build order; each gain is measured in the context of the features before it.
  • Leave-one-out ("loss if removed"). Start from all features on, remove one at a time. It shows what each feature is still worth at the end.
  • Priority order and tier. Both come from the reference scenario, 8 galaxies with today's kernels: take the larger of the feature's greedy gain and its leave-one-out loss there, and sort highest first. P0 ≥ 1.25×, P1 ≥ 1.07×, else P2. One scenario is used on purpose. A maximum over scenarios lets a feature rank high on one column, and substitutes such as bounded dense gather and variable-size lanes both get credit that only one of them earns.
  • Grid. On the features that helped, search topology (stage count × mesh × replicas), batching budget or chunk size, and lanes or arena size. The top result per scenario becomes the best-* preset.
  • Sensitivity. The best configuration re-run with:
    • other seeds (about ±5% noise);
    • 0.5 or 2 TB host RAM per galaxy;
    • 16 or 256 GB/s PCIe per galaxy;
    • decode at 90 or 360 tok/s;
    • a 6 GB reserve per chip;
    • a TP=4-only mesh.
    Faster decode raises prefill goodput because requests finish sooner, fewer lanes carry the same load, and less KV is live.
  • [4,2] stages (TP=2) win the grids by 1-10%. The current KV cache assumes one KV head per chip (TP=4), so they need a KV-head sharding change.

Reading the Explore tab

  • Loading. On load, the charts show the precomputed baseline (today-C). Run sweep simulates your configuration at every concurrency in the grid, in your browser, in about 5-30 s. It also runs the same configuration with an infinite cache, unless you untick that option.
  • Tiles. Goodput; goodput with an infinite cache; TTFT p50/p90 and hit rate at the goodput point; and the peak useful throughput regardless of TTFT.
  • Charts share a log concurrency axis:
    • useful tok/s;
    • p90 TTFT on a log scale, with the SLO line;
    • hit rate.
    "Pin as comparison" keeps a run as a third line.
  • Where processed tokens go. At the goodput point, splits the pipeline's processed tokens into useful, re-prefill and padding.
  • Plan. Updates without simulating. It shows chips, KV capacity, slots or pool and lane sizes, KV bytes per token, and the modelled time of one chunk (at 140k cached) on each stage. Orange bars are stages holding a dense layer; the outlined bar is the bottleneck. The ceiling line is that chunk's tokens divided by the bottleneck time plus the send.

Assumptions and limits

  • Host tier. Host RAM size, PCIe bandwidth and the ideal page DMA are assumptions. Host RAM size matters a lot for the result; PCIe bandwidth hardly does.
  • Pool copies. Assumed to be page-list gather kernels at 50% DRAM efficiency. Arena fragmentation is not modelled.
  • Decode. A fixed per-request speed. Decode-side capacity and KV migration to decode are not modelled.
  • Extrapolation. Batched chunks above 5120 tokens, meshes without a profile, and stage counts other than 16 are extrapolated. [4,2] stage costs come from a single-stage profile.
  • Memory figures are approximate. The 3 GB per-chip reserve and the activation-buffer estimate are approximations.
  • Complexity bins are rough and not checked with the code owners.
