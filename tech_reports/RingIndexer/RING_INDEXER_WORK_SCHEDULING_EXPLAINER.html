Fused Ring Indexer · scheduling explainer

Same work.
Better finish.

Today, every K shard deals its remainder from lane zero. The same few lanes repeatedly receive the tail and become the critical path. The proposed schedule rotates each arrival wave across the full block-column lane space—without changing KC, readiness gates, CCL routing, or the cached program.

01 · Mental model

Three layers, one critical path

Fabric determines when a physical K shard becomes readable. The host-built work list determines which compute lane owns each KC-sized unit. Runtime kv_len determines which capacity-sized units are nonempty. The proposal changes only the middle layer.

①

Shard arrival

Local data is wave 0. Remote shards arrive in paired forward/backward waves and expose midpoint and completion readiness markers.

②

Static work list

Every physical shard is split into KC units. Each unit is assigned to a combined block-column lane before the program is cached.

③

Runtime prefix

Units wholly beyond kv_len are skipped. A nonempty boundary unit still pays the full KC compute cost, so nonempty units—not valid tiles—set scheduling load.

02 · Grid geometry

How 100 or 110 cores become 20 or 22 lanes

A scheduling lane is not one physical Tensix core. It is one (row block, compute column) pair whose K work list is shared down five query-group rows. Two row blocks use all ten grid rows. That makes the lane count 2 × compute columns. The drawing says “rows × columns”; factory equations use grid.x × grid.y = columns × rows.

22 is measured geometry, not an LB constant

The LB run that produced 22 lanes exposed a 12×10 compute-with-storage grid, leaving 11×10 after the AG column. It also reported only one harvested column. A production box exposing 11×10 before AG reservation would leave 10×10 and therefore use 20 lanes, just like QB.

Lane space: block + column × blocks

Each cell is a destination lane. Its large number is the source residue assigned in the active proposed wave. Columns rotate; row-block parity stays fixed.

A cyclic permutation

No unit is created, dropped, split, or moved across a shard. Wave 0 naturally has shift zero.

lane_count = blocks × columns
lane       = block + column × blocks

stride = max(1, floor(columns
              / (wave_count + 1)))
column_shift = (wave × stride) % columns

source_column = (column + columns
                 - column_shift) % columns
source = block + source_column × blocks

unit = source + round × lane_count
05 · Readiness is preserved

Rotate ownership, not arrival order

The two shards in a bidirectional wave receive the same shift. Their physical source offsets remain monotonic, and the work list still interleaves matching offsets. First-half units can use the midpoint marker; later units still wait for completion.

06 · Trace and program-cache stability

Static strategy, dynamic prefix

The rotation is chosen entirely from cached geometry. Runtime prefix metadata still only decides whether a scheduled unit is empty. There is no host-side kv_len heuristic, device strategy branch, extra runtime argument, or second program variant.

07 · Future Ring-32

The formula scales; hardware evidence still matters

Ring-32 has 17 arrival waves: local, fifteen paired waves, and the opposite shard. With 20 lanes the same formula advances through the ten compute columns and wraps naturally. There are no Ring-4 or Ring-8 lookup tables.

Wave start positions across 10 columns

Height is the normalized column offset for each of the 17 waves. Wave 0 begins at zero; later waves wrap when needed.

Analytical acceptance before Galaxy hardware

  • Simulate every tile-aligned prefix and all 32 local ranks.
  • Use exact ring_writes_for, RingIdSequencer, and block-cyclic validity.
  • Track nonempty KC units for execution load and valid tiles for the ideal model.
  • Preserve exact coverage, paired order, monotonic offsets, and all 17 readiness waves.
  • Do not claim Ring-32 correctness or performance until the hardware matrix runs.
08 · Acceptance goals

What makes the change worth keeping

The analytical schedule is necessary but not sufficient. The implementation is kept only if traced hardware results improve the pathological cases without moving a regression elsewhere.
