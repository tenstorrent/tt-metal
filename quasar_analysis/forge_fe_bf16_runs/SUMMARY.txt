--------------------------------------------------------------------------------------------------
FAILURES, GROUPED BY ROOT CAUSE
--------------------------------------------------------------------------------------------------

All 54 failures fall into exactly 2 causes. None is a config or test defect: both are device-side
TT_FATALs raised during program-spec validation, before any kernel runs. A third cause -- silent
numeric corruption in quasar untilize -- was found by the ttnn.to_layout tests before those were
removed, and is kept below because it is the only one that produces wrong numbers rather than an
error.

==================================================================================================
CAUSE A -- 34 of 54 failures        (33 conv2d + 1 linear)
  fp32_dest_acc_en=true is rejected: no unpack_modes entry for the FP32 DFB
==================================================================================================

  TT_FATAL @ tt_metal/impl/metal2_host_api/program_spec.cpp:1076
      dfbs_with_entry.contains(binding.dfb_spec_name)
      Compute kernel 'compute' consumes FP32 DFB 'cb_intermed0' with enable_32_bit_dest=true, but
      provides no unpack_modes entry for this DFB. This configuration requires an explicit choice
      between UnpackMode::UnpackToSrc and UnpackMode::UnpackToDest.

  Forge sets compute_config = <math_fidelity = hifi4, fp32_dest_acc_en = true> on all 53 convs,
  the linear and the mean. It is passed through verbatim, because that is what the sheet records.

  Hits every conv that does NOT need a halo (the 33 stride-1 1x1 convs) and the fc. The other 20
  convs never reach this check -- they fail earlier, at cause B.

  Confirmed to be this flag and nothing else about the config: re-running conv case 47
  (layer4.1.conv1, 2048->512 1x1 @7x7) with fp32_dest_acc_en=False gets past this check and then
  fails at a THIRD, unrelated pre-existing bug -- the quasar matmul in0 receiver kernel does not
  compile:
      ttnn/cpp/ttnn/operations/experimental/quasar/matmul/device/kernels/dataflow/
          reader_bmm_tile_layout_in0_receiver_metal2.cpp:59
      error: 'Semaphore<TENSIX>::get_l1_addr() const' is private within this context
             (declared private at tt_metal/hw/inc/api/dataflow/noc_semaphore.h:241)
  so conv numerics on this build cannot be reached from either direction yet.

==================================================================================================
CAUSE B -- 20 of 54 failures        (all conv2d)
  halo scratch DataflowBuffer is self-looped, which Gen2 forbids
==================================================================================================

  TT_FATAL @ tt_metal/impl/metal2_host_api/program_spec.cpp:1439
      !(is_gen2_arch() && self_loop_kernel->is_data_movement_kernel())
      DataflowBuffer 'gather_scratch0' is self-looped by data-movement kernel 'reader0' (bound as
      both PRODUCER and CONSUMER). Self-loop DFBs are not supported for data-movement kernels on
      Gen2 architectures.

  19 of the 20 name 'gather_scratch0'; conv case 0 (the 7x7 stem) names 'act_sharded' instead.

  Hits exactly the 20 convs that need a halo: the 7x7 stem, all 16 3x3 convs, and the 3 stride-2
  1x1 downsamples. This is the same halo path that failed to COMPILE in the earlier
  ../forge_fe_runs/ sweep (halo_gather.cpp:259, call to non-constexpr get_arg); the build has moved
  on and it now fails validation instead.

  NOTE: max_pool2d also needs a halo and it PASSES here (PCC 0.999). So the halo itself is not
  uniformly broken on Quasar -- it is the conv halo path specifically.

==================================================================================================
CAUSE C -- NOT IN THE CURRENT RUN, kept because it is the serious one
  quasar untilize silently corrupts TILE -> ROW_MAJOR for some tile-grid shapes
==================================================================================================

  Found by the 50 ttnn.to_layout tests in the run of 2026-09-04 before those files were removed
  (11 of them failed). Nothing in the suite watches this any more; reproduce it on demand with
  quasar_analysis/probe_quasar_untilize.py.

  No error, no throw -- just wrong data. PCCs observed:
      0.7553   1x1x3136x256   (sheet 1 rows 15, 23, 31)
      0.7564   1x1x3136x128   (sheet 1 row 33)
      0.8653   1x1x196x1024   (sheet 1 rows 73, 81, 89, 97, 105, 113)
      0.9797   1x1x50176x3    (sheet 1 row 3)
  The other 39 untilizes and the single ROW_MAJOR -> TILE are EXACT (the test asserts equality,
  not a tolerance).

  Narrowed with a follow-up probe (quasar_analysis/probe_quasar_untilize.py):

      shape           roundtrip   to_layout   untilize    untilize_with_unpadding
      1x1x3136x256    1.0000      0.7553      0.7553      0.7553
      1x1x3136x128    1.0000      0.7564      0.7564      0.7564
      1x1x196x1024    1.0000      0.8659      0.8659      0.8659
      1x1x50176x3     1.0000      0.9792      0.9792      0.9792
      1x1x3136x64     1.0000      1.0000      1.0000      0.7551   <-- unpad variant ALSO wrong
      1x1x196x256     1.0000      1.0000      1.0000      1.0000
      1x1x784x512     1.0000      1.0000      1.0000      1.0000

  Three things this settles:
    * "roundtrip" is from_torch(TILE, device) -> to_torch with NO device op at all, and it is
      exact everywhere. The upload/download transport is sound; the corruption is in the device
      untilize.
    * to_layout and untilize corrupt IDENTICALLY, so to_layout is only dispatching -- the bug is
      in untilize, not in to_layout.
    * untilize_with_unpadding has an ADDITIONAL failure mode: it corrupts 1x1x3136x64, which plain
      untilize gets right.

  This is the most serious of the three findings, because it is the only one that produces wrong
  numbers rather than an error. A ported graph would not crash here, just be silently wrong -- the
  same shape of trap as ttnn.softmax returning zeros on Quasar.
