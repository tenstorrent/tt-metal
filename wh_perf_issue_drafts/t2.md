## Summary

On Wormhole, the first tiles of a pack loop decide the packer rhythm ({{M2}}) for the whole loop. A code change that does no work can change two things in those first tiles: the cycle at which the pack core reads its last code lines from L1, and the cycles at which its first instructions reach the packers. Either one can select the slow rhythm. This is the "one nop moves PACK_ISOLATE by up to 46%" effect of #58919.

## Evidence

**The pack core's own code fetch (matmul 1×3, PACK_ISOLATE, pack predictor off, 0 / +1 nop in `_llk_pack_init_`).** Card and Versim: 107,622 / 110,705 cycles.

- Fast: the last loop line (`0xf340`) arrives 10 cycles before the first DEST read. Every L1 write of the first tile is accepted.
- Slow: the loop now ends in one more line (`0xf350`). It is read 33 cycles into the first tile, while packer 3 writes; packer 3's L1 write is refused twice, and the slow rhythm starts in the next tile.
- The pack core reads its code lines once per kernel (7–8 lines over 256 passes in the branch-predictor repro, 7 over 1,024 passes at PR head); after the first pass the loop always hits in its 2 KiB cache. The one read in the first tile is enough.

**A resync at the first tile does not prevent it (Versim, same pair, `TTI_STALLWAIT(STALL_PACK, PACK)` before tile 0 only).** Card 107,632 / 110,715. Per tile in Versim:

| tile | 0 | 1 | 2 | 3 … 2,260 |
|---|---|---|---|---|
| 0 nops: length, packers 1/2/3 refused | resync | 35, 2/2/2 | 35, 2/2/2 | 35, 1/1/1 |
| +1 nop: length, packers 1/2/3 refused | resync | 35, 2/2/9 — pack core reads a code line, packer 3 L1 write waits | 37, 3/4/4 | 36, 2/2/4 |

The resync aligns the packers for tile 0. The code-line read comes in tile 1, after the resync, and it sets the slow rhythm for the remaining 2,260 tiles.

**When instructions reach the packers (eltwise_binary, one tile per loop pass, pack pad 0 / pad 1).** Card and Versim 4,741 / 4,669. There is no extra L1 access, and the pack core waits on a full queue in both builds, so it is not the branch predictor. The packers settle into 1/1/1 refusals per tile (pad 0) or 0/0/0 (pad 1) from tile 3.

## Where it shows

Problem 2. PACK_ISOLATE, L1_CONGESTION[PACK], L1_TO_L1.

## Fix status in #58068

054096d8efa restarts the measured loop from a 512 B aligned point, from a flushed pipeline and a cold instruction cache, with all threads released together. The measured code keeps its address mod 512 B, so a change outside the loop no longer moves when its lines are read or when its first instructions reach the packers. At PR head, moving only the pack thread's code by 4 bytes per function moves 0 of 736 values.

A change inside the measured loop (its size or its alignment) can still select the other rhythm. That is a real code change, but the size of the effect is set by the rhythm, not by the work.

## Note

An earlier note said the slow rhythm also comes back "at block boundaries" (odd tiles per block). The Versim run above does not show that: every tile after tile 2 is the same. The first-tile resync fails because the trigger comes in tile 1.
