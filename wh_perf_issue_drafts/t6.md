Part of {{UMBRELLA}}.

## Summary

On Wormhole, one L1 access by any agent other than the packers, at the wrong cycle while the packers run, can move the packers into the slow rhythm ({{M2}}). If the access comes at a random cycle (the host polling L1 over the NoC, a periodic BRISC poll), the same build gives a different value on every run. This was the main cause of run-to-run differences on Wormhole.

## Evidence

**One L1 read, placed by hand (same ELF, card and Versim).** The math core does one L1 read at spin iteration K. The host writes K before the run.

| K | 0 | 100–175 | 200 | 225–350 | 375 | 400 |
|---|---|---|---|---|---|---|
| card = Versim (cycles) | 9,070 | 9,323–9,314 | 9,070 | 9,309–9,294 | 9,070 | 9,289 |

Versim gives the card value for all 14 values of K. In the waveform, the math read is accepted, in the next cycle packer 3's L1 write waits one cycle, and from the next tile packers 1, 2 and 3 wait 1, 1 and 4 cycles in every tile. A read in packer 3's gap between tiles (K = 200, 375) changes nothing. A nop or a register read at the same place changes nothing; an L1 load or store does.

**Host polling L1 at random cycles (card, PR head 3ff45cbd1c7 with the host poll put back, `LLK_HOST_POLL_L1=1`).**

- One config (math_matmul config885, PACK_ISOLATE), five runs: 88,263 / 78,073 / 84,713 / 71,873 / 83,553. Without the host poll, two runs give 71,873 and 71,873. The values fall between the fast and the slow level because the switch happens at a random tile.
- 100 math_matmul configs, PACK_ISOLATE and L1_TO_L1, three runs: 63 to 71 of 200 values differ by more than 0.5% between runs, up to 27%.
- 184 mixed configs: 49 of 736 values differ between two identical runs (−7.7% to +26.4%). With the overlay-register poll of #58068: 0.

**Versim cannot show the random case.** The same config in Versim with the host poll gives 71,873 cycles in both runs, and the waveform shows no NoC read of L1 during the kernel: the simulator host does not reach L1 through the NoC and the L1 arbiters. The hand-placed L1 read above is the Versim model of this case.

**Other sources of L1 traffic in the window (card):**

| Source | Effect | #58068 change |
|---|---|---|
| Host polls TRISC mailboxes and the BRISC counter in L1 | run-to-run differences (above) | b58fbfbd6d2: poll overlay stream registers instead |
| BRISC reads its command mailbox in L1 every 1 µs | 54 of 736 values move once (−6.0% to +17.9%); in long kernels a nop moves which reads land in the loop (32 of 64 configs) | e02b20f56ee: poll every 100 µs, spin on NOPs |
| Zone start record stored in L1 inside the window | 202 of 736 values change once, up to 112% | df14044db9e: both records after the end read |
| Reader thread polls L1 for the measured zone (older harness) | one more periodic L1 access during the loop | not present at PR head |
| Idle threads fetch their exit code from L1 during the window | see {{T3}} | open |

## Where it shows

Problem 1 (measured again) when the access is at a random cycle; problem 2 when it is tied to the code. Every run type that packs; L1_CONGESTION most.

## Fix status in #58068

The host and BRISC sources are fixed (b58fbfbd6d2, e02b20f56ee); identical runs at PR head give identical values (rerun and reverse order: 0 of 1,346 values move on 323 test cases). e02b20f56ee should say that it removes a bias, not noise: without it, identical runs still agree.

## Open

- Any future harness or firmware change that reads L1 during a kernel brings this back. A check in CI (rerun identity on a sample) would catch it.
