Part of {{UMBRELLA}}.

## Summary

At #58068 head (3ff45cbd1c7), a PACK_ISOLATE value depends on where the unpack and math code sits, although those threads do no work in PACK_ISOLATE. A 4-byte move of their code changes math_matmul PACK_ISOLATE by up to 28.5%. The cause: the idle threads leave TILE_LOOP at once and run their exit code while the packers start. The barrier has just invalidated their instruction caches, so they read every code line from L1, and those L1 reads push the packers into the slow rhythm ({{M2}}).

## Evidence

**Card, PR head, 184 mixed configs (736 TILE_LOOP values).** "+4 B" = one never-executed nop in front of every function (`-fpatchable-function-entry=1,1`).

| Code that moved by 4 bytes | Values that move > 2% | Largest |
|---|---|---|
| all threads | 36 | 28.5% |
| only the pack thread | 0 | 0.3% |
| only the unpack and math threads | 36 | 28.5% |
| only unpack and math, zone helpers kept in place | 16 | 25.7% |

The measured pack loop and its callee are byte-identical, at the same addresses, in both builds.

**Card, PR head, 323 test cases from all perf modules (1,346 values):** moving only the unpack and math code moves 75 values (up to 28.6%): PACK_ISOLATE of matmul (13), unpack_tilize (11), reduce (7), math_matmul (7) and others. Moving only the pack code moves 3 values, all in L1_TO_L1, so MATH_ISOLATE and UNPACK_ISOLATE do not have this problem with pack as the idle thread.

**Versim, PR head with the barrier, math_matmul config12601 PACK_ISOLATE** (Float32 → Float16, HiFi2, 2 tiles, loop factor 1024):

- 71,873 / 92,263 cycles, the same as the card.
- The pack core is identical in both runs: 2,047 mispredicts, 7 instruction-cache line reads, loop at the same address.
- The packers: a loop pass takes 70 cycles (fast) against 90 (slow). Over 60,000 cycles, packers 1, 2, 3 are refused a DEST read for 1,714 / 1,714 / 1,714 cycles against 3,999 / 6,665 / 14,666.
- The trigger: in the first 200 cycles after the release, unpack reads 28 and math reads 32 code lines from L1 (`zone_record`, the rest of `run_kernel`, `main`). The packers start about 115 cycles after the release, so 7–8 unpack reads and 14 math reads land while the packers write their first tiles. With the code moved by 4 bytes, the reads land a few cycles earlier, and unpack reads one more line (`0x5200`). In the second tile packer 1 is refused, and the slow rhythm starts.

## Where it shows

Problem 2. PACK_ISOLATE (math_matmul, unpack_tilize, eltwise_binary). The same can apply to UNPACK_ISOLATE and MATH_ISOLATE with the roles changed.

## Fix status in #58068

Not fixed. 054096d8efa parks every thread after `run_kernel`, but in an isolate run type the idle threads run their zone end, `zone_record`, the end of `run_kernel` and part of `main` before that park, inside the measured thread's window.

## Possible fix

Keep the idle threads halted for the whole window of the measured thread. For example, the idle threads park as their TILE_LOOP zone opens, and BRISC releases them only after the measured thread parks. Or the idle threads finish their (empty) zone first, and BRISC releases the measured thread only after they park again.

## Fix tested on the card

Experiment switch `LLK_ISO_SETTLE=N` (branch `nstojictt/p58-versim`): in an isolate run type, the measured thread runs N nops after the TILE_LOOP release and before its zone opens, so the idle threads finish their exit code first. The wait is outside the measured window.

| Unpack and math code moved by 4 bytes per function | Values that move > 2% | Largest | In isolate run types |
|---|---|---|---|
| PR head | 75 | 28.6% | 50 (48 PACK_ISOLATE, 2 MATH_ISOLATE) |
| PR head + `LLK_ISO_SETTLE=2000` | 25 | 6.2% | 0 (all 25 are L1_TO_L1 or L1_CONGESTION, where unpack and math really run) |

For the config of the waveforms (math_matmul config12601, PACK_ISOLATE), card: PR head 71,873 / 92,263 cycles; with the settle 71,791 / 71,791.

The settle changes 133 values once (up to 22.4%), because it moves the measured loop code and its start. A version that waits until the idle threads have parked, in place of a fixed count, would cost nothing in the window.

## Check

With the fix, moving only the unpack and math code (`LLK_FN_NOPS_THREADS=UNPACK,MATH LLK_THREAD_FN_NOPS=1` on `nstojictt/p58-versim`) must move 0 PACK_ISOLATE values.
