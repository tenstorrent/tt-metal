Gemma 4 Prefill Matmul Sweep

How the cost per token of each prefill projection changes with chunk size C, measured on one Blackhole device with a CP8/TP4 device's shapes and the model's own matmul configs. The goal: the smallest chunk at which the matmuls stay efficient.

Terms

Lane
A 2,048-token slice of a prefill step's token budget. Each lane carries 2K tokens of one request, and one request can fill several lanes; a request alone fills all of them. This is the lane of the Gemma4 AgentX prefill simulator (models/demos/gemma4_d_p/agentx_sim), where --config 2048x8192:pack (lane width × step budget : policy) is "2k x4 lanes". This page writes it as C = 8K (4 lanes × 2K).
Step
One prefill pass through all 60 layers with every lane of the budget. C is the tokens in one step, N lanes × 2048, which can span several requests. For the matmuls a step of N lanes is the same as one chunk of C tokens, because projections only see the total rows (C/8 per device).
Not a KV slot
In this model a KV slot is per user (num_slots = num_users). A lane is a slice of one step and is not tied to a user.

TL;DR

  • Matmul cost per lane falls steeply up to C = 8K (4 lanes × 2K). One step through 60 layers spends 27.7 ms per lane at C = 2K (1 lane), 18.3 ms at 4K, 13.9 ms at 6K and 12.2 ms at 8K (single-chip sweep). C counts tokens per step, which can span several requests.
  • C = 10K (5 lanes × 2K) is the cheapest for the matmuls. Measured in the model on current main, a 5-lane step spends 48.3 ms in matmuls against 45.3 ms at 4 lanes: +6.6% per step, −15% per lane. It is the largest step that still gets the explicit 2D config, and it runs on all 120 cores where 8K uses 96.
  • For the whole step, the fifth lane costs +19%. Attention and collectives grow with the lanes. One request's 240K prefill comes out 5% faster at 5 lanes (43.5 against 45.8 ms per lane). With several requests per step (draft PR #61264), 5 lanes today ends level with 4 lanes (within ±1.2% per lane), because it has to keep activations in DRAM.
  • 5 lanes does not run as-is on current main. One request: the tuned global attention config at C = 10K overflows the 70,656 B kernel-config buffer by 1.2 KB. Batched: a matmul's buffers clash with L1 by about 72 KB. Both were measured with a workaround, below.
  • C ≥ 12K (6 or more lanes) is a matmul cliff. In the model the matmuls take 73.0 ms per step, 61% more than 4 lanes, because they fall back to ttnn's default config. PCC ≥ 0.9987 at every sweep point; batched KV at 4 and 5 lanes matches each request run alone (min head PCC ≥ 0.9977).

Fixed step size, partly filled

Matmuls only: matmul time per filled lane when the step always runs at its full size.

  • If the step shape is fixed, for example traced at the full lane count, empty lanes cost as much as full ones. In matmul time a 5-lane step loses about 5% when its fifth lane is empty. For the whole step, measured below, it loses much more: about 19% for one request (217.7 ms over four lanes against 183.3 ms for a full 4-lane step), and about 18% batched against 4 lanes with the same DRAM-only setting.
  • The AgentX simulator's cost model is calibrated per lane count only up to 4 lanes and reuses the 4-lane value beyond that. What it needs for 5 and 6 is the measured batched step times in the next section, not these matmul-only estimates.
  • This assumes each lane is split across the 8 context-parallel devices the way a chunk is today, so a device holds N × 256 rows. A different placement of lanes on devices would change the per-device shapes.
  • Only the matmuls are covered here. With several requests in a step, attention runs per request against each request's own prefix, so its cost depends on the mix of requests and their positions; the next section measures that case.

Findings

Up to 2K, weight reads set the pace

At C ≤ 2048 each projection reads its whole weight shard from DRAM at 300–380 GB/s while doing little math, so the time per call is almost flat and the cost per token falls as 1/C. Fidelity barely matters here: LoFi and HiFi2 differ by 0–10%.

The 1D → 2D switch at 2304 is a step back

Every op gets slower per token when the config changes from the 1D sharded layout to the 2D layout (up: 94 → 123 µs per call). The curves only recover by 3K–4K.

8K wastes a sixth of the grid

At C = 8192 the 2D config has 32 rows of output tiles. Four per core fills 8 of the 10 core rows, so it runs on 96 of 120 cores and costs about the same per token as 7168. C = 10240 uses all 120 and is about 15% cheaper per token for every op.

Past 10K, the fallback config is the limit

From C = 12288 the explicit config no longer fits L1 and ttnn's default takes over: HiFi2 with bf16 accumulation for attention. Attention gets 1.3–1.6× slower per token than at 8K. Forcing LoFi with fp32 accumulation helps only global QK, and the o_proj ops get much worse.

MLP still gains from larger chunks

Gate, up and down are 15–19% cheaper per token at 10K than at 8K, and up and down keep improving on the default config up to 32K. At 8K the MLP is about 68% of matmul time and about 17% of layer time.

At 8K, SDPA is the bigger lever

Matmuls are 25% of layer time at 8K, against 50% for SDPA, which grows with the prefix in the global layers. At 2K and 4K matmuls are about 32%.

Correctness and variability

Correctness

  • PCC against a torch reference with the dequantized weights is ≥ 0.9987 at every point. All explicit configs are ≥ 0.9997.
  • The lowest values are gate on the bf16-accumulation fallback at C ≥ 12288 (0.9987–0.9994).
  • Real TP-rank-0 weights (layer 0 sliding, layer 5 global) at C = 1K–16K time within 1.3% of random weights, with PCC ≥ 0.9997.
  • This is op-level correctness, not a model accuracy check.

Variability

  • Spread (interquartile range) across the 10 timed calls: 0.7% median, 4.9% worst.
  • Across 3 independent runs on the second galaxy: 0.4% median, 3.7% worst.
  • The two galaxies agree within 5% above C = 2048. At C ≤ 2048 the second one is 5–18% faster, consistently. That region is bound by DRAM reads, so absolute small-chunk numbers depend on the machine; this one's GDDR runs at 14 Gbps.

Method

  • Each projection runs on one chip with one CP8/TP4 device's shapes: C/8 token rows (no padding; C is a multiple of 256) and the TP4 weight shard.
  • The matmul goes through the model's own code (apply_attn_projection, MLP._project), so the program config, compute config, fused GELU and layouts are the model's at every C. Inputs arrive in the layout the model hands each projection: L1 width-sharded from the all-gather at short chunks, DRAM from nlp_concat_heads for o_proj, L1 from gate × up for down.
  • Time is the device kernel duration from the profiler: 2 warm-up calls, then 10 timed calls; the median is reported. Cost per token = median / (C/8). Collectives and host time are not included.
  • FPU utilization = ideal cycles (M·K·N / 32³ tiles × 16 cycles for LoFi, 32 for HiFi2) over measured cycles at 1.35 GHz, across the full 120-core grid. It is relative to each point's fidelity, so HiFi2 points look more utilized than they are fast.
