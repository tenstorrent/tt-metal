========================================================================
  META-PLAN  feasibility = MEDIUM
========================================================================
  The tts_backbone (26x VoxtralDecoderLayer with RMSNorm/Attention/MLP) is a standard Llama-style transformer stack that maps cleanly onto REUSE/ADAPT ops, so that portion should converge normally. The risk is concentrated in codec_decoder and flow_matching, which both discovered as single opaque leaves (occ=1, leaves=1) rather than decomposed submodules -- meaning op_emitter has no per-op target list for them and will need bespoke porting. Prior work in this repo on this exact model (see commit history and the FSQ/reductions findings) already drove full e2e PCC to 0.9986-0.99988 fully on device, so a working path is known, but it required non-default fixes (decomposed reductions, split matmuls, fp32_dest_acc_en on rms_norm) that the auto-iterate loop will not discover on its own.

  risks (5):
    - codec_decoder (VoxtralCodecDecoder) and flow_matching (VoxtralFlowMatching) both report leaves=1 -- discovery didn't decompose them, so the loop has no granular op targets and may try to treat each as one REUSE/ADAPT unit instead of the dozens of ops actually inside
    - Conv1d is absent from both the REUSE and ADAPT lists (only Conv2d/ConvTranspose2d are listed); audio codec/vocoder stacks almost always use Conv1d, so it can silently fall through as unsupported rather than being flagged NEW
    - Audio codecs of this shape typically use RVQ/FSQ-style codebook quantization (argmin/nearest-code lookup), which is not a standard NN op and is exactly the block previously implicated in this repo's Voxtral-TTS code-flip PCC issue
    - flow_matching implies iterative ODE/CFG sampling (repeated timestep-conditioned forward passes), a control-flow pattern the single-leaf discovery doesn't capture and that the emitter's static-graph assumption may mishandle
    - 53x RMSNorm and dozens of matmuls across 26 layers are precision-sensitive on this hardware -- known to need fp32_dest_acc_en and decomposed (not summed) reductions to avoid the ~1% PCC bleed already documented for this model

  recommendations (6):
    - Graduate tts_backbone first via the normal REUSE/ADAPT path -- it's the highest-confidence, lowest-risk component and validates the loop mechanics before spending budget on the two custom blocks
    - Before iterating on codec_decoder/flow_matching, run a targeted trace/submodule dump to get real leaf ops -- don't trust the emitter's single-node view for either
    - Proactively apply the fixes already proven for this model: decompose fp32 reductions as mean (not sum) and split precision-critical matmuls, per the prior finding that got e2e PCC to 0.99988; don't let the loop rediscover this from scratch
    - Enable fp32_dest_acc_en on every rms_norm call in tts_backbone up front rather than waiting for a PCC failure to surface it
    - If codec_decoder uses Conv1d or an RVQ/FSQ codebook lookup, classify it as NEW explicitly and hand-port it rather than letting the loop attempt an ADAPT match against Conv2d/GroupNorm
    - If flow_matching uses iterative sampling, unroll a fixed small step count in the emitted graph rather than relying on the loop to infer dynamic control flow
