Existing reduce helpers — migration and test coverage

Branch: malimpic/migrate-to-host-reduce-helpers · Commit: f808380a87b320e24457c600cc79b05d7a0b8f73 · Audit date: 2026-09-08.

Compute scope: 125 existing explicit compute_kernel_lib::reduce<...>(...) helper calls in 58 source files. Calls already using reduce<Call>(), raw compute APIs, specialized reductions and direct LLK calls are excluded from the compute inventory.

Dataflow extension: 100 old scaler/partial-helper calls in 68 source files, reached by 69 dataflow kernel bodies. The separate dataflow section also counts manual auxiliary producers and additional factories/test builders, giving 218 migration candidates, or 220 including retirement of the explicit compute API. Raw compute calls remain outside the inventory even when their dataflow partners use an old helper.

The compute-side test audit covers 60 factory implementations in 59 host files. One file (F087) contains two factories and has two rows. Two further host files are retained as relationships: F084 is a shared builder and F024 is a non-executing source-composition test. Three compute-helper source files have no static host reference.

Key findings:

  • F034 (distributed DiT RMSNorm) and F036 (attention-residual gather-softmax) have numerical tests in other CI pipelines; neither is scheduled by the audited sanity/L2 commands.
  • F040’s indexer helper fallback is explicitly tested in L2. Sanity’s indexer selections do not reach it.
  • F041 (ring indexer) and F086 (Welford post-all-gather) reference helper-bearing sources, but their retained helper branches cannot be enabled by those factories.
  • F046–F048 (Quasar) have no direct factory tests found. F090 (general large-height softmax) has a disabled smoke test, not enabled coverage.
  • The five Python example/toy factories run in sanity’s helper-library group. That group has no P100 SKU and is not included by L2’s P100 sanity rerun.
  • Standard interleaved distributed-normalization cases and the 2D pre-all-gather factory have single-device simulation tests in L2. Their similarly named legacy or eight-device unit tests do not establish coverage in single-card sanity.

Dataflow helpers and total migration file scope

The previous numbers were 58 compute-kernel source files and 59 factory files. The 58 compute sources include three Python files with inline C++; each of those files also contains a dataflow body and its factory. Kernel bodies and physical files therefore have different totals.

69 dataflow kernel bodies use the old reduction helpers: 67 directly and two through a shared header. There are 100 unique old dataflow-helper call sites in 68 physical files. The direct-call files are 64 C++ kernel files, three Python inline-source files and one shared header. The two DiT writer entry files add indirect users; including that header and both entries gives 70 dataflow-related files.

The dataflow helpers prepare scaler/partial tiles for compute; these are not compute reduce(...) calls. This repository-wide scan also finds dataflow consumers paired with raw/SFPU/Welford compute code, so it extends beyond the earlier 58-source compute-helper inventory. Kernel call counts and accumulation patterns

58 kernel sources, 125 static helper call sites. Seven sources carry a running reduction through a loop; eight combine a fixed prefix and tail; nineteen perform multiple statistics/stages; twenty-four use one helper invocation per independent local reduction. The table below separates the mechanisms used to combine results.

A static site is one explicit helper expression in the inventory. A runtime call is an invocation of that helper, including calls reached through wrappers. Counts below are per compute core’s stated work unit (row, output tile, shard or invocation), not necessarily per whole distributed tensor. They exclude raw reductions and tile traversal inside the helper. Small shapes can collapse an accumulation loop to one iteration.

Here, cross-call accumulation means carrying a running reduced result into the next call for the same reduction, either through Accumulate or a callback. A later fresh bulk reduction over a collection of partials is classified as a separate stage. An outer loop over unrelated rows, or a manual tile-add loop before one final helper call, does not imply helper-result carry.

The accumulator contract says iteration zero does not reload a prior result; later iterations do. See Accumulate documentation. Every source is assigned exactly one category, prioritizing loop carry, then fixed prefix/tail combination, then multiple stages, then a single independent reduction. Runtime alternatives and additional stages are described in its row.
