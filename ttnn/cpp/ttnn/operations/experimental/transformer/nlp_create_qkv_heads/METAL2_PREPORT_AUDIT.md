## Heads-ups  *(mirrors the brief)*

- **CB endpoints (multi-binding shapes to watch):** none. Sharded `c_16` is the two-toucher dual-instance work-split → 1P+1C, **not** the flag. The Interleaved per-group compute descriptors are the *disjoint-node* work-split (one instance per node) — not a two-toucher, not a multi-binding.
- **Sharded: K/V output DFBs are per-node-conditional — plan two WorkUnitSpecs.** Legacy declares `c_17`/`c_18` over `k_cores` while both kernel instances run over `q_cores` (`:533, 549` vs `:566, 575`) and touch the K/V CB only where `read_kv_heads` (an RTA, `:432`, `sharded:25`) is true — which is exactly `k_cores`. In Metal 2.0 a DFB's node set is the **union of its binders' node sets** (`program_spec.cpp:656-668`), and a borrowed DFB receives **one** base address for every node it is bound on with **no per-node shard-grid coverage check** (`program_spec.cpp:1583-1630`; `program_run_args.cpp:495-560` checks only L1 residency and per-bank size). So binding `dfb::kv_out` from a KernelSpec over all `q_cores` would place the K/V DFB on cores that hold no K/V shard. Recommended shape: **two WorkUnitSpecs** — `k_cores` (R binds `q_out`+`k_out`, W binds `q_out`+`v_out`) and `q_cores \ k_cores` (R and W bind `q_out` only) — with **two same-source KernelSpecs per instance** over the disjoint node sets, legal per the disjoint-coverage rule (`program_spec.cpp:84-89`). The kernel's `read_kv_heads` RTA gate must then be **promoted to a define** (e.g. `READ_KV_HEADS`, emitted only on the `k_cores` specs) and the KV block (`sharded:69-119`, incl. the `cb_id_kv_out` CTA read @ `:78`) wrapped in `#ifdef` — because `dfb::kv_out` must not be name-looked-up in a build where it is unbound (port_patterns.md → *Conditional / optional resource bindings*, "Promote a CTA gate to a define"; here the gate is an RTA whose value is host-deterministic per core). When `num_kv_heads == num_q_heads` (`k_cores == q_cores`) the second WorkUnit is empty and must be omitted. The `q_cores \ k_cores` set is the tail of the row-major `grid_to_cores` order (`:405-408`), so it is a `CoreRangeSet` difference the factory computes once. **This promotion is a kernel-structure change beyond a pure syntax swap — confirm it against the port recipe's kernel-side whitelist before starting; if the whitelist forbids it, the port capitulates on `Sharded` and reports the handoff.**
- **Cross-op / shared kernels:** `ttnn/cpp/ttnn/kernel/compute/transpose_wh.cpp` is a **borrowed** shared-pool kernel with **no `_metal2` sibling** in `ttnn/cpp/ttnn/kernel/compute/` → this port creates the first fork there (`transpose_wh_metal2.cpp`) and adds the pointer comment to the original (rung 2 of port_patterns.md → *Caution: Porting a shared kernel*). ## Recipe notes

- **Provenance on an untracked overlay.** The prescribed `git log -1 … -- docs/…/metal_2.0/` prints nothing when the recipe set is an untracked overlay on a `main` worktree. Recorded the overlay's source tip by hand. A one-line fallback in the recipe ("if untracked, record the tip you overlaid from") would make this deterministic.
- **Auditor applying the ops-team fix, then re-auditing in-session.** The recipe routes a Type 1 fold to the ops team and says "re-audit once it lands". Here the user asked the auditing session to make the fix; the report keeps the pre-fix RED under Gate detail and marks the GREEN as contingent on the uncommitted change. The recipe could say how to record an in-session fix (history block + contingency line, as done here) so the two states aren't conflated downstream.
- **Custom concept with an address-only override.** Both overrides refresh exactly the set the *base* concept refreshes automatically. The `Override runtime args method? == yes → CustomProgramSpecFactoryConcept` rule still sends them to the custom concept, where the translated method is a pure `tensor_args` echo. Faithful, but pure ceremony; worth a sentence that this shape is expected and not to be "optimised" into the base concept without a rule allowing it.
- **Device 2.0 Red criteria don't mention raw runtime-arg-area pointers.** `tt_l1_ptr uint32_t* p = (tt_l1_ptr uint32_t*)get_arg_addr(N)` is the standard legacy idiom for RTA arrays. Not data movement, dissolves into varargs — judged a non-violation — but the `CoreLocalMem` guidance could be read either way. A sentence settling it would help.
- **Borrowed DFB on a sub-grid of the kernel's nodes.** CB endpoints has no entry for the shape here: a legacy borrowed CB declared over a **subset** of the touching kernel's core range, with the touch gated by a per-core RTA. It resolves via two WorkUnitSpecs plus an RTA→define promotion, but that promotion is not obviously inside the kernel-side whitelist (the *Conditional bindings* pattern covers CTA gates). A recipe/pattern entry — "per-node-conditional borrowed DFB → split WorkUnits, promote the node-selecting RTA to a define" — and an explicit whitelist ruling would close the gap.
- **Offset-base subject: per-branch vs whole-factory scoping.** The Code-path-scope paragraph frames the gate as row-major vs tiled *factories*; here the fold lived in one shared per-core builder feeding both branches of a single tiled factory, and the dated triage doc claimed one branch was clean. "A fold in shared per-core arg-building code gates the whole factory, whatever the doc's branch caveat says" would have saved a re-derivation.
- **`_metal2` locational rule vs a same-body fork elsewhere.** Rung 1 correctly says "no fork" for the shared-pool `transpose_wh.cpp` even though a byte-equivalent Metal 2.0 fork exists under `data_movement/transpose/`. Treated here as a **naming precedent only** (adopt `dfb::cb_in`/`dfb::cb_out`) because its arg mechanism differs (RTA vs CTA). Worth a sentence so porters neither bind the wrong file nor ignore the vocabulary.
