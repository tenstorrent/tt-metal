## Result

**GREEN → brief issued.** All five gate-bearing subjects clear: Device 2.0 ✓ · Feature compatibility ✓ · TTNN factory concept ✓ · Offset base pointers ✓ · TensorAccessor 3rd argument ✓ (N/A). The porter brief is at `METAL2_PORT_BRIEF.md` in this directory.

This op is large and unusually config-dense — two factories, seven distinct compute kernels, thirteen distinct dataflow kernels, and roughly two dozen CB indices whose meaning and endpoint census change with `use_welford`, `distributed_norm_stage`, `rms_norm`, `FUSE_PRE_ADD`, `DO_COL_MASK`, `skip_write_back`, `input_is_row_major`, `large_tensor_needed`, and the fp32 alias flags. Nothing in that density blocks the port, but it is the dominant risk: the port work is broad rather than deep. The per-`(CB, config)` inventory below and the brief's Construct section are written to carry that breadth for the porter.

**Correction to an earlier revision of this document.** An earlier version raised a second question claiming `c_17` had to be placed on the storage cores or the write-back would silently corrupt memory. That was wrong: a buffer-backed CB takes the *buffer's* address rather than a per-core allocation, so the storage-core half of its core range reserves nothing and the port needs nothing there. The mechanism is set out under CB endpoints below. What the finding became instead is a binding reclassification: the sharded `output` via `c_17` is **Case 2**, not clean. The overall verdict is unchanged.

One finding deserves the reviewer's attention before the port starts, raised as a question at the end of this document:

  1. The recipe's recognition cue for an isolated holdover is a single CB-index argument **and** the corresponding Device 2.0 wrapper object already in scope at the call site. Meeting the cue would take a signature change to a shared in-family header, not a 1-line swap.

The structural reason Device 2.0 gates Metal 2.0 — that the binding tokens need a wrapper object to attach to — does not bite here. `uint32_t cb_id` is an explicitly-✓ donor shape: `dfb::name`'s constexpr cast covers both runtime and template-parameter position, so `get_pointer_to_cb_data(dfb::reciprocals, 0)` is the ordinary mechanical translation. Nothing about this site is missing a Metal 2.0 home.
  3. `get_tile_address` is not on the recipe's sanctioned list, so I am not claiming an exemption — I am reporting that the holdover cue is unmet and that the name's status is undecided.

  **Why `c_17` needs nothing on the storage nodes.** A `CBDescriptor` with `buffer` set does **not** take a per-core SRAM allocation. It is resolved by `UpdateDynamicCircularBufferAddress` ([tt_metal/impl/host_api/tt_metal.cpp:1730-1737](../../../../../../tt_metal/impl/host_api/tt_metal.cpp#L1730-L1737)) into `assign_global_address()`, which sets the CB's address to `buffer->address() + address_offset` ([tt_metal/impl/buffers/circular_buffer.cpp:175-177](../../../../../../tt_metal/impl/buffers/circular_buffer.cpp#L175-L177)); `CircularBuffer::address()` then returns that in place of any locally-allocated address ([tt_metal/impl/buffers/circular_buffer.cpp:168-172](../../../../../../tt_metal/impl/buffers/circular_buffer.cpp#L168-L172)). So `c_17`'s address is simply the output tensor's address, and a tensor sharded in SRAM sits at the same address on every core it is sharded across. That, not the CB's core range, is what lets the writer read `get_write_ptr()` on its own core and use the value as a destination on a storage core. The storage half of `all_worker_and_storage_cores` gives those cores a CB config entry that no kernel reads and that reserves nothing (no core-range check ties a buffer-backed CB to its buffer's shard grid). The port can bind `c_17` on the worker nodes alone.

  The recurring shape behind every `multi-binding flag` row above is the same one, and it is worth naming once: **a compute kernel that `wait_front`s a DFB it produced into, on a DFB a reader also consumes.** The compute kernel's `reserve_back`/`push_back` locks the producer role and its `wait_front` locks the consumer role, so the reader's `wait_front` is a second locked consumer and no relabelling can fit the census into 1P+1C. This is a genuine legacy multi-endpoint FIFO, not a missed 1P+1C, so the flag is correct — and it self-documents the Quasar debt.

## Heads-ups  *(mirrors the brief)*

## Recipe notes

- **The Device 2.0 gate has no rule for an unsanctioned CB-index free function whose wrapper is *not* in scope.** The Green bullet's affirmative exemption is a two-name list; the Red bullet's *isolated holdover* recognition requires "wrapper in scope **and** a wrapper-method replacement exists." `get_tile_address(cb_id, tile_index)` in this op satisfies the replacement half but not the scope half, and it is not on the list — so neither bullet decides it, and the verdict for the whole op turns on that gap (Question 1). The Green bullet's line *"The list is the whole test, and it does not turn on what object is in scope"* is written to protect the two sanctioned names from a false flag, so it does not settle the converse case. Two things would help the next auditor: say explicitly whether the scope half of the Red cue is **necessary** or merely indicative, and consider adding a third disposition for *"replacement exists, wrapper absent, name unsanctioned"* — the shape a shared helper taking a `uint32_t cb_id` produces, which is presumably common.
- **`CBDescriptor` with multiple `CBFormatDescriptor`s is not named anywhere in the recipe.** This op leans on it six times to give one SRAM allocation two buffer indices with different `unpack_to_dest_mode` settings. It maps cleanly onto `DFBAdvancedOptions::alias_with`, and Appendix A's silence correctly means "supported" — but the recipe never connects the legacy construct to that destination, so an auditor either has to find `alias_with` unaided or risks reading the multi-format descriptor as an unlisted-and-therefore-unexamined construct. A one-line pointer in the CB-endpoints subject (multi-`CBFormatDescriptor` → `alias_with`, and count each alias index separately in the census, since each has its own FIFO pointers) would save that search. Relatedly, the endpoint census section could say outright that an alias index is its own DFB for census purposes; I inferred it from the kernels pushing to both indices.
- **The "compute waits on its own push" shape deserves a named row in the endpoint table.** Five CBs in this op reach `multi-binding` by the same route: the compute kernel `reserve_back`/`push_back`es a DFB and then `wait_front`s its own result, locking *both* roles, so a reader's `wait_front` becomes a second locked consumer. The table's `≥2 locked consumers` row covers it correctly, but the surrounding prose frames two-toucher cases as *"usually 1P+1C, reach for the flag only as a last resort,"* which reads as discouraging the flag right where it is the correct answer. Worth an explicit example: a single kernel can be locked to both roles on one DFB, and when it is, *any* second toucher forces the flag.
- **The `get_arg_addr` vararg form isn't in the RTA-varargs recognition list.** Both recognized shapes describe `get_arg_val` / `get_common_arg_val` reads at a varying index. Five sites in this op instead take `get_arg_addr(base)` and cast it to an `L1Ptr`, then index it as an array — the same variable-count block, but it matches neither recognition bullet literally, and it carries an extra port consequence the recipe does not mention: `get_vararg(idx)` returns a value, so a consumer whose parameter is a pointer into the arg region has to change. Adding the pointer-cast form to shape (a), with that consequence noted, would make the classification mechanical.
- **The dated-triage cross-check needs a same-op check, not just a name check.** The 3rd-arg triage's one normalization entry is keyed `normalization_ln_rm_gb_post_allgather`, which reads like a match for this op's [writer_unary_sharded_ln_rm_gb.cpp](device/kernels/dataflow/writer_unary_sharded_ln_rm_gb.cpp); only following the cited `file:line` shows it belongs to `layernorm_distributed`. The recipe tells the auditor to trust their own read over the doc, which is what saved it here, but a sentence warning that triage keys are op-name-like strings rather than paths — and that sibling ops in a family share naming stems — would prevent a plausible misattribution.
