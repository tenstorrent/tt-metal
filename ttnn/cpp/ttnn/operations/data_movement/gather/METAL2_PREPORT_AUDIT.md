## Result

**GREEN by user override; brief issued for all seven factories.** Two user overrides decide this result (see the top of this report). The recipe alone gives a different result:

- With user override 1 only: **RED at op level; subset `SingleRowSingleCore`, `SingleRowMultiCore`, `GatherCodegenProgramFactoryInterleaved`, `GatherCodegenProgramFactoryTiled`, `GatherCodegenProgramFactoryStreaming` is clear.** `RmSingleRowSingleCore` and `RmSingleRowMultiCore` are blocked on `Device 2.0`, routed to the Device 2.0 track.
- With neither override: the three codegen factories are also blocked (no sheet rows, a "spreadsheet is broken" GATE routed to the readiness-sheet owner), and only `SingleRowSingleCore` and `SingleRowMultiCore` are clear.

In plain language: the four row-major kernels call an older form of two shared NoC helper functions, a form that the Device 2.0 migration deprecated. There are 6 such calls, and each fix is a one-line edit (pass the kernel's existing `noc` object as the first argument). The recipe would make that fix a separate step before the port; on the user's instruction, the porter makes it during the port. Every other gate clears for all seven factories.

  **Codegen, 9 sites, Class 2 (value already equals the aligned page).** Each passes `get_tile_size(cb)`. All three tensors are interleaved: `supported_by_codegen` rejects a sharded input or index ([codegen/gather_codegen_supported.cpp:81-83](codegen/gather_codegen_supported.cpp#L81-L83)), and `validate_on_program_cache_miss` rejects a sharded output ([codegen/gather_codegen_device_operation.cpp:176-186](codegen/gather_codegen_device_operation.cpp#L176-L186)). All three tensors must have the default 32x32 tile ([codegen/gather_codegen_supported.cpp:24-28](codegen/gather_codegen_supported.cpp#L24-L28), used at lines 59 and 71), and the CBs leave the tile unset ([codegen/gather_codegen_program_factory.cpp:161-173](codegen/gather_codegen_program_factory.cpp#L161-L173)). ## Recipe notes

1. **Holdovers that are not CB-index free functions.** The Red bullet of the Device 2.0 gate defines isolated holdovers as CB-index-keyed free functions. The holdovers found here are calls to deprecated overloads of in-family shared helpers, which the Device 2.0 migration itself deprecated (PR #47050 added the `Noc` overloads and called the old ones "1.x overloads"; PR #47454 marked them `[[deprecated]]`). I treated them as isolated holdovers because the gate's question is full Device 2.0 compliance, and the Device 2.0 team's own deprecation is the clearest evidence of what is not compliant. Suggest that the recipe name this class (deprecated Device 1.x overloads of shared helpers, with a `Noc` object in scope) so that the next auditor does not have to decide it.
2. **"There is no partial pass" and factory scope.** The Device 2.0 Red bullet ends with "The op is re-audited once the cleanup lands — there is no partial pass." I read this as a statement about one kernel's compliance (a kernel with holdovers gets no partial credit), not as a ban on a factory subset, and I applied Code-path scope because the holdovers are confined to two factories' kernels. Suggest stating which reading is meant.
3. **`constexpr` metadata lookups.** The sanctioned list names only `get_tile_size(cb_id)` and `get_local_cb_interface(cb_id)`. `get_tile_hw(cb_id)` and `get_dataformat(cb_id)` in `constexpr` declarations have no `constexpr`-capable wrapper replacement (`CircularBuffer` getters are not `constexpr`; a `DataflowBuffer` getter cannot fold, per CB→DFB whitelist §A), so they fail the holdover test's second condition. Suggest stating in the Green bullet that a CB-index metadata free function in a `constexpr` declaration is not a holdover, to match whitelist §A.
4. **Raw SRAM element pointers.** The Device 2.0 migration guide shows `CoreLocalMem<T>` as the replacement for raw `reinterpret_cast` access to local memory, but the audit's Device 2.0 section does not say whether raw element access through a buffer's own `get_read_ptr()` / `get_write_ptr()` gates. I followed precedent (56 landed Metal 2.0 kernel sources keep the cast, including those of `sort` and `scatter`). Suggest stating the rule either way.
5. **Variadic-CTA row in the status summary template.** The template has a "*Feature Support* — Variadic-CTA" row, but Appendix A has no Variadic-CTA entry, and the RTA varargs section says CTA varargs port onto `KernelAdvancedOptions::compile_time_varargs` and do not gate. The row looks out of date.
6. **Where a second, independent device operation's report goes.** The recipe says to audit independent device operations separately, and the output section says to write the files to the op's root directory, one level above `device/`. Here the second device operation lives in `codegen/` with no `device/` directory, and the readiness sheet treats `<op>/codegen` as a separate `Op` for other ops. The recipe does not say where that device operation's report goes. I bundled the two with per-DeviceOperation attribution because the request scoped the audit to this directory.
7. **Skipping porter-only subjects after a tiny op-code-side fix.** The Red outcome scoping rule skips the porter-only subjects whenever the fix is on the op-code side, because the fix would make the detail stale. For a fix this small (6 inserted `noc,` arguments, which change no CB, binding, or argument layout), the skip only forces a second pass. That happened here: user override 2 brought the row-major factories into the port after the first pass, so the skipped subjects had to be run in a second pass.
