compact_partial_transpose_r3 -- PERF 3 REBASE of Perf 2's deferred WIN #1 onto the CURRENT tree.
blackhole p150b, 1350 MHz.  Precision contract IDENTICAL in every row and every variant:
fp32 partial/stat CBs, fp32_dest_acc_en=False, MathFidelity.HiFi2, math_approx_mode=False.
Correctness is the only pass/fail.  Nothing here tunes a precision knob for speed.

WHY THIS DIR EXISTS.  perf_experiments/compact_partial_transpose_r2 measured this idea at
6398 -> 1732 ns/block against the PRE-D22 root chain.  Perf 2 then landed D22, which replaced that
baseline entirely, so r2's ratio was against code that no longer exists.  Both sides are re-measured
here against the tree as it stands.

TWO BENCHES, because the idea has two halves and the Perf-3 peel says the second is the bigger one:
  BENCH A  combine_bench.py / test_combine_bench.py -- the root's COMPUTE, single core, everything
           resident, no NoC.  Amortised: ns = (t_9 - t_1) / 8, which cancels the launch floor.
  BENCH B  transport_bench.py / test_transport_bench.py -- the WHOLE combine on the real 64-core
           geometry (gather + semaphore + multicast + fold + the pack/un-pack the layout adds),
           every core starting with its partials resident and ending with the stat in its output
           shard.  ns = the program's DEVICE KERNEL DURATION.  THREE independent profiled runs
           agree within 0.5% on every cell (ops_perf_benchB_run1/2/3.csv; run 3 also carries the
           two RAGGED configs, added after runs 1-2, and reproduces the focus cell to 0.02%).

CROSS-ROUND CALIBRATION (bench A, MODE 6 `base_d19` == r2's baseline, re-run on this box):
   rows=1   982 ns   (r2: 986)      rows=8   6401 ns   (r2: 6398, 0.05%)   rows=32  25064 (r2: 25056)
=> the two rounds' tables are directly comparable; nothing about the box moved.

BASELINE = `base_d22` = kernels/rms_norm_compute.cpp's `is_root != 0` branch as it stands: ONE
cb_wait_front over the whole GATHER_SLOTS*rows window, the two mandatory reconfigs, then per
tile-row one DEST window of GATHER_HALF pairwise add_tiles(acc_to_dest) + the raw-sfpi
stat_finalize_payload at D17's <2,4> VectorMode::C + ONE pack_tile.
CANDIDATE = the SAME code with ONE window per BLOCK instead of one per ROW, because a sender has
already permuted its BLOCK_ROWS partials into BLOCK_ROWS COLUMNS of one tile.

=== 5. THE num_blocks QUESTION (compaction makes ONE ROUND affordable; is one round better?) ==
At the focus geometry (G = 8, 32 tile-rows/core), COMPACT only:

 BLOCK_ROWS   rounds   whole combine   ns/round   compact L1
     2          16        36656          2291        64 kB
     4           8        19481          2435        72 kB
     8           4        10994          2748        88 kB
    16           2         6879          3440       120 kB
    32           1         5428          5428       184 kB

 ONE round beats FOUR rounds 10994 -> 5428 = 2.03x, and beats the CURRENT four-round flat combine
 34772 -> 5428 = 6.41x.  Each round carries a ~2.1 us fixed sync+launch floor (the BLOCK_ROWS = 1
 cell is 2554 ns for a single trivial round), so collapsing 4 rounds into 1 removes ~3 x 2.1 us of
 pure round-trip.
 FLAT CANNOT GO THERE AT ALL: its landing ring is GATHER_SLOTS * BLOCK_ROWS = 1024 fp32 pages
 = 1152 kB of combine CBs at BLOCK_ROWS = 32, which does not fit in a core's L1 (measured L1_OOM).
 Removing the GROUP_SIZE x BLOCK_ROWS term is exactly what unlocks the knob.
 HONEST CAVEAT, stated because this bench cannot measure it: the op's D25 pipeline exists to hide
 the per-round gather latency behind block blk+1's pass A, and at num_blocks = 1 that pipeline is
 VOID.  This bench models NO pass A, so it credits the round collapse with latency D25 already
 hides in the real op.  The BLOCK_ROWS ladder is therefore a knob for the coordinator to re-decide
 with pass A present; the compaction win itself (the flat-vs-compact column at every fixed
 BLOCK_ROWS) does not depend on it.

 PRECISION COST, stated plainly: COMPACT is slightly LESS accurate than the current combine --
 rel-RMS 0.00383 vs 0.00227 at the focus (1.7x), 0.00486 vs 0.00260 at G=32/BR=1 (1.9x), pcc
 0.9999900-0.9999950 vs 0.9999965-0.9999982.  Cause, and it is understood rather than mysterious:
 the permutation matmuls round each value through a 16-bit DEST word twice more (once packing the
 compact tile, once un-packing it) at fp32_dest_acc_en = False.  Both sides are 4-5 ORDERS OF
 MAGNITUDE inside the 0.04 rel-RMS bound and 4 nines inside the 0.9995 pcc gate, so no option here
 trades the precision CONTRACT -- but the candidate is not free on accuracy and that is not hidden.
 The pack/un-pack spelling that avoids it does not exist: there is no fp32 path through DEST at
 this config, and CHANGING the config to get one is exactly the forbidden move.

=== 7. DOES IT MAKE writer_gather_zero UNNECESSARY?  YES, MEASURED ===========================
 `writer_gather_zero` exists ONLY because GATHER_FACES < 4 leaves part of every landing page
 un-written, so it has to pre-define exactly the unshipped faces.  A compact page CANNOT be
 partially shipped: the receiver's un-permute is a matmul, which sums 32 products across the row,
 so an inf/NaN bit pattern in ANY column becomes inf*0 = NaN in column 0.  So compact ships WHOLE
 tiles -- ONE transaction, every byte written by exactly one member per round, defined by
 construction.  Measured on the root's BRISC at the focus geometry: 10949 ns -> 13 ns.
 The ONE residue is the odd-GROUP_SIZE pad slot, which is now ONE page instead of
 GATHER_SLOTS * BLOCK_ROWS (G = 9 measured correct, pcc 0.9999932).  At even GROUP_SIZE (4/8/28/32,
 including the focus shape) the stage does literally nothing.
 This is the stage Perf 2's changelog named as "the honest next target" and said the principled
 route to was "take compact_partial_transpose_r2".  It is taken, and it is measured.

=== 10. INTEGRATION SURFACE (for the coordinator; none of this is measured, it is a checklist) =
 compute  member: reduce -> cb_sum_handoff (rows pages, D18 unchanged) -> ONE matmul-permute pass
                  -> a NEW 1-page cb_compact_handoff.  +219 ns/round, parallel on every core.
          root  : the D22 fused chain with `windows = 1` instead of `rows`, and the finalize scope
                  widened to <1,8> C (BLOCK_ROWS <= 16) / <1,8> RC (above).  D17's <2,4> stays for
                  the NON-combine local finalize, which really does own only column 0.
          all   : after the mcast lands, ONE matmul-permute pass un-packing 1 page -> `rows` pages
                  of cb_row_final.  Pass B is UNCHANGED (it still reads a column-shaped stat).
 writer   ship_partial becomes ONE whole-tile write to page `my_slot`; the gather ring becomes
          GATHER_SLOTS pages; `writer_gather_zero` shrinks to the odd-GROUP_SIZE pad page (a no-op
          at even GROUP_SIZE); the mcast carries 1 page.  D24's publish-own-copy-first and the
          no-self-signal rule are unchanged and still load-bearing.
 host     one host-generated one-hot bank tensor per core (BLOCK_ROWS pages, bf16), plus the
          cb_partials_gathered page count in the L1-bound BLOCK_ROWS solve.
 ordering D25's pipeline issues block blk+1's pass A before block blk's combine; the member's
          permute for block blk must be issued before its ship for blk.  Not measured here.
 ragged   num_rows % BLOCK_ROWS != 0 leaves the last block with rows < BLOCK_ROWS: the compact tile
          then uses only columns 0..rows-1, the rest stay exactly 0, and the widened finalize scope
          is a superset.  MEASURED, not assumed -- bench B carries two ragged configs (rows 20 with
          BLOCK_ROWS 8 -> 8,8,4 and rows 8 with BLOCK_ROWS 3 -> 3,3,2), both CORRECT on both
          variants and 3.11x / 1.59x.  Both kernels derive the round's window as
          `GATHER_SLOTS * rows` (COMPACT: GATHER_SLOTS), identically on every core -- that identity
          is what keeps a remote sender's locally-computed landing address equal to the root's.
