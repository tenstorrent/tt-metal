root_rotation -- ISOLATED bake-off, PERF ROUND 3
================================================
Box/arch: blackhole p150b, 1350 MHz (device 0 of a 4-chip host).
Config, IDENTICAL for every variant and NEVER a lever:
    bfloat16 / TILE_LAYOUT / MathFidelity.HiFi2 / fp32_dest_acc_en=False /
    math_approx_mode=False, bf16 TILE gamma, epsilon 1e-6.
Metric: DEVICE KERNEL DURATION [ns], ONE fresh profiled launch per variant.
Reproduce:  perf_experiments/root_rotation/run.sh -k focus
            python3 perf_experiments/root_rotation/read_results.py focus

IDEA
----
Rotate the cross-core combine's ROOT DUTY per row-block: round `blk`'s root is the
group member at slot (blk + phase) % GROUP_SIZE, instead of one fixed root per group
doing every round's gather + fold + multicast.

VERDICT: REGRESSION everywhere measured.  0.910x on the focus geometry, 0.854x-0.998x
across the sweep.  Correct (bit-exact) everywhere, L1-neutral to the byte, and slower.

BENCH CALIBRATION (why the numbers can be trusted)
--------------------------------------------------
`pure_op` runs the op's OWN descriptor and kernels, untouched, in the same process:
    focus   pure_op 34362  vs  fixed 34259   (0.3%)   vs the op's own perf test 34372
Every case's table carries its own `pure_op` row; all within 0.3-2.7%.

TWO BENCH BUGS WERE FOUND AND FIXED BEFORE ANY VERDICT WAS TAKEN:
 1. `if constexpr` guarding the rotating branch made variant 0 measure 40251 ns against
    the op's 34372 -- a 17% STRAWMAN baseline.  Bisected with RMS_ROT_BISECT to the
    writer copy; the switch is now a preprocessor `#if`, so variant 0's translation unit
    is byte-identical to the op's writer (mcast RT base included).
 2. The gather-zeroing payload was hoisted into a LAMBDA so the rotating variants could
    place it in two spots.  It was not inlined: `writer_gather_zero` measured 7837 ns
    inline vs 13664 ns through the lambda (+5827), which is 2/3 of what first looked
    like "the cost of rotation".  It is now a macro.

ATTRIBUTION of the -3374 ns
---------------------------
 rot+still  = the whole rotating MACHINERY (rotating wire, full-line EXCLUDE-source rect,
              both pipes on every core, per-round sender-coord indexing) with the
              placement held at slot 0            -> -460 ns  (~1.3%, near noise)
 midroot    = one FIXED root moved to an interior slot, i.e. the full-line
              EXCLUDE-source rect a moving sender forces, baseline kernel otherwise
                                                  -> -791 ns  (~2.3%)
 nozero pair= the gather zeroing itself: -2399 ns on the fixed placement,
              -3395 ns on the rotating one        -> rotation's zeroing fan-out
                                                     (1 core/group -> 4) costs ~-996 ns
 rot+nozero vs nozero = the PLACEMENT alone, with zeroing removed  -> -2378 ns
 So: ~1 us of extra gather zeroing + ~2.4 us of placement.  The machinery is free.

WHY IT LOSES (mechanism, read off the zones above)
--------------------------------------------------
The combine is a strictly SERIAL PER-ROUND CHAIN, not a per-core capacity problem:
    gather(r) -> fold(r) -> mcast(r) -> passB(r) -> ship(r+1)
and the writer executes its rounds in order on EVERY core.  The FIXED root is the one
core that never waits in `writer_mcast_recv`: D24 has it publish its own stat copy to
cb_row_final BEFORE broadcasting, so it is a full broadcast latency ahead of its group in
every round -- which is exactly why its 13.4 us of fold is nearly free (it runs in the
window the group spends on the gather + broadcast).  `writer_gather_wait` 4449 ns on the
fixed root vs `compute_root_fused` with no wait is that slack being spent.

A ROTATING root is, by construction, one of the cores that DID wait for the broadcast.
Its BRISC must serially wait out every earlier round's `writer_mcast_recv` (18977 ns,
n=3) before it can publish its own round's gathered block, and its compute blocks on that
publish -- its single fold zone is 7476 ns against the fixed root's 3350 ns/round, i.e.
~4.1 us of pure cb_wait_front the fixed root never pays.  Rotation therefore hands the
fold to the LATEST core in the round instead of the earliest.  It cannot shorten a serial
chain by moving a link to a different core; it can only add that core's later entry
point.  Consistent with this, the penalty GROWS with the number of rounds
(0.968x at 1 round -> 0.944x at 2 -> 0.910x at 4 -> 0.891x at 8 -> 0.854x at 16).

NOTHING WINS.  At num_blocks == 1 (the decode / width-shard geometries) rotation is

block is 4 + 2*span words per core instead of 4, which is 68 words/core at span 32).

OPTIONS THAT WERE MEASURED AND REJECTED
---------------------------------------
  zdefer  Move a future root's gather zeroing off the front of its round-0 ship into the
          mcast wait where its BRISC is idle.  MEASURED MUCH WORSE (0.794x vs rot's
          0.910x): at boot all four future roots zero IN PARALLEL while every core is
          still in pass A, and deferring serializes the zeroing into the round-0 window
          where it delays that core's mcast_recv and with it its pass B.  The op's
          boot placement is already the right one.
  diag    Phase-shift each grid row's rotation so the groups' roots are never all in one
          column.  FLAT (0.908x vs 0.910x) -- root-column NoC contention is not a term
          here.  Inexpressible on the PACKED single-group topology (one group, so a phase
          that varied within it would make its cores disagree about the round's root -- a
          hang); the bench degrades it to phase 0 there and records `diag_applied=0`.
