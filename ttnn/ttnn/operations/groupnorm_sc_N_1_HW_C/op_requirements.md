# Operation Requirements: groupnorm_sc_N_1_HW_C

## Definition
- **Formula**: `y[n,0,h,c] = (x[n,0,h,c] − mean[n,g(c)]) · rsqrt(var[n,g(c)] + eps) · gamma[c] + beta[c]`, `g(c) = c // (C / num_groups)`, `mean` / biased `var` over the `HW · C/G` elements of group `g` of image `n` (`torch.nn.functional.group_norm` semantics on the `(N, C, HW)` permutation).
- **PyTorch Reference**:
  ```python
  def pytorch_reference(x, num_groups, *, gamma=None, beta=None, eps=1e-5):
      xf = x.to(torch.float32)
      N, one, HW, C = xf.shape
      x_nchw = xf.squeeze(1).permute(0, 2, 1)
      weight = gamma.to(torch.float32).reshape(C) if gamma is not None else None
      bias = beta.to(torch.float32).reshape(C) if beta is not None else None
      out = torch.nn.functional.group_norm(x_nchw, num_groups, weight=weight, bias=bias, eps=eps)
      return out.permute(0, 2, 1).unsqueeze(1).to(x.dtype)
  ```
- **Import Path**: `from ttnn.operations.groupnorm_sc_N_1_HW_C import groupnorm_sc_N_1_HW_C`
- **Function Signature**: `groupnorm_sc_N_1_HW_C(input_tensor: ttnn.Tensor, num_groups: int, *, gamma: ttnn.Tensor = None, beta: ttnn.Tensor = None, eps: float = 1e-5, compute_kernel_config: ttnn.ComputeConfigDescriptor = None) -> ttnn.Tensor` — output has the input's shape and dtype, TILE layout, DRAM interleaved.

### [x] Refinement 1 — Fill the grid: ragged 2-D split + grid-synchronisation lamp

**Type**: perf

**Goal**: implement the design's actual work distribution — `rows [i·Ht // Pr, (i+1)·Ht // Pr)`, `cols [j·Ct // Pc, (j+1)·Ct // Pc)` with `Pr = min(P_n, Ht)`, `Pc = min(P_n // Pr, Ct)` — instead of Phase 0's `Pr | Ht`, `Pc | Ct` divisor constraint. On the 11×10 Blackhole grid the divisor constraint leaves the flagship SDXL shape `(1,1,16384,320) G=32` on **80 of 110 cores** (`Ht = 512`, `Ct = 10` → `16 × 5`), `(1,1,4096,320)` / `(1,1,1024,640)` / `(1,1,4096,640)` likewise at 80, and `(1,1,1024,1920)` at 96 + 3 idle: idle silicon that contradicts `op_design.md` → Work Distribution ("ceil/floor balanced", "ragged last group/chunk keeps nominal push/pop counts and narrows only the work"). Per-core `Ht_core` / `Ct_core` (and hence `num_row_chunks`, `num_col_groups`, the ragged last chunk's valid rows/cols) become RT args; reader reads only valid tiles, compute reduces/applies only valid tiles (`ReduceInputBlockShape::of(valid_rows, valid_cols)` per chunk, `IterationShape::grid(valid_rows, valid_cols)`), writer stores only valid tiles; CB capacities size to the max per-core block. Co-tune the `min_tiles_per_core` lamp (`∈ {1, 4, 8}`) in the same phase: for tiny images every extra core pays the gather + multicast handshake for a few tiles of work (the whole `≤ 64`-tile tail of INPUTS sits at the 7–10 µs floor). Patterns: `ttnn/ttnn/operations/examples/master.md` → `width_split` (fill the grid along the axis that has the extent) and `noc_placement` (keep the rectangle row-wise). No SUPPORTED change.

**Verifier notes**: filed first (ahead of the 2:1 cadence) because it is a **design-conformance defect** (planner's split not implemented), not an optional tune. Knob-turn on the `hw` / `ct` core-assignment knobs; the combine is unchanged (records are per-group, not per-tile). Watch the resident predicate: `blk` now differs per core — the CB descriptor must use the max, and the predicate must be evaluated on the max. Do NOT trade this for fewer, fatter cores on the large shapes — the two lamps pull in opposite directions and the large shapes are data-movement-bound (performance baseline: 246 GB/s effective on SDXL bf16, 124 GB/s on `(1,1,1024,1920)`). Keep the `Pr`-tie-break preference (taller `Pr` → each core's gamma/beta slice is the narrower `Ct_core`).

**Done when**: measured device-ns improves on `(1,1,16384,320) G=32` and `(1,1,1024,640) G=32` (bf16, TILE, gamma_beta) with the golden suite green, `device_num_cores` on those shapes ≥ 108 of 110, and no regression across the guard set (including the single-tile floor, where `min_tiles_per_core` must not add time).

**Outcome** (2026-09-15, 11×10 BH grid, bf16, one fresh-cache `--profile` run per variant; `tests/…/test_groupnorm_sc_N_1_HW_C_perf_guard.py` + `probes/compare_perf_guard_csv.py`): the design's ragged split is implemented (`rows [i·Ht // Pr, (i+1)·Ht // Pr)`, per-core `Ht_core`/`Ct_core` RT args, nominal CB quanta, dense valid tiles). Flagship `(1,1,16384,320)` TILE gamma_beta **86.2 → 78.5 µs** (−9 %, 80 → 110 cores); `(1,1,1024,640)` TILE gamma_beta **23.9 → 19.3 µs** (−19 %, 110 cores), no_affine 22.4 → 18.2; `(1,1,1024,1920)` 77.8 → 40.7 (−48 %); `(1,1,256,1280)` 20.8 → 14.2; `(1,1,4096,320)` 29.2 → 26.2; `(1,1,4096,640)` 52.5 → 47.7. Two findings drove the numbers more than the core count: (a) the per-core cost scales with `Ct_core` (pass-2 affine build ≈ 2.5 µs per channel tile, membership generation ≈ 22 ns/lane on the reader RISC), so the tie-break among max-core splits must be **largest `Pc`** for TILE (the verifier's "taller Pr → narrower Ct_core" is inverted: taller `Pr` widens `Ct_core`; measured 22.8 µs tall vs 18.4 µs wide on `(1,1,1024,640)`, and tall regressed `(1,1,4096,{320,640})` 1.8×); (b) the runtime block extents stopped GCC unrolling the per-T / per-chunk helper bodies over constexpr `cols`/`chunk_rows` — the new kernels on the OLD 80-core split are already 21–48 % faster on TILE (i-cache), and re-introducing compile-time shapes (dual `integral_constant` path) or unrolled reader loops regressed again. Going 80 → 110 cores is worth −3…−4 % on the DRAM-bound large shapes but **+0.6–1.4 µs on small-per-core-work shapes** (participant cost of the gather/multicast: `(1,1,1024,640)` TILE is 17.6 µs at 80 cores vs 18.2–18.5 at 110 — kept at 110 per this refinement's ≥ 108-core requirement; a perf-round candidate). `MIN_TILES_PER_CORE ∈ {4, 8}` measured strictly worse on the tiny shapes (`(1,1,64,320)` 8.3 → 10.7 / 18.9 µs) — kept at 1 (adds nothing at the single-tile floor). ROW_MAJOR: the per-stick reader is the critical path (≈ 145 ns/stick), so RM uses the tall tie-break and `SHRINK_TO_CRITICAL_EXTENT` (fewest cores with the same max `Ht_core`/`Ct_core`): RM guard cases within ±4 % of baseline at 80 cores (wide-110 was +27…+61 %). Residual regressions: the single-tile floor **6.97 → 7.49 µs** (+0.5 µs; zones: each reader stage +0.04–0.06 µs, compute pass 1 +0.19 µs — generic runtime-extent loops vs the old fully constant-folded 1×1 block; FillScalar-chain / streaming-square / tilize-dispatch ablations all flat) and the 4-core `single_core_per_image` RM pin +5–11 % (its baseline varies ±1.4 µs run-to-run). Next levers (not taken here): cheaper membership generation on the reader (incremental group index; generate `E` during the combine wait — R5), and letting the core count follow a participant-cost model instead of the max (R4/perf rounds).

### [x] Refinement 2 — Padding-independent non-aligned paths: lift the RM × hw_non_aligned exclusion

**Goal**: remove `{layout: ROW_MAJOR, alignment: hw_non_aligned}` from `EXCLUSIONS` by handling the image's ragged last tile-row **in-kernel** on the RM path: `read_sticks_for_tilize` currently reads `32 · chunk_rows` sticks per block, so the last block of an image reads rows `≥ HW` (the next image's rows, or past the buffer — NaN on `(1,1,17,64)`, wrong statistics on `(1,1,50,128)` / `(2,1,100,128)`). Read only the valid sticks of the last tile-row and zero-fill the remaining stick slots of `cb_x_rm` before the tilize (the design's Mechanism-caps row for `read_sticks_for_tilize`: "zero-fill the pad lanes … `0·NaN = NaN` otherwise"). In the same pass make the alignment paths **independent of the padding contents** rather than relying on `ttnn.from_torch`'s zero padding (the design's documented assumption): (a) zero-fill the pad *lanes* of `cb_x_rm` for `c_non_aligned` RM input explicitly (today it works because the stick's alignment padding happens to be finite and `E_T`'s zero columns mask it), and (b) for TILE input apply the design's partial COL scaler pair (`calculate_and_prepare_partial_reduce_scalers<…, REDUCE_COL, HW % 32>()` + `ReducePartialScaler::with_partial()` on the chunk holding the image's last tile-row) so garbage pad rows produced by an upstream op cannot enter `S`/`Q`. `n_g = Cg · HW` already uses the real `HW`. Both input layouts share the same block schedule, so this is one refinement.

**Implementation skill**: /memory-layouts

**Verifier notes**: knob-free — no block extent changes; the work is the RM reader's stick path and the reduce's partial-scaler call. Keep the pass-2 apply untouched: pad rows/lanes of the *output* tiles may hold anything (`ttnn.to_torch` slices them), only the statistics must be clean. Add an RM `hw_non_aligned` acceptance case with `N = 2` (the overrun reads the next image's rows there and passes silently for `num_groups = 1` unless the second image differs). Manipulation-op wrappers (`ttnn.to_layout` / `ttnn.pad` before the kernel) are **not** acceptable here — the RM stick reader is already in-kernel; extending it is the whole job.

**Done when**: `EXCLUSIONS == []`; every golden `hw_non_aligned` cell (both layouts) is `supported_pass`; the new `N = 2` RM case passes; precision baseline unchanged.

**Outcome** (2026-09-16): `EXCLUSIONS == []`. Reader: `load_x_chunk_sticks` classifies a tile-row as `row_ragged` (image's last tile-row, `HW % 32 != 0`, on the core with `row_begin + Ht_core == Ht`) and/or `lane_ragged` (column group holding the last channel tile, `C % 32 != 0`); such a block is `noc.async_write_zeros` + `write_zeros_l1_barrier`'d, then only `hw_tail` sticks × `C − 32·T_first` lanes are read over the zeros (pass 1; pass 2 skips the fill but never reads past the image). Aligned blocks keep the one-call fast path byte-for-byte. `cb_scaler` holds the `[full, partial]` REDUCE_COL pair when `HW % 32 != 0` (`calculate_and_prepare_partial_reduce_scalers<…, REDUCE_COL, HW % 32>`), and compute passes `ReducePartialScaler::with_partial()` to both column-sum reduces of the chunk holding the image's last tile-row (`hw_tail` CT + `owns_last_row` RT) — both layouts, so TILE statistics are independent of the producer's pad contents (pinned by `test_tile_padding_garbage_independent`, `pad_value ∈ {1000, −333}`). Golden slices `1x1x17x64`, `2x1x100x128`: 33 + 22 xfail → 55/55; `1x1x64x17`, `2x1x64x48`: 55/55; acceptance 51/51; layout matrix 48/48. Finding (not a defect of this refinement): the one-pass `E[x²] − mean²` variance collapses for |mean| ≳ 20·std on tile-ALIGNED shapes too (probe_009: PCC 0.34, rstd → rsqrt(eps)) — the design's deferred `shifted_two_pass_variance` row is the lever if that regime ever matters.

### [x] Refinement 3 — Compute-config surface: 16-bit DEST accumulation for bf16 / bf8b

**Goal**: add `fp32_dest_acc_en=False` to the op's precision surface for `bfloat16` / `bfloat8_b` inputs (keep `float32 + False` refused per `.claude/references/precision_convention.md`), declaring it as a SUPPORTED axis (`SUPPORTED["fp32_dest_acc_en"] = [True, False]`, tagged from the caller's config via `default_compute_kernel_config()`, with `{dtype: float32, fp32_dest_acc_en: False}` in `EXCLUSIONS`). Today `validate()` refuses `False` for every dtype because the statistics pipeline is a Float32-page matmul (`[S;Q] × Eᵀ`, `[mean;rstd] × E_T`) whose correctness contract is HiFi4 + fp32 DEST (`matmul_block_helpers.hpp` → Precision) and every intermediate page is `Float32` (ledger rule: page format follows DEST width). The refinement makes the intermediate-CB formats follow the DEST width (`Float16_b` pages for `cb_xsq` / `cb_colsum` / `cb_membership` / statistics CBs when DEST is 16-bit; the matmul operands then fall under the bf16 rule — HiFi2, `Kt > 1` needs care), re-derives `DEST_AUTO_LIMIT` on the host (already mirrored in `_dest_limit`, 16 / 8 with 16-bit DEST), and adds the skill's precision-matrix test.

**Implementation skill**: /numeric-formats-metal

**Verifier notes**: cheapest tier (precision knob), hence last among the generality refinements. `feature_spec.TARGET` has no `fp32_dest_acc_en` axis — ask the user to add it via `/golden-tests` (TOLERANCES keyed by `(dtype, fp32_dest_acc_en)`) so the golden suite exercises the new cells; until then the skill's precision-matrix test is the acceptance. The design's `cb_xsq` `Float16_b` lamp (halve the bytes through the packer/unpacker for bf16/bf8b input) is the same mechanism — measure it here for the fp32-DEST default too and keep it if it is neutral or better on the guard set. Do not touch the `Float32` page of `cb_gather` / `cb_totals_*` (cross-core record format) unless both ends change together.

**Done when**: `SUPPORTED["fp32_dest_acc_en"] == [True, False]` with the fp32 + False exclusion; the precision-matrix test passes for every `(dtype, fp32_dest_acc_en)` cell at the convention's tolerances; golden suite green; no regression on the guard set at the default config.

**Outcome** (2026-09-16): `fp32_dest_acc_en ∈ {True, False}` is supported for `bfloat16` / `bfloat8_b`, `float32 + False` refused (`ExcludedCell`). **Declaration placement**: `SUPPORTED_COMPUTE_CONFIG = {"fp32_dest_acc_en": [True, False]}` / `EXCLUSIONS_COMPUTE_CONFIG = [{dtype: float32, fp32_dest_acc_en: False}]` in the op file, merged into `validate()`'s per-axis and cell-level checks exactly like `SUPPORTED` / `EXCLUSIONS` — **not** a literal `SUPPORTED["fp32_dest_acc_en"]`, because `eval/registry.unsupported_reason()` xfails any golden cell that lacks a `SUPPORTED` key ("axis missing from cell"), and `feature_spec.AXES` has no `fp32_dest_acc_en`: the literal form would xfail (then XPASS-strict-fail) all 3685 golden cells. ### [ ] Refinement 4 — Speed up the DRAM-bound SD/SDXL cells: block-knob co-tune

**Type**: perf

**Goal**: the large supported cells run at 120–250 GB/s effective (in + out) on Blackhole (bf16 TILE medians: `(1,1,16384,320)` 85.3 µs, `(1,1,4096,640)` 51.6 µs, `(1,1,1024,1920)` 63.4 µs at only 124 GB/s, `(1,1,1024,640)` 22.0 µs) — a clear gap to the DRAM roofline, so the levers are the planner's block knobs, co-tuned on the flagship `(1,1,16384,320) G=32` (per core: `Ht_core = 64` (or 32 after Refinement 1), `Ct_core = 1`, `cols = 1`, `chunk = 32 × 1`): (1) `chunk_tiles_target ∈ {8, 16, 32, 64, blk}` × `x_depth ∈ {2, 3}` (the design's Overlap lamp; `compute_block_size` charges ≈ 1.6 µs per extra helper pass, `double_buffer` saturates at 4–8 tiles per barrier); (2) `reduce_algorithm = AccumulateViaAdd` for the column sums (`reduce_block`: COL wins from ≥ 8 reduced tiles, 3.4× at 32 — `chunk_rows = 32` here — and it lifts the `DEST_AUTO_LIMIT` cap on `cols`); (3) `membership_depth = 2`; (4) `out_block_tiles_target` (8 today) vs 16; (5) the apply realisation lamp (`unary_bcast<ROW>(b_T)` seed + `mul_tiles_bcast_rows(x, a_T)` from row-0 `a_T`/`b_T` instead of full tiles + `DestReuseBinary`; `compute_fusion` says FPU dest-reuse is a net loss); (6) **transfer coalescing + chunk shape** — effective bandwidth on `(1,1,16384,320)` *rises* with tile size (bf8b 190 GB/s → bf16 246 → fp32 290 GB/s in+out), the signature of a per-transaction-bound reader issuing one `noc_async_read` per tile; with `Ct_core = 1` no two tiles of a chunk are DRAM-contiguous, so prefer the split that keeps `Ct_core ≥ 2` and `Ht_core ≥ chunk_rows` (the `Pr`-tie-break currently picks `16 × 5` over `8 × 10` on SDXL and `Pr = 32` on `(1,1,1024,1920)`, whose chunks are then `1 × 5` tiles at 124 GB/s — measure both tie-breaks) and issue one NoC read per contiguous tile-row run (`tile_reorder`, `double_buffer`), same for the writer's `out_block` (the verifier's `out_block = 8` batching measured neutral at the current chunk sizes — the reads bound these shapes). All ⭐⭐ T2 knob-turns on the exposed block surface — try several in one phase. No SUPPORTED change.

**Verifier notes**: run after Refinement 1 (the per-core block shape changes with the ragged split, so tune the final shape). Every lever is already a single host constant (`CHUNK_TILES_TARGET`, `X_DEPTH`, `MEMBERSHIP_DEPTH`, `OUT_BLOCK_TILES_TARGET`) or a CT enum — turn them there, never in the kernels. The ledger's `cb_xsq` sizing scales with `chunk`; a coarser chunk on fp32 input must keep the resident predicate true for the INPUTS shapes (re-check `l1_ledger.md`'s worked default). Fold the ledger's recorded-but-not-taken aliases (`cb_xsq` ↔ `cb_a_full + cb_b_full`, `cb_agg_interm` ↔ `cb_stats_T`) in here only if a coarser chunk makes L1 tight.

**Done when**: measured device-ns improves on `(1,1,16384,320)` and `(1,1,1024,640)` (bf16 TILE gamma_beta, default config) with the golden suite green and no regression across the guard set.

### [ ] Refinement 5 — Speed up the latency floor: cheaper per-image combine

**Type**: perf

**Goal**: every supported cell ≤ 64 tiles sits at a 7–10 µs floor (`(1,1,32,32)` 6.9 µs on 1 core, `(1,1,64,64)` 7.8 µs on 4 cores, `(1,1,128,128)` 7.8 µs on 16) where the data itself is < 1 µs of DRAM time, and multi-image shapes pay the combine once per image serially.
