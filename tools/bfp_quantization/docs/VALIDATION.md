# Validation

## tt-metal integration

Integrated under `tools/bfp_quantization` from upstream base `fa9cc8c6925`.
The independently installed package was rerun with the repository-compatible
NumPy 1.26.4, Python 3.12.14 and PyTorch 2.14.0 on macOS arm64. The CPU native
backend was rebuilt from the repository-formatted C++ source. The documented
test command uses `--confcutdir=.` to exclude tt-metal's device fixtures.
No model weights, calibration datasets or native binaries are committed.

**52 tests passed; 1 optional TTNN module skipped.** The native synthetic example,
source/wheel builds, documentation link checks and the repository's applicable
pre-commit hooks also passed. TTNN packing, full device regressions and Linux
OpenMP execution were not run on this macOS host.

## Version 0.2.0: complete checkpoint export

On the same macOS/Python/Torch environment described below, with safetensors 0.8.0
and Transformers 5.17.0, **52 tests passed; 1 optional TTNN module skipped**.
All tests ran with model/network downloads disabled. The new integration tests:

- Created local tiny Llama models and a tokenizer, with single-file and sharded
  safetensors checkpoints, and captured original-model statistics for GPTQ.
- Exported both max/max−1 and GPTQ + search, then reloaded through the unchanged
  `AutoModelForCausalLM.from_pretrained` and `AutoTokenizer.from_pretrained` calls.
  Every loaded parameter matched the exported checkpoint and forward logits were
  finite. Unselected parameters stayed identical to the original model.
- Compared exports against direct quantizer API results for ordinary BFP4,
  max/max−1 BFP4/BFP8 and GPTQ BFP4, including uneven output-group boundaries.
- Checked shared Hessian factor reuse, exact preservation of the source files,
  index/tokenizer copying, CLI dry runs, invalid selections/statistics, and cleanup
  after a failed export.
- Installed the built wheel into a separate directory and reran all 23 checkpoint
  export tests from outside the checkout; all passed using the installed package.

These checks establish checkpoint compatibility and preprocessing correctness.
They do not establish end-to-end accuracy or TT packing correctness for arbitrary
model loaders. No fresh TT hardware evaluation was performed for this release.

## Version 0.1.0: extracted quantizers

Prepared on 2026-09-18 with Python 3.12.14, PyTorch 2.14.0 and NumPy 2.5.3 on
macOS arm64. The native backend was compiled with Apple Clang in serial mode.

- **29 tests passed; 1 optional TTNN module skipped.** Native-vs-NumPy tests were
  enabled, including both BFP precisions, exponent candidates, ties/saturation,
  partial groups, output shards, GPTQ dead columns, activation ordering, and a
  partial final column block. Calibration hooks preserved outputs and removed
  themselves on exceptions. CLI exports and metadata were checked.
- Frozen fixtures generated by the **original experiment's Python functions**
  matched the extracted implementation. The fixture records source hashes and
  stores the Hessian factor to isolate the GPTQ loop from cross-platform
  Cholesky differences. Fixtures contain synthetic data, not model weights.
- The built wheel was installed into an independent directory. Import location
  was verified, its bundled C++ source compiled, the full example ran using its
  native backend, and CLI export tests passed from outside the source checkout.
- Source distribution and a `py3-none-any` wheel were built. Native binaries are
  compiled on the receiving machine and are not shipped in the wheel.

The standalone example uses 2,048 calibration input rows and 1,024 different
held-out rows, a 65-input/80-output Linear layer, and output shards `[40,40]`:

| Method | Held-out output MSE |
|---|---:|
| Ordinary BFP4 | 0.00370082 |
| Max/max−1 BFP4 | 0.00358524 |
| GPTQ + search BFP4 | 0.000212476 |
| Max/max−1 BFP8 | 0.0000146487 |

This is a synthetic reconstruction check, not a language-model accuracy result.

For a separate 512×257 matrix with a reused Hessian factor and four Torch threads,
the median of three GPTQ + search calls was 29.39 ms with the NumPy/PyTorch loop
and 2.73 ms with serial native C++ (10.75×). Outputs matched bit for bit. This
small CPU microbenchmark excludes calibration/factorization and does not predict
end-to-end model speedup or TT inference speed.

TTNN is unavailable in this local macOS environment, so the new package's optional
TTNN host-packing tests and Linux OpenMP build were **not run here**. The original
experiment validated its underlying quantizers and exports against TTNN on
Blackhole. Run the included checks against your actual TTNN version and layout:

```sh
TT_BFP_TEST_NATIVE=1 python -m pytest --confcutdir=. -q
python -m pytest --confcutdir=. -q tests/test_ttnn.py  # requires installed/configured TTNN
```
