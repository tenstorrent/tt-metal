Experiment C — FSD route produces the same rank bindings as golden

latest tt-metal · fixture tests/scale_out/4x_bh_quietbox (4 hosts × 16 P150) · issue #52859

✓ IDENTICAL placement on both MGDs tested (4×4 and 2×4)

The question

Does solving rank bindings from a Factory System Descriptor (FSD) — the route Fabric Manager (FM) uses — give the same rank bindings as the committed golden placement, on the same machines?

What was run

generate_rank_bindings (tt-run Phase-1) normally builds a PhysicalSystemDescriptor (PSD) from live hardware discovery. For this experiment it was wired (#52859) to take the FM path: when TT_METAL_FACTORY_SYSTEM_DESCRIPTOR_PATH is set it builds the PSD offline with FM's own ported builder build_physical_descriptor_from_file (ported from tt-fabric-manager controller/physical_system_descriptor_builder.cpp) — no hardware, no discovery — then runs the same topology mapper tt-run uses. One -np 1 process builds the whole-system PSD centrally, exactly like FM.

The only non-placement differences vs the golden .yaml files are a hand-authored global_env: block + comments (curated into the fixture, never emitted by generate_rank_bindings) and an absolute-vs-relative mesh_graph_desc_path. The FSD route emits no TT_VISIBLE_DEVICES — that is a host-local device index only the live cluster can supply, so the FSD route is logical placement only; the goldens carry none either.

Why this is the parity proof

Both the PSD route (tt-run) and the FSD route (FM) converge on the same PhysicalSystemDescriptor type and feed the same map_multi_mesh_to_physical mapper. Identical topology ⇒ identical placement. The FSD route simply builds that PSD from the factory descriptor instead of from live discovery, and adds no TT_VISIBLE_DEVICES (the one field it cannot resolve offline).
