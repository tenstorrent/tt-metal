# moe-grouped-topk

## What the code does
`ttnn.experimental.deepseek_prefill.moe_grouped_topk` is the device MoE router of the prefill models
(DeepSeek-V3, DeepSeek-V4 Flash/Pro non-hash layers, Kimi-K2.7, Kimi-K3, GLM-5.3). Per token row it takes
the gate logits `[tokens, n_experts]` and the expert correction bias (same shape, broadcast per expert) and:

1. upcasts both to fp32,
2. applies the score function (`sigmoid`, or `sqrt(softplus(x))` for DeepSeek-V4),
3. adds the bias,
4. selects experts: with `n_groups > 1` (DeepSeek-V3: 8 groups) it sorts each group, sums the top
   `summed_experts_per_group` scores per group, keeps the top `topk_groups` groups and takes the top-k
   experts among them; with `n_groups == 1` it is a plain top-k over all experts (`blocks::topk`),
5. gathers the *unbiased* activated scores of the chosen experts, normalizes them to sum 1 and scales
   by `route_scale`.

Outputs: weights `[tokens, k]` bf16 (ROW_MAJOR in production for k <= 32), indices `[tokens, k]` uint16
TILE. Rows past `padding_config`'s real-token count get the sentinel index `n_experts`.

Work is split across cores by **tile rows of tokens** (`split_work_to_cores(grid, height_tiles)`), and each
core processes all experts of its 32-token tile rows. At the production 640 tokens per chip that is 20 tile
rows, so only 20 of the ~110 Tensix cores do any work. Each tile row runs the whole pipeline serially in one
compute kernel. The sorts are the bitonic `topk_local_sort` / `topk_merge` / `topk_rebuild` LLKs on
transposed tiles, with uint32 index tiles that the writer generates.

## Where the code is
All under `ttnn/cpp/ttnn/operations/experimental/deepseek_prefill/moe_grouped_topk/`:
- `device/moe_grouped_topk_program_factory.cpp`: core split, the ~25 circular buffers, compile-time and
  runtime args, compute config (host side; changing it needs a rebuild)
- `device/kernels/compute/moe_grouped_topk.cpp`: the per-tile-row pipeline
- `device/kernels/compute/moe_gate_common_compute.hpp`: the stage blocks (upcast, score func, add bias,
  sort/topk, group sums, normalize, scale). **Shared with `moe_hash_gate`.**
- `device/kernels/dataflow/reader_moe_grouped_topk.cpp`: reads logits and bias tiles
- `device/kernels/dataflow/writer_moe_grouped_topk.cpp` + `moe_gate_common_dataflow.hpp`: index-template
  generation, gather of the chosen unbiased scores, padding sentinels, output writes
- `device/moe_grouped_topk_device_operation.cpp`: validation and output specs; op wrapper and nanobind
Kernels are JIT-compiled at run time; host files need a rebuild.

The Blackhole LLK sources (`tt_metal/hw/ckernels/blackhole/`: topk sort LLKs, SFPU sigmoid/softplus/sqrt,
unpack/pack) are also editable. They are shared with other ops, so an in-place change must keep the
function's interface and its accuracy (non-approx stays non-approx). A specialized routine that only this
op calls may live in a new function or file.

## What is measured
`tests/ttnn/nightly/unit_tests/operations/experimental/deepseek_prefill/test_moe_grouped_topk_prefill_perf.py`
has 6 cases, one per production model gate. Each is called exactly as `TtMoEGatePrefill` calls it in
production: 640 tokens (one chip's share of a 5k-token prefill chunk), bf16 logits in L1, broadcast bf16
bias in DRAM, a padding config, `stable_sort=True`, ROW_MAJOR weights.

| case | experts | groups (top) | k | score func |
|---|---|---|---|---|
| deepseek-v3 | 256 | 8 (4) | 8 | sigmoid |
| kimi-k2-7 | 384 | 1 | 8 | sigmoid |
| kimi-k3 | 896 | 1 | 16 | sigmoid |
| glm-5-3 | 256 | 1 | 8 | sigmoid |
| dsv4-flash | 256 | 1 | 6 | sqrtsoftplus |
| dsv4-pro | 384 | 1 | 6 | sqrtsoftplus |

There are 3 warmup and 10 measured calls per case. The value is the mean DEVICE KERNEL DURATION in µs from the
Tracy ops CSV. Accuracy is measured against an fp32 torch golden on tie-free bf16 inputs:
- `recall`: the fraction of golden experts selected. The baseline is 0.9955 to 0.998. A few near-tie experts flip
  because the device score functions are not bit-exact fp32. Gate: `recall >= 0.995`.
- `set_weights_max_abs`: the max weight error on rows whose expert set matches. The baseline is <= 0.0022. Gate: <= 0.004.
- `exact_rows` and `weights_pcc` are logged too. Position-wise comparison makes them sensitive to the
  order of near-equal experts, so they are not gated.

## Known ideas and constraints
- The core split is the obvious first lever: 20 busy cores out of ~110. Options include splitting the
  expert axis across cores and merging (top-k is mergeable), splitting tile rows into faces, or overlapping
  stages across cores.
- The single-group path (5 of the 6 cases) is a plain top-k over 8 to 28 tiles of experts. The grouped path is DeepSeek-V3 only.
- Keep the per-call setup cheap: index templates are regenerated by the writer.
- See the campaign rules: the compute config and fp32 pipeline stay, the op's contracts (stable tie order,
  padding sentinels, layouts, grouped and single-group routing) stay, `moe_hash_gate` must keep working,
  and the existing moe_grouped_topk correctness suites must keep passing.
