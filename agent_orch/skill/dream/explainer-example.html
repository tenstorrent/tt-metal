How the attention indexer picks keys, before and after the fix

For each query, the sparse-attention indexer keeps the 1,536–2,048 highest-scoring keys out of tens of thousands. The top-k op was keeping a wrong key about 1 to 4 times in every 1,000 picks. The fix lets the op read 32-bit scores and focus its limited precision right at the cut-off line. Three of four test shapes now make zero wrong picks, and the fourth makes about one wrong pick in 250,000. The op is 4–5% slower.

What the op does

ttnn.experimental.topk_large_indices is used by the DeepSeek sparse-attention (DSA) indexer in models/demos/deepseek_v3_d_p/tt/mla/indexer.py. Each row is one query. Each column is the score of one past key. The op returns the positions of the k highest scores, highest first.

128–640queries (rows) per chip
8K–64Kkeys scored per query
1,536–2,048keys kept per query (k)
1 op callper indexer step

The work happens on each core in three stages:

  • Cut the row into windows of 2,048 columns (1,024 or 512 when k is smaller).
  • Sort each window and merge it into a running "survivor" list of the best 2,048 seen so far. A hardware sorter on the vector unit does this.
  • Write out the survivor's top k positions.

The sorter works on 32-bit words. Each word holds the score and the column number packed together, so the column number travels with the score through every sort and merge. That packing is the root of the problem: whatever bits the column number takes, the score loses.

A wrong pick happens when the k-th and (k+1)-th best scores are so close that the sorter sees them as equal. It then keeps whichever comes first, which may be the smaller one.

The pipeline, step by step

Orange marks a step where precision was thrown away. Green marks a step that now keeps it.

Before

  1. Round the scores to bf16

    The indexer computes 32-bit scores, but the op accepted only bf16 (7 fraction bits). Many close scores became exactly equal before the op even started.

    bf16 input only

  2. Pack score + column number

    Upper 16 bits: the bf16 score. Lower 16 bits: the column number (5 bits of window number, 11 bits of position in the window).

    7-bit score16-bit column

  3. Sort windows, merge into survivor

    Scores closer than about 1 part in 128 compare equal, and the first one seen wins.

    ≈1/128 resolution

  4. Write the top k

    Whatever the survivor holds at ranks 0 … k−1, ties included.

After (32-bit input)

  1. Accept 32-bit scores

    The op now takes FLOAT32 input and copies each window into the vector registers at full 32-bit precision. BF16 input still runs the old code unchanged.

    fp32 input

  2. Estimate the cut-off T

    From the first window's mean and spread, guess where the k-th best score will be. Sort that window, read the value at the matching rank, and use it as T. After 4 windows, refine T from the survivor list.

    T ≈ k-th score

  3. Pack (score − T) + column number

    Subtracting the same T from every score keeps their order, but now scores near the cut-off are close to zero. The same few bits then measure tiny differences near the cut-off instead of the whole value. The window-number field also shrinks to just what the row needs: 1 bit for 2 windows, 5 bits for 32.

    7–11 bits of x−T12–16-bit column

  4. Sort windows, merge into survivor

    Same hardware sorter. Near the cut-off it now tells apart scores that differ by about 1 part in 100,000.

  5. Fix the boundary with exact values

    The writer core reads the exact 32-bit scores around rank k and re-sorts them. When k is below the window size (k = 1,536), it checks the 32 ranks around k. When k = 2,048 there are no spare ranks, so the writer (helped by the reader core on the last row) scans the row again for any dropped score that beats the weakest kept one. A deadline stops this scan before the busiest core finishes, so it never adds to the op's time.

    exact boundarytime-boxed

Where the bits go

The sorter compares whole 32-bit words. In every packed word the column number takes the low bits, so the score keeps only what's left. The fix doesn't get many more bits; it moves the zero point so the bits it has are spent where they matter.

Before: bf16 score + column7 fraction bits of x · about 1 part in 128

A float's fraction bits are relative to its own size. Seven bits on a score of 3.2 resolve steps of 0.016. Seven bits on a difference of 0.004 resolve steps of 0.00003. That's 500 times finer, from the same 7 bits.

T only has to be close, not exact: shifting by any constant keeps the order. A rougher T just means slightly coarser steps near the line. The final exact-value pass then catches the rare tie that survives.

The one wrong pick left in the 32K case sits on the last row of the busiest cores. That row ends the kernel, so the time-boxed rescan never reaches it. Fixing it would mean saving compute time on those cores first, because the case already runs right at the 5% limit.

To benefit, the model has to pass 32-bit scores. BF16 input still behaves exactly as before. Also, the k = 2,048 row rescan runs only when the valid length is a plain number. When it comes from an on-device tensor (valid_length_tensor, which the indexer's metadata path uses), the op still gets the finer x − T keys but skips the exact rescan.
