What the steps are

The framework brings a model up one small step at a time. A test decides whether each step passed. The test is written and frozen before any device code exists, so an agent cannot tune the test to its own code. These are the step types in this run, in the order they happen:

R.* reference
A CPU version of the model, checked against Hugging Face. Everything later is compared with it. One agent.
G.* goldens
The reference is run on the book text at 4k, 16k and 56k tokens, and every layer's output is saved. These saved outputs are the "golden" answers. Script, no agent.
PL.* plan
How the model is split over the 4 chips, and a check that it fits in memory. One agent, then an approval.
C.* component
One piece of one layer, for example the router or the attention. It runs on the device alone, fed from the golden, and its output is compared with the golden. Two agents: a test agent first, then an implement agent.
test agent
Reviews the automatically generated test for the step and makes it stricter if needed. For example, the indexer test got a set-overlap metric instead of plain PCC. It runs the test on the device several times, with the CPU reference and with deliberate mistakes, to show the test catches them.
freeze
The test is locked. It must pass with the CPU reference plugged in and fail with a module that returns zeros. From then on no agent may change it. Script.
implement agent
Writes the device code for the step until the frozen test passes. If existing code already passes, no agent is started.
S.* swap test
The whole layer runs with steps 1 to n on the device and the remaining steps on the CPU. The layer's output is compared with the golden. It catches problems that only show when steps are chained, such as a wrong layout handed from one step to the next. Swap tests come from one template. One test agent, then the freeze.
M.1, L.* ladder
The full device model, run at growing lengths up to 56k tokens and checked layer by layer against the goldens. Not reached yet.
K.1, X.*, O.1
Serving contract, performance profile and picks, and tests for the forked ops. Not reached yet.

Outside the agents: about 2.3 h of gate runs, the checks that decide pass or fail (goldens 0.5 h, swap-test gates 1.0 h, reference gates 0.5 h), and about 2.8 h of test freezing, pre-checks and orchestration. 24 of the 41 component steps passed on the pre-check with no implement agent, because the code from an earlier layer already covered them.

What the numbers say

  1. Reviewing tests costs about 8× more than writing the code. The test agents took 11.8 h and the implement agents 1.5 h. The code was quick because layers 1-4 mostly reuse layer 0's modules, but every test is still reviewed from scratch.
  2. Swap-test review is half of all agent time and rarely changes anything. Its 41 runs took 7.8 h (51%) and changed the test only 4 times, each time to add extra checks. All swap tests come from one template, and every freeze already requires a pass with the reference and a fail with the zero stub.
  3. Component-test review earns its time. It changed 14 of 41 tests. Some changes were important, such as the set-overlap metric for the indexer and the checks that catch a wrong norm epsilon. It is still repeated for layers whose component is identical to one already reviewed (layers 2-4 against layer 1).
  4. Most agent time is device runs, not thinking: 9.8 h running tools against 5.5 h thinking. Each test run opens the 2x2 mesh and loads the weights again, so a test agent spends several minutes per run waiting on the setup.
  5. The one long agent run was a one-off. The reference run (1.9 h) was mostly two full 78-layer CPU sanity passes, reading 1.5 TB of weights from disk. The second pass was needed after the agent found the RoPE bug in the HF code.

Ways to make it faster

1. Freeze swap tests without a review agent

about 6-7 h per bring-up

Render the swap test from the template and freeze it right away. The freeze still requires a pass with the CPU reference and a fail with the zero stub. Fold the 4 kinds of extra checks the agents added into the template once, so every swap test gets them.

Risk: a model with an unusual block wiring could need a hand-written swap check. Keep an opt-in review for block types the plan flags as unusual.

2. Reuse a reviewed component test for a repeated component

about 1.5-2 h

When a block type repeats a component that already has a reviewed, frozen test (same module, same shapes, another layer), render the test from the reviewed one and freeze it without a new review. In this run that covers most of layers 2-4 and layer 1's attention side.

Risk: a layer that is subtly different (another eps, another expert count) would be missed. Only reuse when the module and the layer config match exactly.

3. Keep the mesh and weights loaded between test runs

large, spread over every step

A long-lived test worker that keeps the 2x2 mesh open and caches loaded weights would cut the setup from each of the 380 device runs. This is the largest change to build and needs care with device ownership and resets.

Risk: a hang or a bad kernel state leaks into the next test. The worker must reset itself after any failure.

4. Fewer deliberate-mistake runs per test review

about 1-2 h

The test agents run 4-6 device runs per review to show the test catches injected mistakes. Most of the mistakes they try could be checked on the CPU against the golden (a wrong sign, a missing scale) without the device. Ask the agents to run the sensitivity checks on the CPU and keep one device run.

Risk: small. Device-only failure modes, such as layouts across chips, still need the one device run.

5. A lighter whole-model sanity check

about 0.5-1 h, only when a bug forces a rerun

The 78-layer HF sanity check reads 1.5 TB from disk each time. A cached result per HF-code version, and a quick first check on 256 tokens before the 2048-token one, would make a rerun much cheaper.

Recommendations 1 and 2 together would have cut this run's agent time from about 15 h to about 7 h. They are framework changes and would go through the framework's own selftests. Run1 continues on the current rules.

How these numbers were made

Agent times come from each agent's own transcript: wall time, model time, cost, and the commands it ran. Device test runs count run_safe_pytest.sh calls. "Changed the test" counts runs that edited a file in tests/bringup/. Gate times come from the run's ledger (state.json).
