namespace hal::replay

Blackhole replay HAL

Record a short Tensix instruction sequence once, replay it inline, or place its replay operation inside a MOP configuration.

Architecture Blackhole Language C++17 + SFPI extensions Header hal/replay.h State Per thread
Include the complete replay interface#include "hal/replay.h"

Each Tensix thread has an independent 32-instruction circular replay buffer. A REPLAY instruction either records the next Count instructions into that buffer or emits a previously recorded range into the instruction stream.

Three public operations

record() populates a range, run() issues it now, and get_operation() returns its encoded instruction for another expander such as MOP.

Quick start

Suppose a two-instruction row epilogue must run repeatedly. Record those instructions into slots 16 and 17, then replay them whenever the row completes.

#include "hal/replay.h"

constexpr hal::replay::BufferRange row_epilogue{
    .start = 16,
    .count = 2,
};

// Compile-time path
void configure_row_epilogue()
{
    hal::replay::record<row_epilogue>([] {
        TTI_NOP;
        TTI_NOP;
    });
}

void run_row_epilogue()
{
    hal::replay::run<row_epilogue>();
}

The compile-time form emits one immediate REPLAY instruction before the two recorded instructions and one immediate REPLAY instruction at each call to run().

Compiler-aware lowering

Both compile-time and runtime forms use the SFPI REPLAY builtin internally. Compile-time ranges still become one immediate instruction, while the builtin keeps the operation visible to target-specific optimization and register allocation.

Current SFPI lowering limits

The current SFPI compiler requires the builtin replay start index to resolve to a constant. Its immediate-count path accepts counts 1–32, so compile-time record() and run() do not currently accept counts 33–64 even though the ISA and BufferRange model them. A dynamic count can be lowered when the start index remains constant. get_operation() constructs the raw playback word and supports the documented 1–64 range.

Functional model

The Replay Expander is in each thread's frontend, after the MOP Expander and before the Wait Gate. Non-REPLAY instructions pass through unchanged. The following pseudocode uses the HAL names and shows the state owned by one thread.

replay_buffer = array[32]

forever:
    instruction = next instruction after MOP expansion

    if instruction is not REPLAY:
        emit instruction

    else if instruction records:
        index = instruction.start
        repeat public_count(instruction.count) times:
            recorded = next instruction after MOP expansion
            replay_buffer[index] = recorded
            index = (index + 1) modulo 32
            if instruction.behavior is RecordAndExecute:
                emit recorded

    else:
        index = instruction.start
        repeat public_count(instruction.count) times:
            emit replay_buffer[index]
            index = (index + 1) modulo 32

public_count(0) is 64; every other encoded value is used directly. The HAL keeps this encoding detail private and accepts public counts from 1 through 64.

Count the post-MOP stream

Recording happens after MOP expansion. If the recording body issues a MOP, its expanded operations—not the single MOP control instruction—consume replay slots.

Expansion does not recurse

Replay output cannot travel backward through the earlier MOP Expander. Do not place raw MOP or REPLAY control words in replay-buffer data: they are emitted downstream rather than recursively expanded. A MOP issued normally by the recording body is different—it expands before its resulting operations reach the Replay Expander.

Range and wraparound

HAL fieldISA nameValid public valueMeaning
BufferRange::startIndex0–31First replay-buffer slot.
BufferRange::countCount1–64Number of post-MOP instructions to record or replay. Public 64 is encoded as ISA value 0.

Indexing is circular. {.start = 30, .count = 4} visits slots 30, 31, 0, and 1. Counts larger than 32 revisit slots. Recording 64 distinct instructions overwrites every slot twice, leaving only instructions 33–64; replaying that 64-count range emits the final 32-entry contents twice.

Compile-time ranges are checked with static_assert. Runtime ranges use LLK_ASSERT; invalid runtime values are unsupported when assertions are disabled and are not normalized by the HAL.

Record a sequence

The default behavior stores instructions without sending them farther down the pipeline. Use RecordAndExecute when configuration and first execution should happen together. Both overloads forward any trailing arguments after the callable to the callable itself.

// Compile-time path: range and behavior emit immediate REPLAY.
hal::replay::record<
    row_epilogue,
    hal::replay::RecordBehavior::RecordAndExecute>([] {
    TTI_NOP;
    TTI_NOP;
});

// Mixed path: runtime count, compile-time behavior. The start slot
// must still resolve to a constant (see "Current SFPI lowering limits").
void record_epilogue(const std::uint32_t count)
{
    hal::replay::record<hal::replay::RecordBehavior::RecordOnly>(
        hal::replay::BufferRange{.start = 16, .count = count},
        [](const std::uint32_t n) {
            for (std::uint32_t i = 0; i < n; ++i)
            {
                TTI_NOP;
            }
        },
        count); // Trailing arguments are forwarded to the callable.
}
There is no record terminator

The callable must expand to exactly range.count post-MOP instructions. Too few causes later instructions to be recorded; too many leaves the tail outside the buffer. The HAL cannot infer this count from C++ source.

When gathering is enabled by the JIT build, record() preserves the existing safety workaround by disabling gathering around the recording body and re-enabling it afterward.

Run a recorded sequence

// Compile-time path: one immediate REPLAY instruction.
hal::replay::run<row_epilogue>();

// Runtime-count path: the start slot must still resolve to a
// constant (see "Current SFPI lowering limits").
hal::replay::run({.start = 16, .count = count});

run() does not track initialization. Record the range first, or ensure another configuration path has populated the same per-thread slots. The runtime overload accepts a BufferRange built at runtime, but the current SFPI lowering still requires its start to fold to a compile-time constant; only count may be genuinely dynamic.

Embed replay in MOP

Because MOP expansion happens before replay expansion, any MOP operation field can contain an encoded replay operation. get_operation() returns the playback form without issuing it.

// Compile-time path
constexpr std::uint32_t row_epilogue_op =
    hal::replay::get_operation<row_epilogue>();

constexpr hal::mop::MopConfig<hal::mop::MopTemplate::Template1> rows{
    .outer_loop = {
        .count = 4,
        .end_op = row_epilogue_op,
    },
    .inner_loop = {
        .count = 1,
        .body_op = pack_row_op,
    },
};

A runtime overload, get_operation(range), supports runtime MOP programming. It returns only the encoded word and does not touch the replay buffer. Both overloads intentionally encode playback only; the HAL does not expose raw record-control words for embedding.

Frontend behavior and performance

ModeFrontend inputFrontend outputBehavior
Ordinary instruction1 per cycle1 per cyclePasses through.
RecordAndExecute1 per cycle1 per cycleStores and forwards each instruction.
RecordOnly1 per cycleNone while recordingConsumes the REPLAY control, then stores count inputs.
run()No new input for the remaining expansion1 per cycleConsumes the REPLAY control, then emits the selected buffer range.

There is no transition penalty between modes. Downstream backpressure can extend replay time; gaps in the incoming stream can extend recording time.
