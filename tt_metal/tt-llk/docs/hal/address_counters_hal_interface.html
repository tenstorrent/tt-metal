Blackhole Address Counter HAL

Fluent, type-state builders for programming Blackhole Tensix X/Y/Z/W address counters with the SETADC, INCADC, ADDRCR, and GPR-sourced REG2FLOP instruction families.

Architecture Blackhole Language C++17 Header hal/address_counters.h Namespace hal
Include the address-counter interface #include "hal/address_counters.h"

Symbol, not nested namespacehal::address_counters is the global compile-time builder object inside namespace hal. The package title follows the entry point used by callers.

Quick start

Choose clients, select a channel, assign counters, and finish with an emission operation.

// Compile-time path
hal::address_counters
    .client<hal::AddressCounterClient::Unpacker0>()
    .channel<hal::AddressChannel::Channel0>()
    .X<face_r_dim>()
    .Y<0>()
    .channel<hal::AddressChannel::Channel1>()
    .X<face_r_dim>()
    .Y<0>()
    .apply();

Every operation before apply() returns a new builder type. Client, channel, selected-counter mask, and—on this builder—counter values are all encoded in that type.

Functional model

for each selected client on the issuing thread:
    for each mask-selected X/Y or Z/W counter:
        carry_reset_shadow += configured_increment
        live_counter = carry_reset_shadow

ADDRCRXY applies this transition to X/Y and ADDRCRZW applies it to Z/W. The mask keeps unselected dimensions unchanged. With an increment of zero, the operation reloads the live counter from its existing shadow.

Choose a builder

All constants

address_counters

Use template setters such as X<value>(). Selection and values are compile-time, allowing complete instruction words to be embedded directly.

Runtime data

runtime_address_counters

Use ordinary arguments such as X(value). Selection remains compile-time, so emission has no runtime dispatch; only instruction data is runtime.

GPR source

X/Y/Z/W().from_gpr(hal::gpr<Index>())

Reuse the normal client and channel selectors, choose one X/Y/Z/W destination, then attach a common GPR operand. The result emits one REG2FLOP with no runtime dispatch or completion NOP.

Builder flow

  1. client<...>() adds one or more hardware clients.
  2. channel<...>() selects the channel targeted by subsequent setters.
  3. X/Y/Z/W records a value only for the currently selected channel.
  4. Select the other channel, if needed, and assign its values.
  5. apply(), increment(), advance_and_reset(), or get_operation<...>() consumes the description.
// Compile-time path: keep the returned type when building in stages.
constexpr auto counters = hal::address_counters
    .client<hal::AddressCounterClient::Packers>()
    .channel<hal::AddressChannel::Channel0>()
    .X<0>()
    .Y<0>();

counters.apply();

The builder is immutableCalling a selector or setter without chaining it or storing its return value discards that choice.

GPR-source flow

Select exactly one client, channel, and destination counter with the existing builder, then finish with from_gpr(hal::gpr<Index>()). An optional thread<T0/T1/T2>() after X/Y/Z/W redirects the destination ADC while the source GPR remains in the issuing thread.

GPR mode cannot follow pending constant assignmentsThe counter-less X()/Y()/Z()/W() selectors that begin the GPR-source flow reject a builder that still carries unapplied constant counter values (static_assert: “REG2FLOP cannot share a builder with pending constant assignments; apply them first, then start a new builder”). A chain such as .X<5>().Y().from_gpr(...) does not compile — emit the constant assignments with apply() first, then start a fresh builder for the GPR-sourced write.

// Compile-time GPR-source path
hal::address_counters
    .client<hal::AddressCounterClient::Unpacker0>()
    .channel<hal::AddressChannel::Channel0>()
    .X()
    .from_gpr(hal::gpr<5>())
    .apply();

The client selector is variadic, so one instruction can target several clients where the hardware instruction permits it:

// Compile-time selection
.client<
    hal::AddressCounterClient::Unpacker0,
    hal::AddressCounterClient::Unpacker1>()

Channels

ClientDimensionChannel 0Channel 1
Unpacker 0/1XInput address generation: L1 address plus part of datum countInput address generation: part of datum count
Unpacker 0/1Y, Z, WDecompressor row seek within L1Output address generation: Dst/SrcA for unpacker 0, SrcB for unpacker 1

channel<Channel0>() and channel<Channel1>() accumulate in the builder, but the most recent call becomes the current channel for later setters. Selecting the same channel twice is rejected at compile time.

Instruction emission

The builder selects the smallest applicable instruction form from the counters and channels that were assigned.

DescriptionSetter emissionIncrement emissionAdvance/reset emission

X on both channels, no other counterSETADCXXINCADCXYADDRCRXY
Any other X/Y selectionSETADCXYINCADCXYADDRCRXY
Any other Z/W selectionSETADCZWINCADCZWADDRCRZW

apply()

Issues absolute counter writes immediately. The compile-time builder may emit both instruction families. The runtime-value builder accepts exactly one family per call.

increment()

Interprets the selected values as increments and emits INCADC instructions. As with apply(), split runtime X/Y and Z/W increments into separate builders.

advance_and_reset()

Interprets the selected values as increments to each counter's carry/reset shadow, then reloads the live counter from that updated shadow. It emits ADDRCRXY for X/Y and ADDRCRZW for Z/W. A zero increment restores the live counter from the unchanged shadow; it is not a no-op.

// Compile-time path
hal::address_counters
    .client<hal::AddressCounterClient::Packers>()
    .channel<hal::AddressChannel::Channel0>()
    .W<0>()
    .advance_and_reset();

The compile-time builder emits both instructions when X/Y and Z/W are selected together. The runtime-value builder accepts one family per terminal call.

get_operation()

Returns one SETADC, INCADC, or ADDRCR instruction instead of issuing it, for example for a MOP or replay-buffer slot. Describe exactly one encodable X/Y or Z/W family.

// Compile-time path
constexpr std::uint32_t advance_w = hal::address_counters
    .client<hal::AddressCounterClient::Packers>()
    .channel<hal::AddressChannel::Channel0>()
    .W<1>()
    .get_operation<hal::GetOpType::INCREMENT>();

GPR-sourced REG2FLOP

from_gpr<Width, ByteOffset>(hal::gpr<Index>()) attaches a compile-time GPR slice to the selected destination. Its result emits one REG2FLOP or returns that instruction from the no-argument get_operation(). Valid slices are 32-bit at Byte0, 16-bit at Byte0 or Byte2, and 8-bit at any byte.

REG2FLOP normally takes two cycles, occupies the Scalar Unit for its duration, and blocks subsequent issue from the calling thread. Contending Configuration Unit writes to THCON can extend that latency even though this form targets an ADC.

Live counter versus carry/reset shadowSETADC writes both the live counter and its _Cr shadow. REG2FLOP writes exactly one. X/Y/Z/W() defaults to the live counter; pass AddressCounterValue::Carry to target the shadow.

Common recipes

Reset several counters

// Compile-time path
hal::address_counters
    .client<hal::AddressCounterClient::Packers>()
    .channel<hal::AddressChannel::Channel0>()
    .X<0>()
    .Y<0>()
    .Z<0>()
    .apply();

Apply runtime data without runtime dispatch

// Mixed path: compile-time selection, runtime values
hal::runtime_address_counters
    .client<hal::AddressCounterClient::Unpacker0>()
    .channel<hal::AddressChannel::Channel0>()
    .X(face_r_dim)
    .Y(row_offset)
    .apply();

Configure both channels independently

// Mixed path: compile-time selection, runtime values
hal::runtime_address_counters
    .client<hal::AddressCounterClient::Unpacker0>()
    .channel<hal::AddressChannel::Channel0>()
    .X(input_count)
    .Y(row_seek)
    .channel<hal::AddressChannel::Channel1>()
    .X(datum_count)
    .Y(output_address)
    .apply();

Split runtime X/Y and Z/W operations

// Mixed path: compile-time selection, runtime values
auto selected = hal::runtime_address_counters
    .client<hal::AddressCounterClient::Packers>()
    .channel<hal::AddressChannel::Channel0>();

selected.X(x).Y(y).apply();

// Execute the operation that uses the programmed X/Y counters here.

selected.Z(z).W(w).apply();

Move the upper half of a GPR to a packer carry/reset shadow

// Compile-time GPR-source path
hal::address_counters
    .client<hal::AddressCounterClient::Packers>()
    .channel<hal::AddressChannel::Channel1>()
    .W<hal::AddressCounterValue::Carry>()
    .thread<hal::AddressCounterThread::T2>()
    .from_gpr<hal::AddressCounterGprWidth::Bits16,
              hal::GprByteOffset::Byte2>(hal::gpr<60>())
    .apply();

Compile-time API

inline constexpr object

address_counters

// Compile-time builder
inline constexpr ADC<> address_counters {};

The root of the fully compile-time fluent builder. Callers normally let each chained return type be deduced rather than naming an ADC<...> specialization.

builder method

client

// Compile-time path
template <AddressCounterClient... Clients>
constexpr auto client() const;

Adds the selected client bits to the builder. The variadic form supports broadcasting one counter operation to multiple clients.

terminal builder method

from_gpr

// Compile-time path
template <
    AddressCounterGprWidth Width = AddressCounterGprWidth::Bits32,
    GprByteOffset ByteOffset = GprByteOffset::Byte0,
    std::uint32_t Index>
constexpr auto from_gpr(hal::Gpr<Index> source) const;

Available after a singleton client, channel, and X/Y/Z/W destination have been selected. The common hal::gpr<Index>() operand supplies the source identity; Width and ByteOffset remain operation-specific. The result's apply() emits one immediate REG2FLOP and get_operation() returns its encoded word.

builder method

channel

// Compile-time path
template <AddressChannel Channel>
constexpr auto channel() const;

Adds the channel to the cumulative selection and makes it current. A channel cannot be selected twice in one builder chain.

builder methods

X / Y / Z / W

// Compile-time path
template <std::uint32_t Value>
constexpr auto X() const;

template <std::uint32_t Value>
constexpr auto Y() const;

template <std::uint8_t Value>
constexpr auto Z() const;

template <std::uint8_t Value>
constexpr auto W() const;

Assign a compile-time value to the indicated counter for the current channel.

emitters

apply / increment / advance_and_reset

// Compile-time path
void apply() const;
void increment() const;
void advance_and_reset() const;

apply() emits SETADC, increment() emits INCADC, and advance_and_reset() emits ADDRCR instructions. Compile-time mixed X/Y and Z/W selections emit one instruction from each family.

encoder

get_operation

// Compile-time path
template <GetOpType Operation>
static constexpr std::uint32_t get_operation();

Returns one encoded operation. It does not issue the instruction.

Runtime-value API

inline constexpr object

runtime_address_counters

The runtime-valued builder root. Its client() and channel() methods have the same template interface as ADC.

builder methods

X / Y / Z / W

// Mixed path: compile-time selection, runtime values

constexpr auto Z(std::uint32_t value) const;

The selected slot remains part of the type, while its value is carried by the builder object.

emitters and encoder

// Mixed path: compile-time operation shape, runtime values
void apply() const;
void increment() const;

template <GetOpType Operation>

Each runtime-value terminal must describe exactly one X/Y or Z/W instruction family. This keeps the emitted path branch-free with respect to the selected operation shape.

Constraints and diagnostics

RuleReason
Select at least one client before emission.The instruction needs a nonzero hardware client mask.
Select a channel before assigning counters.Setters write only the current channel slot.
Do not select the same channel twice in one chain.The builder rejects duplicate channel selection with static_assert.
Use one X/Y or Z/W family for runtime terminals.RuntimeADC emits exactly one instruction per terminal call.
Use one encodable family with get_operation().The function returns one 32-bit instruction word.
Keep ADDRCR channel-0 values and channel-1 X/Z within [0, 7], and channel-1 Y/W within [0, 63].These are the instruction's asymmetric encoded field widths; compile-time paths use static_assert and runtime paths use LLK_ASSERT.
Chain calls or retain the returned object.Builders are immutable values; methods do not mutate the source object.
Use a GPR index in [0, 63] with from_gpr.REG2FLOP encodes InputReg in six bits.
Select one client, channel, and X/Y/Z/W destination in GPR mode.The ADC REG2FLOP encoding has singleton selectors rather than SETADC masks.
Do not enter GPR mode on a builder with pending constant assignments.REG2FLOP cannot share a builder with unapplied constant counter values; the counter-less X/Y/Z/W selectors reject it with static_assert. Apply the constants first, then start a new builder.
Match byte selection to width.32-bit accepts Byte0; 16-bit accepts Byte0 or Byte2; 8-bit accepts Byte0 through Byte3.

No implicit hardware readbackThe builder describes writes and increments only. It does not inspect current counter state or validate that a numerical increment is meaningful for the active kernel.

Source

The address-counter builders are in tt_llk_blackhole/llk_lib/hal/address_counters.h, and the shared GPR identity is in hal/utils/gpr.h. Instruction encodings and emission macros come from the Blackhole ckernel headers.
