namespace hal::mop

Blackhole MOP HAL

Configure and run the Tensix macro-operation expander so one MOP instruction can generate a repeated instruction sequence.

Architecture Blackhole Language C++17 Header hal/mop.h Namespace hal::mop
Include the complete MOP interface #include "hal/mop.h"

MOP is a small hardware instruction expander. Software first writes a template configuration for the current Tensix thread, then issues one MOP instruction through a matching Runner. The expander turns that instruction into the configured sequence.

The rule of thumb

Use Template 0 when each iteration chooses a normal or shadow path from a mask. Use Template 1 for a nested loop with optional start, end, alternating, and last-iteration operations.

Quick start

Suppose the unpacker must read a 2×2 grid of faces from operand A and operand B, pairing the two operands face by face. Describe one SrcA unpack and one SrcB unpack with the hal::unpack interface, then use their encoded operations as the alternating Template 1 operations. If the unpack descriptors are new to you, read the unpack HAL guide first; this page only consumes the words it produces. 

#include "hal/mop.h"
#include "hal/unpack.h"

// Compile-time path. Descriptors are plain constexpr values, so one
// factory builds both operations; they differ only in the engine.
constexpr hal::unpack::DataTransfer face_unpack(const hal::unpack::Engine engine)
{
    return {
        .engine     = engine,
        .increments = {.channel0 = {.z = 1}},
        .handoff    = hal::unpack::SourceHandoff::FlipAndSetDataValid,
    };
}

constexpr hal::unpack::DataTransfer unpack_srca = face_unpack(hal::unpack::Engine::Unpacker0);
constexpr hal::unpack::DataTransfer unpack_srcb = face_unpack(hal::unpack::Engine::Unpacker1);

constexpr hal::mop::MopConfig<hal::mop::MopTemplate::Template1> unpack_faces{
    .outer_loop = {
        .count = 2, // Two face rows.
    },
    .inner_loop = {
        .count = 2, // Two A/B face pairs per row.
        .body_op        = hal::unpack::get_operation<unpack_srca>(),
        .alternating_op = hal::unpack::get_operation<unpack_srcb>(),
    },
};

void unpack_tile()
{
    hal::mop::program<unpack_faces>();
    hal::mop::Runner<hal::mop::MopTemplate::Template1>::run();
}

Each logical inner iteration emits the unpack_srca operation followed by the unpack_srcb operation. The two outer iterations and two configured inner iterations therefore unpack four paired faces. The last fields are omitted because the normal final operation is already unpack_srcb.

Configuration fields hold encoded instructions

hal::unpack::get_operation() returns a 32-bit instruction word without issuing it. program() stores that word in the MOP configuration; the unpack operations are issued only when run() expands the template. Any encoded operation works in a MOP field — hal::replay::get_operation() and raw TT_OP_* words follow the same pattern.

Template 0

Mask-selected loop

The configuration describes the normal and shadow sequences. The runner supplies the iteration count and selector mask.

Template 1

Nested loop

The configuration owns both loop counts and all loop operations. The runner may use those counts or override either count for one Blackhole expansion.

Template 1 fields and expansion

Template 1 groups fields by where they execute: outer_loop holds the count and operations surrounding the inner loop, while inner_loop holds the count and operations occupying inner-loop positions. Both count fields accept 32-bit values, and the Blackhole functional model consumes the low ten bits. Every instruction field is optional, so callers describe only positions that differ from the defaults.

How the fields expand

The pseudocode below uses the HAL field names after omitted fields have been resolved according to the table above. 

effective_outer_count = outer_loop.count & 1023
effective_inner_count = inner_loop.count & 1023

if MOP outer override is nonzero:
    effective_outer_count = MOP outer override
if MOP inner override is nonzero:
    effective_inner_count = MOP inner override

if inner_loop.alternating_op is NOP:
    alternating_delta = 0
else:
    alternating_delta = inner_loop.body_op XOR inner_loop.alternating_op
    effective_inner_count *= 2

if outer_loop.start_op is NOP and effective_inner_count == 0 and
   outer_loop.end_op is not NOP:
    reject configuration              // Weak-confidence hardware anomaly.

current_inner_op = inner_loop.body_op
repeat effective_outer_count times as outer index:
    emit outer_loop.start_op unless it is NOP

    repeat effective_inner_count times as inner index:
        if inner index is not the final inner iteration:
            emit current_inner_op
        else if outer index is not the final outer iteration:
            emit inner_loop.last_op_on_nonfinal_outer_iteration
        else:
            emit inner_loop.last_op_on_final_outer_iteration
        current_inner_op ^= alternating_delta

    if outer_loop.end_op is not NOP:
        emit outer_loop.end_op
        emit outer_loop.second_end_op unless it is NOP

Alternating mode

A non-NOP inner_loop.alternating_op (ISA LoopOp1) doubles the effective inner count and alternates inner_loop.body_op, inner_loop.alternating_op. For configured inner_loop.count == 3, one outer iteration contains six positions: 

inner_loop.body_op,
inner_loop.alternating_op,
inner_loop.body_op,
inner_loop.alternating_op,
inner_loop.body_op,
final-position override

Plain NOP has position-specific behavior

Only the opcode is checked. DMANOP and SFPNOP are not plain NOP and remain ordinary instructions.

  • Plain-NOP outer_loop.start_op, outer_loop.end_op, and outer_loop.second_end_op are suppressed.
  • Plain-NOP inner_loop.alternating_op disables alternating mode.
  • Plain-NOP inner_loop.body_op and either last-position override are emitted when their positions are reached.

Template 0 fields and expansion

Template 0 is a counted loop with two configured paths. The runner supplies a 32-bit selector mask. Each iteration consumes one mask bit, starting at bit 0.

Configuration shape

MopConfig<Template0> {
    required {
        start_op;
        start_op_shadow;
    }

    optional_group mid_ops {         // Supply all three or none.
        op_a;
        op_b;
        op_c;
    }

    optional_group end_ops {         // Supply both or neither.
        end_op;
        end_op_shadow;
    }
}

start_op begins the mask-zero path and start_op_shadow begins the mask-one path. The optional mid_ops group runs only on the mask-zero path. The end_op and end_op_shadow pair closes the corresponding path. The HAL derives the hardware enable flags from group presence, so callers never set HasA123 or HasB directly.

How one iteration expands

repeat count times as iteration:
    if mask bit iteration is 0:
        emit start_op
        if mid_ops is supplied:
            emit mid_ops.op_a
            emit mid_ops.op_b
            emit mid_ops.op_c
        if end_op is supplied:
            emit end_op
    else:
        emit start_op_shadow
        if end_op_shadow is supplied:
            emit end_op_shadow

The normal and shadow end fields are one optional pair, so end_op and end_op_shadow are either both supplied or both omitted.

0Middle groupstart_op, op_a, op_b, op_c
0End groupstart_op, end_op
0Middle and end groupsstart_op, op_a, op_b, op_c, end_op

Count and mask encoding

The public runner count is the number of iterations, valid from 1 through 128. Hardware stores Count - 1 in the seven-bit MOP count field. Mask bits 0–15 are encoded in the MOP instruction; bits 16–31 live in persistent per-thread MaskHi state set by MOP_CFG.

Upper-mask handling is automatic

The fully compile-time runner emits MOP_CFG when the mask uses upper bits or the count can consume them. Runtime-bearing overloads program the upper half unconditionally, which also clears stale upper-mask state when the value is zero.

Configure and run

Both templates follow the same three-stage lifecycle.

  1. Describe the sequence.Create a MopConfig<Template0> or MopConfig<Template1> aggregate.
  2. Program the current thread.Call program<config>(), pass tagged runtime counts to program<config>(...), or pass a runtime aggregate for either template to program(config). Programming waits for a preceding MOP expansion before replacing the write-only configuration.
  3. Issue the expansion.Call the Runner specialization for the same template. The programmed configuration remains available for later runs until it is replaced.
Configuration and execution are separate

program() writes the expander state but does not execute it. Runner::run() executes the state already programmed on the current T0, T1, or T2 thread.

Use tagged runtime_field arguments when either or both loop counts are dynamic; operation placement and default resolution remain at compile time. Runtime fields must be unique. Use the runtime Template 1 aggregate when instruction fields are dynamic. 

// Mixed path: compile-time configuration, runtime counts
hal::mop::program<mop_config>(
    hal::mop::runtime_field<
        hal::mop::Template1Field::OuterLoopCount>(outer),
    hal::mop::runtime_field<
        hal::mop::Template1Field::InnerLoopCount>(inner));

Patch one configured field

Use write() when a complete Template 1 configuration is already programmed and only one count or operation changes. The field selector identifies one of MopCfg[0..8] at compile time; the value may be compile-time or runtime. A constant value folds into the same code as a dedicated compile-time overload, so one interface covers both cases. Each call waits for the preceding expansion and performs exactly one configuration-word store.

Template 0 also permits patching an instruction slot selected by Template0Field. Its middle and end enable flags are deliberately not writable through this interface: patch only a slot already enabled by the complete configuration, and call program(config) to change group presence. 

// Mixed path: compile-time field, runtime value
hal::mop::write<
    hal::mop::Template1Field::OuterLoopCount>(num_tiles);

// Compile-time value folded at the call site
hal::mop::write<
    hal::mop::Template1Field::LastOpOnFinalOuterIteration>(final_pacr);

// Running is unchanged.
hal::mop::Runner<hal::mop::MopTemplate::Template1>::run();
Patch only known programmed state

A field write does not resolve omitted operations or validate the complete Template 1 anomaly shape because MopCfg is write-only. Program a complete valid configuration first, then preserve its invariants when patching one field.

Constraints and safety

RuleReason and diagnostic
Template 0 public count must be 1–128.The runner encodes Count - 1 in a seven-bit field. Compile-time forms use static_assert; runtime-count forms use LLK_ASSERT.
Template 0 middle operations are all-or-none.One hardware flag enables all three slots. A partial group is rejected with static_assert.
Template 0 end operations are paired.The same flag enables the normal and shadow end slots. An unpaired group is rejected with static_assert.
Template 1 count fields accept 32-bit values.The HAL writes each value unchanged to MopCfg. Blackhole uses count & 1023 as the effective loop count.
Template 1 instruction overrides are ten-bit values.Zero preserves the corresponding MopCfg count; values 1–1023 replace it for one expansion. The ISA marks this capability as requiring hardware validation.
Do not program while an earlier expansion is active.program() calls mop_sync() before writing the new configuration.
Patch only known, fully programmed state.write() synchronizes and replaces exactly one write-only MopCfg entry; it cannot inspect or validate the other entries.
Program and run on the intended thread.Each T0, T1, and T2 thread owns independent write-only MopCfg and MaskHi state.
Template 1 unsupported anomaly shape

The HAL conservatively rejects a plain-NOP outer_loop.start_op, effective (inner_loop.count & 1023) == 0, and non-NOP outer_loop.end_op. The current ISA describes different unexpected outer-count increments depending on EndOp1 and marks the behavior weak-confidence, so the entire shape is excluded.

Runtime assertions depend on the LLK assertion build

LLK_ASSERT produces the configured runtime assertion behavior when LLK assertions are enabled. Keep runtime inputs valid in every build; release configurations may type-check assertions without executing them.

Why Template 1 writes all nine entries

The configuration registers are write-only and persistent. Optional fields reduce caller input, but the HAL still writes every resolved entry so values from an earlier configuration cannot leak into a later expansion.

The nested aggregates make operation placement visible at the call site. Counts are 32-bit configuration values whose low ten bits determine the effective loop counts. Every instruction field distinguishes omission from an explicitly supplied 32-bit instruction and is resolved according to the Template 1 model. Callers assign an encoded instruction directly or omit the field; they do not need to construct the detail type explicitly.

Examples

Unpack one broadcast value, then all SrcA faces

For scalar broadcast, the unpacker needs the single SrcB value once, followed by every SrcA face. Put the SrcB unpack in outer_loop.start_op and repeat the SrcA unpack in the inner loop. The example reuses the hal::unpack descriptors from the quick start. 

// Compile-time path
constexpr hal::mop::MopConfig<hal::mop::MopTemplate::Template1> unpack_scalar_b{
    .outer_loop = {
        .count = 1,
        .start_op = hal::unpack::get_operation<unpack_srcb>(),
    },
    .inner_loop = {
        .count = 4,
        .body_op = hal::unpack::get_operation<unpack_srca>(),
    },
};

void unpack_scalar_b_tile()
{
    hal::mop::program<unpack_scalar_b>();
    hal::mop::Runner<hal::mop::MopTemplate::Template1>::run();
}

The expansion is unpack_srcb once, then unpack_srca four times. No explicit NOP or last-operation fields are needed.

Pack runtime-selected rows and close the final row

To pack row-major data, each normal PACR advances Y with ADDR_MOD_0. The final PACR instead uses ADDR_MOD_1 and sets Last=1 to close the block and reset Y. The row count may be known only at runtime. Pack operations do not have a HAL encoder yet, so this example builds the PACR words with raw TT_OP_PACR. 

constexpr std::uint32_t pack_row = TT_OP_PACR(
    ckernel::p_pacr::CFG_CTXT_0,
    ckernel::p_pacr::NO_ROW_PAD_ZERO,
    ckernel::p_pacr::DST_ACCESS_NORMAL_MODE,
    ckernel::ADDR_MOD_0,
    ckernel::p_pacr::ADDR_CNT_CTXT_0,
    ckernel::p_pacr::P_ZERO_OUTPUT_DISABLED,
    ckernel::p_pacr::SINGLE_INTF_ACTIVE,
    0, 0, ckernel::p_pacr::NO_CTXT_CTRL, 0,
    0); // Last = 0.

constexpr std::uint32_t pack_last_row = TT_OP_PACR(
    ckernel::p_pacr::CFG_CTXT_0,
    ckernel::p_pacr::NO_ROW_PAD_ZERO,
    ckernel::p_pacr::DST_ACCESS_NORMAL_MODE,
    ckernel::ADDR_MOD_1,
    ckernel::p_pacr::ADDR_CNT_CTXT_0,
    ckernel::p_pacr::P_ZERO_OUTPUT_DISABLED,
    ckernel::p_pacr::SINGLE_INTF_ACTIVE,
    0, 0, ckernel::p_pacr::NO_CTXT_CTRL, 0,
    1); // Last = 1.

void pack_rows_to_l1(const std::uint32_t num_rows)
{
    LLK_ASSERT(num_rows >= 1 && num_rows <= 64, "num_rows must be between 1 and 64");

    constexpr hal::mop::MopConfig<hal::mop::MopTemplate::Template1> pack_rows{
        .outer_loop = {
            .count = 1,
        },
        .inner_loop = {
            .count = 0,
            .body_op = pack_row,
            .last_op_on_final_outer_iteration = pack_last_row,
        },
    };

    // Mixed path: compile-time configuration, runtime inner count
    hal::mop::program<pack_rows>(
        hal::mop::runtime_field<
            hal::mop::Template1Field::InnerLoopCount>(num_rows));
    hal::mop::Runner<hal::mop::MopTemplate::Template1>::run();
}

Because there is one outer iteration, only last_op_on_final_outer_iteration is needed. The first num_rows - 1 positions use pack_row; the final position uses pack_last_row.

Select the unpack replay sequence for the active configuration context

Suppose the unpacker replay buffer contains one row-unpack sequence for configuration context 0 and an equivalent sequence for context 1. Template 0 can select the matching replay instruction on every row. 

// Compile-time configuration
constexpr std::uint32_t replay_half_len = 3;
constexpr hal::replay::BufferRange context0_rows{.start = 0, .count = replay_half_len};
constexpr hal::replay::BufferRange context1_rows{.start = replay_half_len, .count = replay_half_len};

constexpr hal::mop::MopConfig<hal::mop::MopTemplate::Template0> unpack_rows{
    .start_op        = hal::replay::get_operation<context0_rows>(),
    .start_op_shadow = hal::replay::get_operation<context1_rows>(),
};

void unpack_face_rows(
    const std::uint32_t face_r_dim,
    const std::uint32_t active_context)
{
    hal::mop::program<unpack_rows>();

    // Runtime count and mask path; the runner takes the iteration
    // count directly (one MOP iteration per face row).
    const std::uint32_t context_mask = active_context == 0 ? 0 : 0xffff;
    hal::mop::Runner<hal::mop::MopTemplate::Template0>::run(
        face_r_dim,
        context_mask);
}

A zero mask bit replays the context-0 sequence; a one bit replays the context-1 sequence. The runtime runner applies the same choice to each requested row and clears any stale upper-mask state.
