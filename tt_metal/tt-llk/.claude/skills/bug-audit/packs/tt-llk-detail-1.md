# tt-llk (tt_metal/tt-llk and the LLK-facing parts of tt-metal) — bug-audit knowledge pack

Mined 2026-09-26 from the tt-llk repo (217 fix cases) and the LLK-touching part of tt-metal (605 cases), 478 code bugs in all; 283 deep-read, and 159 review-caught defects. The recall-benchmark holdout (tt-llk-holdout.jsonl, tt-metal-holdout.jsonl) was excluded from every step. Class weights are approximate: a post-mortem of benchmark picks found about 12% of triage "code bugs" were not defects (cleanups, lint fixes, feature enablement), so read the table as an ordering, not exact shares.

Full per-class material for `tt-llk.md`. **Candidate sites** are places where earlier analysis suspected an unfixed copy of a fixed bug. They are leads to verify, never findings to report as-is. Line numbers drift, so re-find each site by its code before trusting it.


## `numeric-edge`: SFPU special values: signed zero, NaN, INT_MIN, poles

SFPU float compares look at the raw bits. They are not IEEE compares: '== 0' means all bits are zero and '< 0' / '>= 0' test only the sign bit. So -0.0 is treated as nonzero and negative, and a NaN is ordered by its sign bit. Any predicate, range classifier (overflow/normal/underflow by a derived exponent), clamp or complemented compare (ge written as !lt) therefore sends -0 and ±NaN down the wrong branch, and often into an arm that writes a literal 0, 1, -1 or inf. The comparator does min/max/swap in sign-magnitude, but integer data is two's-complement. INT32_MIN has no sign-magnitude form (it becomes -0 or overflows when negated), a pair of negative values orders in reverse, and UInt32 values at or above 2^31 read as negative. Host-side identities such as min = -max(-x) overflow in the same way. Hand-built arithmetic (exponent bias minus exponent, a magic seed plus Newton-Raphson, exponent/mantissa shifts for float-to-int, a subtract followed by a zero test for equality) is usually guarded at only one end of the range. It then breaks at the other end: 1/0 comes out finite, inf*0 or inf-inf gives NaN, zero or subnormal values convert to nonzero integers. Non-finite results in padded lanes can also corrupt real data that shares a block-float exponent. Fixes usually land on one op, one arch or one entry path, so sibling copies keep the defect.

**Checks**

- For every float predicate against zero or a scalar in SFPU code (==0, !=0, <0, >=0, >0, <=0) and every helper that wraps one, compare the result for +0, -0, +NaN, -NaN, +inf and -inf with the torch/IEEE truth table. Ordered compares with NaN must be false, != must be true, and ±0 must compare equal. Flag ge/le written as the complement of lt/gt, and any test that looks only at the sign bit or at an all-zero bit pattern.
- In range-classifying kernels (exp, pow, other transcendentals) that pick an overflow, normal or underflow arm from a derived integer or a clamped value, send ±NaN through on each arch. Flag any arm that writes a literal constant without first excluding NaN. A NaN's sign bit steers integer and sign-magnitude compares, clamp and min/max.
- Wherever an integer is ordered by SFPSWAP or a float compare, or is converted from two's-complement to sign-magnitude (the INT32_2S_COMP load mode, or a manual 'sign | -x'), test INT32_MIN (it becomes -0 and ties with 0), pairs of negative values (the order reverses) and UInt32 values at or above 2^31 (they read as negative). Flag host code that computes min as -max(-x), and abs or negation of INT_MIN in any width, including in test helpers.
- For arithmetic-built reciprocal, rsqrt, sqrt or divide (bias minus exponent, setexp/exexp, a magic seed plus NR), evaluate both ends of the exponent range: ±0 and denormals must give ±inf, ±inf must give ±0/inf, and NaN must propagate. Trace each NR step for inf*0, inf-inf and denormal flush-to-zero. Require that non-finite lanes are excluded with a bit-level exponent test or is_finite, not a float compare such as 'val != 0'.
- For float-to-integer conversion built from an exponent extract, an implicit-one mantissa and a shift, check that lanes with a negative unbiased exponent (zero, subnormal, |x|<1) are forced to 0, and that NaN, Inf and overflow exponents saturate. Diff each variant (uint8/uint16/int32/uint32, each arch) against its siblings. A guard present in one copy and missing in another is the defect.
- When a numeric-edge fix lands, diff the same routine across the WH, BH and Quasar metal llk_api copies and the tt-llk-tier copies, and across every entry path to the op (tensor-tensor, scalar-first, mixed-dtype FPU fallback, fused unary chain). Fixes routinely cover only one of these.
- Equality or ordering implemented as a subtract followed by a zero or sign test (eqz/gez/lez of sub) is wrong at inf-inf, NaN, ±0 and opposite-sign max magnitudes (the difference overflows). Find every dispatch branch that still lowers this way.
- For elementwise ops that can output block-float (bfp8/bfp4), compute f(pad value), usually f(0). If it is ±inf, NaN or very large, it shares a block exponent with real data on unaligned shapes. A test that picks a special pad_value or narrows the input range is a workaround, not a fix.
- Special-value tests must drive raw bit patterns (0x80000000, 0xFFC00000, 0x7F800000, INT32_MIN/MAX) and read back raw fp32 bits. float('nan') is positive, and bf16 narrowing hides the difference between NaN and inf.
- Check that SFPU constants are loaded at LReg fp32 precision, not as a 16-bit immediate, and that decoders handle subnormals (exp==0 means 1-bias). Also check that a mantissa round-up on an all-ones mantissa carries into the exponent instead of wrapping.

**How fixes for this class went incomplete**

- Fixes are piecemeal per op. Sign and heaviside got signed-zero fixes, and sqrt, rsqrt and log were fixed later one at a time, but the shared zero helper and the sibling predicates (eqz, nez, ltz, gez, logical_not, mask) were never swept. Grep the helper and every sibling predicate when fixing one.
- Fixes stop at the arch boundary. The WH/BH fixes for exp -NaN, sqrt_custom +inf and rsqrt signed zero were not ported to Quasar, which ships the pre-fix form (sometimes with the divergence documented in a comment). Always diff all arch copies.
- Fixes stop at the entry-path boundary. The tensor-tensor eq/ge/le were rewritten with NaN/±0 handling, while the scalar-first path and the mixed-dtype FPU fallback still use subtract then zero test. The scalar unary_comp kernels were never touched.
- A fix that swaps one float compare for another only moves the failure. signbit went from '<= -0.0f' to '< 0.0f', which fixed +0 and broke -0. The durable fix was a bit-level test (shift out the sign).
- Test-only workarounds hide a live defect. Padding with 1.0 for bfp8 log, narrowing input ranges, and xfails that pad sentinels mask all leave the default-padding user path broken. A fix commit that touches only tests is a workaround.
- A fix that relies on an arch-specific NaN encoding (for example BH canonical +NaN) works by accident. An SFPI rewrite of the BH comparison kernels caused regressions and was partially reverted. Verify the fix on silicon per arch, not only in simulation.

## `tt-init-uninit`: Init/uninit and reconfig pairs leave stale state

Hardware state persists across ops in a kernel and across programs on a core. Examples: ALU and unpacker format fields, tile-descriptor X/Y/Z dims, strides, x-end counters, packer counters and L1 offsets, sticky mode bits (transpose/haloize, the source zero-substitution flag, pack/tilize mode, the Dest remap), SFPU programmable constants and the SFPCONFIG control word, and the Src dvalid/bank pointers. Bugs arise when no code clearly owns a field, in four ways. (1) An init or short-init/reconfig programs fewer fields than the full configure does. Often the default compile-time branch is empty, or an "only-if-changed" check keys on too few properties, so the op inherits whatever the previous op left. (2) An uninit is not the exact inverse of its init. It writes hard-coded full-tile constants (16x16 face, 4 faces, y=1), recomputes values from defaulted parameters, ignores the snapshot its init took, or writes registers its init never touched. That last case silently repairs some other op's leak until someone removes it. (3) An op's own init does not load what its body needs. Examples: SFPU helper constants (the Newton reciprocal seed) that are loaded only under a template condition different from the one the body uses, or that a same-named init loads on one architecture but not another. Another is an experimental or custom variant that skips a reset its canonical counterpart makes. (4) The init programs a different unit or shape than the one execute uses. The init's predicate differs from the MOP builder's, block dims or CB ids are not forwarded, or the init runs after Dest has already been written.

**Checks**

- For every init/uninit pair, per architecture, diff the set of registers and fields each one writes. They must be equal. Each restored value must come from the operand's own metadata (face_r_dim, num_faces, format) or from a snapshot the init took. Flag an uninit that writes a hard-coded 16x16 / 4-face / y=1 value, one that ignores a saved scratch register, one that writes a register its init never touches (an accidental repair hiding another op's leak), and one that takes a geometry parameter with a default value.
- For every short-init or reconfig entry point, list every field the matching full hw_configure derives from each input (format, datum size, face_r_dim, num_faces, tile size). Confirm that every compile-time branch, including the default template path and the non-int8 path, rewrites each of those fields, and writes it to the correct operand's address, mask and shift (for example, SrcB data must not go to the SrcA address). An empty else branch is a finding.
- For every conditional 'reconfigure only if changed' wrapper, the skip decision must be the OR of every property the skipped work consumes. Flag an if/else-if chain where an earlier, narrower branch (for example, on a format change) hides a later branch (for example, a geometry change) when both change together. Flag skip keys that compare only the destination format.
- For each sticky global mode (the src zero-substitution flag, transpose/haloize, tilize/pack mode, Dest remap, SFPCONFIG control, implied-format or Fp32 mode), list the inits that set it to a non-default value. Then confirm that every other init that can follow in the same kernel explicitly re-establishes the value it needs, including *_init_short paths that skip hw_configure and experimental/custom LLKs. Diff each experimental init against its canonical counterpart for missing reset or assert calls.
- For every SFPU op, list the programmable constants, LUT LREGs and replay slots read by its body and by every helper it inlines (reciprocal, log, exp). Confirm that the op's own init writes each one under the same template condition the body uses to choose the helper path. Diff the helper init per architecture: an init that is a no-op for APPROX=true on one architecture breaks callers whose body always iterates. Also confirm that the compute-API *_tile_init actually calls the op init and does not stop at the generic unary init.
- For every init that programs 'the unit or loop the MOP will use', confirm it uses the same predicate and parameters as the MOP builder and execute path (unpack_to_dest AND 32-bit input; ct/rt/kt; transpose; CB ids). Check that each shaping parameter reaches every thread's init (unpack, math, pack) on every architecture, and flag hard-coded or defaulted CB ids and dims.
- For inits that change math-side Dest mapping (remap/swizzle) or other state that data already in Dest depends on, check that the call happens before tile_regs_acquire and before the first Dest write of the section, not between the math op and the commit.
- For init/uninit pairs that write global mode bits by RISC MMIO, confirm that the set and the clear come from the same thread and are ordered relative to the dependent work. Flag an empty uninit (commented 'nothing to restore') next to an init that writes anything outside the MOP.
- For Src dvalid publication and clearing: in every path, including unpack-to-dest paths where SrcA is unused, each Src register must be published and cleared the same number of times per tile. Nothing resets bank pointers at kernel start, so an imbalance leaks into later programs.
- When a shared default changes (for example, a packer counter's neutral value) or state ownership moves out of configure/reconfig, search the whole tree for code that relied on the old default without setting it, including model and custom kernels that emit raw instructions. To test, run op A and then an unrelated op B without a device reset, with varied shapes, including tiny tiles and num_faces of 1 or 2.

**How fixes for this class went incomplete**

- Hard-coded full-tile restores in an uninit (z=4 faces, y=1, 16x16) fixed the reported sequence by accident and broke operands with other num_faces. Parametrizing the value then got reverted because other ops had been relying on the accidental repair. The correct fix is that the uninit restores only what its init wrote, from operand metadata, and the op that actually leaks gets fixed.
- Fixes were often made opt-in (an IGNORE default template) or limited to one branch (the 32-bit path only, or the int8 path only), so the common default path stayed broken. Check that the default instantiation receives the fix.
- Fixes applied to canonical LLKs rarely reached the experimental/custom copies or the sibling architecture. A per-op fix (restoring the zero flag in one init) leaves dozens of look-alike inits broken, so sweep every file that issues the same instruction family.
- Restoring a flag to a hard-coded 0 instead of the prior or policy value clobbers the caller's configuration. Later fixes replaced ad-hoc save/restore with a tracked setter plus per-init re-establishment of the default. Raw writes that bypass the tracker must invalidate its cache.
- Moving a register write out of init and into configure/reconfig (or changing a shared default) missed consumers that reach the op through a skipped same-format reconfig, and model kernels that relied on the old default. The follow-ups were a workaround in the compute-API or model layer that stayed in place after the LLK fix, and an LLK_ASSERT guard that is compiled out in production.
- Reverts of an init/format fix were sometimes triggered by an unrelated hang that the fix exposed. When relanding, diff the relanded code against the original and the current file so that no branch's writes are lost.

## `tt-arch-divergence`: Code copied across arches, not re-derived

Code is copied from one arch (usually WH to BH, or WH/BH to Quasar) and keeps the source arch's assumptions, while the target arch differs. The differences seen so far: which config word a field lives in, how thread and mailbox slots are numbered, what an instruction's operand means under a new mode register (for example ZEROACC choosing the Dest bank itself and treating the index as bank-relative), which implicit registers an instruction reads (LUT tables), how much a clear or move covers, which config-write instructions have errata on that arch (REG2FLOP on BH, dummy UNPACR side effects, lo16 Dest<->Src moves while fp32 ALU mode or a Tf32 SrcA format is set), and whether a "blocking" sync primitive really blocks the CPU or only posts a Tensix wait. Other bugs come from a step done in different places on different arches (row transpose in math on one arch, in the unpacker on another), so the init on one arch never programs the required state. Per-arch wrappers and ports also drift apart: they drop parameters or silently ignore them, leave out a dst-format argument, miss headers, keep single-arch allowlists in host code, or keep hand-copied instruction sequences that go stale. The results are usually silent wrong output: zeroed datums, the wrong face cleared, the wrong axis reduced, or INT32_MIN dropped. Sometimes the result is a hang or a fault, and these are often nondeterministic or hidden by an arch skip in the tests.

**Checks**

- For every instruction whose operand meaning depends on a mode register or arch semantics (ZEROACC addressing/bank auto-detect, CLR_16 coverage, fp32 flag, Dest<->Src hi/lo16 move width), derive the region it actually touches on THIS arch. Check three things: every caller encodes the index in that mode's units without adding the bank base twice; the maximum of (current Dest row offset + index) cannot cross a bank or half-Dest boundary at the largest tile count; and every kernel entry path programs the mode before the first use.
- Diff each per-arch copy of a function (WH vs BH vs Quasar), and each per-arch llk_api wrapper against the shared compute-API call site. Any argument one arch forwards to _llk_*_init_ and another omits (formats, face counts, dst_format) is a finding. So is any template or function parameter an arch accepts but ignores without a static_assert pinning it to its default. So is a guard or fix present on one arch copy and missing from the other.
- For every hi/lo16 (DEST_32B_LOW) Dest<->Src move, or any move while Dest is 32-bit, check which ALU control bits and SrcA format that arch requires during the move (on BH: Fp32_enabled cleared and SrcA not Tf32). Confirm they are set before the moves and restored after, including in replayed or runtime variants. Confirm the tests feed values whose lo16 half is non-zero, or a zeroing bug stays invisible.
- For each masked config-register RMW that ORs several field masks or computes its address as base+N, look up every field's word address in THIS arch's generated register map. They must all equal the word the call writes, and a compile-time assertion should say so.
- When a per-arch header enumerates hardware threads, slots, engines or counts (ThreadId, mailbox indices, unpacker/packer instances, thread counts used in host layouts), compare each value to the target arch's own map, not to the arch it was copied from. Check that no caller can index its own slot. Check that the caller runs on a core type that can reach the aperture through that API (a DM core using a TRISC-relative mailbox is a red flag). Check that host and device compute the layout from the same per-arch constant.
- For each blocking-sounding sync API (wait_front, reserve_back) on each arch, decide whether it blocks the CPU or only posts a wait into the Tensix instruction stream. If it only posts one, any CPU-side load, store or address hand-off into the guarded buffer after the call is a race.
- For each op, list the hardware state its math stage depends on (unpacker transpose/haloize, x_end, tile dims, formats). Check that every init variant (full, _short, _delta, uninit/restore) writes each field on every arch, especially where one arch does a step in math and another in the unpacker. Check that restores write the operand-derived baseline rather than a fixed constant.
- Check every config-write instruction and hardware workaround in ported code against the target arch's errata and semantics: REG2FLOP on BH (use STALLWAIT THCON + WRCFG), dummy UNPACR not side-effect-free on BH, cycle-wait primitives that do not work on WH, and the sign-magnitude compare in SFPSWAP (test INT32_MIN, -1, 0, INT32_MAX and mixed signs; watch for host lowerings like min=-max(-x)).
- When a kernel or intrinsic is shared or ported, list the registers and config it reads implicitly (LUT table LRegs, constant LRegs, ADDR_MOD slot increments, SFPU multi-cycle latency, replay NOP requirements) and confirm each against the target arch. Flag an init that loads registers the target arch never reads, and any use of a 'programmable constant' that aliases a table word on that arch.
- When a guard is weakened or an arch is skipped in tests to unblock a port, treat the range it now admits as a candidate bug. Evaluate stride formulas built from num_faces at 1, 2 and 4 against the physical face-column count, and flag per-arch ops with no test coverage on that arch.

## `tt-format-resolution`: Format-derived hardware modes resolved wrongly or stale

A hardware mode bit or operand whose correct value depends on the data format and the Dest width (32-bit Dest mode in ZEROACC, packer Dest-read width/int8/unsigned bits, SrcA ALU format for hi/lo16 Dest<->Src moves, the src zero-flag denormal flush, ELWADD vs MOVA2D datapath, the SFPU load/store layout) is left as a literal, derived from only one axis, or set once at configure and never recomputed on reconfig/short-init. Formats get collapsed onto a shared mode or a truncated field, and the code then infers semantics from that collapsed value: UInt32 and Int32 share the INT32 load mode, so signedness is lost; 4-bit masked enums alias (UInt32 vs Int32, UInt8 vs Int8, Fp8 vs Lf8); one family member is special-cased and its sibling is not (UInt8 handled, Int8 not). Workaround writes to shared format registers leak because nothing restores them in uninit, or because a later raw write gets around a software state cache. Also, a masked RMW drops a field that the code computes. At the host and API tier, integer dtypes are sent to float kernels or to signed kernels, scalars pass through float bits, the reconfig 'old' operand does not match the format actually programmed, and 32-bit unpack-to-dest silently skips Src-side transforms (haloize, face transpose).

**Checks**

- For every instruction operand or config bit that encodes Dest width or row layout (ZEROACC use_32_bit_mode, tiles-per-bank/face-index math, packer Read_32b_data/Read_int8), confirm the value comes from the fp32-Dest template flag or a predicate covering every 32-bit format (Float32/Int32/UInt32). A literal is acceptable only if the function cannot run with 32-bit Dest and has an assert or no fp32 parameter by design. Check that the flag is actually plumbed into the enclosing init.
- For every multi-field config word written by a masked RMW, diff the fields assigned in the value union/struct against the field MASKs passed. A computed field missing from the mask is silently dropped. Also check that the full configure path and the incremental reconfig path program the same field set, and that the adjacent 'fields share one word' static_asserts list every field.
- For any mode bit that depends on format (zero-flag flush, int8 math enable, packer int8/unsigned, Round_10b_mant), check that EVERY format-changing path recomputes it from the NEW format: hw_configure, each reconfig overload, each short init that takes a data type, and mid-kernel fp32-Dest toggles. Where a software cache or state tracker shadows the register, grep all raw writes to that register and require each one to update or invalidate the cache.
- Whenever code branches on a load/store mode, instruction modifier, register width or masked enum to decide a data property (signedness, int vs float, element width), list every DataFormat that maps to that value. If two formats with different semantics collapse onto it, the branch must take the format itself. Test the unsigned formats at bit 31.
- For every masked or truncated enum comparison, check both directions: a truncated read-back compared with an untruncated expected value falsely fails, and a masked equality against one enum value aliases every enum sharing its low bits. - For every init that overrides a shared format register as a workaround (SrcA ALU format, SrcA_val, Haloize, Read_32b_data), find the matching uninit and confirm it restores the value configure would compute, with ALL of configure's terms (for example is_32b_format as well as fp32_dest). Also check whether any reconfig legal between init and execute would undo the workaround.
- For Dest<->Src moves, especially the 32-bit hi/lo variants on WH, determine which format register controls the conversion (possibly another operand's). The op's own init must program it rather than inherit it. 'The output changes with the arguments of an unrelated earlier init' is the signature.
- For ops relying on unpacker-side transforms (within-face/face transpose, broadcast, tilize), list which formats take unpack-to-dest. Each 32-bit format needs an alternate path or a hard assert, and init and per-tile execute must choose the path with the same shared predicate (src AND dst 32-bit).

Flag UINT32 routed to signed ordered-compare/min/max, scalars bit-cast from float into integer kernels, and integer ops that use the default Dest load mode or emulate two's-complement with setsgn, 0x7FFFFFFF masks or +/-1 fixups.

Harnesses that clamp inputs below 2^31 or generate sign-magnitude data hide this class.

## `numeric-formula`: SFPU approximations drift from their math and each other

The SFPU transcendental and activation kernels are hand-built approximations: range reduction, polynomial or rational fits, lookup tables, and Newton iterations. They break in a few ways that keep coming back.
(1) The formula is wrong at the points that matter: cancellation where two terms nearly cancel (k*ln2 + poly(m) just below 1, 1+erf or 1-tanh^2 when the function saturates, v - q*s once the fp32 ULP is larger than the modulus), a fit used outside its fitted interval, a half-range helper given the signed x instead of |x|, or a region boundary or saturation constant that was derived for bf16 but is also used with fp32 Dest.
(2) Constants are wrong: fp16-rounded ln2 in fp32 paths, coefficients that do not match their own derivation, or guards that can never fire (a truncated quotient compared with the value it came from).
(3) An init does not match its body. Consumers hand-copy a helper's programmable constants, overwrite the constant registers the helper's own init just set, or key the init on a flag (approx, fp32) that the compute path does not use.
(4) Fixes land in one copy and the others keep the old code: the no-init variant, the fused or binary variant, the other arch, or another consumer of the same hardware source (the PRNG lane correlation fix went into rand_tile but not into dropout).

**Checks**

- Find every SFPU helper that reads programmable constant registers (reciprocal, log, exp, sqrt). Check that each consumer's *_init calls the helper's own init, with the same approx/fp32 template args the compute path uses. Check that no init writes literal vConstFloatPrgm*/vConstIntPrgm* values the helper owns, or writes them AFTER the helper's init (a clobber). Do this for EACH arch, because the register set a helper uses differs between arches.
- Recompute every hard-coded coefficient and math constant from its own comment or derivation and from the true float32 value. Flag values rounded to fp16 or bf16 (ln2 = 0.692871) in paths that produce fp32 results. Then grep for every other copy of the literal: no-init bodies, binary/fused ops, other arches.
- Evaluate each approximation at its cancellation and anchor points, not just on random [-1,1] inputs. Check log near 1, 1 +/- f(x) where f saturates to +/-1, value and slope at 0, tails and asymptotes, and modulo at magnitudes where the fp32 ULP is larger than the divisor. Where fp32 Dest is supported, require an exhaustive bf16 ULP sweep plus fp32 samples.
- For kernels templated on is_fp32_dest_acc_en, check that saturation thresholds and 'result = const' regions were derived for the precision actually in use. A kernel that uses the flag only to skip the final bf16 rounding, while keeping bf16-derived boundaries, is a finding.
- Compare each LUT, rational, or polynomial fit's stated interval with the op's documented domain. Every region outside the fit needs a clamp, an asymptotic branch, or a special-value path. Half-range helpers extended by symmetry must receive |x| on the negative branch, with a reflection formula that matches the symmetry (odd: -f; erfc-like: 2-f).
- In range-reduction and modulo loops, check three things: each correction step moves the value TOWARD the target interval (v - s, not s - v); a loop placed after a sign fix-up handles both signs; and each overshoot guard can actually evaluate true.
- For piecewise kernels that start with 'result = 0' and are gated only by range compares, check the NaN and +/-inf behaviour. Note that A*|x|+B with A=0 still gives NaN at infinity.
- For every hardware PRNG consumer, check four things. Are lanes or streams mixed before their bits are used? Is the lock-up seed guarded? Does each core get a distinct, non-adjacent seed or stream id? Does the caller's scale computation match the primitive's half-open or inclusive range contract?
- When a fix touches one of several near-copies (fmod/remainder, unary/binary, init/no-init, WH/BH/Quasar), diff all the siblings for the same guard, constant, or init call before accepting the fix as complete.

## `contract-mismatch`: Two sides of one fact disagree silently

One fact gets encoded in two or more places, and they drift apart. The pairs involved are a producer and a consumer, a host and a device, a wrapper and its LLK, or a hand-written table and the hardware or ISA definition. The recurring mechanisms:
(a) An immediate-form instruction macro (an asm constant constraint) gets a runtime argument. It compiles only while inlining happens to fold the value.
(b) A hand-written bit-field struct, enum or modifier literal no longer matches the generated register map or the ISA mode table. Examples are a stale field, a signed code under an unsigned name, or a modifier bit that only means something in other modes.
(c) A wrapper forwards real metadata into a parameter the callee ignores or asserts to a default. A checker gets a locally rewritten value instead of the one that was configured.
(d) Cross-thread or cross-core peers each work out a mode or count from different evidence. The result is mismatched handshakes (hang), an unpack stage filling SrcA while math waits on SrcB, or position-dependent tie-breaks that give complementary halves which overlap.
(e) Scalars arrive as bit patterns but get converted numerically (a uint32 assigned to a float vector, or an int bit pattern compared against a float vector).
(f) Parallel lists or names drift: header vs value tuples, renamed counter keys looked up with .get(k, 0), host vs device stride formulas.
The failure is usually silent: wrong output, a vacuous or dead assert, a metric that reads 0, or a latent build break that only shows up once inlining changes.

**Checks**

- For every TTI_* (immediate-encoded) macro, check that each operand is a literal, constexpr or template parameter at the macro site, not a function parameter or local. The only exception is a force-inlined helper whose every caller passes constants. The runtime form is TT_*. For TT_* with runtime operands, check the value cannot overflow its bitfield, because encoders do not mask.
- Decode every numeric modifier literal (instr_mod, format-select code, enum value) bit by bit against the ISA definition for the mode it selects. Flag bits that are set but only defined for other modes, literals that differ from the named constant used for the same conversion elsewhere, enums that cover only part of the spec's codes, and signed and unsigned formats that map to the same code. This includes backdoor LOADMACRO setup, where comments often repeat the same misreading.
- For every hand-written bit-field struct or union overlaying config words, compare each field's offset and width with the generated SHAMT/MASK defines, per arch and per bank the word is written to or read from. One struct reused for a bank with a different layout is a bug on both write and readback.
- For each unpack+math pairing in a compute API, derive which source register the unpack stage fills and which data-valid it posts for EVERY template enum value, including NONE/pass-through. Confirm math reads that register and waits on that valid. Sibling functions (init, exec, reconfig) and every arch branch, Quasar included, must use the same mapping.
- For every cross-thread or cross-core handshake, find where each side decides whether to take part and how many posts or gets it issues. Both sides must key off one source of truth (a generated constant or the same operand's metadata), and the counts must match per section and per mode (tilize vs non-tilize, unpack-to-dest, multi-tile). This applies equally to fake producer/consumer loops in perf-isolate tests.
- For each wrapper-to-LLK call, bind arguments to parameters by position after overload resolution. Flag parameters the callee marks [[maybe_unused]] or asserts to a default while the caller forwards runtime metadata. Flag sanitizer or assert calls fed a locally rewritten value instead of the configured one. Flag new template parameters inserted before existing ones.
- Parse the first argument of every assert macro. A parenthesized first argument that contains a top-level comma is a comma expression, so the guard tests only its last operand.
- For SFPU scalar parameters, trace how the host packs them. A bit pattern must be reinterpreted (Converter::as_float or a bitcast), never assigned numerically to vFloat. An Inf/NaN/exponent test must compare an integer vector (bitcast) against the hex constant, not a float vector, and must never use float equality with NaN.
- Where two peers each compute one half of a compare-exchange, the order must be a strict total order that does not depend on operand position (for example value then index). Padding sentinels (+/-inf, max, min) must not be able to tie with real data and leak pad indices. Tests must check that indices form an in-range permutation.
- When a fix or rename touches one half of a pair (header vs values, host vs device address formula, old vs new counter name, one arch's copy), grep the other half on the merged tree. Search every spelling (prefixed or constructed strings, dict keys, docs), and flag any lookup with a silent default whose key is never produced.

## `stale-state`: Persistent hardware state inherited across ops and kernels

Tensix state that nothing resets between ops or kernels is written by one op and then consumed by a later op that assumed a default. This state includes cfg register fields, mode and debug bits, GPRs, packer and unpacker counters, the unpacker config-context selector, SFPU constant LREGs, replay-buffer contents, hardware semaphores and Dest contents. Four mechanisms keep recurring. (1) A field is set only on the path that needs a non-default value and never cleared on the complementary path: an if-branch with no else, an init with no uninit, or a set-only reconfig fix. (2) A lighter reconfig or short-init writes a subset of what the full hw_configure derives from format and geometry, or an early-out guard compares fewer inputs than the skipped code consumes. Values derived from num_faces, face_r_dim, tile size or partial_face then stay stale. (3) A configure writes a register block only in part, or at the wrong owner or thread. Fields in the skipped word, fields cached in software shadows that raw writes bypass, and fields written by a thread that does not consume them all go stale or drift. (4) Per-call code assumes a zero or known starting value (RWC counters, accumulating GPRs, context 0, an offset reset after the last loop iteration, LREG11 = -1) that only init, firmware boot or a previous caller established. Failures depend on test order and often hide in isolated tests because the standalone harness and production firmware reset different things.

**Checks**

- Configure/reconfig write-set diff: for every hw_configure and reconfig pair (pack, unpack, math), list each cfg field, GPR and cached value that configure writes, with the input it comes from (src/dst format, num_faces, face_r_dim, tile size, tile_c_dim, partial_face, relu, l1_acc). Check that reconfig rewrites each one from the new operand's full descriptor, or that a named init owns it and every path runs that init. A field that configure writes and reconfig leaves unwritten, and that something consumes, is a finding.
- Skip-if-unchanged guards: every 'old vs new operand' wrapper, and every cache comparison of the form flag != key, must compare ALL inputs that feed the state it skips. That means src and dst format plus geometry, and for replay caches every runtime value the recorded body captures. A guard that compares only pack_dst_format is the usual failure.
- Set/clear symmetry: for each conditionally enabled mode bit (exp threshold, zero-src flush, L1 accumulate, tileize_mode/shift_amount, reduce mask, debug-feature bits, fp32 mode), confirm that every path able to set it also explicitly clears it in the complementary case. Check this in configure, in reconfig and in every sibling overload (single srca, single srcb, combined, old/new, short init), for every instance of a replicated unit (packer 0..3), and on both arches.
- Init/uninit pairing: every *_init_ that writes a non-default value to shared state needs a paired uninit that restores the neutral default, or configure must set that neutral default (not a geometry-derived one). Then check that callers switching op families call the uninit, including compute-API experimental helpers whose pairing is only documented.
- Assumed-zero per-call state: for each per-tile entry point, list the counters, GPRs, context selector and address/offset registers it reads before writing. - Shadow caches and ownership: when software mirrors a register (src_zero_flag state tracker, replay-recorded flags), every raw cfg write to that field must go through the setter or invalidate the cache. The write must run on the thread that consumes the bit and be ordered after that pipeline drains.
- Fixed SFPU constants: any SFPCONFIG or other write to an LREG that the sfpi ABI treats as a constant (LREG11 = LCONST_neg1 / vConstNeg1) must be restored before return on every path, since only firmware boot seeds it.
- Post-loop stale addresses: when a MOP or loop post-increments an address or offset register for the 'next' element, every access issued after the loop and before the reset runs one past the end. Check buffers that end exactly at the top of L1, and diff the same function across WH/BH/Quasar for guards that were ported to only one copy.
- Cross-kernel sync and residue: hardware semaphores, mailboxes, CB tile counters and Dest contents (when zero flags were disabled) must be back at their initial or neutral state on every exit path, including non-matching branches. Treat invariants that only an LLK_ASSERT protects as unguarded, because the assert compiles out in production. ## `arg-binding`: Defaulted or hard-coded args bind the wrong operand

Most bugs in this class come from a defaulted parameter that quietly supplies the wrong value. A CB/operand id defaults to 0 or 16, a build-mode flag (fp32 dest accumulation) defaults to false, a thread id defaults to the math thread, a rounding mode defaults to stochastic, or an activation parameter defaults to 0. When a caller leaves the argument out, or a port from another arch leaves it out because it was implicit there, the code still compiles, and the unpacker, packer, math or SFPU resolves format, geometry, mode or register slot from the wrong source. The usual results are wrong output, a hang from the unpack and math threads disagreeing, or nondeterminism. A second mechanism is positional mis-binding. A constant belonging to one instruction field gets passed in another field's slot, a new parameter inserted before existing same-typed defaulted parameters shifts every positional caller, or a CB id placed after defaulted flags binds to the default when a caller passes only the flags. A third is lost or dropped arguments across layers: a wrapper hard-codes a subset of the LLK's template flags, init and execute get different mode flags, one epilogue passes fewer args than its sibling, a dispatcher sorts or min()s operand indices and loses operand order for non-commutative ops, or a kernel takes per-operand indices and ignores them. The last is literal resource indices in instructions (descriptor or table index 0) that are justified by a belief that the mode makes the operand unused, when in fact the hardware still fetches or validates it.

**Checks**

- For every LLK, llk_api or compute-API parameter that names a CB, operand, output or DFB (operand, icb, ocb, cbid, input_operand, pack_output), flag it if it has a literal default (0, 16, c_0, c_16). Then check two things: whether the body indexes per-CB tables with it (formats, face/tile dims, get_operand_id, unpack_src_format[]), and whether any caller omits it. Include uninit, restore and cleanup functions, experimental/ and 2_0 layers, and newly added wrappers.
- For every parameter that encodes a global build mode (fp32 dest accumulation, sync mode, approx mode, unpack-to-dest), check that the default is the build macro (DST_ACCUM_MODE etc.) or that there is no default at all, never a literal false or 0. Flag any arch or experimental copy that keeps a default its sibling arch removed.
- When a register bank that is per-thread on one arch is a shared, thread-indexed region on another, check every setter that takes the thread or core index. The default must come from the calling thread's compile-time identity, and a missing identity must fail the build. Watch for sentinel defaults that mean 'all threads' and loop over fewer threads than exist.
- Diff argument lists across sibling call sites of the same helper: bias vs no-bias epilogues, sharded vs interleaved, per-arch copies, init vs execute. A site that passes fewer args than its siblings is a bug when the missing parameters have defaults. Also check that a default of 0 is valid for every op that reads it. A default of 0 for a multiplier, reciprocal or scale is a red flag.
- When a compute-API wrapper calls a templated LLK, check that it forwards every template or mode parameter the LLK exposes rather than hard-coding a subset. Check that paired init and execute calls receive identical flags, especially where one arch applies the mode at init (MOP) and another applies it per execute.
- For multi-field instruction macros with many positional integer operands (TT_OP_/TTI_ UNPACR_NOP, PACR_STRIDE, etc.), check that each named constant comes from the struct or namespace of the field it lands in and fits that field's documented width. Separately, check that the macro's *_VALID width table matches the ISA widths. A validator that is too wide hides mis-bound args.
- Flag any descriptor, buffer-table or resource index operand that is a literal (especially 0) instead of the thread's allocated resource id. Do not accept a comment that says a no-write, masked or NOP mode makes the operand unused unless the ISA docs confirm that the fetch and validation are skipped.
- Where a multi-operand dispatch sorts, min/max's or subtracts operand indices into a base plus offset, check that non-commutative ops keep operand order and that unsigned subtraction cannot wrap. Flag kernels that take per-operand index parameters but ignore them ([[maybe_unused]], hard-coded tiles) with no static_assert or runtime assert on the only supported values.
- For numeric conversion and rounding helpers in device math, look up the default rounding argument. Flag any call that omits it when the default is stochastic or PRNG-driven, unless the op is explicitly a stochastic-rounding op. Pair this with a run-twice bit-identical determinism test.
- When a parameter is added to an existing signature, check that it is appended after the existing same-typed defaulted parameters, or that every positional caller is updated, including downstream repos and test sources. Also check that new call sites match the current template argument list.

## `tt-reconfig-drain`: Config rewritten under in-flight Tensix consumers

A config register or global mode bit (unpacker or packer base address, tilize or format fields, Dest width, remap or swizzle, INT8 math enable, source-bank contents) gets rewritten while a Tensix unit that reads it is still queued or running. That unit might be a MOP or replay from this call or the previous one, the other half of a two-pass MOP, or math or pack on another thread. The usual mechanism is a drain primitive that does not order the write path actually used. A STALLWAIT gates only Tensix instruction classes, so it cannot hold a RISC MMIO `cfg[...]=` store. STALL_CFG does not gate THCON-path writes (REG2FLOP). A THCON wait orders only the GPR producer, not the consuming unit. A source-valid wait reads a bank pointer that a bank-flipping op issued just before it has not updated yet. A related failure is a semaphore or context release placed before the config stores, or with no TRISC_CFG wait before the first consumer. Two lesser mechanisms are drains keyed on the wrong condition (misencoded stall-mask vs wait-condition operands, fixed-cycle delays) and partial reconfigs. A partial reconfig recomputes a shared bit from one operand, or leaves state that a full configure would re-derive, so the value goes stale or leaks across kernels.

**Checks**

- For every RISC MMIO store to a Tensix config register (`cfg[X] =`, `regfile[...] =`), list the Tensix instructions or MOP/replay slots that read X. Check that (a) any UNPACK_SYNC semaphore_post or context release comes AFTER the stores, (b) a STALLWAIT(..., TRISC_CFG) whose stall mask covers the consumer's class (UNPACK for UNPACR, CFG for WRCFG or replayed cfg ops) sits between the last store and the first consumer, and (c) for WAR, something RISC-blocking (wait_for_next_context on a double-buffered context, wait_for_idle, tensix_sync) keeps the store from landing while earlier queued consumers still use the old value. A Tensix STALLWAIT placed before the store orders nothing.
- Check each ordering both within one call (between two MOP runs, or mid-loop before a SETC16 context-offset switch) and across successive calls of the same function. The previous call's trailing MOP is the usual unguarded consumer, especially on paths that force context 0 via reset_config_context and never call wait_for_next_context.
- For every in-stream config write (WRCFG, REG2FLOP, cfg_reg_rmw_tensix, SETC16), check two separate fences. One is the GPR-producer fence (STALLWAIT on THCON after SETDMAREG/ADDDMAREG). The other is the consumer drain: STALLWAIT on the unit that samples the register (UNPACK0/1, PACK, MATH), or a documented latch-at-start guarantee plus a draining instruction. A THCON-only wait before a WRCFG to an address or format register is a candidate. Compare init against uninit or reconfig in the same file: if one drains the unit and its sibling does not, flag the sibling.
- For every write to a global mode bit that changes how another engine reads a shared resource (Dest remap/swizzle, 32-bit Dest mode, debug-feature bits, INT8 math enable, formats), confirm every engine that could be in flight has drained, not only the writer's own thread (both math AND pack). Also confirm that a per-kernel entry path sets the value unconditionally, so it cannot leak into the next kernel. Order-dependent tests are a symptom of such a leak.
- At every STALLWAIT that guards a write into a double-buffered source bank (MOVD2A/MOVD2B, dummy ZEROSRC publication), check whether a bank-flipping op (SETRWC CLR_A/B/AB, ELW*/MVMUL/GAPOOL with clear, CLEARDVALID) can still be in flight. That includes the previous MOP iteration's end op when the wait is replayed as a start op. If one can, the wait needs MATH in addition to SRCA_VLD/SRCB_VLD. Diff per-arch and op-local copies of the same file for condition bits present in one and missing in the other.
- For every short or partial reconfig API, list each field the full hw_configure derives from the operands (per-operand formats plus shared bits such as INT8 math enable, signedness, FP32 accumulate). Confirm each field is rewritten, on the owning thread, and that a shared bit derived from several operands is recomputed from ALL of them (using cached formats), not only from the operand being changed.
- Decode both STALLWAIT operands against the arch's enum. The first must be a STALL_* 'what to block' mask and the rest 'what to wait on' conditions. Also confirm the wait condition covers the actual producer: TRISC_CFG tracks RISC stores, not Tensix-issued RMWCIB. Resolve what a helper such as cfg_rmw expands to on that arch before judging a stall needed or removable. It is MMIO on WH/BH and an in-order Tensix instruction on Quasar.
- When a later perf change narrows or removes a drain (drops PACK/UNPACK/MATH from a mask, or replaces tensix_sync with a fixed wait), treat it as a regression candidate unless it cites hardware evidence and a re-run of the original repro. A fixed-cycle delay is never a drain.
- For kernels that insert a separator (CLR_SRC, stall) only when consecutive per-tile formats differ, check what the FIRST entry of a call is compared against. If it is not the previous call's last format, the cross-call transition is unguarded unless the call ends neutral or the next call clears conservatively.
- Apply arch-specific rules per arch. The BH ADDDMAREG/MULDMAREG -> WRCFG path needs a THCON stall. Plain SETDMAREG -> WRCFG does not. Account for MOP/replay slot order, not source order.

## `precision`: Silent narrowing, truncation and cancellation in LLK math

Values that should stay at fp32 get narrowed without anyone noticing, in four recurring ways. (1) Round-trips through narrow registers: an fp32 value in Dest is moved through SrcA/SrcB (19-bit, TF32) for a transpose, broadcast or second pooling stage. The same happens when an FPU op (bcast multiply, eltwise add, reduce) reads fp32 CB data through a source register ahead of a step that is sensitive to cancellation. The mantissa is cut to 10 bits even though an is_fp32_dest_acc_en flag is accepted, and that flag is often left unused on the path. (2) Truncating stores: SFPU kernels compute in fp32 LREGs and store to a 16-bit Dest. The store truncates toward zero and does not round to nearest-even, so any op without an explicit RNE step has a 1-ULP low bias. The rounding step is usually present in one op and missing in its neighbour, or present on one arch (WH/BH/Quasar) and missing on another. Intermediates spilled to Dest and reloaded mid-computation truncate again at each round trip. (3) Coarse or saturating approximations: 3-segment 8-bit-coefficient LUTs, int16 or sign-magnitude-16 conversions used for floor/trunc/range reduction (these saturate at 32767), and runtime scalars loaded as bf16-precision immediates. (4) Format-driven cancellation: 1 - f(x)^2 or 1 +/- f(x) where f saturates (tanh, sigmoid, erf) and is rounded to bf16 first, so the result collapses to 0. Block-float (bfp8/bfp4) intermediate CBs after a transpose or reshuffle: one Inf or large value takes over the shared exponent and flushes the finite values next to it.

**Checks**

- Trace every accumulated Dest value that goes through SrcA/SrcB (MOVD2B/TRNSPSRCB/MOVB2A/MOVB2D) in a function templated on is_fp32_dest_acc_en. If 32-bit Dest is allowed, the path must split hi/lo (DEST_32B_LOW-style moves) or avoid the round-trip. A flag that is accepted but never read on that branch is a finding. Check every stage of a multi-stage reduce (scalar = row then column, or MAX vs SUM branches), because fixes often cover only one stage.
- For every SFPU kernel that writes a computed float to dst_reg: does it know the Dest width (an is_fp32_dest_acc_en template or equivalent)? On the 16-bit path, does it round to nearest-even explicitly (convert<vFloat16b>(.., RoundMode::Nearest), float32_to_bf16_rne, or a stochastic-round FP32->FP16B step) before the store? Compare every BinaryOp/branch in the same function: if DIV rounds and MUL does not, or mul rounds but XLOGY does not, you have a candidate.
- Diff the WH, BH and Quasar copies of the same SFPU op and LLK math file for a rounding step, an fp32 branch, a Newton-iteration count or a 32-bit move flag that one arch has and another lacks. Arch divergence is the most common form an unfixed sibling takes.
- Flag SFPU intermediates written to dst_reg and read back within one computation (log body, reciprocal spilled to Dest). On a 16-bit Dest each round trip truncates, so the result can be wrong even when the final store rounds.
- For FP32-capable compute paths (norms, var/std, welford, softmax), trace each operand from its CB to its first consumer. An FPU binary/bcast/reduce that reads fp32 through a source register before a subtraction of large similar values (x-mean, variance) truncates to TF32. Check for UnpackToDest on fp32 CBs, or for scaling moved to after the sensitive step. Test with large-offset inputs (e.g. 1e6 plus small noise).
- For every approximation-mode SFPU kernel, find its LUT or polynomial and measure the error across all finite bf16 inputs, plus fp32 points near segment joins and saturation, against a float64 reference. Also check sign symmetry, range bounds (|tanh|<=1, sigmoid in [0,1]), continuity at joins, and whether +/-inf gives NaN (A*|x|+B with A=0 gives 0*inf).
- For every floor/trunc/round/range reduction done via a narrow integer conversion (float_to_int16, convert<vSMag16>, stochastic-round to INT16), work out the input magnitude at which it saturates. Then check whether a user-reachable input (x/s with a tiny scalar, large angles, large exponents) goes past it. Check that runtime scalars reach the SFPU at full fp32 (programmable constants or two-part loads), not as one bf16 immediate.
- For derivatives and activations of the form 1 - f^2, 1 - f or 1 + f, where f saturates to +/-1: if f is rounded to bf16 (16-bit Dest or a composite op boundary) before the subtraction, the output is 0 across the whole saturation band. Test with per-point ULP bounds, never with an atol larger than the true value.
- For ops that transpose or re-tile data into an intermediate CB, check the CB data format. If it inherits a bfp8/bfp4 input format, the shared exponents now group different values. Check that the CB is upcast to bf16/fp32 or that validate rejects block-float dtypes, especially when the op pads with or expects +/-Inf.
- Check that the test harness exercises the shipped path. Tests that route an op through a generic or legacy kernel (e.g. generic calculate_sfpu_binary instead of the dedicated mul/pow kernel) can pass while the production rounding path goes untested, and the reverse also happens.

## `ordering`: Handoff published before the effect completes

Most bugs in this class are a signal that becomes visible before the work it announces has finished. (1) Cross-thread release: a thread queues Tensix-side work (config-unit RMWs, WRCFG, MOPs) or makes an MMIO store to one unit (the semaphore/sync block), then releases a peer with a RISC store to a different target (mailbox, L1 flag). A STALLWAIT only gates later Tensix instructions and never holds a RISC store. Swapping the source lines only fixes program order, and stores to different memory-mapped targets can complete in either order. When the consumer decrements a counting semaphore that floors at zero, the early decrement is silently lost and the producer's later wait-for-zero hangs. (2) Hand-rolled barriers that are incomplete at the compiler level or the hardware level: a blocking read-back whose result nothing consumes, inline asm that touches memory with no "memory" clobber or m-operand, or a clobber placed in a separate empty asm after the access. asm volatile alone is not a compiler barrier, so plain loads and stores move across it. (3) Front-end mode switches (turning instruction gathering or the instruction cache on or off by CSR) that are not serialized against prediction and prefetch, plus writers of a shared resource (the replay buffer) that bypass the helper that brackets the mode. These give layout-sensitive hangs that move when the profiler or extra NOPs change the code layout. (4) Data-hazard ordering inside one instruction stream: a 32-bit Dest value is moved in hi16/lo16 passes, and the hi write goes back before the lo read of the same row. A hi-mode move may write all 32 bits, so the lo half is clobbered. The same shape covers a multi-cycle SFPU result read too early, and a config read-back that is "protected" by a guessed NOP count.

**Checks**

- For every cross-thread release (mailbox_write, L1 flag store, semaphore post), find the effect it announces and the primitive that guarantees that effect is complete, not just issued. Accept only a RISC-blocking drain (tensix_sync/mop_sync), a read-back of the same address whose value is then used, or a fence that covers that target. Reject a STALLWAIT, a NOP count, or source-line order on its own.
- For every STALLWAIT, check that its wait condition matches the real producer (RISC-MMIO cfg writes vs config-unit instructions, own thread vs another thread) and that its block mask covers the consumer's instruction class. A consumer that waits on its own thread's RISC-MMIO condition cannot see another thread's queued RMWs.
- In any protocol that pairs a counting semaphore with a separate wake-up, check that the consumer can never decrement or SEMGET while the value is still zero. Saturating or flooring decrements drop silently and turn a race into a hang in the producer's wait_on_zero or wait_on_max.
- For every hand-written barrier or blocking-read idiom, check three things. A later instruction must consume the loaded register, and its destination must not be x0 or an unused volatile local. The asm that performs the access must carry its own "memory" clobber, not rely on a separate trailing asm. Every copy of the idiom across the WH, BH and Quasar trees and the firmware headers must have been upgraded.
- Grep every inline asm that dereferences a pointer or is meant to order memory (lw/sw/vle/vse/amo/fence/cache invalidate). Each one needs an m, +m or =m operand or a "memory" clobber.
- When 32-bit Dest data moves in two 16-bit passes, draw a per-row timeline of reads and writes. Flag any read of one half that comes after a write of the other half to an overlapping row, including broadcast and transpose source rows. Look up what the active SrcA format and Fp32_enabled make each move write, since a 'hi' move may write all 32 bits and a 'lo' move may be undefined on BH.
- Treat LLK_ASSERT as no guard, because it compiles out in production. If an assert is the only thing that makes a hazardous branch unreachable, count that branch as reachable.
- Every CSR write that changes front-end fetch behaviour (gathering, instruction cache) needs the arch's full serialization before the first dependent instruction. Every writer of the replay buffer must run in the safe mode, including raw TTI_REPLAY/lltt::record calls and compiler-emitted records. A build-macro guard must match the runtime hardware state on every boot path (firmware, standalone test harness, reset default).
- When a fix, removal or workaround lands in one kernel, branch or arch copy, grep its siblings: runtime and reinit variants, tiny-tile or num_faces branches, matmul/conv/SDPA users of the same primitive, and WH/BH/Quasar twins. New branches often copy the old broken sequence back.
- For multi-cycle SFPU ops (SFPSWAP, SFPSHFT2 shuffle modes) whose result the next instruction reads, check the ISA page for the auto-stall rule on each arch. Auto-stall is lost inside SFPLOADMACRO, so there a NOP or an independent instruction is needed.

## `data-race`: Cross-thread config, source-bank and shared-state races

Three TRISC threads (unpack, math, pack), and on Quasar several cores running the same image, share config words, source and Dest banks, per-core registers and memory. The code usually assumes an ordering that nothing enforces. (1) Ownership mismatch: a config field that one thread's engine reads is written from a different thread. Examples are math-read ALU accumulation or format bits written by unpack init, and a mode bit set by one thread and blind-cleared by shared firmware init on another. A masked RMW or a mutex stops lost updates but does not order the write against the consumer. That matters most when the consumer never waits on the writer's data (SFPU fill, ZEROACC, pack-only flows), or when the writer skips a software shadow the owner keeps. (2) Source-bank handoff: Dest-to-Src moves and dummy valid-publish unpacks are not gated by hardware. A wait on bank-valid alone can see the old bank before the previous FPU op flips the pointer, and the MATH condition does not cover SFPU writes to Dest. So moves collide with the unpacker's zero-source or fill. (3) Producer/consumer handoffs over semaphores or L1: posts issued with no stall on the producing engine, or before the last in-place write. Each thread reading a shared L1 word at its own time. Tensix semaphores used over MMIO from several TRISCs, which silently drop accesses. (4) Mutable plain static variables or globals that describe per-core hardware state become shared when many cores run the same binary. (5) Values stored to Dest through a macro pipeline and then read back, where the gap between the write and the read depends on issue timing.

**Checks**

- For every config field or register write, work out which engine reads it and which thread drives that engine, then list every writer (masked RMW, WRCFG, REG2FLOP, SETC16, direct MMIO stores). A write from a non-consumer thread is a race unless an explicit handshake or drain orders it before every consumer. Include consumers that do not wait on the writer's data: SFPU-only ops, constant fills, ZEROACC, pack-only flows.
- Flag writes to a field whose owning thread keeps a software shadow or 'already configured' cache (zero-flag state, format-config-set). A write from elsewhere makes the cache wrong, so the owner's later configure call returns early and leaves the hardware stale.
- For every Dest->SrcA/SrcB move, and every other instruction that WRITES a source bank without an ownership gate, check the STALLWAIT in front of it. It must include the bank-valid condition AND the MATH-idle condition if an earlier instruction on this thread can still flip or release that bank (CLR_AB, CLEARDVALID, SETRWC clear). It must also include WAIT_SFPU if the SFPU may have just written the Dest rows being moved or accumulated.
- Check that a dummy or NOP unpack that sets data-valid or zeroes a source gates on its OWN bank and is ordered after every earlier UNPACR on that thread. Removing a stall before it lets valid be published before the data exists.
- For per-core registers that several RISCs write (debug/feature-disable, chicken bits), flag any blind whole-register write in shared init or prologue code. Require either one owner that both sets and clears, or a masked RMW with defined ordering. A go-message or mailbox barrier does not prove that an earlier RISC store has reached the register. When a setter moves to another thread, check that the clear moved with it.
- For semaphore-gated or split early-start consumers, find every writer of the consumed region (pack, in-place mask or bias stamp, push). Check that the post comes after the last of them and carries a stall on the producing engine, not p_stall::NONE, and that every consumer phase, including the first, waits on a token.
- For any value all three compute threads need (a count, flag or pointer from a reader), require one reader plus a mailbox broadcast, or a barrier. Flag UNPACK, MATH and PACK each dereferencing the same L1 word, reads of a CB page after it has been popped, and Tensix semaphores accessed over MMIO by more than one TRISC.
- On arches where identical cores run one image (Quasar), list the mutable namespace-scope, function-local and inline static variables in kernel-side headers. If one describes per-core hardware (bank parity, allocator cursor, config-done cache), it needs thread_local or per-core storage defined in firmware.
- After any race fix, diff the WH, BH and Quasar copies of the file, including experimental/ variants. Hardening hunks such as MATH drains, WAIT_SFPU and own-bank gating regularly land on one arch only.
- In SFPLOADMACRO or replay pipelines, trace every intermediate that is stored to Dest by a macro and reloaded from an offset row (prev_offset, negative offsets). Each round trip is a Dest write-to-read hazard that depends on timing. Keep intermediates in LRegs, or prove the minimum spacing and run a determinism hash test with timing perturbation.

## `tt-tile-shape`: Non-32x32 tile geometry dropped, stubbed or hardcoded

A large share of the LLK stack was written for a full 32x32 tile (4 faces of 16x16), and support for tiny, narrow or partial-face tiles was added later, one arch and one layer at a time. Bugs of this class share three mechanisms. (1) Loop counts, MOP outer/inner counts, face offsets and strides come from num_faces, face_r_dim or narrow_tile through expressions such as num_faces/2, a literal 2/32/64, TILE_C_DIM or a face_r_dim-1 loop. These give 0 iterations (a hang), too many (over-unpacking past the tile), or a wrong stride for num_faces=1/2, narrow tiles or face_r_dim<16. (2) Geometry is lost between layers. An arch's metadata getters return 32x32 constants instead of reading the per-CB tile tables. A wrapper takes num_faces or face_r_dim and marks it "not used", or passes a default instead. An init lacks the geometry parameter that its execute has. A kernel never passes its real face height. When that happens, the MOP is programmed for the default shape. (3) State lifecycle skips geometry. Only hw_configure writes geometry-derived config. Reconfig, short-init and uninit paths either don't rewrite it or restore a hardcoded 16-row face. A "switch operand" fast path compares only data formats, so a change in shape alone is skipped. The same class also covers operand-role swaps (in0 feeds SrcB, in1 feeds SrcA), where init and execute resolve per-operand shape flags from different operands. It also covers strides that confuse the dense L1 face layout with the register layout, which has a fixed 16-row face pitch.

**Checks**

- For every loop count, MOP outerloop/innerloop, replay length or address stride derived from num_faces, face_r_dim, narrow_tile or tile dims, evaluate it over num_faces {1,2,4} x narrow_tile {0,1} x face_r_dim {1,2,4,8,16}. Remember that the MOP's own per-run count multiplies the software loop count. Flag any combination that gives 0 iterations, more face unpacks than the tile has faces, or a stride that does not match the face layout.
- Check whether init and execute (and mop_config) take the same geometry parameters. Flag an init or mop_config that takes fewer shape inputs than its execute, or one that reads narrow_tile in execute but not in the MOP. Either way the MOP is programmed for a default shape.

## `integer-width`: Fixed-width counters, fields and integer ranges silently overflow

A value outgrows the bit width it is actually stored, encoded or computed at, and nothing catches it. Four shapes keep coming back. (1) Free-running producer/consumer counters are really 16-bit, but one copy of the credit math widens them to 32 bits, so after a wrap the free-space result is off by 2^16. (2) Instruction and config bitfields: an immediate valid on one arch (a 2-bit mode, a 16-bit stride field) goes into a narrower field on another arch or into an address-generator field. The *_VALID validators are wider than the real field, and TTI_ forms are never validated, so the value truncates or aliases with no error. (3) Integer math done through float or narrow ints: fp32 is exact only below 2^24, float_to_int16 saturates past 32767, and a hardware counter*stride carry keeps only a limited window. Large operands, tiny divisors or wide shapes give saturated, rounded or wrapped results. (4) Signed int32 extremes: compares done as subtract-then-test-sign overflow when operands are 2^31 or more apart. Float-style sign handling (setsgn, negation, sign|magnitude) gets applied to two's-complement lanes. INT_MIN has no sign-magnitude form. The Dest encoding the kernel assumes differs from what the production caller writes, and tests only use the harness default encoding.

**Checks**

- For every pair of free-running counters (tiles_received/acked, pages pushed/popped, semaphores), find the width each side is really stored and updated at. The final difference must be truncated or compared at that width. Diff every copy of the calculation across arches and across dataflow vs compute. Capacity must be capped below 2^width on EVERY path that sets it, including device-side reconfiguration, not only in the host validator.
- For every TT_/TTI_ macro call with literal or constexpr operands, look up each field's width for THAT arch and confirm the value fits. Watch for a value whose meaning comes from another arch (a 2-bit mode used where this arch has a 1-bit flag, or address-mode indices above 3). Also compare the is_valid(field, N) widths in ckernel_ops.h with the per-arch encoding: a validator wider than the field hides the bug.
- Where a hardware address is base + counter*stride, or a stride is shifted into a config field, find the largest value any legal shape can produce: rows*stride*datum_size, with FP32 doubling it. Compare it with the field width and any carry window. Require a range assert or a rebase when it can overflow.
- Wherever integer math goes through float (cast to fp32, op, cast back), or a float is narrowed to int16/int32/uint16 as a floor/trunc step, bound the largest intermediate for extreme inputs (0xFFFF*0xFFFF, tiny divisors, big dividends). Check it against 2^24, 2^15 and 2^31. The back-conversion must wrap or saturate as the integer contract requires.
- For every integer ordered compare, min/max or clamp (v_if(a < b) on vInt/vUInt, SFPIADD then a sign-bit test, SFPSWAP), check that it survives opposite-sign operands 2^31 or more apart. It needs a sign split, an MSB/XOR fold, or a narrow-range variant that is chosen only for inputs known to fit that range.
- Int32 lane encoding: the kernel's assumed Dest layout (two's complement vs sign-magnitude, set by DataLayout or the load/store mode) must match what the production caller writes, not the harness default. INT_MIN must survive: negating INT_MIN overflows, sign-magnitude cannot represent it, and a shift result of exactly 1<<31 may not round-trip. Flag setsgn, abs or copysign on integer lanes.
- Sibling APIs (relu_min vs relu_max, fmod vs remainder, unary vs binary, WH vs BH vs Quasar copies) must decode scalars the same way and carry the same range guards. When one sibling gets a width fix, diff all the others.
- For every correction guard after an approximation (if q > x then q -= 1), prove its condition can actually be true given how q was built. A truncated value compared with its own source can never exceed it, so the guard is dead.
- When a fix adds a parameter defaulted to the old unsafe behaviour (stride = 0 meaning legacy), check every wrapper and overload of that entry point. Also check fixed-size local arrays filled by a shape-dependent loop (MAX_UNITS=16 with ct/4 entries).

## `build-config`: Duplicated constants, headers and paths drifting apart

The same fact is stored in several places: a hardware address in a linker-script PROVIDE, a #define in a per-arch memory map, and a C++ constant; a register-field define in both the test-harness copy and the downstream vendored copy of a header; include paths in tooling scripts; per-platform toolchain checksums. One copy gets hand-typed or edited, and the others do not follow. Examples are a missing hex digit, a symbol set to the neighbouring block's base, a define added to only one header copy, or a path that points at a directory that does not exist. A second mechanism is header-only ODR hygiene. A third mechanism comes from moving code between layers or repos: macros or symbols that exist only in the source layer (debug waypoint macros, helpers from the metal layer) come along, and edits to a signature repeated across files leave some copies syntactically broken. ## `missing-case`: Unhandled dtype, domain or mode branches

A dispatch over formats, dtypes, modes or template slots handles the cases the author had in mind. Every other case falls into a default branch whose meaning is wrong for it, and nothing fails at compile time or at run time. The recurring shapes:
(1) Host if-chains or ternaries turn a DataType into a kernel template argument, and the final else is a real flavour (Float16_b, Int32, the uint32 path) instead of an error. A 32-bit or unsigned integer type then gets 16-bit load/store, a signed shift with sign fill, or a subtract-then-sign-test compare that can never go negative.
(2) A 16-bit/32-bit Dest-mode flag is derived from a single format equality (== Float32) instead of Dest width, so Int32 and UInt32 get the wrong clear width or the wrong tiles-per-bank addressing. Masking the format first makes some enum compares alias, and others can never be true.
(3) SFPU math kernels have no branch for domain edges: negatives, plus or minus 0, Inf, NaN, |x|<1, and exponents large enough that a runtime shift amount wraps modulo 32. Often one arch or approximation variant has the guard and its siblings do not.
(4) A guard over N optional template slots tests only the first one.
The defect often survives because goldens model the kernel instead of the dtype's real semantics, and test values never exceed 16 bits.

**Checks**

- For every host-side chain, ternary or switch that maps DataType to a kernel template argument, define or function name, list every dtype the op's validation admits and every format the kernel's static_assert accepts. Each must have an explicit arm. A final else that selects a real implementation (Float16_b, Int32, UInt32) instead of TT_FATAL or static_assert is a finding whenever an unlisted dtype can reach it.
- Check every entry path to the same op for the same dtype mapping: unary/TSS, binary_ng TTS/TST, ternary TTT, experimental Quasar copies, and the WH, BH and Quasar kernel copies. Fixes routinely land on one variant only. Also check that the routing predicate (for example is_binary_sfpu_op), the op-config switch and the init/func selector list the same dtypes for each op and for its sibling ops.
- Wherever a 16-bit/32-bit Dest mode flag or a tiles-per-bank value is computed (ZEROACC clear width, dest addressing), confirm it is derived from Dest width: fp32 accumulation or any 32-bit format (Float32, Int32, UInt32). A single format equality is not enough. If the format is masked before comparison, check that each compared enum constant survives the mask. A constant >= 16 under a 4-bit mask is dead code or an alias.
- For `if constexpr (FMT == A) {...} else {...}` in dtype-templated SFPU kernels, enumerate every format that falls into the else branch and check that it matches that branch's semantics: signedness, width, sign fill, compare direction and LO16 vs 32-bit load/store.
- For every transcendental or special-function SFPU body (log, sqrt, pow, xlogy, acos, lgamma and similar), check that each domain edge has an explicit branch or a provably correct fall-through: negative, +0, -0, subnormal, +Inf, -Inf and NaN. Check every arch copy, every FAST_APPROX/accurate variant, and every legacy helper body that other ops reuse. A NaN test written as `x == nan` never fires, so treat it as a missing case.
- When a float-to-int conversion shifts the mantissa by a runtime amount (exp - bias), check that every lane reaching SFPSHFT has passed a condition-code clamp on BOTH sides, because SFPSHFT uses only the low 5 bits of the amount. Compare against sibling conversions in the same file that do clamp (fp32->int32 and fp32->uint32).
- When a function takes N independently optional template parameters that default to a sentinel and emits an action under a guard, the guard must OR across all N parameters. Compile each single-parameter instantiation, or write a codegen/golden-word test, to confirm the action is emitted.
- In enum or mode dispatch chains, both host C++ and Python golden generators, check that there is an else that raises or static_asserts, that no path returns an uninitialised or unbound result, and that each broadcast/reuse mode configures the correct source unpacker.
- Reject goldens that reinterpret or rewrite inputs to mirror the kernel. Goldens must come from an independent reference (numpy or C semantics for the dtype). Require test values that expose truncation or sign handling: 32-bit values above 65535, the MSB set for unsigned types, negatives, and Inf/NaN.
- When a refactor rewrites a block, diff it against the block's history to confirm earlier special-case additions (extra formats, edge branches) were carried over.

## `index-math`: Dest/L1/ring index base and scaling errors

Index and address expressions get their base or their units wrong. (1) Bank base: an instruction either applies the current Dest bank or offset itself (auto-detect, per-thread offset register, hardware-tracked section) or expects an absolute index. Code passes a value that already includes the bank base to a relative instruction, or omits the base for an absolute one, and the mismatch changes with sync scheme (semaphore vs dvalid, SyncHalf vs SyncFull) and with arch. The symptom is wrong data on every other dest section or iteration. (2) Unit mixing: hardware sums a row offset with a block or face index. At the top of a full bank the sum crosses into the other half, and the operation clears or reads the wrong bank. (3) Block vs full width: blocked kernels compute row strides or column offsets from the block width instead of the full width. Or the block index never reaches the address math because a parameter defaults to 0 at some API tier. Or a MOP loop count fixed at init disagrees with the width passed at a tail call. (4) Ring and FIFO cursors: an increment drops the count factor (count*stride), a wrap test uses == where the step can jump past the limit, a wrap resets to base and discards the overshoot, or one global counter stands in for per-channel or per-thread state. Refactors that move cursor state into a new struct often lose a term.

**Checks**

- For every instruction that takes a Dest index, tile, face or block index (pack/unpack source index, ZEROACC, MOVB2D, SETC16 dest offset), write down per arch what base the hardware adds: absolute, per-thread offset register, auto-detected sync bank, or the current RWC row. Then check that the operand at each call site matches that base under every sync scheme (semaphore/dvalid) and buffering mode (SyncHalf/SyncFull). If the operand includes get_dest_buffer_base() and feeds a bank-relative instruction, that is a bug. So is a bank-relative operand feeding an absolute instruction.
- When hardware adds a row offset to a block or face index for bank selection, compute the maximum of (dest row offset + index) over all valid dst_index, face and fp32/16-bit combinations. The worst case is the last face of the last tile of a full bank. Flag any case where the sum can reach the rows per bank, especially when both the dest pointer and the index advance per face.
- Treat a bug that alternates between even and odd iterations or sections under half-sync Dest as a double-counted or missing bank base until proven otherwise. Look for sibling paths (strided, tiny-tile, sparse face, unpack-to-dest) that set the same index without the same bank correction.
- In blocked kernels where block_dim < full_dim, check three things. The L1 row stride must come from the FULL width. The per-block start must include block_index*block_dim. The block index must reach the address math at every tier (compute API -> llk_api -> LLK). A block-index parameter that defaults to 0 is a red flag on any multi-block path.
- When init bakes a width into MOP loop counts, check that every later call in the same init scope passes that width, including remainder and tail blocks. If it does not, the tail packs or unpacks the init width, which means stale Dest columns and L1 overrun.
- For every push/pop/commit cursor advance, check that the increment is count*stride and not a constant stride. Check that the wrap uses >= or modulo, never ==, whenever the stride is > 1 or the limit is computed as last-entry-end. Check that a reset-to-base wrap is valid only when capacity is a multiple of the transfer size, and that the code asserts this. Compare producer and consumer, and the DM and compute copies of the same buffer, against each other.
- Check that mutable per-core tracking state (bank parity toggles, dest offsets, allocator cursors, per-tile-counter indices) has per-hardware-thread storage (thread_local on multi-Neo Quasar), is kept per channel rather than as one global counter, and is reset by the matching init function.
- After a refactor that moves index or cursor state into a new struct or helper, diff the arithmetic before and after term by term. Dropped multipliers and dropped offsets are the usual casualties.
- Check that range asserts use base+size as the upper bound, and that bit-field extraction keeps every explicit bit (the mask and shift must not drop an LSB before rounding).
- Tests must fill Dest to capacity (the last tile, last face, bank 1), use count > 1 per push/pop, use full_dim > block_dim, and use capacities that are not a multiple of the stride. Otherwise every one of these bugs passes.

## `stale-sibling`: Fix lands in one copy; twins stay stale

tt-llk keeps many near-identical copies of the same logic: one per arch (WH, BH, Quasar), experimental and TTNN-private forks, the metal llk_api tier next to the vendored tt-llk tier, and sibling golden generators in the Python tests. A correctness fix, a new template parameter (most often the Dest accumulation mode), or a stronger guard (for example adding the FPU-pipeline drain to a source-bank wait) goes into one copy, and the twins keep the old behaviour. A second form of the same problem is a contract that drifts: a helper's init or signature changes (new init function, different programmable constants, a module renamed in a package split) while callers still use the old one. Both kinds fail quietly: precision drops to bf16, a Dest-to-Src move overwrites a bank the unpacker still owns, constants don't match the algorithm, or a lazy import fails inside a broad except that only warns. None of them hang, so a green namesake test rarely catches them.

**Checks**

- Diff the template parameter lists and guard conditions of every per-arch copy of a kernel or helper (WH/BH/Quasar, and experimental/ forks). If a parameter exists in one copy but not another (especially is_fp32_dest_acc_en / Dest mode), or one copy has a stronger STALLWAIT condition than another, treat it as a lead until the missing copy is shown to be unreachable or unnecessary on that arch.
- For every instruction that writes a double-buffered source register from somewhere other than the unpacker (MOVD2A/MOVD2B), find the guard on the target bank's valid bit. If a bank-flipping or clearing FPU instruction (CLR_A/CLR_B/CLR_AB on SETRWC/ELW*/MVMUL/pool, or a MOP end_op) could still be in flight when the guard runs, including from the previous call, the guard must also carry the MATH drain. Check every copy of the helper, not only the one a fix touched.
- For every SFPU kernel that narrows explicitly (FP32_TO_FP16B stochastic/RNE round, float_to_fp16b, a 16-bit store mode), confirm the Dest mode is a template parameter and the narrowing sits under `if constexpr (!is_fp32_dest_acc_en)`. Also flag Dest-mode parameters that have a default and APIs that only document '16-bit Dest assumed' without a static_assert on DST_ACCUM_MODE.
- For composite SFPU ops whose body calls another helper (reciprocal, exp, log, sqrt), confirm the op's init calls that helper's CURRENT init with the same variant/iteration choice the body uses, and that the vConstFloatPrgm/vConstIntPrgm registers the two inits write do not collide. - When a hardware numeric behaviour (FTZ, rounding mode, face-count support) is modelled in one golden generator, check that every sibling golden models it the same way and only for the formats where the hardware applies it. ## `tt-approx-guard`: SFPU numeric guards lost across modes, ranges, arches

SFPU transcendental kernels are piecewise approximations. Each one quietly depends on guards: the input is inside the math domain, the range-reduction quotient fits the integer conversion, the reconstructed biased exponent stays in 1..254, and NaN/inf/-0 take the right branch. Bugs show up in four ways. (1) Building 2^k by writing an integer into the exponent field (setexp, (k+127)<<23) with a clamp that is off by one, missing, or dropped when the kernel was ported to another arch, so the exponent wraps into a NaN or a negative value. (2) Range reduction whose integer quotient saturates (int16/SMag16 caps at 32767) or that subtracts k*C using a single constant C, which gives garbage or cancellation for large or near-multiple inputs. (3) Missing domain or special-value predicates: out-of-domain inputs return a finite polynomial value, a saturating sub-step (sigmoid, min clamp, a LUT tail A*|x|+B with A=0) turns NaN or inf into a finite value or NaN, and a multiply flushes -0 with no copysign after it. (4) A precision step (bf16 rounding, extra Newton iteration) or an approximation-mode branch applied to the wrong combination of APPROX mode and Dest accumulation. A classic case is rounding in approximate mode, which silently changes the numerics models were tuned against. Converting a bool mode flag to an enum can do the same by collapsing both branches.

**Checks**

- For every kernel that builds 2^k by integer bit construction (setexp with a computed exponent, (k+127)<<23, i<<23, adding to the exponent), work out the input range where the biased exponent leaves 1..254. Confirm a guard covers both ends with the correct inclusive/exclusive boundary (inf on overflow, 0 on underflow, NaN still propagated), or that every caller provably bounds the input. Test boundary values such as +/-88.03, -88.72 and 88.72 on each arch and each Dest precision.
- For every variant named _unsafe_, or any unguarded fast helper, list its callers and confirm each one clamps into the documented safe range BEFORE the call. Also confirm that no new caller has joined without a clamp.
- When a kernel exists in several arch copies (WH/BH/Quasar metal llk_api and the tt-llk common/inc/sfpu tree), diff the guard structure: v_if bounds, special-value branches, template 'unsafe' flags. A guard present in the source arch but missing in the port is a finding.
- For every range reduction (trig by pi or pi/2, exp by ln2, pow by integer part), find the instruction that produces the quotient k and its saturation range (SMag16/int16 caps at 32767). Compare that with the input range the op accepts. Also check that x - k*C splits C into hi/lo parts (Cody-Waite) and does not use a single constant.
- Write down the mathematical domain of each op (asin/acos |x|<=1, log/sqrt x>=0, acosh x>=1, atanh |x|<=1, log1p x>=-1). Confirm that an explicit predicate writes NaN (or +/-inf at the boundary) on EVERY precision path and arch copy, and that a NaN input lands in the NaN branch. Shared log/sqrt bodies reused by other ops must guard themselves, or all their callers must.
- Trace NaN (both signs), +/-inf and +/-0 by hand through each path of each transcendental (approx LUT, bf16 polynomial, fp32 accurate). Watch for saturating sub-functions (sigmoid, exp clamp) that make NaN finite, sfpi::min/max clamps built on sign-magnitude swap ordering rather than IEEE ordering, a LUT tail with slope 0 (0*inf = NaN), and a final odd-polynomial multiply with no copysgn.
- For each precision-dependent step (convert to vFloat16b, round-to-nearest, extra Newton iterations), confirm it runs only in the intended (APPROXIMATION_MODE x is_fp32_dest_acc_en) combinations, that APPROX mode keeps its previous numerics, and that the compute API really forwards the Dest-accumulation template argument instead of defaulting it to false or marking it unused.
- For each if constexpr on APPROXIMATION_MODE, or on an enum-typed approximation mode, confirm that BOTH modes compute and store a valid result (never an uninitialized register). Also confirm that enum-typed flags compare against a named enumerator instead of relying on integer truthiness, and that each rewritten guard still picks different branches for different modes.
- Confirm the tests push stimulus into the guarded regions (|x| > 88, |x| > 1e5 for trig, out-of-domain values, NaN/inf/-0) on every path and output format. A test limited to [0,1] or [-1,1], or one that pins a known divergence as expected, does not guard the invariant.

## `rounding`: Floored counts and non-RNE narrowing in LLK

Two mechanisms recur. (1) Integer-granularity rounding: an instruction, loop or replay count comes from right-shifting or dividing a row or datum count by a per-instruction granularity (8 rows per ELW or MOV, rows per face). It floors where it should round up, so tiny tiles and faces (face_r_dim 1/2/4, or fewer than 8 total rows) get a count of 0. The 0 then feeds `n - 1` in unsigned arithmetic (wraps to 0xFFFFFFFF, giving about 4 billion issues or garbage addresses), a MOP outer or inner loop of 0 (the last-loop CLR_AB or CLR_valid op never issues, so the pipeline hangs), or a zero-length REPLAY through a runtime helper that has no len>0 guard. The code is usually latent because tests only use 32x32 tiles. (2) Floating-point rounding: fp32 SFPU/FPU intermediates are narrowed to bf16 on store by truncation, or through helpers whose default rounding mode is stochastic, so results are off by one ULP or change from run to run. The RNE helper is applied unevenly across sibling ops (MUL, DIV, ADD/SUB) and across arches. Approximations built as reciprocal-then-multiply double-round in the narrow-precision branch. Special-value overrides and the add-0x7fff RNE trick mishandle NaN payloads, signed zeros, and inf.

**Checks**

- For every count derived as `size >> log2(G)` or `size / G` (rows per instruction, rows per face, datums per word), enumerate the smallest shapes the validator or LLK_ASSERT admits (face_r_dim 1/2/4/8, num_faces 1/2/4, and 4-row math variants). Confirm the result is never 0 while work remains. Floor where ceil was intended is the bug; the fix is `(size + G - 1) >> log2(G)` or an assert that pins the shape.
- Follow each derived count to its consumers: `n - 1` on std::uint32_t, loop bounds, MOP outer/inner loop args to ckernel_template, set_inner_loop_len(n-1), and REPLAY/load_replay_buf length. With count 0, check whether the last-outer-loop or last-inner-loop op (the one that clears src valid) is skipped, and whether the consuming helper guards zero.
- Compare sibling overloads of the same helper (template vs runtime, e.g. load_replay_buf) for guards that one has and the other lacks. A zero-length or zero-count guard present only on the compile-time version is a latent hole.
- For every path that narrows an fp32 value to bf16/fp16 on store (SFPSTORE, FPU output, dst_reg write under `!is_fp32_dest_acc_en`), determine the rounding actually applied. Check that RNE is applied consistently across all sibling BinaryOps and across WH/BH/Quasar, and that it matches what the compute-API documentation promises.
- Test RNE helpers and overrides on edge bit patterns: ties (low 16 bits == 0x8000 with both LSB parities), NaN whose payload lives only in the low 16 bits (the add-and-mask trick turns it into inf), values near FLT_MAX (overflow to inf), -0, and 0*inf / 0*NaN special-value overrides.
- Where a result is built from an approximation (x * recip(y), exp/log compositions), check whether the refinement or residual step runs only under fp32 Dest. If so, the bf16 branch double-rounds, first in the approximation and then in RNE.
- For every SFPU int/float conversion call or SFP_STOCH_RND/SFPCAST encoding, resolve the effective rounding mode, including the library default when the argument is omitted. A stochastic mode outside an intentional stochastic-round op is a bug. Symptoms: output drift across repeated runs, or failure only on the first run after reset.
- When a value passes through an intermediate integer conversion (float->int16, etc.), check that the integer width covers the full range the preceding guard admits, e.g. a |v| < 2^30 guard feeding an int16 conversion saturates.
- Treat a 'hang' or timeout fixed only by shrinking the test matrix as unresolved: it hides runtime blowups and never proves the root cause.

## `validation-gap`: Guards disagree with what the LLK really supports

The guards around LLK entry points (static_assert, LLK_ASSERT, debug coverage allow-lists, host-side limits) do not match what the code under them really handles. It goes wrong two ways. (1) Too loose. A guard is missing, commented out, or never checks what it should. Common forms: a hand-unrolled or LOADMACRO path that ignores its ITERATIONS parameter; one arch's copy of an API with no dest-index bound check that the other arch has; wrappers that call the unchecked params function directly and skip the checked macro; a check on the loop variable instead of the scaled index actually passed on; a mode template parameter that accepts values the code can't handle; a limit enforced only in host Python and not in device code. In all of these, a bad configuration silently computes wrong results or corrupts dest or memory. (2) Too strict. The guard is sized for the common case, such as num_faces==2 or a hand-copied list of tile shapes seen in tests. Then a legal tiny or partial tile (1 face, face_r_dim 1/2/4/8) fires an assert. Or a stub checker returns a constant false, so debug or LLK-assert builds halt or hang while release builds pass. Every one of these guards compiles away in production, so neither kind of mismatch shows up outside debug builds.

**Checks**

- For every template or runtime count parameter (ITERATIONS, num_faces, face_r_dim, ntiles), trace EVERY code path that uses it, including #ifdef variants such as the LOADMACRO build and the DISABLE_SFPLOADMACRO or plain-loop build. A fixed-count hand-unrolled or replay path must branch on the value or reject other values with a static_assert. If one build mode honors the parameter and another ignores it, that is a finding.
- Grep for commented-out or deleted static_assert/LLK_ASSERT lines. Check whether the code below still depends on the condition. If it does, disabling the guard has turned a compile error into silent wrong output.
- Diff the same API across arches (WH vs BH vs Quasar llk_api/*_api.h). A dest-index bound check (dst_index < get_dest_max_tiles*) or format/mode assert that exists on one arch and not another is a finding. Check matmul, reduce, transpose_dest, datacopy (including start+ntiles block loops) and the binary FPU paths, not only SFPU.
- Find every direct call to an unchecked inner function, e.g. _llk_math_eltwise_*_sfpu_params_, from llk_api wrappers, especially experimental/ ones. Each call skips the checked-macro bound check. Also flag check helpers whose capacity-defining template parameters (sync mode, accumulation width, tile shape) are unnamed or [[maybe_unused]].
- For each shape guard or allow-list, enumerate the legal parameter space: tile heights 1/2/4/8/16/32, widths 16/32, and face layouts 1x1, 1x2, 2x1, 2x2. Walk the loop counts and address or Z increments at edge value 1 to decide whether the code handles each shape. It is a bug if the guard rejects a handled shape (hang or abort in debug builds) or accepts one the code gets wrong.
- Flag any validation checker wired to an assert macro that returns a constant (e.g. a 'return false;' stub). Trace what happens when the first call site is added.
- Check that a bound assert tests the exact expression passed to the callee, e.g. the scaled i*reuse index or start_dst_index+ntiles-1, not a pre-scaling loop variable. Check that the capacity it compares against matches the real tile shape: a Tile32x32 capacity used for tiny tiles is the wrong bound.
- For a mode, format or template enum with a restricted valid set, including format combinations known to be unsupported (e.g. unpack-to-dest with Float32 on some paths), require a static_assert or explicit rejection. Silent fall-through is a finding.
- Check that capacity limits (zones, table sizes, buffer slots) are enforced where the resource is consumed (device code) and match the real memory budget. A table indexed by a runtime value must carry its size (std::array or a size parameter) together with a bounds check.
- When a change ADDS a new assert, ask whether existing callers were silently violating it before. If they were, the caller fix is a separate bug. Also check that the assert was not later relaxed or commented out to make those callers pass.

## `platform-divergence`: Per-arch assumptions leaking across boot, link and errata paths

Code that is right on one arch or boot path is silently wrong on another, because an invariant holds only under one platform's conditions. There are three recurring forms. (1) Address identity: a link-time address differs from where the object really lives at run time, for example data placed in a code section that one arch relocates into instruction RAM. That address is then handed to hardware or to another core (NoC return address, unpacker/DMA base, mailbox). (2) Boot-state parity: hardware resets to an unsafe default (Blackhole instruction gathering on, caches, chicken bits). Production firmware turns the feature off, but a second boot path does not, such as the standalone tt-llk test harness, a simulator or a bring-up tool. The code that brackets the hazard is also gated on a build macro, not on the real runtime state, so results depend on instruction layout (adding one nop flips pass/hang). (3) Per-arch errata and missing primitives: an instruction that is unreliable on one arch (REG2FLOP on Blackhole; WRCFG is the approved path there) gets used through arch-shared helpers or MOP-encoded forms. Shared multi-arch helpers also call primitives (cache invalidate, load_force, barriers) that don't exist or don't order anything on some target. Generic compiler builtins like __sync_synchronize may not emit the fence the baby RISC-V cores need. Harness code may also hardcode machine-specific tool paths.

**Checks**

- For every hardware feature firmware disables or reconfigures at boot (CSR 0x7c0 bits, gathering, caches, branch prediction), list every boot path that issues Tensix/RISC instructions: tt-metal firmware (trisc/brisc/ncrisc/erisc), tt-llk tests/helpers boot code, simulators, bring-up tools. Confirm each one applies the identical setting under the identical guard.
- Code that brackets or assumes a hardware mode (e.g. disable_gathering around replay record) must key off the same condition that actually sets the runtime state. Flag it when a build macro (ENABLE_GATHERING) controls the bracket while a runtime option or CSR controls the hardware, and flag every call site that bypasses the bracketing helper.
- Wherever the address of a linker-placed object is given to hardware or another processor, verify that the link address equals the runtime address on every arch and core type. Custom section attributes, code-region placement, IRAM/XIP relocation and ring-buffer kernel loading all break this. Hardware-visible shared locations should come from fixed memory-map constants.
- Keep a per-arch errata list of instructions or register-write paths (e.g. REG2FLOP on Blackhole). Grep that arch's LLK and metal llk_api trees for live uses, including TT_OP_* MOP/replay encodings and convenience macros in common headers, and flag any new caller.
- When a kernel 'fix' swaps a short init for a full init, or reorders ops so a test passes on one arch, treat it as evidence that the previous op's uninit/restore is broken or racy on that arch. Audit the uninit, not the kernel.
- For every shared multi-arch helper (tests/helpers/include, common headers), confirm that each ckernel:: primitive it calls (invalidate_data_cache, load_force, fences, CSR helpers) is defined on every arch the helper compiles for, including Quasar. Also confirm it has the same semantics there, not merely the same name.
- Reject generic compiler barrier builtins (__sync_synchronize, std::atomic_thread_fence) in core-side code unless the emitted instruction is confirmed to give the needed ordering on the target core. Prefer the codebase's arch barrier/load_force helper.
- Harness and host scripts must not depend on machine-specific absolute paths to external tools (reset utilities, compilers). Resolve them from PATH or the setup script.

## `loop-bounds`: Shape-derived MOP/SFPU loop counts reaching zero

Hardware loop counts (MOP outer/inner loop, replay length, SFPU ITERATIONS) are computed with arithmetic on tile geometry, such as `face_r_dim - 1`, `num_faces - 1`, `num_faces >> 1` or `block_ct_dim / 2`. The formula is tuned for the common full 32x32, 4-face tile. At the smallest legal shape (1-row faces, 1 face, a block of 1, an odd count) the result is 0. A zero MOP loop count is invalid. The MOP never completes, the packer or unpacker wedges, and the hang usually shows up in the NEXT stage or iteration, not in the one that was misprogrammed. The template builder (ckernel_template constructor and program()) writes loop lengths with no range check, so a 0 or too-wide count fails silently. A second shape is a zero-trip software loop: an SFPU calculator whose default ITERATIONS is 0, or doesn't match its dst_reg stride, or an integer-divided num_loops that is 0 for an accepted parameter. That silently leaves Dest or SrcA untouched, so the output is wrong but nothing hangs.

**Checks**

- For every value passed to ckernel_template(outer, inner, ...), load_replay_buf/replay_insn length, or ckernel_unpack_template, evaluate the expression at every value the function's own LLK_ASSERT/static_assert/doc accepts, not just the default. Try num_faces=1, face_r_dim=1, block/ct_dim=1, odd counts under /2 or >>1, and x-1 at x=1. Flag it if any accepted input gives 0 or exceeds the loop field width (roughly 127). Only a runtime or static guard counts; a debug-only LLK_ASSERT is compiled out in production.
- Cross-check the asserted parameter domain against each ternary branch. A function often asserts `num_faces in {1,2,4}` and then has a branch (zero_srcA, respect_trigger, full tile_c_dim, dense) whose formula is only nonzero for 2 or 4. Enumerate the template-flag x runtime-shape product.
- Treat a hang whose stuck unpacker is waiting on a packer (or the reverse) as a possible zero loop count in the OTHER thread's MOP from the previous iteration. Audit that MOP config for shape-derived counts.
- For each SFPU calculator template, check that the default ITERATIONS times the per-iteration dst_reg advance covers exactly one face (normally 8 iterations x 4 rows; 4 when the stride is 2). Flag a default of 0, a mismatch with the stride, or a default present on one sibling (min vs max, WH vs BH, metal-tier vs LLK copy) and missing or different on the other.
- For software loops whose trip count comes from integer division of a shape (num_loops = x / y), check that the count is nonzero for every accepted input, especially narrow tiles or num_faces=1. A zero-trip loop silently skips the unpack or compute.
- When a MOP config is fixed for one arch, diff the same function on the other arch and in the _runtime / experimental / custom variants. These copies share the formula and usually keep the bad arithmetic.

## `tt-test-param-drop`: Harness drops, swaps or rewrites swept test parameters

The LLK is correct, but the test harness never exercises the parameter point the test ID names. This happens in four ways. (1) A per-operand parameter (tile size, num_faces, partial-face flag, face_r_dim) gets bound to the wrong operand somewhere along Python config -> generated header -> kernel -> LLK call. This is easy to do because the LLK's naming does not match the test's: matmul in0 is LLK "operand A" but it feeds the SrcB unpacker. (2) Stimuli layout and golden slicing use the input tile's stride or layout instead of the real L1 tile layout or the output's per-tile stride. The first tile then passes, and later tiles come out wrong, or show up as clean multiples of the golden (x2, or shifted by one tile) when regions overlap. That looks like an LLK Dest-addressing bug, but it is not one. (3) A config constructor quietly promotes, clamps or overrides a swept value (for example, it forces dest_acc to Yes for exponent-B-input -> Float16-output pairs on non-Quasar arches). Two test cases then build the same kernel, and result keys collide or get averaged. (4) A kernel declares a swept parameter that the build config never sets, or a new format or pack handler is left out of the list that forwards shape parameters. Either way it silently runs on defaults. Such failures are usually masked while tests use full 32x32 tiles and a single shared input format. They only show up with tiny or partial tiles, mixed formats, more than one output tile, or a non-zero dst_index.

**Checks**

- For every operand-specific parameter (tile size, num_faces, partial_face, face_r_dim, format), trace Python config -> generated header -> kernel -> LLK argument, and confirm it lands on the SAME operand under the LLK's own naming. For matmul, in0 = LLK A = SrcB, and in1 = LLK B = SrcA.
- Diff the argument order of every test kernel that calls the same LLK (_llk_unpack_AB_matmul_, _llk_math_matmul_init_, and so on). An argument order that differs between siblings is a strong signal of a swap. It stays latent until the test uses tiny tiles for one operand or mixed formats.

- When a result is a clean multiple of golden (x2) or shifted by one tile, compute each operand's L1 region and each output's Dest slot from the harness and confirm they are disjoint before blaming the LLK. A hard-coded 32x32 Dest slot is by design if the packer uses the same slot addressing.

## `other`: Stale state, dead guards and incomplete keys

This bucket holds mixed defects that share one habit: code assumes some state or invariant that nothing enforces. (1) A parameter or piece of state is silently dropped. A Dest tile offset gets overwritten by a constant counter set, a CB index is hard-coded to 0, a wrapper marks face_r_dim [[maybe_unused]], or a "skip if unchanged" or cache key compares only a subset of the inputs the guarded reconfigure or build actually reads (format but not face geometry, marker file but not arch or options). The previous configuration then persists. (2) Guards and specialisations exist but never take effect. Examples: a correction whose condition cannot be true given how its operands were derived (truncated value > its own source), a repair loop placed after copysgn that only fixes one sign, and a same-named MOP template in an inner scope that is never programmed. Code like this has never run, so the encodings inside it are unverified too. (3) Shared hardware resources are clobbered through undeclared cross-owner dependencies. Examples: SFPU programmable constant registers (LREG11 = -1.0, or reciprocal constants that some other op's init happened to set), raw TTI writes to fixed LREGs that the sfpi compiler does not know about, whole-word config writes or software read-modify-writes over fields another thread owns, semaphores "borrowed" by instrumentation, and hard-coded Dest slots above the fp32/half-sync capacity. (4) Ordering and handshake shortcuts. A RISC MMIO cfg store reaches an UNPACR (directly, or through a semaphore-released MOP) with no TRISC_CFG stall, or a reset-mode CLEARDVALID drops an already-published bank. (5) Arch splits and blind tests hide all of the above. The BH/WH branches of tests and wrappers diverge, non-strict xfails XPASS forever, and sweeps pin the risky parameter to 0.

**Checks**

- Parameter-to-instruction trace: for every LLK/API entry that takes a Dest tile offset, CB/operand index, face_r_dim/num_faces or mode flag, follow the value to the instruction or config write that consumes it, in EVERY branch (narrow_row, diagonal, dense, 8-bit, per-arch #ifdef). A literal counter set (SET_W to a constant, set at init, reset at exit), a literal CB id, or a [[maybe_unused]] parameter means the argument is ignored on that branch.
- Skip/cache key completeness: for every 'reconfigure only if different' guard and every on-disk 'already built' marker or hash, list every input the guarded function or build actually reads (src+dst formats, tile size, face_r_dim, num_faces, narrow/partial flags, arch, compile options, header contents). A key that is a strict subset of those inputs is a stale-state bug. Check the pack, unpack and math siblings and each arch copy of the same guard.
- Reachability of guards: for each correction or repair branch, derive what its operands can be. Truncated-from-X is never > X, abs() is never negative, and a loop after copysgn only sees one sign. Diff guard conditions across near-copies of the same maths (scalar vs tensor, fmod vs remainder, WH vs BH), because a fix to one copy often leaves the others dead. Test with nextafter(n*s,0) and negative inputs, not random tiles.
- Shared-register ownership: list every register that compiled or hand-written code assumes holds a constant (SFPU LREG11-14, reciprocal/exp polynomial constants). Find every writer (SFPCONFIG to those indices, other ops' *_init). Confirm the expected value is restored before any consumer, and that every op in a fused loop runs its own init after the last init that could overwrite shared constants. Flag comments of the form 'can omit X init because Y init does it'.
- Raw TTI vs sfpi coexistence: in any function (after inlining) where sfpi vFloat/vInt values are live and raw TTI_SFP* instructions name fixed LREG0-7, require an in_use() or equivalent clobber declaration. Without one, correctness depends on the compiler's register allocation and breaks on a toolchain bump.
- Config-word field ownership: for every whole-word config write (WRCFG_32b, cfg[]=, REG2FLOP) and every software read-mask-write helper, look up all fields at that ADDR32 and which thread owns each. Any foreign field means the write must be a masked hardware RMW. A same-thread STALLWAIT does not fence other threads' writes, and identically named helpers can be MMIO on one arch and Tensix instructions on another.
- MMIO-store-to-consumer ordering: for each RISC store into unpacker/packer cfg (base addresses, tile descriptors), prove that a same-thread STALLWAIT(consumer, TRISC_CFG) or equivalent drain sits before every consumer. That includes a MOP issued earlier and released by semaphore_post, and the WAR case where queued UNPACRs still read the old context value. Delays and NOPs do not count.
- Dest slot capacity: for every compute helper with fixed Dest indices, compute the maximum index. Compare it to capacity for each reachable (fp32_dest_acc_en, sync mode) pair, which is 4 tiles for fp32 with half sync. Where a slot is aliased between an input and an output, check in every implementation (fused, decomposed fallback, model-local copies) that the input is read before the output is written.
- Builder objects committed in scope: every ckernel_template or replay/config builder must be programmed in the scope where it is declared. Flag inner-scope declarations that shadow an outer one (-Wshadow). Before reviving a previously dead body, check its instruction macro argument order against the target arch's signature.
- Test blind spots: list non-strict xfails and skip-on-arch markers and check whether each still fails. Look for parameter sweeps pinned to the risky value (offset=[0], stimuli kept below 2^31), and for per-arch test branches or wrappers that pass fewer arguments or different template flags than the production compute API does on that arch.

**How fixes for this class went incomplete**

- Fixing a key or guard by adding just the field that showed up in the failing case leaves the other missing fields. The unpack reconfig key gained dst-format first and needed face geometry later, and the pack-side twin was never fixed. Enumerate every input of the guarded function at once and fix every sibling (pack/unpack/math, WH/BH).
- Fixes to one copy of duplicated code do not propagate. The fmod guard was fixed while the identical scalar-remainder guard stayed dead. The SDPA Dest-slot fix skipped the model-local copy and was reintroduced in a later Quasar decomposed path. The WH dest-offset handling does not cover the narrow_row branch. Grep for the pattern tree-wide, including models/ and experimental/, not just the file that failed.
- Bringing dead code to life exposes latent bugs in it. When the shadowed tilize template was un-shadowed, its UNPACR_NOP encoding turned out to have been ported with the wrong argument slot for the target arch's signature and needed a second fix. Treat never-executed bodies as unreviewed.
- A first fix can be too narrow in scope, or it can break the execution model. The dest-offset fix covered ct but not rt. The follow-up reprogrammed the MOP inside the execute call, costing performance, and was reworked again. The cache fix keyed the headers but not the build dir. Check every dimension of the state, and keep init/execute separation.
- Some fixes avoid the problem instead of root-causing it, and the hazard stays. Examples: sampling forced stable_sort=true after the unstable network produced invalid indices, a reset-mode CLEARDVALID masked a hardware sequencing defect and caused hangs, and consumers used full re-inits or arch skips to hide a broken uninit. Treat stopgaps, 'workaround' comments and skip markers as open leads.
- Removing a marker or helper can collide with concurrent merges (an import was removed while another change started using it). Test retirements need a whole-file check on the merge target. Removing a restore as part of a fix, as happened with the DEST-access-control fix, can create a new stale-state dependency for readers that relied on it.
