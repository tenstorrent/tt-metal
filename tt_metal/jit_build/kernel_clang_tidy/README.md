# Kernel clang-tidy (post-hoc, from real JIT compiles)

This directory holds the clang-tidy configuration for device (kernel) code.
The flow it belongs to is documented in
[`tech_reports/code-indexing/kernel-clang-tidy.md`](../../../tech_reports/code-indexing/kernel-clang-tidy.md)
and driven by [`scripts/build_kernel_clang_tidy_commands.py`](../../../scripts/build_kernel_clang_tidy_commands.py).

## Where are the mock SFPI headers?

There are none, on purpose. An earlier attempt at kernel clang-tidy
(PR [#37252](https://github.com/tenstorrent/tt-metal/pull/37252)) had to
hand-write stub headers (`jit_stubs/`) faking SFPI internals, generated
`chlkc_*` content, and compile-time args so host clang could parse anything at
all. That approach was abandoned: the fakes drifted from reality and the
analysis ran against invented program facts.

Two things make the fakes unnecessary today:

1. **Real generated content, captured — not synthesized.** A normal test run
   leaves every kernel's real generated files (`chlkc_unpack/math/pack.cpp`,
   `chlkc_descriptors.h`, `kernel_includes.hpp`, `defines_generated.h`, ...)
   and the real compile command (real `KERNEL_COMPILE_TIME_ARGS`, real defines)
   in the durable tt-metal-cache directory. Capturing the compiler invocations
   with `bear` and replaying them through clang gives the analysis the same
   program facts the device build used.

2. **SFPI ships its own analysis-tool fallback.** Since SFPI 7.x,
   `<sfpi>/include/tensix_builtins.h` detects a non-SFPI compiler (no
   `__riscv_xtttensix*` predefine), derives the extension macro from the
   `ARCH_WORMHOLE`/`ARCH_BLACKHOLE`/`ARCH_QUASAR` define that every kernel
   compile already carries, defines the `__xtt_vector` types, and includes
   `tensix_builtins.def` — machine-generated declarations of every
   `__builtin_rvtt_*` intrinsic (generated by `sfpi/scripts/gen-decls.py` from
   the compiler's own `rvtt-insn.def`). Its header comment says it exactly:
   "provided so that code analysis tools will not just give up in the face of
   an unknown function call." Clang parses the *real* `sfpi.h` stack with no
   help from us. Verified with the SFPI release tt-metal pins (7.73.0, see
   `tt_metal/sfpi-version`): `tensix_builtins.def` is present in the shipped
   tarball's `include/` directory.

The remaining GCC/clang gaps are small and handled by the filter script as
flag translation, not fakes (see the script's docstring): `--target`/`-march`
mapping, `-std=c++17`+`-ftt-*` → `-std=c++20`, SFPI's own newlib/libstdc++
headers via `-isystem`, and the riscv32 `int32_t`-is-`long` type-model
overrides that `sfpi.h` itself static_asserts.

## Known gaps

* `[[maybe_unused]]` on *template parameters* is a GCC extension clang
  rejects (any -std). It appears in
  `tt_metal/tt-llk/tt_llk_wormhole_b0/llk_lib/llk_pack.h:393`, so **wormhole
  PACK-role (TRISC2) TUs currently fail to parse** (MATH and UNPACK are
  clean). One-line upstream fix: drop the attribute from the template
  parameter (it is cosmetic there). Several quasar-only headers use the same
  extension; quasar is untested in this flow anyway.
* The check list in `.clang-tidy` was tuned for PR #37252's stub-based parse
  and has not been re-triaged for this flow; expect to re-enable some checks
  (and disable others) after the first full CI capture.
* `clang-analyzer-*` checks are disabled wholesale (cost + noise); worth
  revisiting once the baseline is quiet.
