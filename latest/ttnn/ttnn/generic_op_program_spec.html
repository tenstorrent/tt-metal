    Running your own kernels with generic_op and a ProgramSpec

    ttnn.experimental.generic_op runs a program that you describe yourself: the kernels, the buffers between them, the tensors they read and write, and the values of each call. It takes the program as a Metal 2.0 ProgramSpec, everything fixed about the program, and a ProgramRunArgs, the values of one call. Kernels find everything they use by name.

    This form is experimental while its API settles, so everything it adds lives under ttnn.experimental. The ProgramDescriptor form, ttnn.generic_op, keeps working. The ProgramSpec form also runs on Quasar.

    Each Python class has the fields of the C++ struct with the same name, whose comments document them: TT-NN’s MeshProgramSpec and MeshProgramRunArgs are in generic_op.hpp, and the others in the workload headers (tt_metal/api/tt-metalium/workload/), apart from the advanced options, which stay experimental in advanced_options.hpp. Of the advanced options, Python binds only DFBAdvancedOptions.alias_with, which lets buffers of the same total size share memory; the others are C++ only. So far the GlobalSemaphore fields are C++ only too: ProgramSpec.global_semaphore_parameters, KernelSpec.global_semaphore_bindings and ProgramRunArgs.global_semaphore_args. Two fields differ in type: ProgramRunArgs.tensor_args takes a ttnn.Tensor for each name and keeps it alive, where C++ holds the tensor’s MeshTensor; and the data_format_metadata of a DataflowBufferSpec or ScratchpadSpec takes a ttnn data type, such as ttnn.bfloat16, so a format without one, such as Float16, cannot be set, and ttnn.int8 reads back as ttnn.uint8. In Python, argument values are integers from 0 to 2**32 - 1.

    An example

    This program computes exp(x) for every element of a tensor in DRAM. On each node a reader kernel copies tiles from the input tensor into a buffer, a compute kernel applies exp to each tile, and a writer kernel copies the results to the output tensor. The three kernels already exist in TT-NN. With torch and ttnn imported and device an open device:

    E = ttnn.experimental
KERNELS = "ttnn/cpp/ttnn/operations/eltwise/unary/device/kernels"

num_tiles = 8
torch_input = torch.rand([1, num_tiles, 32, 32]).to(torch.bfloat16)
input_tensor = ttnn.from_torch(
    torch_input, dtype=ttnn.bfloat16, layout=ttnn.TILE_LAYOUT, device=device, memory_config=ttnn.DRAM_MEMORY_CONFIG
)
# generic_op does not create its output: preallocate it.
output_tensor = ttnn.allocate_tensor_on_device(input_tensor.spec, device)

grid = device.compute_with_storage_grid_size()
_, cores, group_1, group_2, tiles_1, tiles_2 = ttnn.split_work_to_cores(grid, num_tiles)

dm_schema = E.KernelSpec.RuntimeArgSchema(runtime_arg_names=["num_pages", "start_id"])
spec = E.ProgramSpec(
    name="exp",
    kernels=[
        E.KernelSpec(
            unique_id="reader",
            source=f"{KERNELS}/dataflow/reader_unary_interleaved_start_id_metal2.cpp",
            dfb_bindings=[E.producer_of("in", "in")],
            tensor_bindings=[E.TensorBinding(tensor_parameter_name="input", accessor_name="src")],
            runtime_arg_schema=dm_schema,
            hw_config=E.create_reader_datamovement_config(),
        ),
        E.KernelSpec(
            unique_id="writer",
            source=f"{KERNELS}/dataflow/writer_unary_interleaved_start_id_metal2.cpp",
            dfb_bindings=[E.consumer_of("out", "out")],
            tensor_bindings=[E.TensorBinding(tensor_parameter_name="output", accessor_name="dst")],
            runtime_arg_schema=dm_schema,
            hw_config=E.create_writer_datamovement_config(),
        ),
        E.KernelSpec(
            unique_id="compute",
            source=f"{KERNELS}/compute/eltwise_sfpu_metal2.cpp",
            compiler_options=E.KernelSpec.CompilerOptions(
                defines={"SFPU_OP_EXP_INCLUDE": "1", "SFPU_OP_CHAIN_0": "exp_tile_init(); exp_tile(0);"}
            ),
            dfb_bindings=[E.consumer_of("in", "in"), E.producer_of("out", "out")],
            runtime_arg_schema=E.KernelSpec.RuntimeArgSchema(runtime_arg_names=["num_tiles"]),
            # 32-bit data also needs enable_32_bit_dest=True and unpack_modes={"in": E.UnpackMode.UnpackToDest}
            # here; with the defaults, or with UnpackToSrc, it loses precision.
            hw_config=E.ComputeHardwareConfig(),
        ),
    ],
    dataflow_buffers=[
        # Each entry holds one tile of the input's data type.
        E.DataflowBufferSpec(
            unique_id=name,
            entry_size=ttnn.tile_size(input_tensor.dtype),
            num_entries=2,
            data_format_metadata=input_tensor.dtype,
        )
        for name in ("in", "out")
    ],
    tensor_parameters=[
        E.TensorParameter(unique_id="input", spec=input_tensor.spec),
        E.TensorParameter(unique_id="output", spec=output_tensor.spec),
    ],
    work_units=[E.WorkUnitSpec(name="exp", kernels=["reader", "writer", "compute"], target_nodes=cores)],
)

# The values of this call, by argument name and then by node. Tensors are bound by name.
num_pages, start_id, start = {}, {}, 0
for group, n in ((group_1, tiles_1), (group_2, tiles_2)):
    for core in ttnn.corerange_to_cores(group):
        num_pages[core], start_id[core] = n, start
        start += n
dm_args = {"num_pages": num_pages, "start_id": start_id}
run_args = E.ProgramRunArgs(
    kernel_run_args=[
        E.KernelRunArgs(kernel="reader", runtime_arg_values=dm_args),
        E.KernelRunArgs(kernel="writer", runtime_arg_values=dm_args),
        E.KernelRunArgs(kernel="compute", runtime_arg_values={"num_tiles": num_pages}),
    ],
    tensor_args={"input": input_tensor, "output": output_tensor},
)

output_tensor = E.generic_op([input_tensor, output_tensor], spec, run_args)

    A WorkUnitSpec runs its kernels on each of its target_nodes. A node is a block of the chip’s grid at an x, y coordinate, such as a Tensix core, and Python names one with a ttnn.CoreCoord; the RISC-V cores that run the kernels are inside it. A program can have several work units, each running some of the program’s kernels on its own nodes, and a kernel can be in more than one.

    A kernel’s source is the path of its source file: an absolute path, or one that Metal looks up in the current directory, then in TT_METAL_KERNEL_PATH, the system kernel directory and the tt-metal root, where it finds the example’s TT-NN kernels. To give the code itself instead, pass E.KernelSpec.SourceCode(code=...).

    How a kernel finds its inputs

    Everything a kernel uses has a name, which the kernel code reaches through a generated namespace. For a buffer, tensor, semaphore or scratchpad, that name is the accessor_name of the kernel’s binding; the unique_id of the spec only ties the binding to it. In the example, the reader reads tensor parameter input as tensor::src. E.producer_of and E.consumer_of make a buffer binding from the buffer’s unique_id and the accessor name; the example’s buffers and their accessors share the names in and out.

    What a kernel needs, where you set it, and how the kernel reaches it:

    • A value fixed at compile time: KernelSpec.compile_time_args. In the kernel: get_arg(args::<name>).

    • A value per node: a name in RuntimeArgSchema.runtime_arg_names, and the values in KernelRunArgs.runtime_arg_values. In the kernel: get_arg(args::<name>).

    • A value shared by all nodes: a name in RuntimeArgSchema.common_runtime_arg_names, and the value in KernelRunArgs.common_runtime_arg_values. In the kernel: get_arg(args::<name>).

    • A list of values fixed at compile time: KernelSpec.compile_time_array_args. In the kernel: get_arg(args::<name>)[i].

    • A list of values per node: an ArrayArgDecl (name and size) in RuntimeArgSchema.runtime_array_args, and the values in KernelRunArgs.runtime_array_arg_values. In the kernel: get_arg(args::<name>)[i].

    • A list of values shared by all nodes: an ArrayArgDecl in RuntimeArgSchema.common_runtime_array_args, and the values in KernelRunArgs.common_runtime_array_arg_values. In the kernel: get_arg(args::<name>)[i].

    • A tensor: a TensorParameter and a TensorBinding, and the tensor in ProgramRunArgs.tensor_args. In the kernel: TensorAccessor(tensor::<accessor_name>), or LocalTensorAccessor<T>(tensor::<accessor_name>) for the node’s own shard in L1.

    • A buffer between two kernels: a DataflowBufferSpec, with a producer and a consumer binding. In the kernel: DataflowBuffer(dfb::<accessor_name>).

    • A buffer on a sharded tensor’s memory: a DataflowBufferSpec whose borrowed_from names the TensorParameter. In the kernel: DataflowBuffer(dfb::<accessor_name>).

    • A semaphore: a SemaphoreSpec and a SemaphoreBinding. In the kernel: Semaphore(sem::<accessor_name>).

    • Private scratch memory: a ScratchpadSpec and a ScratchpadBinding. In the kernel: Scratchpad<T>(scratch::<accessor_name>).

    An array has the same length on every node, and get_arg(args::<name>).size() gives it. For a list whose length differs from node to node, such as a list of node coordinates, declare the longest length and pass each node’s count in another argument. The Python classes do not bind varargs, the positional kernel arguments that Metal 2.0 keeps in its advanced options for a few niche uses: array arguments replace them.

    The lists and dicts these classes return are copies, and so are their other fields that hold an object, such as KernelSpec.hw_config, TensorParameter.spec and WorkUnitSpec.target_nodes. A change to a copy is lost: assign the whole field instead, as in kernel.compile_time_args = {"block": 2} rather than kernel.compile_time_args["block"] = 2. That holds one level up too: spec.kernels[0].compile_time_args = ... changes a copy of the kernel, so take the list, change it and assign it back (kernels = spec.kernels, change kernels[0], then spec.kernels = kernels). Only four fields return the object itself, so that a change to it changes the object that holds it: KernelSpec.compiler_options, KernelSpec.runtime_arg_schema, TensorParameter.relaxations and DataflowBufferSpec.advanced_options.

    Tensors

    io_tensors lists the tensors the program uses, once for each tensor parameter a tensor is bound to, with the output last; generic_op returns the last entry, or, when the tensors are not all on the same devices, only its parts on the devices of the tensor that is on the fewest devices (see “Running on a mesh”). Each tensor must be on the device and match its parameter’s TensorSpec, unless the parameter’s TensorSpecRelaxations allow a difference, such as a dynamic shape. Bind each tensor parameter to a tensor that io_tensors lists.

    Note

    A tensor parameter can also be bound to a per-device view of a listed tensor, from ttnn.get_device_tensors, if the view holds every device its program runs on: on each device it runs on, a program reads that device’s part of the tensor, whichever view is bound.

    Calls and the program cache

    The first call with a given program compiles its kernels and sets it up on the device. A later call with the same program only writes the new values: argument values and tensors can change from call to call without a recompile. ttnn.experimental.prepare_generic_op takes the same arguments, compiles the program and puts it in the cache without running it.

    The cache key is a hash of the whole ProgramSpec, combined with the devices it runs on, apart from ProgramSpec.name, WorkUnitSpec.name and the tensor fields that a parameter’s TensorSpecRelaxations allow to differ. So renaming or reordering kernels or buffers gives a new cache entry. generic_op computes that hash on every call while the program cache is on. The key holds a kernel’s source path, not the file’s contents, and so do Metal’s caches of compiled and loaded kernels within a process, so after you edit a kernel file, run it in a new process. A kernel given as KernelSpec.SourceCode is keyed on its code. Unlike the ProgramDescriptor form, the ProgramSpec form takes no custom_program_hash, because a key the caller picks could give two different programs the same cache entry.

    Every call checks its run args against the spec before Metal sees them: each kernel gets exactly the runtime arguments and arrays it declares, each array with its declared length, each tensor parameter gets a tensor from io_tensors that matches it, and each dataflow buffer (DFB) size override names a buffer of the spec, at most once and with no size of 0. Whether every node got its values is checked on later calls only when ttnn.CONFIG.validate_program_args is on, which it is not by default; with it off, a node that a later call leaves out keeps its previous values. A DFB size override in ProgramRunArgs.dfb_run_overrides stays in effect for later calls that reuse the cached program, including calls with an equal spec from other code, until a call changes it. prepare_generic_op with a program that is already cached applies its run args to it the same way, even if the preparation then fails.

    Running on a mesh

    With a ProgramSpec, generic_op runs the program on the devices of the tensor in io_tensors that is on the fewest devices, and every other tensor must be on those devices too; usually all the tensors are on the same devices. If the output is on more devices than that, its parts on the other devices are not written, and the tensor generic_op returns holds only the parts it wrote; the tensor you passed in still holds them all. To run different programs on different devices, give a program for each mesh coordinate range. On a 1x2 mesh, for example:

    left = ttnn.MeshCoordinateRange(ttnn.MeshCoordinate(0, 0), ttnn.MeshCoordinate(0, 0))
right = ttnn.MeshCoordinateRange(ttnn.MeshCoordinate(0, 1), ttnn.MeshCoordinate(0, 1))
output_tensor = E.generic_op(
    [input_tensor, output_tensor],
    E.MeshProgramSpec(programs=[(left, spec), (right, other_spec)]),
    E.MeshProgramRunArgs(programs=[(left, run_args), (right, other_run_args)]),
)

    The ranges must stay inside the mesh and must not overlap, every device in them must hold every tensor, and the run args must have the same ranges as the spec. The ranges need not cover every device: the output’s parts on a device that no range covers are not written.

    Moving a kernel from the ProgramDescriptor form

    The lines that fetch a kernel’s inputs change, as TT-NN’s unary kernels in both forms show: the compute kernel (eltwise_sfpu.cpp and eltwise_sfpu_metal2.cpp) and the reader (reader_unary_interleaved_start_id.cpp and reader_unary_interleaved_start_id_metal2.cpp).

    • Arguments by position become arguments by name: get_arg_val<uint32_t>(0) becomes get_arg(args::num_tiles), with num_tiles declared in the kernel’s RuntimeArgSchema, and get_compile_time_arg_val(0) becomes get_arg(args::<name>) with the name in KernelSpec.compile_time_args. A read by position that is left in may still compile and read whatever value is at that position, so change every one.

    • Circular buffers by index become dataflow buffers by name: tt::CBIndex::c_0 becomes dfb::in, with in the accessor name of the kernel’s binding to a DataflowBufferSpec. Calls such as copy_tile(dfb::in, 0, 0) take it directly, and so do the circular-buffer calls on Wormhole and Blackhole. The DataflowBuffer calls, which Quasar needs, take it wrapped as DataflowBuffer(dfb::in), as both kernels above do, and a data-movement kernel reads its page size with get_entry_size().

    • Tensor addresses passed as arguments become bound tensors: TensorAccessor built from an address and TensorAccessorArgs becomes TensorAccessor(tensor::src).

    • On the host, each CBDescriptor becomes a DataflowBufferSpec with its bindings, and a kernel’s runtime arguments, a list of values per node, become KernelRunArgs.runtime_arg_values: a dict from each argument name to a dict from node (a ttnn.CoreCoord) to value.

    On Wormhole and Blackhole the loops that move and compute data can stay as they are. The Metal 2.0 kernels above also have changes that are not part of the move: eltwise_sfpu_metal2.cpp splits its loop with dram_read::for_each_chunk and can set a packer ReLU, and reader_unary_interleaved_start_id_metal2.cpp can take its page size from defines. On Quasar the circular-buffer calls do not work, so the data-movement loops use the DataflowBuffer calls instead (reserve_back, push_back, wait_front, pop_front), as both unary readers above already do. A Quasar data-movement kernel that makes many transfers smaller than a tile, such as row-major sticks, also passes disable_dfb_implicit_sync_for_all=True to create_reader_datamovement_config or create_writer_datamovement_config: such transfers stall Quasar’s implicit counting of buffer entries, and the flag leaves the counting to the kernel’s own calls. TT-NN’s factories pass it in other cases too, such as matmul’s multicast kernels, where the implicit counting would acknowledge one entry more than the kernel’s own pops; when you port a TT-NN kernel, keep the flag if its factory sets it.

    Some features of the ProgramDescriptor form are not available in the ProgramSpec form yet, such as global circular buffers, fabric connections and per-core allocated tensors. From Python, global semaphores are not available yet either, and a semaphore always starts at 0. Programs that need any of these stay on ttnn.generic_op.

    More examples

    test_generic_op_program_spec.py builds programs with two inputs, array arguments, aliased buffers, buffers on a sharded tensor’s memory, semaphores, the mesh form and, on Quasar, a compute kernel with two threads. The API reference lists the arguments of ttnn.experimental.generic_op().
