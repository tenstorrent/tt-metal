KDA cache adapter experiment

An end-to-end report on converting prefill-native recurrent S and convolution history to and from the K3 migration contract. It covers tensor geometry, the original three-core bottleneck, the 110-core row-major copy prototype, latency, layer-relative impact, effective DRAM bandwidth, and correctness.

Verdict. The contract layout is viable. The optimized adapter keeps every measured one-way handoff below 29 µs per KDA layer and below 0.283% of layer latency. At SP4xTP2, convolution export improves 7.88× and import 11.80× without changing the contract.

Transfer accounting

One conversion reads the source and writes the destination. Estimated DRAM traffic is therefore 2 × local cache bytes.

Why S was faster

Tiled copy partitioned hundreds of tiles over 110 cores. SP4 Tracy measured 16.410 µs export and 16.278 µs import device-kernel medians.

Why convolution was slow

DefaultRowMajor partitioned [1,3,W] by its three logical rows, so only 3 cores redistributed as many as 288 tiny pages per row.

Parallelize within logical rows

The contract and KDA adapter API stay unchanged. Only the generic row-major copy work partition changes when both endpoint page boundaries share an aligned unit.

Guarded generic path

The common unit must be smaller than the row, aligned for both buffers, and no larger than the existing 256 KiB subblock limit. Unaligned and uneven cases remain on the legacy whole-row path. S remains on the existing tiled path.

Effective DRAM bandwidth per device

Final prototype timings. The 512 GB/s theoretical limit is per Blackhole device: 8 GDDR6 channels × 64 GB/s. Values count both the source read and destination write.

DRAM BW/device = 2 × local cache bytes / measured time utilization = DRAM BW/device / 512 GB/s

Direct-layout ablation

Current recurrent scan and convolution consumers require interleaved state. Therefore the measured explicit adapters remain the smallest supported prefill/decode boundary; direct contract consumption was not available in PR7.
