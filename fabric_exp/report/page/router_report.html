Summary

The fabric router is the program that moves data across each Ethernet link between two chips. Here the new router is compared with main's router on how much of each link it uses and round-trip latency.

% of link
payload delivered ÷ the most payload the link can carry at that packet size, after Ethernet framing and the packet header. 100% is the link limit.
GB/s
payload only, from the measured time per packet at the router's clock: 1.35 GHz on Blackhole, 1 GHz on Wormhole.
1 hop
the packet crosses one chip-to-chip link. With 3 hops, the routers on the chips in between forward it.
Neighbor exchange
a fabric mode where each chip sends only to its direct neighbors, with no forwarding.
Multicast
one packet delivered to several chips along its route.
400G, 200G and 100G
the links of a Blackhole P150x8 (8 chips), a Blackhole Galaxy (32 chips) and a Wormhole T3K (8 chips). One link per connection. On Wormhole the router runs on one core per Ethernet link.

How to read the evidence tags

    Tried and dropped

    Bandwidth
    Payload GB/s from the measured cycles per packet on the router clock (payload bytes × clock ÷ cycles): 1.35 GHz on Blackhole, 1 GHz on Wormhole. Cycles per packet follow in parentheses; fewer is faster.
    Line rate
    A packet's time on the wire: payload + header + 56 B per 4,114 B frame + 84 B, over 37.04 B/cycle at 400G, 18.52 at 200G (both at 1.35 GHz) or 12.5 at 100G (1 GHz). A 4,352 B 2D packet takes 125.4 cycles at 400G, 250.8 at 200G and 371.5 at 100G.
    Systems
    400G links: a Blackhole P150x8 (8 chips). 200G links: a Blackhole Galaxy (32 chips). 100G links: a Wormhole T3K (8 chips as a 2x4 mesh; the ring is its 8-chip perimeter), where each router runs on one core. One link per connection, bandwidth telemetry off. On the Galaxy the driver reports some chips' clock settling at 1,337–1,343 MHz at start (it does not name them); the profiler reads 1,350 MHz on the sending chips. Cycles are the device's own counts; GB/s and the line rate assume 1.35 GHz, so on a chip at 1,337 MHz the GB/s would read 1% high.
    Y torus at 400G
    The torus tests ask for a torus along Y only (the fabric's 2D Y-torus, written for the Galaxy, where Y is 8 chips long). The P150x8 runs as a 2x4 mesh: Y is 2 rows long and has no wrap-around (the 4-chip rows along X do). So the fabric maps these tests onto the mesh (it logs that the Y-torus cannot be realized), while the N/S routers still run in torus mode with deadlock avoidance, as requested. No traffic crosses a wrap-around link. The tests are 1-hop E/W and N/S (one way and both ways), 3-hop E/W and multicast. The 8-chip ring tests are realized as rings.
    XY torus
    On the Galaxy (200G) the fabric realizes both axes as rings (it logs Y=RING X=RING), and the wrap rows send across a wrap-around link. On the P150x8 (400G) only the 4-long axis can wrap: X on the shipped 2x4 mesh (each 4-chip row is a ring), Y on a 4x2 mesh descriptor written for these tests; the 2-long axis stays a line. Deadlock avoidance is on in all four directions in both cases, and the runs were validated (data-checked all-to-all) first.
    Controls
    Two passes in reversed router order. Main is main's router as shipped. The new router ran with a 1,000-cycle Ethernet keepalive; section 2 shows what that changes.

    One-way traffic and the keepalive

    When traffic flows one way only, the Ethernet keepalive interval matters. With main's shipped setting, one-way tests with packets above 4,114 B settle near 187.5 cycles per packet whatever the router does. A 1,000-cycle interval removes most of that floor. The new router's runs used 1,000 cycles; everywhere else on this page main runs as shipped. These are the tests where the setting changes main's result. It does not change latency (section 3).

    VC0 and VC2 sending on one east-west link, at 400G on the P150 and at 200G on the BH Galaxy. Each bar is the link's combined bandwidth measured in one run: all bytes delivered over the run's time, with the packet counts set so both VCs send for the whole run (they finish within 1% of each other). The split shows each VC's share of the packets. A separate check, each VC's rate measured while the other sends in two other runs and summed, agrees closely (see the table). Each router runs its own slot allocation, as shipped; VC2 has fewer slots than VC0 in both. All channels share the ERISC's buffer space, so the two routers divide it differently, and a VC with few slots can be limited by how many packets it has in flight rather than by the router or the link.     Where the cycles go

    Where each ERISC spends a packet's time, main's router against the new router, at five test points. Both ERISCs of every router were sampled over the debug bus while the test ran (sampling leaves the measured rate unchanged); each sample is mapped to its source line and grouped into seven categories, so each bar adds up to the measured cycles per packet. Each bar is one router: for each ERISC, the busiest one (the largest share of samples in its main work: Ethernet send on the sending ERISC, NoC commands on the receiving one). Polls are time spent checking for work or room, waiting included. A split within one ERISC does not say which ERISC limits the rate. Mean of two passes in reversed router order. The new router is the same build as on the other tabs.

    Code and stack

    Both ERISC programs of a router load from one 26,624 B kernel config buffer, which also holds the runtime args. On every two-ERISC configuration both routers build, the new router is the smaller one, and every configuration it builds runs at -O3. Main's router with VC1 does not fit at -O3 and ships at -Os.

    new router, -O3main, -O3
    • Main cannot build VC1 + VC2 (its stack use reaches 2,176 B) or VC2 on one ERISC. The new router does not admit VC1 + VC2 yet either; two earlier builds of it have built and run that combination.
    • The new router is larger than main only on one-ERISC binaries, where one image holds both programs: up to +1,244 B (Galaxy express).
    • Not yet built for either router: a configuration with every feature at once (inter-mesh, express, bubble flow control, VC1 and VC2).
