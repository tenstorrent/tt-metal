Blackhole Fabric Router Study

A new fabric router against main's router on 400G and 200G Ethernet links: bandwidth, latency, code and stack, and what the new structure makes possible.

DraftEvery number is the final build of the new router against main as shipped, in the same jobs, two passes in reversed order, 2026-11-03. At 400G (one P150x8): the two-ERISC suites (2D mesh, 1D line, ring, Y torus, XY torus) at five packet sizes, and the one-ERISC, mux and two-mesh tests. At 200G (Galaxy): the mesh, 1D line, ring and XY torus suites at five packet sizes, with main also run at a 1,000-cycle keepalive. The keepalive table on the Bandwidth tab still uses an earlier build of the new router.

Bandwidth
Payload GB/s from the measured cycles per packet on the 1.35 GHz router clock (payload bytes × 1.35 ÷ cycles). Cycles per packet follow in parentheses; fewer is faster.
Line rate
A packet's time on the wire: payload + header + 56 B per 4,114 B frame + 84 B, over 37.04 B/cycle at 400G or 18.52 at 200G. A 4,352 B 2D packet takes 125.4 cycles at 400G and 250.8 at 200G.
Systems
400G links: a P150x8 (8 chips). 200G links: a Galaxy (32 chips). One link per connection, bandwidth telemetry off. On the Galaxy the driver reports some chips' clock settling at 1,337–1,343 MHz at start (it does not name them); the profiler reads 1,350 MHz on the sending chips. Cycles are the device's own counts; GB/s and the line rate assume 1.35 GHz, so on a chip at 1,337 MHz the GB/s would read 1% high.
Y torus at 400G
The torus tests ask for a torus along Y only (the fabric's 2D Y-torus, written for the Galaxy, where Y is 8 chips long). The P150x8 runs as a 2x4 mesh: Y is 2 rows long and has no wrap-around (the 4-chip rows along X do). So the fabric maps these tests onto the mesh (it logs that the Y-torus cannot be realized), while the N/S routers still run in torus mode with deadlock avoidance, as requested. No traffic crosses a wrap-around link. The tests are 1-hop E/W and N/S (one way and both ways), 3-hop E/W and multicast. The 8-chip ring tests are realized as rings.
XY torus
On the Galaxy (200G) the fabric realizes both axes as rings (it logs Y=RING X=RING), and the wrap rows send across a wrap-around link. On the P150x8 (400G) only the 4-long axis can wrap: X on the shipped 2x4 mesh (each 4-chip row is a ring), Y on a 4x2 mesh from a study descriptor; the 2-long axis stays a line. Deadlock avoidance is on in all four directions in both cases, and the runs were validated (data-checked all-to-all) first.
Controls
Two passes in reversed router order. Main is main's router as shipped. The new router ran with a 1,000-cycle Ethernet keepalive; section 2 shows what that changes.

One-way traffic and the keepalive

When traffic flows one way only, the Ethernet keepalive interval matters. With main's shipped setting, one-way tests with packets above 4,114 B settle near 187.5 cycles per packet whatever the router does. A 1,000-cycle interval removes most of that floor. The new router's runs used 1,000 cycles; everywhere else on this page main runs as shipped. These are the tests where the setting changes main's result. It does not change latency (section 3).

Each bar is the link's combined bandwidth measured in one run: all bytes delivered over the run's time, with the packet counts set so both VCs send for the whole run (they finish within 1% of each other in every run). The split shows each VC's share of the packets. A separate check, each VC's rate measured while the other sends in two other runs and summed, agrees within 0.5% (mean of two passes). Each router runs its own slot allocation, as shipped; VC2 has fewer slots than VC0 in both. Slots are listed per channel. VC0 and VC2 each have a worker channel, which the local sender here uses; VC0 and VC1 also have forwarding channels for traffic passing through from the router's other links. Those are idle in these tests except VC1's, which carries the forwarded VC1 flow. The receiver is the far router's buffer for that VC. All channels share the ERISC's buffer space, so the two routers divide it differently. A VC with few slots can be limited by how many packets it has in flight rather than by the router or the link.

Code and stack

Both ERISC programs of a router load from one 26,624 B kernel config buffer, which also holds the runtime args. On every two-ERISC configuration both routers build, the new router is the smaller one, and every configuration it builds runs at -O3. Main's router with VC1 does not fit at -O3 and ships at -Os.

new router, -O3main, -O3
  • Main cannot build VC1 + VC2 (its stack use reaches 2,176 B) or VC2 on one ERISC. The new router does not admit VC1 + VC2 yet either; two earlier builds of it have built and run that combination.
  • The new router is larger than main only on one-ERISC binaries, where one image holds both programs: up to +1,244 B (Galaxy express).
  • Not yet built for either router: a configuration with every feature at once (inter-mesh, express, bubble flow control, VC1 and VC2).

What the new structure enables

Where the new router is not ahead yet

Every test in the latest data where the new router is slower than main by more than noise. Full-ring multicast at 200G and 4,352 B is the one large gap; the Ring jam tab shows what causes it.

Measurements still to run

A ring jam at 200G

On Galaxy's 200G rings the new router runs full-ring multicast about 29% faster than main up to 3,072 B, then about 41% slower at 4,352 B. The slowdown appears only when the new router's receiving ERISC handles a packet faster than the link delivers one. Main's receiving ERISC is slower than a 200G link, so main never gets there.

Galaxy full-ring multicast (the 8-chip rings set its rate), write, cycles per packet; mean of two passes in reversed router order, main and the new router in the same jobs (Slurm 169482/169483, 2026-11-03). Line time: the packet's time on a 200G link.

How we know the receiver's speed causes it

We slowed only the receiving ERISC, by a fixed number of cycles per packet. If it were the bottleneck, every row would get slower. Instead the large-packet rows got faster, until the receiver's own time per packet passed the line time; from there on all three sizes run on one line, set by the receiver.

Galaxy Slurm 169903 (bh-glx-110-a01u14), 2026-11-03: the new router with a delay on the receiving ERISC only (the build is byte-identical to the new router at delay 0), two passes in reversed order. Cycles per packet.

The reverse holds too: skipping the receiver's local write makes it faster, and pushes rows into the slow mode. Giving the receiver more slots (32 to 48) did not help.

Galaxy Slurm 169871 (bh-glx-110-a08u20), 2026-11-03: the local write of data-only packets dropped on the receiving ERISC (the build is byte-identical to the new router with the switch off). Cycles per packet.

Why it happens (hypothesis)

workerforwarding channel→ link →receiver ring→ forward →next forwarding channel→ …
  • Rings avoid deadlock with bubble flow control: a worker may send only if the next chip's receiver ring has 2 free slots; a forwarded packet needs 1.
  • In the new router one ring hop has two buffers in series: the receiver ring and the next sending ERISC's forwarding channel. The check reads only the receiver ring (outlined).
  • When the receiver outruns the link, the queue moves into the forwarding channels (shaded), which the check cannot see. Workers keep sending until the whole ring is full; it then advances one free slot at a time, each move waiting a full credit round trip.
  • Past saturation this is known behavior of bubble flow control: Chen, Wang and Pinkston, IPDPS 2011, sections II.C and V.C.

Fix tried on the Galaxy: hold back injection

A worker (or, on a torus, a turn from the other axis) may send only if the straight forwarding channel holds fewer than T packets, or K forwarded packets have gone out since the last injection. K = 6 matches an 8-chip ring, where each link carries 7 flows. Holding back injection removes the jam: the 8-chip ring at 4,352 B drops from 371 to 254 cycles, below main's on the full-ring row.

Galaxy Slurm 170016 (bh-glx-110-a06u02), 2026-11-03, two passes in reversed order, every arm validated with data checks and flow control on. Cycles per packet; green or red where an arm moves by more than 1 cycle from the throttle off.

The same throttle at 400G

A P150 has no jam to remove (every router there is slower than its 400G link), so the throttle only costs. A fixed K holds the worker below its share where each link carries fewer flows (both-way ring and 2x4 torus multicast, up to +21.5 cycles), and the torus version costs 4 to 7 cycles on 1-hop writes even where it never engages. It is not a general fix yet. Next is a trigger that tells a jam (the link idle for lack of credits) from an ordinary queue; that too is a hypothesis to test.
