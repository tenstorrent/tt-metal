Fabric Router Optimizations

A new fabric router against the old router on Blackhole's 400G and 200G Ethernet links and Wormhole's 100G links: bandwidth, latency, and code and stack. Packets go up to 4,352 B, the fabric's default largest payload (four 1,088 B Bfp8_b tiles): larger transfers travel as 4,352 B packets unless the payload limit is raised.

Detail

Summary

The fabric router is the program that moves data across each Ethernet link between two chips. Here the new router is compared with the old router on how much of each link it uses and round-trip latency.

    One-way traffic and the keepalive

    When traffic flows one way only, the Ethernet keepalive interval matters. With the old router's shipped setting, one-way tests with packets above 4,114 B settle near 187.5 cycles per packet whatever the router does. A 1,000-cycle interval removes most of that floor. The new router's runs used 1,000 cycles; everywhere else on this page the old router runs as shipped. These are the tests where the setting changes the old router's result. It does not change latency (see the Latency tab).

    Several VCs on one link

    These runs use test-infrastructure additions not yet in main (a VC2 benchmark sender and several traffic streams per link); they land in a separate change.

Each router runs its default slot allocation: the old router's fixed option table, and the new router's staged allocator, the default in this change. VC2 has fewer slots than VC0 in both. All channels share the ERISC's buffer space, so the two routers divide it differently, and a VC with few slots can be limited by how many packets it has in flight rather than by the router or the link.     Code and stack

    Both ERISC programs of a router load from one 26,624 B kernel config buffer, which also holds the runtime args. On every two-ERISC configuration both routers build, the new router is the smaller one, and runs at -O3 in every configuration but VC1 + VC2 together, which it builds at -Os by default. The old router with VC1 does not fit at -O3 and ships at -Os.

    new router, -O3old router, -O3
    • The old router cannot build VC1 + VC2 (its stack use reaches 2,176 B) or VC2 on one ERISC. The new router builds VC1 + VC2 on mesh routers, not yet on ring or torus routers.
    • The new router is larger than the old router only on one-ERISC binaries, where one image holds both programs: up to +1,244 B (Galaxy express).
    • Not yet built for either router: a configuration with every feature at once (inter-mesh, express, bubble flow control, VC1 and VC2).

    A ring jam at 200G

    On Galaxy's 200G rings the new router runs full-ring multicast about 29% faster than the old router up to 3,072 B, then about 41% slower at 4,352 B. The slowdown appears only when the new router's receiving ERISC handles a packet faster than the link delivers one. The old router's receiving ERISC is slower than a 200G link, so the old router never gets there.

    Galaxy full-ring multicast (the 8-chip rings set its rate), write, cycles per packet; mean of two passes in reversed router order, the old router and the new router in the same jobs. Line time: the packet's time on a 200G link.

    How we know the receiver's speed causes it

    We slowed only the receiving ERISC, by a fixed number of cycles per packet. If it were the bottleneck, every row would get slower. Instead the large-packet rows got faster, until the receiver's own time per packet passed the line time; from there on all three sizes run on one line, set by the receiver.

    Galaxy: the new router with a delay on the receiving ERISC only (the build is byte-identical to the new router at delay 0), two passes in reversed order. Cycles per packet.

    The reverse holds too: skipping the receiver's local write makes it faster, and pushes rows into the slow mode. Giving the receiver more slots (32 to 48) did not help.

    Galaxy: the local write of data-only packets dropped on the receiving ERISC (the build is byte-identical to the new router with the switch off). Cycles per packet.

    Why it happens (hypothesis)

    workerforwarding channel→ link →receiver ring→ forward →next forwarding channel→ …
    • Rings avoid deadlock with bubble flow control: a worker may send only if the next chip's receiver ring has 2 free slots; a forwarded packet needs 1.
    • In the new router one ring hop has two buffers in series: the receiver ring and the next sending ERISC's forwarding channel. The check reads only the receiver ring (outlined).
    • When the receiver outruns the link, the queue moves into the forwarding channels (shaded), which the check cannot see. Workers keep sending until the whole ring is full; it then advances one free slot at a time, each move waiting a full credit round trip.
    • Past saturation this is known behavior of bubble flow control: Chen, Wang and Pinkston, IPDPS 2011, sections II.C and V.C.

    Fix tried on the Galaxy: hold back injection

    A worker (or, on a torus, a turn from the other axis) may send only if the straight forwarding channel holds fewer than T packets, or K forwarded packets have gone out since the last injection. K = 6 matches an 8-chip ring, where each link carries 7 flows. Holding back injection removes the jam: the 8-chip ring at 4,352 B drops from 371 to 254 cycles, below the old router's on the full-ring row.

    Galaxy, two passes in reversed order, every arm validated with data checks and flow control on. Cycles per packet; green or red where an arm moves by more than 1 cycle from the throttle off.

    The same throttle at 400G

    A P150 has no jam to remove (every router there is slower than its 400G link), so the throttle only costs. A fixed K holds the worker below its share where each link carries fewer flows (both-way ring and 2x4 torus multicast, up to +21.5 cycles), and the torus version costs 4 to 7 cycles on 1-hop writes even where it never engages. It is not a general fix yet. Next is a trigger that tells a jam (the link idle for lack of credits) from an ordinary queue; that too is a hypothesis to test.
