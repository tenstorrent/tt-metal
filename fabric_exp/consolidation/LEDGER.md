# Router study ledger (RESULTS §1–§81)

Every change or idea the Blackhole router study built or proposed (RESULTS.md, V3_INVENTORY.md, variants/README.md), one row per idea, classified against today's build: router v2 at `TT_FABRIC_EXP_FLAGS=13129088` = s79mc. Numbers are cycles/packet (1.35e9 / packets per s) unless marked ns or GB/s; deltas are against the base named in that section.
Counts (94 classified rows): **IN 31 · LOST-SUBSTANCE 19 · LOST-CONTEXT 8 · LOST-UNCLEAR 3 · MIXED 5 · OPEN 28**. Measurement/tooling and the DRISC line are listed apart (§7, §8 below). LOST-UNCLEAR = lost, and RESULTS gives no evidence for substance or for context.
Look at these first in a whole-router redesign:
1. **Smaller sender-channel state** (bit 24, s77t, s78l; LOST-CONTEXT ×3). 128–320 B off E0's frame, which has ~1 KB free; each loss came from SRA/allocation shuffles, not from work.
2. **Shared runtime forwarding step** (old bit 27, s80; LOST-CONTEXT). −20% on forwarding as a patch (§35/§36), near even in s80 (§81); the shape that scales to VC1's up to 9 sender channels.
3. **Loop function boundaries** (noinline main loop §78, separate E0 loop §47, cold connection helpers §79). Decides whether E0 and E1 can be their own functions; the costs were pointer access to kernel_main's state and duplicated code.
4. **How load groups are expressed** (§46 plain volatile LOST-CONTEXT vs §48 fences IN). Bit 8's group alone is worth ~23 (§17) and bit 23's ~4–5 (§28), but asm and fences both encode compiler behavior.
5. **E1 cached downstream credits** (§80, OPEN). ~5–7/packet off E1 on forwarders; designed so the gain does not hinge on allocation.
6. **Worker visit latency** (§73, OPEN). ~40 of E0's ~70 per-pass overhead is two loads behind stack loads (payload size, teardown flag); the per-pass check must stay.
7. **E1 completion/deferral shape** (§68 placement cost, §26 per-command-buffer batch check, §76 1D/ring coverage; OPEN). Deferral's +2 is one taken jump; bit 22's batch check is safe only by timing; 1D gets no deferral or hold, ring routers no batching.

Status key: **IN** in the current build (flag bit in 13129088, or hard-wired in v2/s79mc). **LOST-SUBSTANCE** rejected for a reason independent of codegen (hang, unsafe, inherent work, latency, no effect, user rule). **LOST-CONTEXT** lost, with RESULTS evidence pointing at codegen around it: a re-test candidate in a redesign. **MIXED** a substantive trade-off between rows. **OPEN** proposed, parked or never run.

## 9. User rules

- ERISC-only mode: no DRISC offload.
- No RX work on E0 (the sending ERISC stays lean).
- One worker channel per router; mix flows on a link through forwarded traffic, not a second worker.
- Keep the worker connection check on every pass; never defer it to the outer loop.
- A design that hangs even once is out. Don't probe hang boundaries.
- No register pinning, no allocation-dependent changes, no layout steering (`[[likely]]`, `__builtin_expect`, hot/cold), no compiler-fragile tricks. The source must not assume compiler behavior. README's "Strict E0 Codegen Rules" are observations about GCC 15.1 at -O3, not rules to code by.
- Benchmark-only behavior can't ship, and benchmark-only bits never go in validation yamls.
- Never score telemetry-on runs (`TT_FABRIC_NO_BW_TELEMETRY=1`); the telemetry switch must not ship.
- A design must hold at -O3 and at -Os (VC1 builds).
- Judge whole builds by suite means across configs, opt levels and perturbations. Disassembly explains results; it does not drive edits.
