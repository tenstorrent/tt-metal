# feat(llk): static checker for compute-kernel API ordering (#62681)

Closes #62681

## Summary

Adds a static checker for the compute-kernel API's init / uninit / reconfiguration
ordering protocol, expressed as a machine-readable rule table at the LLK API level.
The checker analyses each kernel's real compiled translation unit, follows calls
through the Compute API and helper headers, and reports ordering mistakes without
hardware.

This implements the bounty's five deliverables:

1. a curated, machine-readable rule table with citations and a test that keeps it
   consistent with the LLK Sanitizer's operation model;
2. a checker that reports missing init, init/operation argument mismatch, a different
   init between an init and its operation, missing required uninit, deprecated init
   use, and (warning-only) loop-invariant init;
3. positive and negative test kernels for every rule, including reproductions of
   [#61146](https://github.com/tenstorrent/tt-metal/issues/61146) and
   [#59276](https://github.com/tenstorrent/tt-metal/issues/59276);
4. a corpus run with per-rule counts, triage, and false-positive accounting;
5. documentation and a non-blocking CI workflow.

No compute, LLK, or dataflow production code is changed.

## What was added

### Rule specification

- `tt_metal/tt-llk/infra/compute_api_order_rules.yaml` — LLK-level operations for
  UNPACK / MATH / PACK, with:
  - required init(s) and the init/operation argument positions that must agree;
  - calls that invalidate a configured init (`reconfig_data_format`,
    `pack_reconfig_data_format`, hardware configure);
  - the curated set of operations that require an uninit (tilize, untilize,
    broadcast, fast tilize), rather than a blanket "every init needs an uninit";
  - deprecated init APIs, with a check against `.github/deprecations.json`;
  - a citation for every rule (API doc comment, sanitizer hook, or bug).
- `tt_metal/tt-llk/infra/compute_api_order_sfpu.yaml` — generated SFPU
  `*_tile_init` / `*_tile` pairs, mined from
  `ttnn/.../unary/common/unary_op_utils.cpp`; the generator is checked for
  staleness in CI.
- Sanitizer-agreement test parses every `SAN_HOOK` in the Wormhole and Blackhole
  LLK API trees and fails if the table and the sanitizer disagree about an
  operation both cover.

### Checker

`tt_metal/tt-llk/infra/check_compute_api_order.py`:

- parses the actual per-thread kernel TU (UNPACK, MATH, PACK), so preprocessor and
  `if constexpr` variants are the ones the device build sees;
- follows helper functions and headers, stopping at the LLK API rules;
- performs bounded path-sensitive analysis for correlated runtime conditions
  (e.g. two `if (step == 0)` sites around one init/operation pair);
- compares compile-time template arguments and runtime argument expressions, and
  reports a value it cannot prove as **unknown** rather than guessing;
- attributes each diagnostic to the outermost kernel source line and names the
  earlier conflicting call;
- supports both `kernel_main` and the `TT_KERNEL` named-argument entry;
- accepts `--kernel`, `--compile-db`, and captured JIT `--log` input.

### Corpus runner and reports

- `tt_metal/tt-llk/infra/run_compute_api_order_corpus.py` — discovery or captured
  compile-database mode, Markdown report, triage, false-positive rate, and
  process-isolated units so a libclang crash is a coverage hole, not a lost run.
- `tt_metal/tt-llk/infra/compute_api_order_corpus.md` — reviewed bounded corpus run.
- `tt_metal/tt-llk/infra/compute_api_order_corpus_triage.yaml` — exact
  fingerprint-to-verdict map used to render the report.
- `tt_metal/tt-llk/infra/compute_api_order_true_positives.md` — reviewed true
  positives grouped by pattern.
- `tt_metal/tt-llk/infra/compute_api_order_ttsim_verification.md` — CPU-only ttsim
  verification, including an injected-bug comparison.

### Tests

- `tt_metal/tt-llk/infra/tests/test_check_compute_api_order.py` — 43 tests across
  both architectures and all three threads.
- `tt_metal/tt-llk/infra/tests/compute_api_order_fixtures/` — positive and negative
  kernels for every rule, including:
  - `pack_reconfig_data_format` after `tilize_init` (#61146);
  - init configured differently from the operation that follows (#59276);
  - missing binary/SFPU/broadcast init, missing tilize/untilize/broadcast uninit;
  - wrong init, deprecated init, loop-invariant warning;
  - unknown runtime arguments and `if constexpr`.

### Documentation and integration

- `docs/source/tt-metalium/tools/compute_api_order_checker.rst` and the tools
  toctree entry.
- `.github/workflows/llk-compute-api-order.yaml` — non-blocking
  (`continue-on-error`) unit tests plus a bounded discovery sweep; uploads the
  report as an artifact. The full corpus run is designed to replay a captured
  kernel compile database from the weekly kernel clang-tidy job.

## Verification

- **43/43 tests pass** on the current `main`.
- Both real ttsim-captured compute kernels (matmul and eltwise examples):
  **0 findings, 0 coverage holes**.
- ttsim clean runs: `metal_example_add_2_integers_in_riscv` (result 21),
  `metal_example_matmul_single_core` (PCC 0.9813, passed),
  `metal_example_eltwise_binary` (passed).
- Injected-bug check: removing `add_init` from `tiles_add.cpp` makes ttsim fail
  with `mop_ingest: outer_loop_len=0`; the checker reports `missing-init` for
  `llk_math_eltwise_binary` (MATH) and `llk_unpack_AB` (UNPACK) at the
  `add_tiles` line. Source was restored.

## Corpus result

Bounded discovery sweep: 40 model kernels × 2 architectures × 3 threads = 240
units, 0 holes.

- 347 findings total.
- 45 error findings reviewed: **40 true positives, 5 false positives — 11.1%
  error false-positive rate**.
- 302 warning-only `loop-invariant-init` findings triaged as intentional re-inits
  and excluded from the error FP rate.
- Reviewed true positives include:
  - `copy_init` → `mul_binary_tile_init` → `copy_tile` in `gdn_rows_scan`,
    `gdn_step`, and `router_tail` (the FPU is re-seated for the binary op before
    the datacopy executes);
  - `llk_unpack_A` acc-to-dest mismatch at the same sites;
  - missing `unary_bcast_uninit` in six model kernels.
- The five false positives are the Blackhole `fast_tilize_*` fallback path; the
  kernel does call `fast_tilize_uninit`, but the checker's branch-correlation
  model does not yet follow that runtime fallback.

## How to run

```bash
# One kernel / one thread
python3 tt_metal/tt-llk/infra/check_compute_api_order.py \
    --kernel path/to/compute.cpp --arch wormhole_b0 --thread MATH

# A captured JIT build log (the recommended real-compile path)
TT_METAL_LOG_KERNELS_COMPILE_COMMANDS=1 TT_LOGGER_LEVEL=info <workload> 2>&1 | tee build.log
python3 tt_metal/tt-llk/infra/check_compute_api_order.py --log build.log

# Tests
python3 -m pytest --noconftest tt_metal/tt-llk/infra/tests/test_check_compute_api_order.py
```

## Limitations / follow-up

- The reported corpus is bounded (40 files). The full run should replay the
  weekly kernel-clang-tidy compile database; the checker already accepts it.
- `--log` replay with SFPI 7.94 needs an analysis-compatible SFPI (7.73 works)
  because of an analysis-only header-order regression in 7.94; the synthesized
  modes are unaffected.
- The Blackhole `fast_tilize_*` fallback false positives are a checker
  refinement, not a kernel bug.
- Quasar, dataflow kernels, folded LLK 2.0 execution APIs, and runtime sanitizer
  changes remain out of scope, matching the bounty terms.
