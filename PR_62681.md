# feat(llk): static checker for compute-kernel API ordering (#62681)

Closes #62681

## Summary

Adds a static checker for the compute-kernel API's init / uninit / reconfiguration
ordering protocol, expressed as a machine-readable rule table at the LLK API level.
The checker analyses each kernel's real compiled translation unit, follows calls
through the Compute API and helper headers, and reports ordering mistakes without
hardware.

It covers the six diagnostics requested by the bounty: missing init, init/operation
argument mismatch, a different init between an init and its operation, missing
required uninit, deprecated init use, and a warning-only loop-invariant init.

No compute, LLK, or dataflow production code is changed.

## Deliverables

### 1. Rule specification

- `tt_metal/tt-llk/infra/compute_api_order_rules.yaml` — LLK-level operations for
  UNPACK / MATH / PACK, with:
  - required init(s) and the init/operation argument positions that must agree;
  - calls that invalidate a configured init (`reconfig_data_format`,
    `pack_reconfig_data_format`, hardware configure);
  - the curated set of operations that require an uninit (tilize, untilize,
    broadcast, fast tilize), rather than a blanket "every init needs an uninit";
  - deprecated init APIs, with a check against `.github/deprecations.json`;
  - a citation for every rule (API doc comment, sanitizer hook, or bug).
- `tt_metal/tt-llk/infra/compute_api_order_sfpu.yaml` — generated SFPU
  `*_tile_init` / `*_tile` pairs, mined from
  `ttnn/.../unary/common/unary_op_utils.cpp`; the generator is checked for
  staleness in CI.
- Sanitizer-agreement test parses every `SAN_HOOK` in the Wormhole and Blackhole
  LLK API trees and fails if the table and the sanitizer disagree about an
  operation both cover.

### 2. Checker

`tt_metal/tt-llk/infra/check_compute_api_order.py`:

- parses the actual per-thread kernel TU (UNPACK, MATH, PACK), so preprocessor and
  `if constexpr` variants are the ones the device build sees;
- follows helper functions and headers, stopping at the LLK API rules;
- performs bounded path-sensitive analysis for correlated runtime conditions
  (e.g. two `if (step == 0)` sites around one init/operation pair);
- compares compile-time template arguments and runtime argument expressions, and
  reports a value it cannot prove as **unknown** rather than guessing;
- attributes each diagnostic to the outermost kernel source line and names the
  earlier conflicting call;
- supports both `kernel_main` and the `TT_KERNEL` named-argument entry;
- accepts `--kernel`, `--compile-db`, and captured JIT `--log` input.

### 3. Tests

- `tt_metal/tt-llk/infra/tests/test_check_compute_api_order.py` — 44 tests across
  both architectures and all three threads.
- `tt_metal/tt-llk/infra/tests/compute_api_order_fixtures/` — positive and negative
  kernels for every rule, including:
  - `pack_reconfig_data_format` after `tilize_init` (#61146);
  - init configured differently from the operation that follows (#59276);
  - missing binary/SFPU/broadcast init, missing tilize/untilize/broadcast uninit;
  - wrong init, deprecated init, loop-invariant warning;
  - unknown runtime arguments and `if constexpr`.

### 4. Corpus runner and reports

- `tt_metal/tt-llk/infra/run_compute_api_order_corpus.py` — discovery or captured
  compile-database mode, Markdown report, triage, false-positive rate, and a
  supervised multiprocessing worker pool. Workers reuse one libclang parse
  environment, recycle every 50 units to bound memory, and a crashed worker is a
  coverage hole rather than a lost run.
- `tt_metal/tt-llk/infra/compute_api_order_corpus.md` — full 563-kernel corpus run.
- `tt_metal/tt-llk/infra/compute_api_order_corpus_triage.yaml` — rule-wide triage
  verdicts with per-site overrides where needed.
- `tt_metal/tt-llk/infra/compute_api_order_true_positives.md` — reviewed true
  positives grouped by pattern.
- `tt_metal/tt-llk/infra/compute_api_order_ttsim_verification.md` — CPU-only ttsim
  verification, including an injected-bug comparison.

### 5. Documentation and integration

- `docs/source/tt-metalium/tools/compute_api_order_checker.rst` and the tools
  toctree entry.
- `.github/workflows/llk-compute-api-order.yaml` — non-blocking
  (`continue-on-error`) unit tests plus a bounded discovery sweep; uploads the
  report as an artifact. The full corpus run is designed to replay a captured
  kernel compile database from the weekly kernel clang-tidy job.

## Verification

- **44/44 tests pass** on the current `main`.
- Both real ttsim-captured compute kernels (matmul and eltwise examples):
  **0 findings, 0 coverage holes**.
- ttsim clean runs: `metal_example_add_2_integers_in_riscv` (result 21),
  `metal_example_matmul_single_core` (PCC 0.9813, passed),
  `metal_example_eltwise_binary` (passed).
- Injected-bug check: removing `add_init` from `tiles_add.cpp` makes ttsim fail
  with `mop_ingest: outer_loop_len=0`; the checker reports `missing-init` for
  `llk_math_eltwise_binary` (MATH) and `llk_unpack_AB` (UNPACK) at the
  `add_tiles` line. Source was restored.

## Corpus Report

Full discovery sweep: **563 kernel files**, 2 architectures × 3 threads =
**3,378 units**, **0 coverage holes**, **100% of discovered kernels analysed**.
The run used the supervised 8-worker pool with `--max-paths 4`; wall time was
**777.7 s**.

### Findings breakdown by report

| Rule | Findings | True positives | False positives | Unreviewed |
| --- | ---: | ---: | ---: | ---: |
| `init-arg-mismatch` | 12 | 12 | 0 | 0 |
| `loop-invariant-init` | 1581 | 0 | 1581 | 0 |
| `missing-init` | 43 | 43 | 0 | 0 |
| `missing-uninit` | 56 | 56 | 0 | 0 |
| `wrong-init` | 8 | 0 | 8 | 0 |
| **Total** | **1700** | **111** | **1589** | **0** |

- **Error findings:** 119 reviewed — 111 true positives, 8 false positives,
  **6.7% error false-positive rate**.
- **Warnings:** 1,581 `loop-invariant-init` findings triaged as intentional
  re-inits (excluded from the error FP rate).

Reviewed true positives:

- **56 missing uninit** — broadcast/tilize operation groups that never call
  `unary_bcast_uninit` / `tilize_uninit`; includes the `qwen38_flash_next`
  broadcast users and several `tt-train` softmax/normalization kernels.
- **43 missing init** — pack-only `gpt_oss` decode kernels without
  `compute_kernel_hw_startup` / `pack_init`, and `unary_bcast`/reduce helpers
  reaching the operation without the matching init on this path.
- **12 init/operation argument mismatches** — `tt-train` SDPA kernels where the
  unpacker or datacopy init and its execute use different compile-time arguments
  (`acc_to_dest` / datacopy configuration).

The 8 `wrong-init` false positives are in `groupnorm_sharded_v2.cpp`:
`compute_kernel_lib::reduce` derives a helper-local `constexpr bool is_sfpu` from
`is_sfpu_reduce_path<...>()`; the checker cannot evaluate that helper constexpr and
follows the SFPU `copy_init` branch before the FPU `reduce_tile`. This is a checker
refinement, not a kernel defect.

The original five Blackhole fast-tilize false positives are **eliminated**:
condition keys now strip redundant grouping around primary expressions, so
`full_dim == 1` and `block == 1` correlate when both call sites pass the same
compile-time value. The regression is covered by
`test_blackhole_fast_tilize_fallback_has_no_false_positives`.

## Bugs or limitations

- **Bugs found (not fixed here):** the full corpus surfaced 111 true positives
  across 563 files:
  - 56 missing uninit: broadcast/tilize operation groups without the matching
    `unary_bcast_uninit` / `tilize_uninit` (qwen38 model kernels,
    `tilize_8x32_kernel.cpp`, and several `tt-train` kernels);
  - 43 missing init: pack-only `gpt_oss` decode kernels without
    `compute_kernel_hw_startup` / `pack_init`, plus `unary_bcast`/reduce helpers
    reaching the operation without the matching init;
  - 12 init/operation argument mismatches in the `tt-train` SDPA kernels
    (`acc_to_dest` / datacopy configuration).
  These are documented with sites and suggested fixes in
  `tt_metal/tt-llk/infra/compute_api_order_true_positives.md` and should be filed
  or fixed separately from this checker change.
- **8 triaged false positives:** `groupnorm_sharded_v2.cpp` `wrong-init` findings
  come from a helper-local `constexpr bool is_sfpu` that the checker cannot
  evaluate. Tracked as a checker refinement; the error FP rate is 6.7%.
- **Corpus scope:** 563 files is the full discovered set across `ttnn`, `models`,
  `tests`, `tt-train` and `tt_metal`, including the `*_impl_kernels` and
  `kernels_qsr` directories. The run is discovery-based with synthesized JIT-like
  flags; the checker also accepts a captured compile database, which should be
  used for a hardware-true corpus.
- **SFPI log replay:** `--log` replay with SFPI 7.94 needs an analysis-compatible
  SFPI (7.73 works) because of an analysis-only header-order regression in 7.94;
  the synthesized `--kernel` / `--discover` modes are unaffected.
- **Path analysis is bounded:** `--max-paths` defaults to 8 and the full corpus
  used 4; a condition combination beyond that cap may be missed. Workers recycle
  after 50 units by default to bound memory.
- **Out of scope:** Quasar execution, dataflow (NoC) kernels, folded LLK 2.0
  execution APIs, and runtime sanitizer changes, matching the bounty terms.

## How to run

```bash
# One kernel / one thread
python3 tt_metal/tt-llk/infra/check_compute_api_order.py \
    --kernel path/to/compute.cpp --arch wormhole_b0 --thread MATH

# A captured JIT build log (the recommended real-compile path)
TT_METAL_LOG_KERNELS_COMPILE_COMMANDS=1 TT_LOGGER_LEVEL=info <workload> 2>&1 | tee build.log
python3 tt_metal/tt-llk/infra/check_compute_api_order.py --log build.log

# Tests
python3 -m pytest --noconftest tt_metal/tt-llk/infra/tests/test_check_compute_api_order.py

# Full 563-kernel discovery corpus (8 workers, 3,378 units)
python3 tt_metal/tt-llk/infra/run_compute_api_order_corpus.py \
    --discover --arch wormhole_b0 --arch blackhole \
    --threads UNPACK MATH PACK --jobs 8 --max-paths 4 \
    --output /tmp/compute_api_order_corpus.md
```
