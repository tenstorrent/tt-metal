# Front B-fused-u16-plan (design/recon swarm, 2026-08-17)

## Verdict

GO — scoped. Fused-u16 end-to-end merge/rebuild is implementable for rows whose padded width fits 32 chunks of the LLK window (num_chunks <= 32; for K=2048 that is W <= 65536), with the existing unfused path retained behind a compile-time factory gate for wider rows. The bit budget is exactly 5 bits of chunk id at K=2048 — 6 bits is physically impossible (information-theoretic: the u16 field must address every global position, 2^16 = 65536), so production width 66560 (33 chunks) can never run fused e2e and stays on today's path; production width 61440 (30 chunks) and every 65536-wide anchor qualify. The runtime-chunk-id stamp is a one-instruction LLK change (TTI_SFPLOADI -> TT_SFPLOADI), avoiding 32 template instantiations. Modeled from silicon-measured constants: ~3.5-3.7K cycles saved per chunk (per-chunk split deleted ~1.95K, unfused->fused rebuild ~1.45K, merge ~0.15K), ~112K cycles ≈ 80 us per 32-chunk row. Expected anchors (modeled, ±15%, must be measured): leaf per-row 356.4->~277 us (proxy 363->~283, ~1.28x), tree 34.3->~26-28 us, GLM cell 467.4->~365-375 us (~1.26x incremental, ~1.9x cumulative vs pre-campaign 712.3). Tie identity on exact-bf16-tie rows changes (chunk_id becomes the dominant tie-breaker in fused compares) — covered by the op's documented non-stable contract and the routing predicate's !stable gate, same I5 acceptance class the hybrid landed under, but requires the I5-style tie audit and may perturb tie-sensitive nightly cells.

## Plan

## Deliverable 1 — bit budget, verified in code

The fused word is EXACTLY 32 bits with no slack: `[bf16 value (high 16) | u16 index (low 16)]` (ckernel_sfpu_topk_xl.h:23-33). The stamp `_topk_xl_add_lsb_indices_<K, APPROX, core_id>` builds the u16 as: bits [15:11] = core_id (5 bits), low bits = within-chunk coordinate (topk_xl.h header comment :2664-2668; core_id load+shift at :2695-2696 — `TTI_SFPLOADI(LREG1, USHORT, core_id)` then `TTI_SFPSHFT(11, ...)`). The op's row-major decode `_topk_xl_decode_row_major_index_<K>` (:2925-2972) consumes raw bits [10:0] only — `[col 10:6 | tile 5 | row 4:0]` — and masks every field, so bits [15:11] are ignored by the existing decode (they pass through untouched). At K=2048 the coordinate needs all 11 low bits (2048 positions), leaving exactly 5 free bits. **6 bits is not available by any bit-stealing**: (a) the word has no slack — bf16 needs all 16 high bits for the value compare to be a value compare; (b) fundamentally, a u16 must address every recoverable global position, so W <= 2^16 = 65536 regardless of encoding. 66560 > 65536: NO encoding fixes it. (Matches the campaign memory's recorded correction: "5-bit chunk-id stamp OVERFLOWS at 33 chunks/width 66560".) Side finding for K=512/1024 windows: the coordinate leaves SCATTERED free bits (K=1024: {5, 11-15} = 6 bits -> 64x1024 = 65536; K=512: {4, 5, 11-15} = 7 bits -> 128x512 = 65536), so a v2 split-field stamp can lift k<=1024 shapes to the same 65536 cap — but v1 should use only [15:11] (num_chunks <= 32, any K), which already covers the flagship k=2048 shapes. DS-V4 k=512 @ W=65536 (128 chunks of the 512 window) is v2, not v1.

Today the op stamps core_id=0 always (`topk_xl_add_lsb_indices<K, 0>` — compute.cpp:120, topk_large_indices_compute_common.hpp:133), i.e. bits [15:11] are unused in this op — free real estate.

## Deliverable 2 — runtime vs template chunk id

Template dispatch would need one instantiation per chunk id: 32 instantiations of `_topk_xl_add_lsb_indices_<K, APPROX, id>` + a 32-way switch (~60 TRISC1 instructions each incl. the 16-slot recorded body and outer loop; est. 300-400 B/instantiation ≈ 10-13 KB of TRISC1 IMEM) — reject. **Runtime-stamp variant**: the ONLY compile-time use of core_id is `TTI_SFPLOADI(p_sfpu::LREG1, SFPLOADI_MOD0_USHORT, core_id)` at :2695. `TT_SFPLOADI` (runtime-composed issue via `ckernel::instrn_buffer[0]`) exists at ckernel_ops.h:680. Add `_topk_xl_add_lsb_indices_rt_<K, APPROX>(uint32_t chunk_id)` that is the existing body with that one line replaced by `TT_SFPLOADI(p_sfpu::LREG1, sfpi::SFPLOADI_MOD0_USHORT, chunk_id)` (or pre-shifted `chunk_id << 11` and drop the SFPSHFT). Cost: a handful of RISC cycles ONCE per chunk, outside the SFPU hot loop; SFPU instruction count unchanged. Plumbing precedent exists: `_llk_math_eltwise_unary_sfpu_params_` already passes runtime args (llk_math_eltwise_unary_sfpu_topk_xl.h:99-105, the row_major init passes runtime chunk_base). New wrapper `llk_math_eltwise_unary_sfpu_topk_xl_add_lsb_indices_rt<K, APPROX>(dst, chunk_id)` + compute-API `topk_xl_add_lsb_indices_rt<K>(idst, chunk_id)` in tt_metal/hw/inc/api/compute/experimental/topk_xl.h. Keep the template variant untouched (distributed-topk consumer). In compute_tree.cpp the stamp is `start_chunk + c` (start_chunk is already a runtime arg, :45) — global chunk ids come free.

## Deliverable 3 — tie-order semantics

Today: within-chunk sort is ALREADY fused (finish_chunk stamps indices then fused local_sort — compute.cpp:119-123), so within-chunk ties already break by raw coordinate under the sign-magnitude fused compare (SFPSWAP orders by sign-magnitude total order — SORTING.md:92-93; for equal POSITIVE values the larger u16 wins the max, for equal NEGATIVE values the smaller u16 wins — asymmetric, already shipping). Cross-chunk merges today are UNFUSED: SFPSWAP compares FP32 value words whose low16 is 0, so exact ties resolve by merge-network position, not by index. After the change, cross-chunk ties resolve by fused word order with chunk_id as the DOMINANT tie field (bits 15:11). What changes observable at the API: on rows containing exact bf16 duplicates straddling the k-th boundary or reordering within the top-k, WHICH duplicate's index is returned changes; values output is bitwise identical (tied values are bit-equal bf16, and the split clears low16 so -inf padding still compares exactly 0xFF800000 for mark_neginf — compute.cpp:61-72). -inf handling is unchanged in kind: stamped -inf lanes are negative-NaN bit patterns that sort below -inf in sign-magnitude order and already flow through today's fused local sort; mark_neginf still assigns the 0xFFFFFFFF sentinel post-split. Contract coverage: the op is documented non-stable and ttnn.topk routes to it only under !stable (topk.cpp routing predicate; campaign memory "documented non-stable contract, I5 acceptance class" — the hybrid landed with tie-identity as the sole delta class). Caveat inherited from the hybrid pull-back lesson: this changes tie identity for the SAME explicit call (not an opt-in), so it needs the I5-style tie audit and a nightly pass; any `matches_default`-style bit-compare cells on tie-heavy random bf16 inputs are the failure surface.

Chunk-skip interaction (row-parallel only): `chunk_skip_decide` compares the chunk max (low16 = 0, computed pre-stamp) against the K-th survivor's VALUE word via strict sign-magnitude less-than (topk_large_indices_chunk_skip.hpp:292-298). Under fused e2e the threshold word carries tie bits in low16, making the skip marginally more aggressive on exact ties (violates the header's "strictly below" proof). One-line fix: mask `thr_bits &= 0xFFFF0000u` at :297 to restore today's exact predicate.

## Deliverable 4 — single split placement + epilogue changes

New LLK split `_topk_xl_separate_indices_row_major_global_<K>`: existing `_topk_xl_separate_indices_row_major_` body (:2974-2998) + 3 extra SFPU instructions per iteration for K=2048 — because chunk_id sits at bits [15:11] and chunk_id*2048 == (idx & 0xF800), the global index is `(idx & 0xF800) | decode_row_major(idx)`: one SFPMOV, one SFPAND against a 0xF800 constant (loaded once into a config LREG at init, LREG13/14 pattern at :2871-2872), one SFPOR. ~33 instr x 64 iters ≈ 2.1K cyc once per row. No LREG12 chunk_base and no `advance_chunk_base` calls at all — the base is implicit in the stamp (deletes :127/:140/:194/:207 call sites in row-parallel kernels and the start_chunk advance loop in compute_tree.cpp:83-85).

Row-parallel (compute.cpp, mirrored in compute_with_values.cpp and the byte-identical copies in topk_large_indices_compute_common.hpp per its NOTE:9-13): `finish_chunk` becomes stamp(chunk_id)+init<K,true>+local_sort (drop the 3 separate_* calls, :125-127); the merge loop drops `topk_xl_init<K,false>` (:215) and calls `topk_xl_merge<K,true>` / `topk_xl_rebuild<K,true>` (:216-217, also :177-178 for num_chunks==1). DST layout: slot1 = tiles_per_sequence (2 for K=2048) instead of 2*tiles_per_sequence (4) — the fused merge expects operand1 at distance 64*tiles words = +2 tiles (topk_xl.h:1981) and `topk_xl_copy_tile(recv, 2, ...)` overwrites tiles 2-3 each iteration (:673-677); DST footprint drops 8 -> 4 tiles. The single split runs after the LAST rebuild, before `mark_neginf_indices` (insert between :218 and :235); it writes u32 indices at indices_offset = 128 words = tiles 2-3, exactly the layout mark_neginf (:58) and materialize_index_rank_order (:88-90, reads idst+tiles_per_sequence) already consume — the epilogue (mark_neginf, transpose materialization, pack_untilize at slot0+tiles_per_sequence) is UNCHANGED apart from split insertion. Values path (with_values variants): split keeps bf16 in the high half of the fp32 container exactly as today (:2986-2988) — packer conversion unchanged. Chunk-skip: threshold mask fix above; the max-fold reads slot1 pre-stamp (pure value<<16 words) — unchanged.

Tree path (compute_tree.cpp / compute_tree_root*.cpp): leaves stamp global chunk id start_chunk+c, keep the survivor FUSED, ship 2 fused tiles instead of 4 unfused (ship_values_cb+ship_indices_cb collapse to one ship_fused_cb, pack_block of tiles_per_sequence from slot0; CB data format must be UInt32 so packing cannot denormal-flush index bits — the blaze IndexerLocalTopK precedent, glm-callsite-map.md:69). Tree nodes copy the 2-tile partner to slot0+2 and run fused merge+rebuild in place. ONLY the root runs the global split + mark_neginf + materialize. Halves per-level pack/NoC/copy traffic. Factory (topk_large_indices_program_factory.cpp: kernels created at :352/:1076/:1091-1092; tree CBs sized around there) resizes ship/recv CBs and adds the gate define.

## Deliverable 5 — cycle estimate and anchors

Measured constants (SORTING.md): fused macro merge K=2048 = 142 cyc/call (331 shipping; :442), fused macro rebuild K=2048 = 1554 (1810 shipping; :406-423), of which Dst transposes 539. Structure gives the unfused costs the docs never measured in isolation: unfused merge fires 2x the bodies (n_iters = rsf*4 vs rsf*2, topk_xl.h:1990) at the same 16-instr macro body -> ~290 cyc; unfused rebuild doubles the transpose faces (16 vs 8, topk_xl.h:1267-1279 -> +539) and doubles lattice/big-block load-store traffic -> ~2.9-3.1K cyc. Per-chunk split today: 64 iters x ~30 inline TTI issues (:2982-2997 + 23-instr decode) ≈ 1.95K cyc. Per-chunk delta: -1.95K (split) -1.4-1.5K (rebuild) -0.15K (merge) -~0.1K (drop the per-chunk init<K,false> mode flip) ≈ **-3.6K cyc/chunk**; per 32-chunk row: 32x1.95K + 31x1.6K ≈ -112K net of the +2.1K one-time global split ≈ **-80 us at ~1.4 GHz** (sanity: observed per-row ≈ 363 us ≈ 490K cyc ≈ 15.3K/chunk; modeled per-chunk budget 252 copy + 290 stamp + ~8K fused local sort + 1.95K split + 0.3K merge + 3K rebuild + ~0.4K inits ≈ 14.2K — consistent; the untouched local sort is the Amdahl cap). **Expected anchors (modeled ±15%): leaf/RP per-row 356.4 -> ~277 us (as-shipped proxy 363 -> ~283), ~1.28x; single-row tree 34.3 -> ~26-28 us (leaf ~2.4 us + 5 levels x (~1.15 us fused merge+rebuild delta + ~0.4 us halved ship/copy)); GLM cell 467.4 = rp 359.4 + rect 99.0 + concat 8.8 -> ~365-375 us (rp ~280, rect ~76-80, concat unchanged), ~1.26x incremental, ~1.9x cumulative vs the pre-campaign 712.3.**

## Deliverable 6 — W > 65536 fallback

Compile-time factory gate, not runtime: `FUSED_E2E` define set when max num_chunks (derived from PADDED width, K-window) <= 32; else compile today's unfused body. Padded width bounds every runtime valid_length/num_chunks (num_chunks is a runtime arg, compute.cpp:140), so valid_length sweeps stay safe under one program. Both kernel bodies live in the same source behind `#ifdef` (JIT recompiles per define; no host rebuild). Program-cache: the gate derives from input padded shape — verify compute_program_hash covers it (shapes normally hash; explicit check per the program-hash trap). Production consequence: GLM width 61440 (30 chunks) runs fused; width 66560 (33 chunks) stays unfused FOREVER at K=2048 (information-theoretic); k<=1024 @ 65536 upgrades later via the v2 scattered-bit stamp. A mid-row fused->unfused switch at chunk 32 (the LLK's extended-256K machinery: separate + init<K,false>) is a possible v3 for slightly-over widths — defer.

## Risks

- Tie identity changes on the SAME explicit call (not an opt-in): cross-chunk exact-bf16 ties re-break by chunk_id order instead of merge-network position; covered by the non-stable contract and I5 class, but nightly matches_default-style cells on tie-heavy random bf16 inputs may fail and must be adjudicated, and the Galaxy tie audit becomes mandatory
- Cycle estimates for the UNFUSED merge/rebuild (~290 / ~3.0K) are structural derivations, not silicon measurements — no doc in the tree isolates them; the projected 1.26-1.30x could compress if the unfused macro path is closer to fused than the 2x-body model suggests
- Fused local sort (~8K cyc/chunk, unmeasured in isolation at K=2048) is untouched and caps the leaf win (Amdahl); if it is a larger share, relative gains shrink though absolute saving stands
- v1 does NOT cover DS-V4 k=512 @ W=65536 (128 chunks of the 512 window) — that anchor needs the v2 scattered-bit stamp; quoting the 358.3->x improvement for it would be wrong in v1
- W=66560 production shape permanently excluded (information-theoretic); both kernel bodies must stay live and CI-covered forever, doubling the maintenance surface of the compute kernels
- Program-cache: the FUSED_E2E define derives from padded shape — if compute_program_hash does not already cover the derived gate, cache hits could serve the wrong body (classic works-first-time bug); verify explicitly
- Tree ship-CB format change (2 fused UInt32 tiles, single CB) touches writers, readers, factory CB sizing and the pairwise handshake — the highest-churn part of the change; denormal-flush of index bits if any CB is left bf16/fp32-formatted is a silent-corruption trap
- Chained-stage correctness is the known blind spot (SORTING.md's faster-and-wrong macro bug passed all single-merge tests); fused e2e must be gated on num_chunks>=4 chained coverage at every K before any perf claim
- Chunk-skip aggressiveness subtly changes unless the threshold lo16 mask is applied — without it the soundness proof's 'strictly below' premise is violated on exact ties
